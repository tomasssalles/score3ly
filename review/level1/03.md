## apps/worker/src/index.ts
- **What it does:** the Worker's Hono app and entry module. Registers middleware (request log, optimistic locking, model-list conversion of added configs on every `/api/*` request), and routes: health, `/api/info` (host = cloudflare), project CRUD (list with "where the pipeline is" via a correlated subquery, create from multipart form with PDF upload to R2 checked by R2's `sha256` option, rename/run mode PATCH, opened, delete), PDF lookup by hash with the next free name, PDF download, content PUT/GET by SHA-256 (immutable cache headers), issue-number reservation (atomic `UPDATE … RETURNING`). Then mounts the other modules' routes.
- **Exports:** `default app`; re-exports types `ListedProject`, `Project`, `RunMode` from `@score3ly/core`.
- **Imports:** activity, costs, projectStats, failures, runTimes, deletion, names, fingerprints, llmRoutes (`llmRoutes`, `readSettings`, `convertAddedConfigs`), pipeline (`defaultForNewStages`, `newPipeline`, `pipelineRoutes`), versions, projectFile, requestLog; `hono`; `@score3ly/core` types. Platform: D1, R2 (`put` with `sha256`, `get`, `head`), `crypto.randomUUID`.
- **Notable internal helpers:** `toProject` (row → camelCase), `isNameConflict` (matches the SQLite error text), `getProject`, `takenNames`, `isSha256` (hex-64 check), `pdfKey` (`pdfs/<sha>.pdf`), `contentKey` (`content/<sha>`).
- **Findings:**
  - l.117: `isSha256` is the fourth copy of the same hex-64 test: `pipeline.ts` `isKey` l.387, `projectFile.ts` `isSha256` l.232, `fingerprints.ts` `HEX64` l.30, and inline in `llmRoutes.ts` l.487. certain
  - l.121/l.166: `pdfKey`/`contentKey` are rewritten as literals in `projectFile.ts` (l.258, l.462, l.471) and `deletion.ts` (l.74–79). The R2 key layout should live in one module. certain
  - l.43: `isNameConflict` duplicated as the same string test in `projectFile.ts` l.430; the "first free name, insert, retry up to 5 times on a name conflict" loop (l.233–268) is duplicated in `projectFile.ts` l.412–432, and `takenNames` (l.112) is inlined there (l.413). certain
  - l.213–219: the PDF upload (put with `sha256`, 400 on mismatch) duplicates `PUT /api/pdfs/:sha256` in `projectFile.ts` l.467–476. certain
  - l.146–162 vs l.185–197: the two GET handlers build the same immutable-object response (body, Content-Type, Content-Length, Cache-Control); a small helper would do. certain
  - l.67–70: `convertAddedConfigs` runs on every `/api/*` request, including content and PDF transfers; it is memoized per isolate after the first (llmRoutes.ts l.404), so it costs one settings read per isolate start. Fine, but the middleware ordering means a D1 failure there fails any request. check
  - l.170–183, l.216: the whole body is buffered (`arrayBuffer()`) with no size limit before R2 checks it; a PDF of 100+ MB counts against the Worker's memory (128 MB). check
  - l.89–99: the "first stage not done or carried" correlated subquery is the same rule as `readPipeline`'s consumers in the web; fine. The "last stage is done = finished" rule elsewhere (runTimes/projectStats/costs) is a different query. no finding
  - l.229–231: `readSettings` and `defaultForNewStages` both read settings (two reads of the same row set). minor. check
  - l.272–307: PATCH with a body of `{}` or a non-object JSON (e.g. a number) gives 400 "expected a 'name' or a 'runMode'": fine.
  - l.322–335: issue-number reservation is a single atomic statement: fine.
- **Size:** 347 lines, two jobs (app wiring and the project/PDF/content routes); the project routes could join a `projects.ts` like the other route modules. check

## apps/worker/src/versions.ts
- **What it does:** optimistic locking middleware on `/api/projects/:id/*`: classifies each request by method and path (checked and raised / raised only / nothing), refuses a "checked" request whose `X-Project-Version` header differs from the project's version (409, `stale_version`), raises the version after a successful request, and sets the header on every answer about a project. Classifying `outputs`/`finish` needs a DB read of the stage's status.
- **Exports:** `VERSION_HEADER`, `STALE_MESSAGE`, `versionRoutes`.
- **Imports:** `hono` types. Platform: D1.
- **Notable internal helpers:** `whatOf` (route classification by hand-parsed path segments), `versionOf`.
- **Findings:**
  - l.54–66: check-then-act, not atomic: two "checked" requests sent with the same version can both pass the check before either raises it (the raise is a separate statement after `next()`). The usual fix is a conditional `UPDATE … SET version = version + 1 WHERE id = ? AND version = ?` before the change. check (D1 serializes statements, but not this pair)
  - l.23–41: the route table is duplicated as string matching on path segments, apart from the routes themselves (pipeline.ts); a new route needs an entry here or it isn't locked. Fragile. check
  - l.66: the version is raised `WHERE id = ?` without `deleted_at IS NULL`; harmless. no finding
  - l.69–72: each GET under a project costs an extra D1 read for the header; acceptable. check

## apps/worker/src/pipeline.ts
- **What it does:** a project's pipeline in D1 and all its routes: read the pipeline (stages joined with their model config's columns, per-stage cost with VAT, outputs, dropped cards), set a stage's config (in place or by replacing the stage and rewriting everything after it), start (with reuse of a done stage by stage key), record outputs (running: insert-or-ignore; WIP: upsert, and count the save per quarter of an hour), heartbeat, finish, stop (throw away outputs, put a planned copy in place), add a manual fix, edit a finished manual stage (copy as WIP, with its inputs and outputs), resolve a carried stage (compare what it read with the outputs it would read now, by content keys), add a further review or a human review (each with its own `apply_review`), drop a stage, dismiss a dropped card. The core helper `rewriteFrom` rewrites a pipeline from a position: planned stages kept, run ones replaced by planned copies, manual/further-review stages carried, optionally applying a model config to later LLM stages. Also: stale-heartbeat detection, closing a stopped stage's running calls.
- **Exports:** types `Pipeline`, `Dropped`, `StageStatus`, `Stage`, `Output`; constants `RECIPE`, `MANUAL_STEPS`, `LLM_STEPS`, `STALE_MS`, `STOPPED_CALL`, `INTERRUPTED_CALL`; functions `isLlm`, `withModelConfig` (set `modelConfigId` in a config JSON), `defaultForNewStages`, `newStageConfig`, `newPipeline`, `anyRunning`, `pipelineRoutes`.
- **Imports:** vat (`COST_WITH_VAT`), requestLog (`logFields`), activeTime (`QUARTER_MS`), llmRoutes (`deletedConfigMessage`, `readSettings`, `resolvedModel`, `unsupportedConfigMessage`, `unsupportedOf`, `ModelConfigRow`), llm/models types; `hono`. Platform: D1 (`batch` as transaction), `crypto.randomUUID`.
- **Notable internal helpers:** `isManual`, `isFurtherReview`, `isCarried`, `plannedStage`, `rewriteFrom`, `readPipeline`, `entry` (stage at a position, live project), `closeRunningCalls`, `isStale`, `withItsApply`, `touchProject`, `isKey` (hex-64), `isStringArray`, `isTiming`/`timingValues`, `stageModelConfig`.
- **Findings:**
  - l.33 vs l.969: `Stage.modelConfig` is typed `{ name; model; deleted }` but `stageModelConfig` returns `unsupported` too, which the web reads (web `api.ts` l.28, `pipeline.ts` l.165). The worker's type lies; the web keeps its own copy of the type. certain (type), check (share the API types through `@score3ly/core`)

  - l.387: `isKey` duplicates index.ts `isSha256` (see there). certain
  - l.205, l.451, l.860, l.901: four near-identical `INSERT INTO stages (…) VALUES (…'planned'…)` statements; `plannedStage` and `newStageConfig` already cover most. And l.726 vs l.893: the WIP manual stage insert twice (fix, human review); l.522, l.730, l.897: the `stage_inputs` insert three times. certain
  - l.419, l.481, l.554, l.620, l.645, l.668, l.708, l.750, l.796, l.847, l.880, l.920: the same `entry` + 404 + (often) carried 409 + `anyRunning` 409 prologue repeated in every route; a small guard helper would shorten each. certain
  - l.371–381: `withItsApply` makes two queries for two adjacent positions; one query (`position IN (?, ?)`) suffices. certain (minor)
  - l.299 (and runTimes.ts l.49, activeTime.ts l.23): grouping into a `Map` by spreading the array on every row (`[...(m.get(k) ?? []), row]`), quadratic; `Map.groupBy` does it. certain
  - l.819: `resolve` builds `IN (?, ?, …)` from all `inputIds`; D1 allows at most 100 bound parameters per statement (projectFile.ts l.201 says so and chunks). A carried `human_review` or `fix_layout` on a score with >100 inputs (systems, pages) would fail. check (likely a real bug)

## apps/worker/src/projectFile.ts
- **What it does:** export and import of a project. Export: the rows of the current pipeline (stages, outputs, links, calls incl. those served from other stages, manual saves, configs, fingerprints) with links outside cut, and the content hashes referenced; refuses while running or when a call has no place. Import: maps model configs by value equality (secrets compared as key-sorted JSON) or creates them (numbered names); reuses done stages by stage key, mapping their outputs by (item, type); maps calls by request key (live, or revive a deleted one) or inserts them; inserts copied stages, outputs (parents first), links, saves, fingerprints and the project with a free name, all in one batch with retry on name conflict. Routes: export, "which content is missing" (HEAD per object, ≤200), PUT a PDF, import.
- **Exports:** `EXPORT_FORMAT`, types `ProjectExport`, `Imported`; `exportProject`, `exportProblem`, `importProject`, `projectFileRoutes`.
- **Imports:** names (`firstFreeName`, `MAX_NAME_LENGTH`), pipeline (`anyRunning`, `withModelConfig`), llmRoutes (`PLACEHOLDER_ITEM`, `placeProblem`); `hono`. Platform: D1, R2 (`head`, `put` with `sha256`), `crypto.randomUUID`.
- **Notable internal helpers:** `list` (alias-prefixed column list), `rowsByIds` (chunked `IN` queries for D1's 100-parameter limit), `isSha256`, `canonicalJson` (top-level key sort), `sameConfig`, `pick` (columns from a row), `insert` (generic INSERT from an object).
- **Findings:**
  - l.237–244: `canonicalJson` re-implements `canonicalJson` from `@score3ly/core` (keys.ts l.11), and only sorts the top level. certain
  - l.232: `isSha256` duplicate (see index.ts). certain
  - l.258, l.462, l.471: R2 keys as literals (see index.ts). certain
  - l.467–476: `PUT /api/pdfs/:sha256` duplicates the upload in index.ts `POST /api/projects`. certain
  - l.412–432: the name-retry loop and `isNameConflict` text duplicated from index.ts. certain
  - l.286, l.316, l.417: one statement per keyed stage, per ok call, and every row of the import in a single `batch`: a large project means hundreds or thousands of statements in one invocation (D1's per-invocation query limit, statement-size limits). check
  - l.462: up to 200 sequential `head` calls; `Promise.all` (in chunks) would be faster. check
  - l.201: `rowsByIds` is the only place that respects D1's 100-parameter limit; pipeline.ts `resolve` (l.819) doesn't. Belongs in a shared D1 helper. check
  - l.386: an output whose call wasn't mapped (e.g. a non-ok call of a reused stage) silently loses its `call_id`. check
  - l.347: an unmapped config falls back to the exported id, which then fails the foreign key with an opaque D1 error rather than a message. check
  - l.450: an export with a call without a place answers 500 though it is the data's state, not a server fault (409 or 422 would fit). check
  - l.125 `list`/l.435 `pick`/l.439 `insert`: small generic row helpers; the column lists duplicate the schema (0001) by hand, as fingerprints.ts and pipeline.ts do. check
- **Size:** 487 lines, export + import + routes; acceptable, import could be split. check
