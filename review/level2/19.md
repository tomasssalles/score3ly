# Level 2, group 19: Layout and skew, from analysis to editors

## Map
- **imaging skew.ts:** `findSkew` (angle, staves, up to 5 lines; `SkewLine` `{x0,y0,x1,y1,angle}` in page fractions, angle in degrees) and `deskewAngle(lines, width)` (the straightening decision, `DESKEW_VERSION`). Runs in the page-image worker (`measureSkew`) and in runLayout.
- **prompts layout.ts:** `layout`'s texts, `LAYOUT_SCHEMA`, `LayoutBox`/`LayoutSystem`/`LayoutAnswer`, `checkLayoutAnswer` (validates and sorts the bar lines, accepts them up to 0.02 outside their box).
- **web, step modules (pure):** skewAnalysis.ts (config, key, note, `angleLabel`), layout.ts (`PageLayout` = stored form: `angle`, `severelySkewed`, `systems`, `flagged`, `note`, `rounds`; key; note), fixSkew.ts (`PageLines` `{lines}`, `lineThrough`, note), fixLayout.ts (sort, box drawing/resizing, bar line add/move, `systemAt`, `fixedLayout`, `systemsChanged`, `firstNumbers`, note).
- **web, runners and finishers:** runSkewAnalysis (stores the whole `Skew` per page, type `skew`), runLayout (straightens by `deskewAngle` of the latest `skew_analysis`/`fix_skew` lines, up to 3 rounds, stores `PageLayout`, type `layout`), finishFixSkew/finishFixLayout (fill untouched pages from the source stage, count changes; export `linesBytes`/`layoutBytes`, which the editors import).
- **web, editors:** pageEditor.tsx (`useViewport` gestures, `usePageImage`, `useSaver`, toolbar parts, `BoxHandles`, `LineHandle`), handles.ts, viewBounds.ts; SkewEditor.tsx and LayoutEditor.tsx (each: outer shell with page index and per-page histories + a module-level `saved` Map, and an inner per-page editor). Mounted by ArtifactView (73, 79), which also draws the finished views (`LinesOverlay` 170, `LayoutPageView` 256).
- **PageView.tsx:** not a page-image view at all: the menu's pages (About, Settings, Statistics, Help).

Contracts: (1) a "lines" content is `{ lines: SkewLine[] }` for both `skew` (a full `Skew`) and `lines` (fix_skew) outputs; read by runLayout, finishFixSkew, SkewEditor, ArtifactView. (2) A `layout` content is `PageLayout`, written by runLayout, finishFixLayout and LayoutEditor (both via `fixedLayout`: sorted, `flagged: false`), read by musicInputs, runAnalyze, finishHumanReview, ArtifactView, LayoutEditor. (3) Its coordinates are fractions of the page straightened by its own `angle`, so every reader rebuilds the same `StraightRecipe` (group 03 #6). (4) Editor saves go through `PUT /api/content` + `POST …/outputs` (a "checked" request under optimistic locking, versions.ts 37–39) + fingerprints.

## Findings
1. **SkewEditor saves pages on separate chains, so two saves can be in flight and the second is refused as "changed on another device"** — SkewEditor.tsx 111: `useSaver` lives in the per-page `PageEditor` (remounted per page, `key={page.item}` 69), so each page (and each visit to a page) gets its own chain. Edit page 1, flip to page 2 (ArrowRight) and edit before page 1's `recordOutputs` has answered: both POSTs carry the same `X-Project-Version`; the Worker raises the version on the first (versions.ts 66) and answers the second 409 `stale_version` → "Saving failed: This project was changed on another device…" plus App's global "changed elsewhere" dialog (group 07 #4). Same if one returns to page 1 while its old chain still runs (two chains for one item; without the lock they could even land out of order). LayoutEditor has one chain for the whole editor (85, 115) and avoids it. Fix: one chain per editor/stage (finding 4). **certain** (mechanism), **check** (likely on a phone's network).
2. **The browser's project version can go backwards, so a save right after a refresh can be refused as stale** — api.ts 84–86 `projectFetch` stores whatever version the latest *arriving* answer carries. Every editor save calls `onEdited` → ProjectView `refresh` (601, 643), a GET whose answer carries the version read at its end (versions.ts 69–71). If the next save completes (version V+2) before that GET's answer arrives but after the GET read V+1, the map is set back to V+1 and the save after it gets 409 `stale_version`. Editors save on every drag release, so they are where this shows. Fix: keep the larger (versions only rise), `versions.set(id, max(known, current))`. Untested (level 1 06: the header logic has no test). **certain** (mechanism), **check** (timing; for group 07's area, found here).
3. **The editors' `saved` caches are never cleared, contrary to their comments** — SkewEditor.tsx 45–46, LayoutEditor.tsx 64–65 (and fieldList.tsx 14, group 20): "until the pipeline the app has" / pageEditor.tsx 315 "until the pipeline is fetched again", but nothing deletes an entry (grep: no `saved.delete`/`clear`), and the cache is set *before* the save (pageEditor 321, LayoutEditor 114). So after a failed save, closing and reopening the editor shows the unsaved state with no error, as if stored, while Finish (finishFixSkew/finishFixLayout) records the server's older content. The cache wins over `linesSha256`/`layoutSha256` from the pipeline forever in that tab. Fix: set the entry after a successful save, or drop it when the pipeline's content hash for the item equals the saved one; or drop the cache and read the pipeline (the editors already refetch it on every save). **certain** (comment lies), **check** (impact: failed saves only).
4. **The save chain: `useSaver` has one user, rewritten three times** — pageEditor.tsx 317–331 is used only by SkewEditor; LayoutEditor.tsx 110–128 writes the same chain + "Saving failed" message inline; fieldList.tsx 48–57 and ExtractionView.tsx 306–323 again (groups 20/18). They differ in the one thing that matters (finding 1: per page vs per editor). One `useSaver(store)` held at the editor (stage) level, one chain per stage, keyed cache handled as in finding 3; LayoutEditor's `show` and the others use it. **certain**.
5. **Bar lines at a box's edge or on top of each other are accepted, by the check and by the editor, and make empty stretches** — prompts layout.ts 95–97 accepts any bar line within 0.02 of the box, including one at (or just inside) `right`: the system's end line, which the prompt (19) and the check text (layoutCheck 29) both warn against, a sign models do give it. Duplicates (two equal values) pass too. In the editor, `addBarLine` (fixLayout.ts 75) clamps a tap onto the box's edge, and two taps at one place add two lines. Each gives a stretch of zero width: `stretchCropBoxes` (extract.ts 35) crops just the margins, `extract` must classify an empty stretch, MEI gets a zero-width zone. Group 02 #7 proposes clamping lines outside the box into it, which turns a line just past the end into exactly this case. Better one `normalizeBarLines(system, ε)` beside `LayoutSystem` (prompts layout.ts): drop lines within ε (say 0.005) of either edge or outside, merge lines closer than ε, sorted; used by `checkLayoutAnswer`, `addBarLine`/`moveBarLine`/`withinBox` (fixLayout.ts). Test both. **certain** (code path), **check** (how often real answers hit it).
6. **The two editors are one editor written twice** — outer shell: page index, clamp, `go`, `key={page.item}`, module `saved` Map, per-page histories (SkewEditor 51–80, LayoutEditor 67–163); `step` vs `stepBack` (SkewEditor 176–189, LayoutEditor 240–247: drop an anchor first, then undo/redo); key handling (SkewEditor 245–258, LayoutEditor 347–368); the "keep the fingerprint" tail of every save (SkewEditor 116–117, LayoutEditor 121–123). Reach constants: `LINE_REACH = 14` twice (SkewEditor 42, LayoutEditor 60), `HANDLE_REACH` twice with different meanings (SkewEditor 43: 26 px from a point; handles.ts 14: 22 − CORNER/2 = 15 px from the drawn shape, group 02 #13). Shared: in pageEditor.tsx a `usePageEditorShell(pages, stageId)` (index, nav, histories, saver from finding 4) and `editorKeys(event, { undo, redo, remove, escape, flip })`; reach constants in handles.ts. **certain**.
7. **A layout is drawn as SVG twice, lines twice** — boxes, bar lines and numbered colour labels in LayoutEditor.tsx 430–480 (image px, labels in SVG) and ArtifactView.tsx `LayoutPageView` 269–296 (viewBox 0–1, labels as HTML); a page's lines with `angleLabel` in SkewEditor.tsx 307–317 and ArtifactView.tsx `LinesOverlay` 186–197. Both colour by index on the page (`LAYOUT_COLOR_HEX[i % …]`), as imaging's draw.ts does for the model; they agree today, by copy. One `<LayoutMarks systems first size scale>` and `<LineMarks>` in pageEditor.tsx (or a `marks.tsx`) used by the editors and the views. **certain** (duplication).
8. **The "lines" content is typed three ways** — `Skew` (runLayout.ts 66 casts fix_skew's `{lines}` to `Skew`), `PageLines` (fixSkew.ts 12, finishFixSkew, SkewEditor), `PageSkew = Skew` (skewAnalysis.ts 36, used only by ArtifactView 177, which reads fix_skew's lines with it too). Readers need only `.lines`: read both through `PageLines` (`Pick<Skew, "lines">`), drop `PageSkew`. **certain** (minor).
9. **What `skew_analysis` stores beyond the lines has no reader, and a page at the search limit says nothing** — `angle`, `confidence`, `atLimit`, `staves` (skew.ts 9–22) are read nowhere in the app (grep); an `atLimit` page gets `lines: []` (skew.ts 158) and the card says only "lines on 9 of 10 pages" (skewAnalysis.ts 39–41), while the one useful action (raise the max angle) is in the config's hint. The stored fields are documented (overview §6), so keep them; a note "1 at the angle limit" would use them. **check** (UX).
10. **Every editor save fingerprints the page again** — SkewEditor.tsx 117 (`pageImage` + `keepFingerprints`), LayoutEditor.tsx 122–123 (`straightPage` + `keepFingerprints`): a worker round trip and a POST per edit, for the same image every time; once per page per editor session would do (a Set of recipe keys done). Group 03 #8 covers LayoutEditor's null-angle key. **certain** (waste, minor).
11. **LayoutEditor's `change`/`step` close over the render's `history`** — LayoutEditor.tsx 150–160 push onto `history` from the render, while SkewEditor 167/177 reads `histories.get(...)` at call time. Two changes within one render would lose the first; React renders between discrete events, so not reachable today. Folds into 6. **check** (low).
12. **`fixSkewNote` and `fixLayoutNote` are one function** — fixSkew.ts 41–44, fixLayout.ts 120–123: `fixNote(noun, changed, pages)`; with `skewNote`/`layoutNote` the plurals of group 22. **certain** (level 1, confirmed).
13. **skew.ts does two jobs, coupled by a hidden write** — `findStaves` sets `strips.strength` (403) that `measureLine` reads (209); the angle search (≈ 1–150, 320–360) and the staves/lines (380–481, 186–258) could split into skew.ts and staves.ts, with `strength` returned by `findStaves` and passed. **certain** (coupling), **check** (the split).
14. **`layout`'s stage key doesn't cover `LAYOUT_ROUNDS`** — prompts layout.ts 5 says to raise the version when "the texts, the schema or the checks change"; the number of rounds changes the result as much, and isn't in `layoutStageKey` (runLayout 44–49), so a change would reuse done stages. Add "or the rounds" to the comment (or put `LAYOUT_ROUNDS` in the key). **check** (minor).
15. **Small:** PageView.tsx's name says page image, it is the menu's pages (rename `MenuPage.tsx`; group 23), and its Help text 13 says "MEI and LilyPond" (level 1, confirmed); runSkewAnalysis.ts 1 and skewAnalysis.ts 1 point to docs/stages/analyze.md for a step in pages.md (confirmed); `EditorPage`/`LayoutEditorPage` (SkewEditor 32, LayoutEditor 49) are one shape with `linesSha256`/`layoutSha256`, exported but built inline by ArtifactView 70–78 — one `EditorPage { contentSha256 }` would let ArtifactView build both the same way; `checkLayoutAnswer` 100 turns a non-string `note` into `""` (confirmed, minor). **certain**.

## For level 3
- **Saving under optimistic locking** (component A ↔ B): any page that fires checked requests in parallel, or refreshes while saving, can refuse its own saves as "changed elsewhere" (findings 1, 2). The rule belongs with the lock: one save queue per project in api.ts (all checked requests of a project serialized) and a monotonic version map would fix every editor (skew, layout, forms, human review) at once, instead of each editor getting its chain right.
- **The layout's stored form** is the input of all crop geometry (group 02): normalize bar lines once, where answers and edits enter (finding 5), rather than clamping in one place.
- **An editor kit:** pageEditor.tsx + handles.ts + viewBounds.ts + the shell and drawing of findings 6–7, and HumanReviewCards' DrawLayer on the same gesture code; the box editing of fixLayout.ts (group 02 #8) moves there too. Belongs with the UI kit (group 22), while the step modules (fixSkew.ts, fixLayout.ts) keep only stage logic.
- PageView.tsx belongs to routing/menu (group 23), not here.

## Patterns
- **A shared hook written and then not used** (1: `useSaver`, one user of four copies; the copies differ in the property that matters). Cause: the second editor was written beside the first's code rather than on the hook extracted from it; the hook's per-page placement wasn't questioned.
- **Concurrency against the lock not considered** (2: per-page chains, non-monotonic version map). Cause: optimistic locking added globally after the editors, whose saves assumed independence; no test of the browser side of the lock.
- **A cache whose comment promises an eviction that was never written** (1, in three editors). Cause: the eviction ("until the pipeline is fetched again") described intent; the refetch path never learned about the cache.
- **Two components drawing the same thing** (2: layout marks, lines; plus two editors ×4 shared blocks). Cause: the view and the editor written at different times, each with its own coordinate system (fractions vs image px), so the second didn't reuse the first.
- **A tolerance that accepts without normalizing** (1: bar lines at edges and duplicates; also group 02 #7). Cause: the check refuses the clearly wrong, and the near-misses' effect downstream (empty stretches) wasn't followed.
- **A type restated for one content** (1: lines as `Skew`/`PageLines`/`PageSkew`). Cause: each reader typed what it fetched with the nearest type at hand.
- **Stale or misleading names and doc pointers** (3: PageView, the analyze.md pointers, chevron icons). Cause: files and docs moved or split after the code was written.
