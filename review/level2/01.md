# Level 2, group 01: Hashes, keys, canonical JSON

## Map
- **packages/core/src/keys.ts**: `sha256Hex` (WebCrypto, async), `canonicalJson` (keys sorted by code unit at every level, undefined dropped from objects), `keyOf` = `sha256Hex(canonicalJson(v))`. The one source of content keys, recipe keys, stage keys and request keys for the web app, the Worker and the scripts. Runs in browsers, Workers, Node.
- **packages/imaging/src/fingerprint.ts**: private `sha256Hex` (raw pixels → `pixelsSha256`), private base64 pair. `imaging` doesn't depend on `core`.
- **Worker:**
  - index.ts: `isSha256`, `pdfKey` (`pdfs/<sha>.pdf`), `contentKey` (`content/<sha>`); `PUT/GET /api/content/:sha256` and the PDF upload rely on R2's `sha256` option to verify bytes against the key (the desktop R2 adapter checks it too, apps/desktop/src/r2.ts 82).
  - pipeline.ts: `isKey` (hex-64) on `stageKey`, `contentSha256`, `recipeKey`; start reuses any done, live stage with the same `stage_key` (498). The Worker never computes a stage key: it trusts the browser's.
  - llmRoutes.ts: the request key `keyOf({provider, model, effort, request: keyedRequest(request)})` (885), cache lookup by it; `recordedRequest` (images → recipe key + sha256 of bytes); `putJson` (canonical JSON → `content/<sha>`); `listKey` (`sha256Hex(JSON.stringify(...))`); `sameValues` for configs.
  - projectFile.ts: `isSha256`, its own `canonicalJson(text)` (top level only, `localeCompare`), `sameConfig` over `CONFIG_VALUES`; import reuses done stages by `stage_key` (285–286).
  - fingerprints.ts: `HEX64`, `Fingerprint` type restated.
  - deletion.ts, llm/replay.ts, scripts/callPlaces.ts: R2 key literals `content/…`, `pdfs/….pdf`.
- **Web:**
  - Stage keys: one `*StageKey` per step (rasterize.ts `stageKey`, skewAnalysis.ts, layout.ts, analyze.ts, extract.ts, review.ts, applyReview.ts, engrave.ts `buildMeiStageKey`; runEngrave.ts inline), all `keyOf({step, version, …})`; LLM ones take `modelKey(config)` (llm.ts 26: provider, model, effort) and an `imageRecipe` of the imaging versions.
  - Recipe keys: `keyOf(recipe)` in pageImages.ts, llm.ts 104, runRasterize.ts, runEngrave.ts, ImagesDiffer.tsx; the same key names the OPFS file (imageCache.ts, `cache/pdf-<sha>/<key>.png`), the fingerprint on the Worker, and the image in an LLM request.
  - Content keys: `putContent` (api.ts 296) = `sha256Hex(bytes)`; bytes are `canonicalJson` everywhere (eight hand-rolled `json`/`*Bytes` helpers, level 1 batch 06).
  - fixLayout.ts `systemsChanged`: `JSON.stringify` comparison.
- **apps/web/scripts/leipzig.ts**: a sync Node `sha256Hex(Buffer)` (node:crypto) for the font check.

Contracts: (1) request key, worker-side only, but the browser must send the same request twice (without and with images) → `keyedRequest` drops `image` and `cacheUpTo`, tested (llmRoutes.test.ts 751–769). (2) Stage key, browser-side only; the Worker matches it blindly, across projects and on import. (3) Content key = SHA-256 of the bytes, verified by R2 on put. (4) The model part of keys is written twice: `modelKey` (web llm.ts 26) and the request key's fields (llmRoutes.ts 885–889); both use provider, model, effort today.

## Findings
1. **`canonicalJson` writes invalid JSON for `undefined` (or a function) inside an array** — packages/core/src/keys.ts 12: `value.map(canonicalJson)` returns `undefined`, which `join` turns into `""`, so `[1, undefined]` gives `"[1,]"` (JSON.stringify gives `[1,null]`). Every content put and the `JSON.parse(canonicalJson(x))` normalizations (runExtract 164, runReview 187/201, runApplyReview 313/350, runAnalyze 207) would then store unparseable content or throw. Fix: map undefined in arrays to `null` as JSON does; add the test (keys.test.ts gap noted at level 1). certain (bug in the function); whether any caller passes such an array: check.
2. **`canonicalJson` ignores `toJSON` and treats typed arrays/Maps as plain objects** — keys.ts 13: a `Date` gives `{}`, a `Uint8Array` gives index keys sorted as strings (`"0","1","10","2"`). No caller is known to pass one (recipes and content are plain JSON). Document "plain JSON values only" in its comment, or honour `toJSON`. check.
3. **Hex-64 check written five times** — index.ts 117 `isSha256`, pipeline.ts 387 `isKey`, projectFile.ts 232 `isSha256`, fingerprints.ts 30 `HEX64`, llmRoutes.ts 487 inline. Must behave the same (all keys come from `sha256Hex`). Shared version: `isSha256Hex` (or `isKey`) in `@score3ly/core` keys.ts beside `sha256Hex`; the Worker already depends on core. certain.
4. **R2 key layout spelled by hand in six files** — `pdfKey`/`contentKey` in index.ts 121/166, literals in projectFile.ts 258/462/471, deletion.ts 74–81, llmRoutes.ts 554/900, llm/replay.ts 27, scripts/callPlaces.ts 42 (+ callPlaces.test.ts 43; apps/desktop/src/r2.ts names them in a comment). One Worker module (e.g. `apps/worker/src/r2Keys.ts`: `pdfKey`, `contentKey`, the two prefixes for deletion's orphan scan) used by all. certain.
5. **Two content-addressed puts in the Worker, two ways** — llmRoutes.ts `putJson` 551 (canonical JSON → bytes → sha → put with `sha256`) and index.ts `PUT /api/content` 170 (bytes from the browser). Same contract; `putJson` would use `contentKey` from finding 4. And in the web, eight local `json`/`jsonBytes`/`layoutBytes`/`linesBytes` (runAnalyze 57, runExtract 34, runReview 38, runApplyReview 66, runLayout 116, runSkewAnalysis 51, finishFixSkew 11, finishFixLayout 12, finishFixMetadata 9) all = `TextEncoder(canonicalJson(v))` → one `putJson(value)` in api.ts (or `jsonBytes` in core). certain.
6. **`canonicalJson` twice, and config equality twice** — projectFile.ts 237 is a different function under the same name (parses text, sorts the top level with `localeCompare`, falls back to the raw text) used by `sameConfig` 246; llmRoutes.ts 1267 `sameValues` does the same comparison with core's `canonicalJson` over a hand-written key list that equals `CONFIG_VALUES` minus `secrets_json`. They must agree (both decide "same config": one on create/clone, one on import). Shared: export one `sameConfigValues(a, b)` from llmRoutes.ts (projectFile.ts already imports from it) driven by `CONFIG_VALUES` moved there; drop the private `canonicalJson`. Since `secrets_json` is stored canonical already (llmRoutes.ts 1287), comparing the parsed objects with core's `canonicalJson` suffices. certain.
7. **`sha256Hex` copies** — imaging/fingerprint.ts 41 (needed: imaging can't import core, unless the dependency is added; imaging→core would be harmless, core has no dependencies); apps/worker/src/index.test.ts 44 and llmRoutes.test.ts 91/671 (should import core's); apps/web/scripts/leipzig.ts 18 (sync node:crypto, Node-only script: legitimate, but rename to avoid the clash with core's async one, e.g. `sha256OfBuffer`). certain.
8. **LLM stage keys leave out the stage's config apart from the model** — layout.ts 20, analyze.ts 48, extract.ts 204, review.ts 283, applyReview.ts 331 take `model` and `imageRecipe` but not `stage.config`; correct today since `LLM_CONFIG` (steps.ts 60) has only `modelConfigId`, but steps.ts 60's comment invites "another setting… beside it", which would then have to be added to five keys by hand, or done stages would be wrongly reused (the Worker reuses by key blindly, pipeline.ts 498). The five wrappers are the same one-liner; one generic `llmStageKey(step, version, {config, model, imageRecipe, inputs})` would take the whole resolved config. check (design risk, not a bug now).
9. **`skew_analysis`'s key has no version of `findSkew`** — skewAnalysis.ts 31–32 relies on `SKEW_ANALYSIS_VERSION` being bumped by hand when imaging's skew code changes, while every other imaging operation has its own version constant in imaging (CROP, DRAW, ROTATE, SCALE, DESKEW, FINGERPRINT) that goes into recipes and keys. Add `FIND_SKEW_VERSION` in skew.ts and put it in the key. certain (inconsistency); confirms level 1's check.
10. **The model part of keys written twice** — web llm.ts 26 `modelKey` and llmRoutes.ts 885–889 list the same three fields; if one side adds a field (e.g. a parameter that changes the answer, §5.2) the other must follow. Could live in core as `modelKeyOf({provider, model, effort})`. check (minor).
11. **`listKey` hashes `JSON.stringify` by hand** — llmRoutes.ts 398: equivalent to `keyOf(list.models.map(...))` (arrays only, so order-sensitive by design). Exported but used only in the file (and maybe its test). certain (trivial); changing it reconverts once, harmless.
12. **`JSON.parse(canonicalJson(x))` as "normalize as stored"** — runAnalyze 207, runExtract 164, runReview 187/201, runApplyReview 313/350: six uses of the idiom so that in-memory values equal what is stored (sorted keys, undefined dropped). A named helper (`asStoredJson` in core keys.ts) would say why. check (style).
13. **`systemsChanged` compares by `JSON.stringify`** — fixLayout.ts 106: key-order sensitive, but both sides come from stored canonical content (finishFixLayout.ts 24–28), so harmless today; `canonicalJson` would make it independent of where the objects come from. check (minor; level 1's check downgraded).
14. **The `Fingerprint` shape written twice** — apps/worker/src/fingerprints.ts 6–16 restates imaging's `Fingerprint` plus `recipeKey`/`pdfSha256`, which web api.ts 571 composes as `StoredFingerprint`. The Worker doesn't depend on imaging; a shared type would sit in core (with imaging importing it, see 7) or the Worker could import the type only from imaging. check (types only).
15. **Base64 decode by hand three times** — imaging/fingerprint.ts 35, llmRoutes.ts 501 `base64Bytes`, googleServiceAccount.ts 122 (plus encoders in web). Out of this group's core but touches hashing (`recordedRequest` hashes decoded bytes). For group 09/08. check.

## For level 3
- `@score3ly/core` keys.ts should become the one place for "what a key is": `sha256Hex`, `canonicalJson` (fixed), `keyOf`, `isSha256Hex`, maybe `jsonBytes` and the model part of keys; letting `imaging` depend on `core` removes its private copy.
- The Worker trusts browser-computed stage keys globally (across projects, on import): correctness of reuse rests entirely on the web's `*StageKey` functions listing every input; a component-level look at the stage-key inputs vs what each run*.ts actually reads (group 06) is worth it.
- R2 key layout belongs to the Worker's storage component (groups 15, 24: deletion, export/import, desktop R2).
- Content puts in the web (group 06's "putting JSON content") and the Worker's `putJson` are one contract.

## Patterns
- **A helper written again instead of imported** (6: hex-64 check ×5, `sha256Hex` ×4 incl. tests, `canonicalJson` ×2, `json`/`*Bytes` ×8, `putJson` vs `PUT /api/content`, base64 decode ×3). Cause: each file written in its own session, with a quick inline version faster than finding the shared one; core's exports weren't the first place looked; package boundaries (`imaging` without `core`) pushed a copy.
- **A convention spelled as literals in many files** (1: R2 key layout in six files). Cause: the first module made private helpers (`pdfKey`, `contentKey`), and later modules couldn't import them from the entry module (it may only export handlers), so they wrote the strings again.
- **A contract restated on both sides** (3: the model part of keys in web and Worker, the `Fingerprint` shape, config equality's column list). Cause: no shared module for the types and constants both sides need; each side written to match the other by reading it.
- **Same idea, two functions, by hand each time** (2: five `*StageKey` wrappers that each pick their inputs, `JSON.parse(canonicalJson(x))` ×6 without a name). Cause: copy the previous step's file and adapt it; nothing forces the stage's whole config into the key.
- **A versioning rule kept by hand** (1: `findSkew` without its own version in the skew key). Cause: the rule "every imaging operation has a version" was followed when the operations were written, but the skew code came in through another step.
- **An edge-case bug in a generic helper** (1: `canonicalJson` with undefined in arrays; plus 1 undocumented limit: `toJSON`, typed arrays). Cause: written for the cases at hand, tests only of those.
- **Comparison by `JSON.stringify` where canonical comparison exists** (1: `systemsChanged`). Cause: quick local check, safe only because of where the data happens to come from.
