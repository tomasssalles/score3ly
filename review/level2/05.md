# Level 2, group 05: Pipeline state, both sides

## Map
- **D1** (migration 0001): `stages.status` CHECK `planned|running|failed|done|wip|stopped` (81), `in_recipe` (92), `heartbeat_at` (101, comment "about 3 minutes"); `pipeline_entries` (project, position, stage, `carried`) (111–120); `outputs` with `UNIQUE (stage_id, item, type)` (194); `dropped_stages` (243).
- **Worker `pipeline.ts`**: the stored shape `Pipeline`/`Stage`/`Output`/`Dropped` and `StageStatus` (12–48); the step lists `RECIPE`, `MANUAL_STEPS`, `LLM_STEPS` (51–79); the rules `isManual`, `isFurtherReview`, `isCarried` (62–74), `isStale` + `STALE_MS` (114, 364); `rewriteFrom` (planned kept, run → planned copy, manual/further review → carried); `readPipeline` (the GET's answer); the routes that move a status: start (planned|failed|stale → running, or reuse), finish (running → done|failed, wip → done), stop (running → `stopped`, out of the pipeline, a planned copy in its place), resolve (carried → kept or dropped + a `dropped_stages` card), drop.
- **Worker `index.ts` 87–107**: `GET /api/projects` gives each project's `current` (`PipelinePosition`, core) by "first entry not done or carried".
- **core `project.ts`**: `Project`, `RunMode`, `PipelinePosition` (status union inline, 20), `ListedProject`. The only pipeline type both sides import.
- **Web `api.ts` 9–42**: `ApiPipeline`/`ApiStage`/`ApiOutput`/`ApiDropped`, restating the Worker's types by hand ("Mirrors…").
- **Web `pipeline.ts`**: `toPipeline` turns `ApiPipeline` into the UI's `Stage` (its own `StageStatus` adds `ready`, drops `stopped`): local run overrides, stale → failed "interrupted", carried → planned, first not-done planned → ready; `nextStaleAt`; queries `currentStage`, `pipelineState`, `canRun`, `progressOf`; `stateLabel` shared with `home.ts` `positionState` (the same states from `PipelinePosition`).
- **Web `steps.ts`**: the step registry (kind, `optional`, fixes, config form, artifacts); `FIX_STARTS`, `carriedInputs`, `reviewInputIds` (what a carried stage would read now, sent to `resolve`).
- **Contracts:** (a) `readPipeline` ↔ `ApiStage` (no shared type, no test); (b) the status set: CHECK ↔ Worker `StageStatus` ↔ core `PipelinePosition.status` ↔ web `ApiStage.status`; (c) the stale rule: Worker `isStale` ↔ web `toPipeline`, `nextStaleAt`, `home.positionState`; (d) step facts: Worker `LLM_STEPS`/`MANUAL_STEPS`/`RECIPE` ↔ web `STEPS[*].kind`/`optional` (only `LLM_STEPS` pinned, by a test that regexes the Worker's source); (e) "first stage not done" on both sides; (f) the drop rule: Worker drop route ↔ web `droppable`; (g) `carriedInputs` ↔ the resolve route's comparison.

## Findings
1. **The API's pipeline types restated by hand, already drifted** — worker pipeline.ts 12–48 vs web api.ts 9–42. Worker `Stage.modelConfig` is `{name, model, deleted}` but `stageModelConfig` (969) also returns `unsupported`, which the web reads (pipeline.ts 166); `config` is `unknown` vs `Record<string, unknown> | null`. Nothing checks the two agree (the web's types are trusted casts of `res.json()`). Shared version: `packages/core/src/pipeline.ts` (beside `project.ts`, which already holds `PipelinePosition`): `Pipeline`, `Stage`, `Output`, `Dropped`, `StageStatus`; the Worker's `readPipeline` annotated with it, the web's `Api*` become aliases or go. Core is a dependency of both already. certain.
2. **The stage status union written four times** — CHECK 0001 81, worker pipeline.ts 18, core project.ts 20 (inline), web api.ts 20; plus the Worker's `PositionRow` (index.ts 100) using core's. One `StageStatus` in core (finding 1), `PipelinePosition.status: StageStatus`. The CHECK stays (SQL), as the single other copy. certain.
3. **`stopped` never reaches a pipeline, but every reader handles it** — stop (pipeline.ts 661–686) marks the stage `stopped` and replaces its entry with a planned copy; reuse picks only `done` stages; export takes the pipeline's stages. So `stopped` in `ApiStage.status`, `PipelinePosition.status`, web `toStage` 150 ("if one shows up anyway") and `home.positionState` 35 is dead. Either narrow the API's type to what a pipeline holds (`StageStatus` without `stopped` for the API, the row type keeps it) or keep the guard and say why once. check (dead branches, harmless).
4. **The stale rule in four places, on two clocks** — Worker `isStale` (pipeline.ts 364), web `toPipeline` 125, `nextStaleAt` 192, `home.positionState` 30, with `STALE_MS` twice (worker 114, web 111, "the same limit"). The browser decides with its own `Date.now()` against the Worker's heartbeat timestamps: a device clock ahead by 2+ min shows a healthy run elsewhere as "Interrupted" with Run enabled, and start then gets 409 "it is running"; a clock behind keeps showing "running" after the Worker would let it restart. Better than moving `STALE_MS` to core: the Worker computes it once and sends it (`interrupted: boolean` and `staleAt` on a running stage in `readPipeline`, and in `PipelinePosition`); the web then has no `STALE_MS`, `nextStaleAt` reads `staleAt`, and home and panel can't differ. Minimum fix: `STALE_MS` + `isInterrupted(status, heartbeatAt, now)` in core, used by all four. certain (duplication), check (clock skew: low on NTP-synced devices).
5. **"The first stage not done" written seven times, in two variants** — worker index.ts 93–97 (`status <> 'done' OR carried`), worker resolve 798–801 (the same, as a count before a position); web `toPipeline` 130 and `currentStage` 207 and `pipelineState` 221 (on UI stages, where carried was already mapped to planned), `ProjectView.resolveCarried` 369 (`s.carried || s.status !== "done"` on `ApiStage`), `toasts.ts` 48 (on snapshots of UI stages, so carried is already handled). They agree today only because `toStage` maps carried → planned first; a reader on `ApiStage` that forgets `carried` gets it wrong (`resolveCarried` remembers it by hand). One `firstNotDone(stages: ApiStage[])` (carried counts) in web pipeline.ts, used by `toPipeline`, `resolveCarried`, toasts; `pipelineState` reuses `currentStage`. The two SQL copies could share one fragment (`NOT_DONE = "(s.status <> 'done' OR e.carried = 1)"`). certain.
6. **Step facts declared on both sides, one pinned by a regex test** — Worker `LLM_STEPS`, `MANUAL_STEPS`, `RECIPE` (pipeline.ts 51–79; `MANUAL_STEPS` again as `MANUAL` in runTimes.ts 16) vs web `STEPS[*].kind` (steps.ts). steps.test.ts 37–46 reads the Worker's source text to compare `LLM_STEPS`; `MANUAL_STEPS` has no test at all, though the Worker's carrying and dropping rest on it and the web's `kind: "manual"` on the same set. Shared version: `packages/core/src/steps.ts` with `STEP_KINDS: Record<StepId, "ingest"|"computed"|"llm"|"manual">` and `RECIPE`; the Worker derives `isManual`/`isLlm` from it, the web's `STEPS` is typed `Record<StepId, …>` and takes `kind` from it (the regex test goes; a new step can't be half-declared). certain.
7. **`StepInfo.optional` is `kind === "manual"` under another name** — steps.ts 53; true exactly for the six manual steps, false for every other, and read once, ORed with `kind === "manual"` (pipeline.ts 182). Its comment ("added by the user… can be dropped") describes a further review too, which is a per-stage fact (`inRecipe`). Remove it. certain.
8. **The drop rule twice** — worker drop route 922 (`isManual || isFurtherReview`) vs web `droppable` 182 (`manual || optional || review && !inRecipe`). Agree today. With finding 6/7 the web's becomes `STEP_KINDS[step] === "manual" || (step === "review" && !inRecipe)`; could be one `isDroppable({step, inRecipe})` in core used by both (the Worker's `isFurtherReview` takes `in_recipe` as a number: adapt at the call). certain (small).
9. **`resolve` binds every input id in one statement: fails on D1 past 100** — pipeline.ts 817–820 `WHERE id IN (?, ?, …)` with all of `carriedInputs` (steps.ts 541): a carried `human_review` sends one extraction per system + 1 (humanReview.ts 38–42), a carried further review `reviewInputIds` ≈ systems + 2 × pages + 3, `fix_layout`/`fix_skew` one per page. D1 refuses more than 100 bound parameters (projectFile.ts 201 says so and chunks by 90); local `wrangler dev` and the desktop's `node:sqlite` don't, so no test sees it. A score of 100 systems with a human review, then any upstream change → the carried stage can't be resolved, the pipeline is stuck with "Checking … failed". Fix: chunk as `rowsByIds` does (move it to a shared module), or compare in SQL against a `json_each(?)` of the ids (one parameter). certain (level 1 check confirmed by the input counts).
10. **No run identity: a stale run and its restart write to the same stage** — start 484–526 accepts a stale `running` stage and keeps the same id; heartbeat 622, outputs 556 and finish 646–648 accept any `running` stage. Device A offline for 3+ min mid-run (a phone), device B restarts it: both run, both pay for calls, outputs first-in wins (`INSERT OR IGNORE`), and the first finish ends it, the other then fails with 409 "isn't running". A heartbeat from A also makes the stage un-stale again under B. A run token (e.g. the `started_at`/a `run_id` that start returns and the browser sends with heartbeat/outputs/finish) would refuse A's late writes. Related to level 1's read-decide-write race on start (two tabs), which is group 06's. check (rare; design).
11. **Run time on the card spans retries and manual work** — web pipeline.ts 152–155: `finishedAt − startedAt`, and start keeps the first `started_at` (`COALESCE`, 518): a stage failed yesterday and retried today shows a day's "run time"; a manual stage shows how long it stayed open. runReport.ts 57 computes it again (level 1). Decide what the card means (the outputs' summed `duration_ms`, as the statistics do, docs/database.md 57?) and compute it in one place. check (meaning, for the docs).
12. **`toStage`'s `later` parameter unused** — web pipeline.ts 147, computed per stage at 121 (`slice(i + 1)`, quadratic in pipeline length). certain (trivial).
13. **`ProjectView.run` restates `canRun`** — ProjectView.tsx 398 `current.status !== "ready" && !== "failed"` is `!canRun(…)` (pipeline.ts 236). certain (trivial).
14. **`readPipeline` groups outputs by spreading on every row** — pipeline.ts 299 (level 1, quadratic; `Map.groupBy` or push). Same for runTimes/activeTime (group 14). certain (minor; confirmed).

## For level 3
- **The Worker ↔ web API has no shared types beyond `Project`.** This group's types are one case; groups 07 (errors), 08 (LLM request), 12 (configs), 13/14 (stats) will find the same `Api*` mirror in api.ts. A level 3 decision: `packages/core/src/api/*.ts` for every response shape, the Worker's routes annotated with them (`c.json<T>`), api.ts keeping only the client.
- **Derived state computed in the browser that the Worker could send** (stale, first not done, droppable): the Worker already knows; sending it once removes the rule from the web and the clock question. Weigh against "the Worker only records" (overview §5.8).
- **D1's 100-parameter limit** is handled in projectFile.ts only; every `IN (…)` built from a list (grep `map(() => "?")`) should be checked across the Worker, and the limit isn't present in local dev or the desktop, so a test helper that enforces it in the test D1 would catch them.
- Concurrency of runs across devices (10) belongs with the stage runner's design (group 06) and the optimistic locking (versions.ts), which doesn't cover the runner's own requests.

## Patterns
- **A type or constant restated on the other side of the API instead of shared** (5: pipeline types, status union ×4, `STALE_MS`, step lists, drop rule). Likely cause: `@score3ly/core` started with keys and `Project`, and each later API shape was written where it was first needed (Worker), then mirrored in api.ts with a "Mirrors…" comment rather than moved; the regex test on `LLM_STEPS` shows the drift was noticed and patched by test instead of by sharing.
- **One rule re-derived at each reader** (2: "first stage not done" ×7, the stale rule ×4). Cause: each screen (panel, home, toasts, the run loop, the resolve route) written for its own data shape (`ApiStage`, UI `Stage`, `PipelinePosition`, snapshots, SQL), so the rule was rewritten for each shape instead of computed once upstream.
- **A field that duplicates another** (1: `optional` ≡ manual). Cause: a flag added for a meaning ("can be dropped") that later moved to a per-stage fact (`inRecipe`), the old flag left in place.
- **Defensive handling of states that can't occur** (1: `stopped` in four readers). Cause: the type includes every DB value, so each reader handles it "just in case" rather than the API narrowing what it sends.
- **Platform limits only in production** (1: D1's 100 parameters). Cause: local dev and desktop use SQLite without D1's limits; the limit was learned in one file (projectFile.ts) and not turned into a shared helper or a test.
- **Dead parameters and trivial restatements** (2: `later`, `canRun`). Cause: code changed and its callers or helpers not revisited.
- **Concurrency of a resumed run not designed** (1: no run identity). Cause: the stale rule was designed for "the tab closed", not for "the device came back".
