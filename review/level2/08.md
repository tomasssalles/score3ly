# Level 2, group 08: The LLM request path

## Map
- **core `sse.ts`** `readSse(response, onData)`: line-wise `data:` reader. Users: web api.ts `streamedAnswer`, Worker google.ts and openrouter.ts (group 09). **core `callEvents.ts`** `CallEvent` (`started` | `progress`): the only part of the browser↔Worker LLM contract that is shared.
- **web `llm.ts`**: `stageModelConfig` (refuses deleted/unsupported configs, restating the Worker's messages), `modelKey` (the model part of keys), image and request size limits, `PlannedRequest` (images as recipe + `make`), `withImages`, `ask` (the two-round protocol: ask with recipe keys only → `{imagesNeeded}` → make images, size check, ask again → keep fingerprints if ok → `noteAnswer` → throw on non-ok).
- **web `api.ts` 485–590**: wire types `LlmContent`, `LlmRequest`, `CallPlace`, `LlmAnswer`; `callLlm` (JSON for cached / images needed / refusals, SSE when sent), `streamedAnswer` (inline event union), `LlmRefused`, `markUnusable`.
- **web `callProgress.ts`**: `trackCall` → `CallProgress` per call (to `StageRun.call`) and `ItemProgress` per item (to `StageRun.item`, characters summed over an item's rounds); `charsText`, `itemText`. **web `itemTiming.ts`**: module-global per-item counters (`noteAnswer`, `noteImage`, `timed`).
- **Worker `llmRoutes.ts` 453–571, 836–1250**: the wire request type (`RequestImage`, `CallRequest`, private), `requestProblem`, `keyedRequest` (key), `recordedRequest` (R2 record: recipe key + sha of bytes), `providerMessages`, `putJson`, `CallAnswer`, the `/unusable` route, the `/llm` route (stage checks → request key → cache lookup → images needed → `prepareCall` → SSE stream around `runCall`), `placeOf`/`PLACEHOLDER_ITEM`/`placeProblem`, `StreamEvent`, `throttled`/`throttledProgress`, `prepareCall`, `runCall` (insert row `running`, `started`, provider or replay, status/cost/VAT/UPDATE, or the error record).
- **Worker `llm/index.ts`** (adapter factory), **`llm/types.ts`** (the provider port: `LlmRequest`, `LlmContent`, `LlmResponse`, `LlmProgress`, `LlmError`, `withJson`), **`llm/fake.ts`** (offline answers, failure models, `fake-slow` progress), **`llm/replay.ts`** (answers by place from the project's recorded calls).
- **Contracts:** (a) the wire request (web `LlmRequest` ↔ Worker `CallRequest`), validated only on the Worker; (b) the request key (`keyedRequest` drops bytes and marks, so the two rounds of `ask` share a key; group 01); (c) the answer (`LlmAnswer` ↔ `CallAnswer`), JSON or as the SSE stream's last event; (d) the stream events (`CallEvent` shared; `answer`/`error` restated); (e) the place (`CallPlace` both sides, stored in `llm_calls.item/round`, read by replay.ts and the export); (f) `/unusable` ↔ the cache (a marked call is never served again).

## Findings

1. **The wire types of an LLM call are written on both sides, with clashing names** — web api.ts 488–515 (`LlmContent`, `LlmRequest`, `CallPlace`, `LlmAnswer`) vs llmRoutes.ts 467–473 (`RequestImage`, `CallRequest`), 559–569 (`CallAnswer`), 988 (`CallPlace`), 1020 (`StreamEvent`); the web's stream union is a third copy inline at api.ts 560. They have drifted already: web `LlmAnswer` lacks `vatPercent`. The names cross: web `LlmRequest`/`LlmContent` are the *wire* shapes, Worker llm/types.ts `LlmRequest`/`LlmContent` are the *provider* shapes (no recipe keys, a `model`); web llm.ts 96 `RequestImage` (recipe + `make`) and Worker llmRoutes 467 `RequestImage` (wire) are different things too. The media-type list is written three times (api.ts 490, llmRoutes 467 + 486, types.ts 10). Shared home: `packages/core/src/callEvents.ts` grown into `llmCall.ts`: `CallRequest`, `CallContent`, `CallPlace`, `CallStatus`, `CallAnswer`, `StreamEvent` (beside `CallEvent`), `IMAGE_MEDIA_TYPES`, `MAX_CACHE_MARKS`; the web keeps only `PlannedRequest`. Same level-3 decision as group 05 (API types) and 07 (error body). certain.

2. **`CallProgress` is computed, stored and never shown** — callProgress.ts 8–17, 36–59 build it, stageRunner 27 / ProjectView 419 / pipeline.ts 87, 114, 123 carry it to `Stage.call`, and no component reads `stage.call` (grep: only `stage.item` is rendered, StageCard 135). docs/project-view.md 61 decided the item line instead of a call-level view (time out of timeout, a clock: decided against). So `callId`, `label`, `startedAt`, `timeoutMs`, `outputTokens`, `endedAt` and `ended()` are dead in the web, and of `CallEvent` only `textChars + thinkingChars` matter to the browser (`started.callId/startedAt/timeoutMs`, `progress.elapsedMs/outputTokens` are sent and dropped). Either remove `CallProgress`/`StageRun.call`/`LocalRun.call`/`Stage.call` and keep `trackCall` for items only, or keep the fields as the documented contract (docs/llm.md 61 leaves "what to show" to a view) but drop the plumbing. Level 1's "`tracked.ended()` not called on throw" (llm.ts 140–155) is moot for the same reason. certain.

3. **A cached row whose R2 answer is missing makes every identical request pay again, forever** — llmRoutes 893–921: the lookup takes the *earliest* `ok` row (`ORDER BY started_at LIMIT 1`); when its `content/<sha>` is gone it falls through to "images needed" and a new paid call, which is recorded as a new `ok` row; the next identical request finds the same broken earliest row again and pays again. Fix: skip it (`… AND id NOT IN (…)` loop / try the next row) or clear its `response_sha256` (or mark it) when the object is missing. Rare (objects disappear only by hand on the desktop, or an orphan collection bug), but costs money silently. certain (logic), low likelihood. Settles level 1's check (899–921).

4. **The replay model can't replay a place whose answer was served from the cache** — replay.ts 54–69 finds recordings only by `llm_calls.stage_id = <recorded stage>`. A call served from the record inserts no row for the serving stage; the output names the served call (`outputs.call_id`), which belongs to another stage (a replaced stage after a re-run, or another project). So (a) such a place fails with "no recorded answer", and (b) a recorded stage all of whose calls were served from the cache has no calls of its own and is left out of `recordedStages` (56), shifting the turn mapping for later stages of the same step (a second `review` would be fed the first's recordings). The fake fixture has no cached calls, so the replay test doesn't see it; real projects' fixtures (the planned ones, after any re-run) will. Fix: look up through the recorded stage's outputs (`call_id`) as well as its own rows; for `layout`'s earlier rounds, which outputs don't name, its own rows. certain (reading), not yet hit.

5. **Exporting such a project imports the served calls with `stage_id` NULL, so they count as Test requests** — projectFile.ts 156 exports calls named by outputs even when their stage isn't exported; on import (311, 343–346) their `stage_id` maps through `stageMap.get(...)` to `undefined`, which `insert` (441) binds as NULL. On a fresh instance (the replay's, or another user's) they become stage-less rows: costs.ts 67 counts `stage_id IS NULL` calls as "Test requests", and replay can't find them (finding 4). For group 15 (export/import); found here through the replay. Fix: map them to the importing stage that names them, or to a stub, or don't copy them as rows (the outputs only need the answer content). certain (reading).

6. **`/unusable` can mark another project's call** — llmRoutes 836–846: the `EXISTS` checks only that the stage is in the project, not that the call belongs to it; by design for a cached answer (the served call is another stage's, maybe another project's, finding 4). Consequence: that other project's history changes (`ok` → `unparseable`: its statistics, and its own replay, which takes only `ok` calls), and the marking stage has no row saying it rejected the answer. Acceptable for two users, but worth one comment at the route (the route can't check more: a served call has no link to the stage it was served to until an output names it). check.

7. **A failure after the provider answered loses the known usage** — llmRoutes 1161–1221: R2 put of the response, `readSettings` and the UPDATE are inside the provider's `try`; if one throws, the catch records `status='error'`, `error_kind='unknown'`, no tokens, cost NULL (so "may have been billed, unknown"), although the tokens and cost were in hand. If the D1 UPDATE itself failed, the catch's UPDATE likely fails too, `runCall` throws, the stream sends `error`, and the row stays `running` until `ZOMBIE_MS` (group 13). Fix: end the provider `try` at `send`'s return; record in a second step whose failure is retried or logged. certain (reading), low likelihood. Settles level 1's check.

8. **"Stopped" message with another error kind** — llmRoutes 1225–1234: when the browser's signal aborted but the adapter threw, say, a network `LlmError`, the message is `ABORTED_CALL` and `error_kind` stays `network`; the Usage tab (group 14) groups by kind, the card shows "Stopped". `kind` should be `aborted` whenever `signal?.aborted` (as `timeout` already wins when `timedOut`). certain, small. Settles level 1's check (left to this group by 07).

9. **llmRoutes.ts: the call machinery is a module of its own** — 453–571 and 988–1250 (wire types, validation, key and record shapes, `putJson`, places, stream events, throttle, `prepareCall`/`runCall`/`sendCall`, ~450 lines) are used by two routes (`/llm`, Test) and nothing about configs; `throttled`/`throttledProgress` are generic and exported only for tests. Split: `apps/worker/src/llmCalls.ts` (request → key/record/provider shapes, `prepareCall`, `runCall`, cache lookup, which the `/llm` route inlines today at 893–921 and builds a second `CallAnswer` literal for), `apps/worker/src/throttle.ts`; `placeOf`/`PLACEHOLDER_ITEM`/`placeProblem` with scripts/callPlaces.ts (group 15). Confirms level 1's "four jobs" check for this part. certain (structure).

10. **The replay provider is chosen after a fake adapter was already built for it** — llmRoutes 1112 (`createAdapter`) then 1157 (`isReplay ? replayProvider(...) : adapter`): `prepareCall` builds a `FakeProvider` that is thrown away, and the choice of provider lives in two places (llm/index.ts's factory and `runCall`). `REPLAY_MODEL` is spelled as a literal in scripts/replay.ts 194 and llmRoutes.test.ts 446 (level 1 check, confirmed; scripts can't import Worker modules cheaply, the test can). Small. certain.

11. **The "unsupported/deleted config" texts written three times** — Worker `deletedConfigMessage`/`unsupportedConfigMessage` (llmRoutes 435–441, used by the start route, pipeline.ts 493–495), restated by the web (llm.ts 19–20, "Said as the Worker says it"), and the `/llm` route's own inline unsupported text (llmRoutes 879) in a third form. The web copy exists because the start refusal's text doesn't reach the screen (group 07 #1); with that fixed, the web check in `stageModelConfig` can go (the Worker refuses the start anyway). certain.

12. **The Worker's SSE framing is written by hand on three sides, and the test doesn't use the reader** — llmRoutes 943 writes `data: …\n\n`; api.test.ts 135/148 frames it by hand; llmRoutes.test.ts 62 `sseEvents` parses it by hand instead of with core's `readSse`, so no unit test pins the Worker's writer to the browser's reader (only `npm run replay`, end to end). A `sseData(value)` encoder beside `readSse` in core, used by the route and the tests, and `readSse` in llmRoutes.test.ts. certain, small.

13. **Cache key without the place: identical requests at two places get the first place's answer** — by design for real models (§5.2). For the replay model it means a replay place whose request equals an earlier place's (same provider/model `fake-replay`) is served the earlier place's recording, not its own. Unlikely with today's requests (each carries its page/system); check.

14. **`ask` and the size limits untested** — llm.ts has no test: the two-round protocol (images made only after `imagesNeeded`, fingerprints kept only on `ok`, "sent without its images"), `requestSizeProblem`, `imageLimitFor`; api.test.ts's fake `fetch` makes it cheap. The request-key half is pinned on the Worker (llmRoutes.test 751–769, group 01). certain (gap).

## Level 1 checks settled
- callEvents.ts: full stream type not in core → confirmed (1).
- sse.ts 9–15 multi-line `data:` and `event:`/`id:` ignored → dropped: every writer (the Worker, Google, OpenRouter) sends one-line JSON; Anthropic goes through its SDK.
- sse.ts 16–24 reader not cancelled when `onData` throws → confirmed as low for the browser (the Worker never writes bad JSON); for the adapters, where a throwing `onData` would leave the provider's stream running, → group 09.
- llm.ts 87–92 hand-written base64 of a Blob → confirmed, the only encoder in the web (with the Worker's decoder, group 01 #15 → group 09). `Uint8Array.prototype.toBase64` where available.
- llm.ts 34 `imageLimit(_config)` → confirmed; belongs with `requestLimits` (group 03 settled `CLAUDE_IMAGE_LIMIT`'s place).
- llm.ts 140–155 `tracked.ended()` not called on throw → dropped: nothing reads `endedAt` (2).
- llm.ts 71–73 base64 length compared as bytes → dropped as a bug: base64 is longer than the bytes, so the check errs on the safe side; the limits themselves are marked "to check" in the comment. The message's "MB" could say "MB as sent".
- llm.ts 149 "sent without its images" wording → minor; only reachable if the Worker misbehaves.
- callProgress.ts 65–70 `charsText` vs `Intl` compact → dropped: the docs fix the format ("1.23k", two decimals), which `Intl`'s compact notation doesn't give.
- itemTiming.ts 11 racy → group 06 #15 (confirmed there).
- llmRoutes 931 `prepareCall` outside a try → group 07 #10.
- llmRoutes 1161–1221 → confirmed (7). 1230–1234 → confirmed (8). 899–921 → confirmed, worse than "falls through once" (3).
- llmRoutes 1107–1112 cap check not atomic → dropped: calls are sequential by design and the cap is against bugs.
- llmRoutes 496 `maxOutputTokens` ≤ 0 accepted → minor: the provider answers 400, recorded as not billed; the browser never sends it.
- llmRoutes 943 SSE framing by hand → confirmed (12). 1030–1060 `throttled` duplicates a web throttle → dropped: no throttle/debounce in web, desktop or packages (grep); the `undefined` sentinel is harmless for `LlmProgress`.
- llmRoutes 1001–1008 `placeProblem`/`PLACEHOLDER_ITEM` placement → confirmed (9), with group 15.
- llmRoutes: `StreamEvent`, `CallAnswer`, `PROGRESS_INTERVAL_MS`, `throttled*` exported without outside users → confirmed (1, 9).
- llm/index.ts 57–63 missing secret typed away → dropped here: `secretValues` (llmRoutes 453) refuses a config with a missing secret before `createAdapter`; only a config whose secret fields don't match the adapter's set could reach it, and `configProblem` checks the set. Group 09/12 for the two naming schemes.
- fake.ts 8 "Three steps" but four → confirmed (trivial). 71–75 abort listener never removed → confirmed (`{ once: true }` and removal on resolve). 43–45 `fake-other-model` returns parsed json → dropped: the route answers `error`, and the browser never reads `json` of a non-ok answer. Stage recognition by property names → kept as structure only: a renamed property makes the fake fall back to `simplest`, which then fails the stage's checks loudly (no silent pass). `FAKE_SLOW_MS` export → only used in the file, harmless.

## For level 3
- **The browser↔Worker API has a third contract to move into core** (after group 05's pipeline types and 07's error body): the LLM call's request, answer, place and stream events (1). With them, a written SSE encoder beside `readSse` (12).
- **Replay and export/import must agree on where a call's answer lives:** today a stage's answers are partly its own rows and partly other stages' rows named by `outputs.call_id`; export copies both, import orphans the second kind (5), replay sees only the first (4). A component-level rule ("a stage's answers are the calls its outputs name, plus its own rows") would fix both; group 15 owns the import side.
- **Progress plumbing built ahead of a view that was then decided against** (2): the component review of the project screens should check what of `Stage` (web) is read by any view.
- **Recording a call is one long `try`** (7, 8): the call recorder is where costs (group 13) and usage reasons (group 14) come from; its error paths deserve their own small tests (provider ok + R2 failure; abort + network error).

## Patterns
- **A wire type restated on the receiving side, then drifting** (1: five types, one already missing a field; names crossing between wire and provider shapes). Cause: `CallEvent` was moved to core when the stream was added, but the older request/answer types had been written first in the Worker and mirrored in api.ts, and nobody moved them with it.
- **State plumbed for a view that was never built** (2). Cause: the data path built first ("what to show is the view's choice"), then the view decided differently, and the plumbing stayed.
- **A failure path that assumes the happy path's rows are consistent** (3: a broken cached row always chosen first; 7: bookkeeping failures recorded as provider failures; 8: kind and message disagree). Cause: each error branch written for the case at hand, without asking what the next request will find.
- **A feature reading one of two places the same data is kept** (4, 5: calls by `stage_id` vs by `outputs.call_id`). Cause: the cache serving without a row was designed before replay and export, which then each picked one of the two lookups.
- **A message restated on the other side because the original doesn't reach the screen** (11). Cause: group 07's finding 1.
- **Hand-written test doubles of the shared parser** (12). Cause: tests written with the side under test, not against the other side's code.
