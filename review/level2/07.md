# Level 2, group 07: Errors and request plumbing

## Map
- **Worker, what it sends on failure:** every route answers a refusal as `c.json({ error, code? }, status)` (~110 sites: index.ts, pipeline.ts, llmRoutes.ts, projectFile.ts, versions.ts). `error` is text, `code` a string literal where some caller needs to tell the case apart: `stale_version` (versions.ts 60), `deleted_model_config`, `unsupported_model_config`, `no_model_config`, `same_values`, `default_model_config`, `spending_cap`, `missing_secret`, `unsupported` (llmRoutes), `running`, `missing` (projectFile). No shared list of codes; no `app.onError`, so an exception becomes Hono's text/plain "Internal Server Error" 500 (no `{error}`). Inside a streamed call (llmRoutes 945–956) an exception becomes an SSE `{event:"error", error}`.
- **Worker, `requestLog.ts`:** middleware, one line per `/api/*` request (path with ids shortened, status, fields added by routes); `deferLog` for the streamed call. Sees the status of a refusal, not its `error` or `code` unless the route adds them (only the LLM route does: `refused`, `error`).
- **Web, `api.ts`, four ways a failed response becomes an exception:**
  - `checked` (L65) → `ApiError(status, code)`, message always `"HTTP <status>"`; parses the body only on 409, only for `code`; dispatches `STALE_EVENT` on `stale_version`. Used by ~55 functions.
  - `callLlm` (L545) → `LlmRefused(code, error)` when the body has a code, else `ApiError(status)`; a streamed `error` event → plain `Error(error)` (L566).
  - `refusedOr` (L681) → `WorkerRefusal(status, body)`, message = the Worker's `error`; for model configs only (create, rename, test, delete).
  - `importRows` (L744) → plain `Error(error ?? "HTTP n")`.
  - Outside api.ts, two more: `pdf.ts` 38 `Error("HTTP n")`, `pageImages.ts` 66 `Error("Loading the PDF failed (HTTP n).")` (and eval's PdfPane/useMarks, same idiom).
- **Web, showing errors:** each screen turns the exception into text itself: `${err}` (21 sites: App ×5, ProjectView ×13, Delete/ExportDialog, SettingsPage 315) → "Error: HTTP 409"; `err instanceof Error ? err.message : err` (32 web sites, 10 more in worker/desktop/eval) → "HTTP 409"; status-based rewrites in App rename, DeleteProjectDialog, ExportDialog; `stageRunner` 69 stores the message as the stage's error in D1, shown on the card. `toasts.ts` derives pipeline toasts from snapshots (no error text; "X failed. Pipeline stopped"). `errorText.test.ts` checks the `error-text` class by class name.
- **Contracts:** `{error, code?}` body (Worker writes, four web readers parse it differently); the code literals (both sides, unshared); `X-Project-Version` + `stale_version` (versions.ts ↔ `projectFetch`/`checked`); the SSE `error` event (llmRoutes ↔ `streamedAnswer`).

## Findings

1. **`checked` throws away the Worker's message: the user sees "HTTP 409" / "Error: HTTP 409"** — api.ts 51/65–69. The Worker writes a reason for every refusal, but `ApiError`'s message is only the status, and that is what ~50 screens show and what `runPlan` stores as a failed stage's error (stageRunner 69 → D1 → StageCard 142, kept for good). Concrete cases: start refused because another tab started it ("the stage can't start: it is running", pipeline.ts 485) → panel "HTTP 409"; a stage stopped from another device, then `recordOutputs` → failed stage "HTTP 409"; Settings → "Saving failed: HTTP 400" where the Worker said "expected an amount in US dollars above 0" or `"X" … it can't be the default` (llmRoutes 693–699); every ProjectView action → "Dropping the stage failed: Error: HTTP 409". Against style.md 192 ("Not 'Error', … not a code"). `WorkerRefusal` (L673) already does it right: message = `body.error ?? "HTTP n"`. certain.
2. **Export of a project with unfilled call places shows "Exporting failed: Error: HTTP 500"** — projectFile.ts 450 answers the known condition `placeProblem` (whose text names the fix: run `fill-call-places.ts`, llmRoutes 1004–1007) with status **500**, and `fetchExport` goes through `checked` (api.ts 715), so the instructive text is lost twice (finding 1, and a 500 reads as a crash). Should be a 409 with a code, and its message shown. certain.
3. **Four error classes for one thing; merge into one** — `ApiError`, `LlmRefused`, `WorkerRefusal`, the plain `Error` of `importRows` all mean "the Worker answered not ok, with `{error, code?}`". `LlmRefused` is never caught by type nor its `code` read (grep: only api.ts); `WorkerRefusal` adds `config` for `same_values`. One `ApiError(status, body)` with `message = body.error ?? fallback`, `code`, `body` (for extras like `config`), and the stale dispatch, built by one `checked` that parses the body on every non-ok status; `refusedOr`, `LlmRefused`, `importRows`' branch go away. Lives in apps/web/src/api.ts (only the web reads Worker errors; scripts/appServers.ts and replay.ts have their own throwaway `${status} ${text}`, fine). certain.
4. **Stale refusals show twice** — `checked` dispatches `STALE_EVENT` (App's "Changed elsewhere" dialog, App.tsx 266–275) *and* throws, and the caller shows its own banner: ProjectView 280–532 ("Dropping the stage failed: Error: HTTP 409"), LayoutEditor/pageEditor saves, Finish, SettingsPage isn't project-scoped. Only App's rename handler special-cases `err.stale` (App.tsx 237). Either the dispatching path throws a marked error every catch ignores (`if (isStale(err)) return`), or the one error-text helper (finding 6) returns null for it. certain.
5. **The stale text written three times, the Worker's never shown** — versions.ts 18 `STALE_MESSAGE`, App.tsx 270 dialog text, App.tsx 238 "The project was changed elsewhere: reload first.". Similarly the project "name taken" text is the web's (App.tsx 240) while the model-config one is the Worker's (`NAME_TAKEN`, llmRoutes 1264, shown through `WorkerRefusal`): two renames, texts from opposite sides. Decide one rule: the Worker's `error` is the user-facing text (then it must follow style.md), the web overrides only by `code`. certain (inconsistency), check (which rule).
6. **Error → text written ~50 times, two ways that differ** — `${err}` (21 web sites) prints "Error: …"; `err instanceof Error ? err.message : err/String(err)` (32 web + 10 elsewhere); `String(e)` in pdf.ts 48 / PdfView 31 (also "Error: …"). One `errorText(err: unknown): string` in a small web module (and the same three lines in the worker's call recorder and the worker-thread shells of group 04 #3, which can't import web code; core could hold it, it is platform-free). With finding 3, `errorText` is where "HTTP n" becomes a sentence ("The server refused (HTTP 500).") and stale returns null. certain.
7. **Worker error texts have two audiences and two styles** — most are terse API diagnostics in lower case ("no such stage in this project's pipeline", "expected 'outputs' with an item…", "the stage waits for its turn"), others full sentences for the user with the way out (`deletedConfigMessage`, spending cap, `unsupported_model_config` 879, `STALE_MESSAGE`). Today only the sentence-style ones reach the user (via `LlmRefused`/`WorkerRefusal`), by accident of which web class reads them; fixing finding 1 makes all of them visible. So: the refusals a person can cause (start/stop/fix/drop/edit conflicts, settings, rename, import) need user sentences; the ones only a bug can cause (malformed bodies, 400s) can stay terse. check (an audit of ~110 sites for the plan).
8. **Codes are untyped literals on both sides, not pinned by a test** — the web reads `"stale_version"` (api.ts 58, 68) and `"same_values"` (NewModelConfig 109); the Worker writes 11 codes. A typed `ErrorCode` union (and the `{error, code}` body type) in `@score3ly/core` beside `CallEvent`, used by the Worker's routes (a `refuse(c, status, error, code?)` helper) and by `ApiError.code`. Belongs with group 05's level-3 note on sharing API types. certain (contract restated), small.
9. **Status codes used as meanings by the web** — DeleteProjectDialog 45 and ExportDialog 32 map *any* 409 to "a stage is running"; App 239 maps any non-stale 409 to "name taken". True today (each route has one 409 besides stale; export sends `code: "running"`, delete sends none, index.ts 81), but a second 409 added to those routes would be mislabelled. With finding 1 the screens can show the Worker's text, or match on `code` (delete's 409 needs one). check (fragile, not wrong yet).
10. **No `app.onError`: a thrown error breaks the `{error}` contract** — index.ts has no `onError`; Hono answers text/plain "Internal Server Error". Every web reader then falls back to "HTTP 500". Cases: a D1 failure in any route; `prepareCall` (llmRoutes 931) runs outside a try (level 1 check, see below) → stage fails with "HTTP 500" and no call recorded. An `onError` that logs (with `logFields`) and answers `{ error: "The server failed: <message>", code: "internal" }` 500 keeps one shape everywhere. certain (contract), small.
11. **The request log doesn't say why a request was refused** — requestLog.ts logs status and route-added fields; ~110 refusals add none (only the LLM route logs `refused: code`). A shared `refuse` helper (finding 8) that also calls `logFields(c.req.raw, { error, code })` gives every 4xx line its reason for free. check (useful for "the Worker's logs", docs/database.md).
12. **`errorText.test.ts` misses error displays without an error-named class** — PdfView.tsx 41 shows the load/draw error in `<p className="pdf-status">` (no `error-text`, and `String(e)` → "Error: HTTP 404"); the test can't see it. Confirms level 1's check. Either rename the class (`pdf-error`) or the test also flags elements whose child expression is named `*error*`/`*Error`. certain (one miss found).
13. **`callLlm` not-ok without a code → bare `ApiError`, not wrapped with the item** — llm.ts `ask` adds `what` ("System 12: …") to non-ok answers (L156) and size problems, but a refusal or HTTP error from `callLlm` (400 `requestProblem`, 409 "the stage isn't running", 500) reaches the stage error unlabelled ("HTTP 400"). With finding 3, `ask` can prefix `what` uniformly. check (small; group 08 owns `ask`).

## For level 3
- **The web↔Worker error contract** is the second API contract after group 05's types to move into `@score3ly/core`: `ApiErrorBody = { error: string; code?: ErrorCode; … }`, `ErrorCode`. The Worker's routes would use one `refuse()` (also giving the log its reason), the web one `ApiError` + `errorText`.
- **Who writes user-facing text** is a component-wide decision (finding 5, 7): today a mix of Worker texts (LLM refusals, configs, stale, import) and web texts (rename, delete, export, stale dialog). The docs' style guide applies to both; the plan should name one owner per kind.
- **The stage error stored in D1 comes from `err.message`** of whatever threw in the browser, so the quality of every failed card, the run report and the Usage tab's reasons depends on the exceptions in api.ts, llm.ts and the runners (groups 06, 08, 14).
- Fixing finding 1 makes ~110 Worker texts visible: worth doing together with the audit of finding 7, not before.

## Patterns
- **An error class written per call site, each parsing the body itself** (4 classes + 3 `Error("HTTP n")` throws). Cause: each new kind of request (LLM calls, config forms, import) needed the Worker's message, found `ApiError` didn't carry it, and got its own class instead of `ApiError` being fixed.
- **Error → text idiom repeated, in two variants** (~60 sites, 21 of them printing "Error: …"). Cause: written inline in each catch, from memory, with no helper to find.
- **The same message written on both sides** (stale ×3, name taken in two places with different owners). Cause: the web couldn't show the Worker's text (finding 1), so screens wrote their own; the Worker kept writing texts nobody sees.
- **A status code used as a meaning** (3 screens map 409 to one case). Cause: no codes on those refusals, and no `code` parsed except on 409.
- **A known condition answered as 500** (export's `placeProblem`). Cause: a new refusal added without a convention for which status a "can't do that yet" gets.
- **A lint-like test that checks names, not behaviour** (errorText: one miss). Cause: a regex over source is the cheap check; the convention (class names ending in `error`) isn't enforced where the element is written.
