# Level 2, group 02: Boxes and geometry

## Map
- **The `Box` type** (`{left, right, top, bottom}`, fractions 0–1), spelled six times: imaging crop.ts 8 (`Box`), notation lens.ts 18 (`Box`), prompts layout.ts 68 (`LayoutBox`), prompts review.ts 134 (`ReviewBox.box`, inline), web fixLayout.ts 10 (`Box = LayoutSystem["box"]`), and the schema `FOUR_EDGES` (prompts extract.ts 216). The web imports it from three of them: notation (extract, review, transcription, humanReview, pageEditor, ExtractionView, HumanReviewCards), imaging (rendering, pageImages), fixLayout (handles). Structurally equal, so TS never complains.
- **"A system's layout" `{box, barLines}`** three times: imaging draw.ts 29 `LayoutSystem`, prompts layout.ts 69 `LayoutSystem` (same name, same shape), humanReview.ts 146 inline.
- **Validation** (0–1, left < right, top < bottom), four copies: imaging `boxProblem` (crop.ts 13; used by `crop` and the script-only regions.ts), lens.ts 243–246 (extract's issue boxes), prompts layout.ts 86–91 (`checkLayoutAnswer`), web review.ts 198 (a review's new issue boxes; no `typeof` check).
- **Crop ↔ page mapping:** crop→page `onPage` (extract.ts 53; used by extract's and review's answers) and `toPage` inline (HumanReviewCards.tsx 347); page→crop clipped in `boxesOnCrop` (transcription.ts 48) and unclipped `toCrop` (HumanReviewCards.tsx 346).
- **Overlap:** `area`+`overlap` (intersection area) verbatim in review.ts 18–19 and transcription.ts 27–31; boolean `overlaps` ExtractionView.tsx 506; horizontal-only inline in review.ts 32 (`placesOf`); vertical-only inline in HumanReviewCards.tsx 189 (`where`); point-in-box in fixLayout.ts 92 (`systemAt`).
- **Stretch edges** `[box.left, ...barLines, box.right]`: extract.ts 26 (`edges`, `stretchBox`, `stretchCropBoxes`) and notation mei.ts 216 (`partBox`, the facsimile zones).
- **Crops with margins:** extract.ts `MARGINS`, `systemCropBox`, `stretchCropBoxes` (rounded to 6 digits for recipe keys); used by runExtract, runReview, runApplyReview, transcription (`shownSystem`), review (`placesOf`).
- **Which system a box is on**, five rules (see finding 3): review.ts `placesOf`/`systemsOf` (2D overlap with the tight box *or* the crop, per system), transcription.ts `homeOf` (largest overlap with tight box, crop weighted by 1/1000, first box only), HumanReviewCards `where` (vertical overlap with the tight box), review.ts `newIssue` (the image's source system), runApplyReview/applyReview (`systemsOf(...)[0]`).
- **Editing boxes:** fixLayout.ts `boxThrough`, `MIN_BOX`, `BoxHandle`, `BOX_HANDLES`, `handlePoint`, `resizeBox`; handles.ts (`handleRect`, `handleAt`); used by LayoutEditor/pageEditor and by HumanReviewCards' `DrawLayer` (there in crop fractions for `boxThrough`, page fractions for `resizeBox`).
- **Clamp and round:** fixSkew.ts 15/30 (`round(v, digits)`, inner `clamp`), fixLayout.ts 16–17 (`clamp(v, lo, hi)`, 5 digits), extract.ts 16–17 (`clamp(v)`, 6 digits), inline min/max in HumanReviewCards 350, viewBounds 21.
- **Drawing:** imaging draw.ts (`drawLayout`: boxes by `Math.round`, crop by floor/ceil, both fine); marked crops (issue boxes drawn with their ids) built the same way in runReview.ts 140–149 and runApplyReview.ts 248–256.

Contracts: (1) a box from a model is validated, then mapped from its image to the page (`onPage`), stored on the page, mapped back onto every crop it falls on (`boxesOnCrop`) for drawing and for the next model; the two maps must be inverses. (2) Stretch k of a system is `[edges[k-1], edges[k]]`, in extract.ts and in mei.ts. (3) "The systems a box covers" decides the two-systems rule, where apply_review begins, where a note is shown, and which issues a review may choose on: all should agree.

## Findings
1. **`Box` defined six times, `{box, barLines}` three times** — crop.ts 8, lens.ts 18, layout.ts 68 `LayoutBox`, review.ts 134 inline, fixLayout.ts 10, plus draw.ts 29 `LayoutSystem` = prompts layout.ts 69 `LayoutSystem` (same name *and* same shape, not another shape as level 1 thought), humanReview.ts 146 inline. Shared: `Box` (and `boxProblem`) in `@score3ly/core` (no deps; imaging→core is already proposed by group 01; notation and prompts would import it, prompts already depends on notation, so `LayoutBox`/`ReviewBox` become `Box`, `ReviewBox` = `LensIssue["boxes"][number]`); `LayoutSystem` in imaging re-exported or imported by prompts. The web then imports `Box` from one place. certain.
2. **Box validation four times** — crop.ts 13, lens.ts 243–246, layout.ts 86–91, review.ts 198. One rule, four messages. `boxProblem` in core would serve all (each keeps its own wording around it). review.ts 198 has no `typeof … === "number"` test: a string `"0.5"` passes `>= 0`/`<= 1` by coercion and `left >= right` compares as strings; constrained output makes it unlikely. certain (duplication); check (the gap).
3. **`placesOf` counts a system when the box overlaps its crop with margins, per system, so a box inside system N near its edge also "covers" system N±1** — review.ts 28: the comment says "its tight box, else its crop", the code does "tight box OR crop" for every system. Crop margins are 15% of the system's height (extract.ts 14), often more than the gap between systems, so a box at the top of system 5 overlaps system 4's crop. Effects: humanReview.ts `boxProblems` refuses a clarification with boxes on 5 (near its top) and 6 as "systems 4, 5, 6"; applyReview.ts 38–41 starts the call at 4 with window [4, 5], so a review issue on 5 and 6 (accepted by review, which counts by image, review.ts 200) gets a window without 6; runApplyReview.ts 217 files it under 4 while transcription.ts `homeOf` shows it under 5. Fix: the crop only as a fallback when no tight box is overlapped (what the comment says), and one `systemsOf` used by every rule. Tests use systems 0.2 apart (review.test.ts 7–11), so the case is untested. certain (the code doesn't do what its comment says); check (how often real layouts hit it).
4. **Five rules for "which system is this box on"** — besides finding 3: transcription.ts 41 (largest overlap, crop/1e3, first box only), HumanReviewCards.tsx 189 `where` (vertical overlap with the tight box only: a box in a system's margin is "on system 3" for `boxProblems` but the card says just "page 3"), review.ts 200 (the image's system), applyReview/runApplyReview (`systemsOf()[0]`, the lowest). The note's home in the view and the system apply_review begins on can differ. One module (`apps/web/src/boxes.ts` or core) with `systemsOf` and `homeOf` used by all. certain.
5. **Crop↔page mapping four times, two transforms** — `onPage` extract.ts 53 and `toPage` HumanReviewCards.tsx 347 (identical); `boxesOnCrop`'s inline map transcription.ts 58–63 (clipped) and `toCrop` HumanReviewCards.tsx 346 (unclipped). Shared `onPage(crop, box)` / `onCrop(crop, box, {clip})` beside `Box`; no test pins them as inverses. certain.
6. **Box intersection five ways** — `area`/`overlap` review.ts 18–19 = transcription.ts 27–31 (verbatim), `overlaps` ExtractionView.tsx 506, horizontal overlap inline review.ts 32, vertical HumanReviewCards.tsx 189. Notation and imaging have none. Shared `area`, `intersection`, `overlaps` in the same box module. certain.
7. **Stretch edges twice, and a bar line accepted outside its box makes an inverted stretch** — extract.ts 26 `edges` and mei.ts 216 `partBox` both build `[left, ...barLines, right]`. `checkLayoutAnswer` (layout.ts 72–97) accepts bar lines up to 0.02 outside the box (`BAR_LINE_TOLERANCE`) and stores them as they are (runLayout.ts 97 doesn't clamp either); then stretch 1 (or the last) has left > right: `stretchBox` returns an inverted box (code issues and warnings point at it; `overlap` gives 0, so it's drawn nowhere and has no home), and `partBox` writes an MEI `zone` with `lrx < ulx`. fixLayout's `withinBox` drops such lines only after a resize. Fix: clamp accepted bar lines into the box in `checkLayoutAnswer` (what a tolerance means), test it (layout.test.ts 17 tests only refusal); a shared `stretchEdges(system)` used by extract.ts and mei.ts. certain (code path); check (whether models give such lines).
8. **Generic box editing lives in a stage module** — fixLayout.ts 13–64 (`MIN_BOX` "isn't a system", `boxThrough`, `BoxHandle`, `BOX_HANDLES`, `handlePoint`, `resizeBox`) is used by handles.ts and HumanReviewCards' `DrawLayer`, where `boxThrough` runs in crop fractions (MIN_BOX then means 1% of the crop, and rounding to 5 digits happens before `toPage`, so stored clarification boxes are unrounded) and `resizeBox` in page fractions (clamped to the page, not the crop). Move them with handles.ts into one `boxEdit.ts`; the comment of `MIN_BOX` and the coordinate space of each call should say what they are. certain (placement); check (the mixed spaces are harmless today).
9. **Marked crops built twice** — runReview.ts 136–149 and runApplyReview.ts 245–256: notes from issues, `boxesOnCrop`, `MarkedCropRecipe` with ids as labels, identical. One `markedCropRecipe(issues, system, box, limit)` in review.ts or pageImages.ts. Also these recipe boxes aren't rounded, while extract.ts 17 rounds crop boxes "for the crop's recipe"; deterministic either way, so only an inconsistency. certain (duplication).
10. **`clamp` and `round` to N digits written five times** — fixSkew.ts 15/30, fixLayout.ts 16–17, extract.ts 16–17, inline in HumanReviewCards.tsx 350 and viewBounds.ts 21. The digit counts differ on purpose (5 for stored layout and lines, 6 for crop recipes); one `clamp(v, lo = 0, hi = 1)` and `roundTo(v, digits)` in the box module. certain.
11. **transcription.ts 41 `overlap(tight) || overlap(crop) / 1e3`** — two scales mixed so a tight-box hit always wins; works, but a tuple compare (or a comment) would say it. certain (minor).
12. **fixSkew.ts 28–36: the angle comes from the unclamped points, the ends are clamped after** — only for an end dragged off the page; the stored angle then disagrees with the stored endpoints. certain (minor; level 1's check confirmed).
13. **handles.ts 14/40 `HANDLE_REACH`** compared as `HANDLE_REACH - CORNER / 2` from the drawn shape: name and comment don't say it (level 1, confirmed). certain (minor).

Its natural home is `@score3ly/core` (imaging, notation, prompts and web all need `Box`), which needs imaging and notation to depend on core (group 01 proposes the same for `sha256Hex`).

## Patterns
- **A type restated per package** (2: `Box` ×6, `{box, barLines}` ×3). Cause: each package written on its own, with no neutral package for shared shapes (imaging has no dependency on core; prompts restates notation's types instead of importing them).
- **A small geometric helper written again in place** (5: validation ×4, crop↔page ×4, intersection ×5, clamp/round ×5, stretch edges ×2). Cause: a few lines are quicker to write than to find; the first copies were private (`const area` in review.ts) or in a stage module (`onPage` in extract.ts), where the next author didn't look.
- **One question answered by several rules** (1: which system a box is on, five rules). Cause: each consumer (view, check, runner) wrote the rule it needed when it was built, and the shared one (`placesOf`) has a subtle comment/code mismatch nobody tested with close systems.
- **A comment that doesn't match the code** (2: `placesOf`'s "else its crop", `HANDLE_REACH`). Cause: code changed or simplified after the comment, tests too coarse to notice.
- **A tolerance that accepts without normalizing** (1: bar lines outside their box). Cause: the check was written to refuse bad answers; what happens to the accepted near-misses downstream wasn't followed.
- **Generic code in a stage module** (2: box editing in fixLayout.ts, `onPage`/crop boxes in extract.ts). Cause: written for the first stage that needed it, then imported by later ones from there instead of being moved.
- **The same runner block copied between stages** (1: marked crops in runReview and runApplyReview). Cause: the second runner was written by copying the first.
