# Level 2, group 15: Projects: names, export, import, deletion

## Map

- **Worker `names.ts`**: `MAX_NAME_LENGTH` (200), `defaultName` (file name → base), `firstFreeName` (" (n)", case-insensitive). Used by index.ts (lookup, create), projectFile.ts (import: project and configs), llmRoutes.ts (config names).
- **Worker `index.ts`, project part**: list (with position), `GET /api/pdfs/:sha` (projects + `newProjectName` hint), PDF file, content PUT/GET, `POST /api/projects` (PDF put with `sha256` or `head`, then the free-name/insert/retry loop), PATCH (name 1–200 or 409 via `isNameConflict`), opened, issue numbers, DELETE → deletion.ts.
- **Worker `projectFile.ts`**: `exportProject` (current pipeline's rows, served calls reassigned to the first stage naming them, configs, fingerprints, content list; refuses running / unplaced calls), `exportProblem`, `importProject` (configs by value, done stages by stage key, ok calls by request key: live → used, deleted → revived *in place*, else new row; one big batch with its own free-name/retry loop), routes export, `content/missing`, `PUT /api/pdfs/:sha`, import.
- **Worker `deletion.ts`**: marks project, unshared stages, calls no live output names; deletes outputs nobody uses; `collectOrphans` (whole-bucket scan, 1-hour grace) inside the DELETE request.
- **Migrations 0002** (`imported_at`, written only by import), **0004** (`item`/`round`, placeholders `'?'`/0) ↔ `PLACEHOLDER_ITEM`/`placeProblem` (llmRoutes) ↔ `scripts/callPlaces.ts` (own `PLACEHOLDER_ITEM`) ↔ `fill-call-places.ts` (CLI).
- **Web**: `names.ts` (`MAX_NAME_LENGTH` again, `nameProblem`) → RenameDialog; `projectFile.ts` (zip/unzip with fflate, format check, `exportProject`, `importArchive`) → ExportDialog, App; `api.ts` project functions (`createProject`, `lookUpPdf`, `deleteProject`, `fetchExport`, `storePdf`, `missingContent`, `importRows`, `ProjectRows`); DeleteProjectDialog (+ `deleteCachedPdf`), KnownPdfDialog (PDF and archive), App (`pdfPicked`, `archivePicked`, `importProject`, `newProject`).
- **Contracts**: (a) name rules: length, trimming, numbering, case-insensitivity — Worker enforces, web restates length and (for configs) numbering; (b) PDF/content upload: two PDF routes, one content route, R2 key layout; (c) `.s3l`: web manifest + Worker rows, `EXPORT_FORMAT` ↔ `EXPORT_FORMATS` (pinned by a test that reads the Worker's source), `ProjectExport` ↔ `ProjectRows`; (d) deletion ↔ import ↔ cache: which call rows are alive, and which stage a call belongs to; (e) call places: placeholders written by migration *and* by import, refused by export, filled by the script.

## Findings

1. **The free-name / insert / retry loop written twice** — index.ts 232–268 (create) and projectFile.ts 409–432 (import): same "read every live name, `firstFreeName`, batch, retry up to 5 on `UNIQUE constraint failed: projects.name`"; `isNameConflict` (index 43) inlined as the same string at projectFile 430, `takenNames` (index 112) inlined at 413. The import's base rule (`slice(0,200).trim() || "Untitled"`, 411) restates `defaultName`, and App 131 gets the hint for an archive by passing `${name}.pdf` as a fake file name to `lookUpPdf` so that `defaultName` produces the same base. Must behave the same. Shared: a Worker `projects.ts` (the project routes moved out of index.ts, level 1's "two jobs") exporting `insertProject(db, base, rowsFor(name))` with `isNameConflict`/`takenNames`; the archive lookup could take a `name` query instead of a fake file name. **certain**.

2. **`firstFreeName` and `MAX_NAME_LENGTH` on both sides** — worker names.ts 3/13 and web names.ts 3, configForm.ts 145 (identical body; its comment says it mirrors the Worker's). Both packages depend on `@score3ly/core`: a `core/src/names.ts` (`MAX_NAME_LENGTH`, `firstFreeName`, maybe `defaultName`) used by worker names/llmRoutes/projectFile and web names/configForm/NewModelConfig. Group 12 (15) found the two default *config* names already drift past ~180 characters. **certain** (duplication).

3. **Numbered names can exceed the 200 characters PATCH enforces** — `firstFreeName` appends " (n)" to a base already cut to 200: create (index 229/236), lookup hint (141), import project (projectFile 411–414), import config (274), `configName` (llmRoutes 1261). The stored name then fails the rule every other path enforces (the rename dialog opens on a name it calls too long). Fix in the shared `firstFreeName`: cut the base so that base + suffix fits. **certain**, minor.

4. **A revived call keeps its deleted stage, so an import after a deletion is not whole** — projectFile 329–335 brings a deleted call back to life but leaves `stage_id` on the deleted project's stage (on purpose: "its cost stays where it was paid"). Consequences, by reading: (a) the imported stage owns none of its ok calls; a call no output names (`layout`'s rounds before the last, runLayout 117 names only the final call) is linked to the new project by nothing, so exporting the imported project leaves it out (export takes the stages' own calls + those outputs name, 154–157); a fixture made from such a project fails the replay at `layout` round 1, and a stage with no own calls drops out of replay's `recordedStages` (replay.ts 56, group 08 finding 4); (b) the next deletion of *any* project re-marks it (deletion.ts 46: stage deleted, no live output names it) and `collectOrphans` removes its request/response again. "Delete, then re-import the backup" is exactly the case the revival was built for (index.test 1811), and it tests only a call an output names. The same (a) holds for a call matched to a live call (`callMap` 327) of a copied stage. Fix options for the plan: revive only calls outputs name and insert the others as new rows of the imported stage; or move `stage_id` and accept that the cost moves; or let export/replay find a stage's calls by `item`/`round` through outputs *and* rows of the same request key. **certain** (mechanism), matters once real projects' fixtures are made.

5. **Group 08's finding 5 is wrong: served calls don't import with `stage_id` NULL** — export reassigns them at projectFile 166–172 (`servedTo`: the first pipeline stage whose output names the call), so import maps them through `stageMap` like the stage's own; the `c.stage_id !== null` filter (311) never drops one from a well-formed file. What remains: (a) no test covers the reassignment (index.test 1777 has no served call); (b) `servedTo` takes the *first* output of an unordered result (144, no `ORDER BY`), so when two stages name the same call which one gets it is arbitrary (it decides the replay turn the call belongs to). **dropped** (08/5); (a) test gap certain, (b) check.

6. **The PDF upload written twice** — index.ts 213–219 (`POST /api/projects`, multipart) and projectFile.ts 467–476 (`PUT /api/pdfs/:sha256`), same `put(..., { sha256 })` + 400 text, with the key spelled as a literal in the second (and in deletion.ts 79, projectFile 258/462). One `storePdf(bucket, sha, body)` beside group 01's `r2Keys.ts`; `createProject` could even become `storePdf` + a JSON create (one upload path, no multipart). **certain**.

7. **The export format restated across the seam** — `EXPORT_FORMAT` (worker projectFile 17) vs `EXPORT_FORMATS` (web projectFile 16), kept equal by a web test that reads the Worker's *source text*; the "newer version / isn't one this version reads" messages written twice (web 64–69, worker 217–220, differing in punctuation); the format checked twice from two fields (`manifest.format` on the web, `rows.format` on the Worker, equal only because the web copies one into the other, 96); `ProjectRows` (api.ts 712) loosely restates `ProjectExport` (projectFile 22). Shared: `core/src/projectExport.ts` (`EXPORT_FORMAT`, the `ProjectExport` type, `formatProblem(format)`), imported by both; the source-reading test goes. **certain**.

8. **`importArchive` ignores the hash `putContent` returns** — web projectFile 115: a content object damaged in the file is stored under its *new* hash while the rows name the old one; the Worker's import doesn't check content (projectFile 256–257, by design: it trusts the browser), so the import succeeds and the project later fails to read that output. One comparison (`if (await putContent(...) !== key) throw "damaged"`) closes it. Whether fflate's `unzip` already rejects it by CRC wasn't checked. **certain** (missing check), low likelihood.

9. **`importArchive`'s progress is never shown** — App 146 calls `importArchive(archive)` without `progress`; the import, which can upload many MB, shows only "Importing …" while export has a progress bar. The parameter is dead today. **certain**, minor (UX).

10. **The import is a few very large D1 batches** — projectFile 286 (one `SELECT` per done stage), 316 (one per ok call), 417 (every row of the project, plus pipeline entries) in single `batch` calls. A 50-system project means hundreds of statements in one batch and thousands in the last. Whether D1 counts batch statements against the per-invocation query limit (50 Free / 1000 Paid) or a batch size limit wasn't checked; local SQLite (wrangler dev, desktop, the replay test) enforces neither, so only an import on the deployed instance would show it. Same class as group 05's 100-parameter finding. **check** (verify on the deployed instance with a real project; important if it fails, as export/import is the backup path).

11. **Import writes configs no other path could** — projectFile 266–278 inserts the file's config rows after only `sameConfig`: no `configProblem`, no `secrets_json` parse (group 12 finding 6, confirmed: a non-JSON `secrets_json` breaks `GET /api/model-configs`). A provider unknown here fails the whole import with D1's `CHECK` error text as the user's message. Also, a concurrent config created under the same name makes the batch fail on `model_configs`' unique index, which the retry loop (430) doesn't recognize → 500. **certain** (validation gap), check (the race).

12. **Deletion collects R2 only on deletes, inside the request** — deletion.ts 56: content younger than an hour (e.g. a project deleted right after a run) stays until the *next* deletion, so "as if it had never existed" / "real deletion" holds only eventually, and on a quiet instance indefinitely; the scan lists the whole bucket in the DELETE request. A scheduled collection (cron on Cloudflare, at start-up on the desktop) or `waitUntil` would answer both. Related race: `missingContent` reports an *old orphan* present, so the import doesn't upload it; a deletion elsewhere before `importRows` collects it, and the import then names missing content. **check** (design for the plan; race low).

13. **The three project dialogs have three busy policies** — DeleteProjectDialog 56–61 and ExportDialog 42–47 block backdrop/×/Cancel but not Esc (level 1: Esc mid-delete → `onCancel`, App keeps showing the deleted project: certain); RenameDialog 52–58 blocks nothing while saving. The "a stage is running[, here or on another device]" text built twice (Delete 46, Export 33) from *any* 409 (group 07 finding 9). For group 22's dialog shell: one `busy` prop that also cancels the `cancel` event. **certain** (confirmed).

14. **A new or imported project flashes "doesn't exist"** — App 148/161: `navigate` to the new id before `refresh()` returns, and `current` comes from the list (App 64), so the route shows "This project doesn't exist (any more)." until the list arrives. Fix: refresh first, or put the returned project into the list. **certain** (level 1 check confirmed), minor; routing is group 23's.

15. **"Already stored" can go stale between lookup and create** — App 320 sends only the file name when the PDF had projects; if the last of them is deleted meanwhile (its PDF collected, deletion.ts 79), `POST /api/projects` answers 409 "send the file itself" (index.ts 223), which `checked` turns into "Creating the project failed: Error: HTTP 409" with no retry with the file. **check**, rare.

16. **The "one-time" call-place script isn't one-time** — import inserts placeholders for files without places (projectFile 352–353) and revives deleted calls without them (334), so placeholder rows can appear after the script ran; such a project can't be exported (`placeProblem`, 168–171) until `fill-call-places` runs again. So callPlaces.ts/fill-call-places.ts (and `PLACEHOLDER_ITEM` redefined at callPlaces 16, level 1 certain) can't be removed as the overview suggests while format-1 files without places exist. For the plan: fill places during import (the same logic, from the file's requests) or raise `EXPORT_FORMAT` and refuse/convert old files. **check**.

17. **Page count at ingest** (group 03 finding 15): the natural home is `projects` (a column set by `POST /api/projects`, exported/imported with the project row), with the browser counting pages when the PDF is picked. Agreed as a candidate; costs a pdf.js parse at pick time. **check**.

## For level 3

- **Which stage a call belongs to** is decided in four places with different rules: the cache (served calls get no row), export (reassigns to the first naming stage), import (revived/matched calls keep their old stage), replay (only own rows), deletion (alive iff its stage or a live output). Groups 08 and 15 both hit it. A component rule ("a stage's calls are its rows plus the calls its outputs name; import makes them the imported stage's") would settle 4, 5 and group 08's 4.
- **The Worker's storage component**: R2 keys, the two PDF uploads, content, orphan collection and the D1 limits (100 parameters, batch size) belong in one storage module with a test helper that enforces D1's limits in the local tests.
- **Shared names in core**: names (2), export format (7), together with group 01's hex check and group 14's item shape: `@score3ly/core` is underused for what both sides restate.
- **Export/import is the backup path** and the fixtures' source; 4, 10 and 16 decide whether it holds for real projects. Worth one end-to-end check on the deployed instance before the real fixtures are made.
- **User-facing errors of these flows** (`${err}`, any-409 mappings, Worker text lost by `checked`) are group 07's; the dialogs' shell is group 22's; the navigation flash group 23's.

## Patterns

- **The same loop or helper written again in the second route that needed it** (3: name/insert/retry loop, PDF upload, `firstFreeName` on the web): the import was written as its own module and copied what index.ts had, because index.ts may export only handlers and nobody moved the helpers out. Cause: the entry module's export rule makes private helpers there sticky.
- **A constant or type restated across the seam** (3: `MAX_NAME_LENGTH`, the export format and its messages, `ProjectRows`/`ProjectExport`; plus `PLACEHOLDER_ITEM` in a script): kept equal by comments or a test reading source text, not by an import from `core`. Cause: `core` wasn't considered the home for small shared rules.
- **A rule for one feature that the next feature didn't know** (3: revived calls vs export/replay/deletion, served calls' ownership, placeholders written by import after the "one-time" script): export/import was designed after the cache and deletion, replay and call places after export, each correct alone. Cause: no written invariant for "a stage's calls"; each feature picked the lookup it needed.
- **A limit only production enforces** (1: D1 batch size): local SQLite has none. Cause: same as group 05.
- **Number appended after the length cut** (1, five call sites): the cut and the numbering were written in different functions.
- **Busy-state handling per dialog** (3 dialogs, 3 policies): each dialog written from scratch rather than from a shared shell.
- **Write without the check the read side assumes** (2: import's configs skip `configProblem`/secrets parse; archive content not compared with its key): the import trusts its own export, but the file passes through a user's hands.
