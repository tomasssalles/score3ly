# Level 2, group 18: Issues across the stages

## Map
- **web extract.ts** (issue part, 96–121): `StoredIssue`, `StoredWarning` (the central stored types of four stages, here because extract came first), `storedExtraction` (model issues → page boxes via `onPage`, ids from `first`; code issues via `codeIssue`), `storedScoreChecks`, `codeIssue` (code issues, `applications` from "extract").
- **notation lens.ts 236–257**: validation of extract's issues (boxes on the images sent, keys single letters and unique, `applied` among them, lilypond by class). No two-systems rule, no "a box on this system".
- **prompts review.ts / applyReview.ts**: prompt texts (`review*Text`, `applyReview*Text`, the logs differ only in the "by" label), schemas, `ReviewAnswer`/`ApplyReviewAnswer`, `reviewFromModel`/`applyReviewFromModel` (sentinels → null).
- **web review.ts**: `placesOf`/`systemsOf` (which systems/stretches a box covers), the model's views of the score and issues (`reviewScore`, `reviewIssues`, `reviewWarnings`, `modelName`), `ReviewEntry`/`StoredReview`, `checkReview` + `newIssue` (validation of review's new issues), the fold `applyEntries` → `withKept` → `reviewedIssues`, log entries, note, key.
- **web applyReview.ts**: `needsApplying`, `applyCalls` (windows), `StoredApplyCall`, `checkPatch` (incl. reverts with new answers), `appliedIssues` (the fold after apply), `callWarnings`, `isNewCodeIssue`, log entries.
- **web humanReview.ts**: `StoredHumanReview` (= review entries), `humanReviewedIssues` (fold via `applyEntries` + resolved), editing (`chooseAnswer`, `writeAnswer`, own issues), `boxProblems` (two-systems rule for clarifications), `placedSystems`.
- **web transcription.ts**: notes (issues + warnings), `homeOf` (the view's home of a note), `boxesOnCrop` (page → crop, used for the view *and* the marked crops sent to models), `answerTags`.
- **web attribution.ts**: walks the chain with its own `issuesAfter` fold (load / `reviewedIssues` / `humanReviewedIssues`), relying on "choices and applications only appended".
- **run*.ts**: runExtract reserves numbers per system and for the checks; runReview folds earlier calls (`issuesBefore`), checks, renumbers new issues, draws marked crops; runApplyReview folds the reviews (`reviewedIssues`/`humanReviewedIssues`), plans calls, checks patches, folds `appliedIssues`, re-homes issues into the new transcription and raises fresh code issues (two inline copies). finishHumanReview gates clarifications with `ownIssueProblems`.
- **Views**: ExtractionView `useTranscription` folds review calls (inline copy of `reviewedIssues`), apply calls, the human review (`withHumanReview`), reserves numbers for clarifications; HumanReviewCards `AnswerPicker` restates the next letter and the "same answer" rule for its own state.
- **Worker** `POST /api/projects/:id/issue-numbers` (index.ts 322): `next = MAX(next, above+1) + count`, monotonic; `above` = the caller's largest known id.
- **Contracts:** (a) `StoredIssue`, one schema written by extract, review, apply_review, human_review, read by all of them, the view, attribution, engrave's report; (b) choices and applications only appended (attribution's walk depends on it); (c) answer keys "a, b, c …": what validation accepts ↔ how the next key is made; (d) the two-systems rule, at every place an issue is created; (e) "the systems a box covers" (group 02 #3/#4) ↔ which issues a call may choose on, where apply_review begins, where an issue is stored and shown; (f) the numbering counter ↔ `above` ↔ the replay's counter setting (docs §12); (g) code-issue identity (question text + page boxes) ↔ `isNewCodeIssue`.

## Findings

1. **The next answer key collides with an existing one when the keys aren't a, b, c in order — and extract's check allows that.** lens.ts 249–250 accepts any unique single letters (an extract issue with keys "a", "c" passes); every place that adds an answer takes `letter(answers.length)`: review.ts 132 `nextKey`, applyReview.ts 189, humanReview.ts 66, HumanReviewCards.tsx 40 (`otherKey`). For "a", "c" the new answer is "c" again: two answers with key "c", the choice ambiguous, `needsApplying`/`answerTags`/AnswerPicker (React `key={a.key}`) all confused. Review's own new issues must be "a, b, c, … in order" (review.ts 207), code's are (lens.ts 443), user's are ("a"). Fix: one rule for all creators (in order, as review demands) checked in lens.ts too, and one `nextAnswerKey(answers)` (notation, beside the check; or the first unused letter). Also nothing stops a 27th answer ("{"). **certain** (mechanism; unlikely with constrained models).

2. **The two-systems rule isn't checked for extract's issues,** though docs/notation.md 212 says it is "checked when the issue is created, whether by a model (… as `extract`'s checks do)". lens.ts 238–257 checks no system rule: an extract issue may have boxes on "previous system" and "next system" (systems n−1 and n+1), or only on a neighbour (no box on its own system, which review.ts 202 requires of review's issues). applyCalls then caps the window at two systems (applyReview.ts 42) and the third system's part lies outside it (only "allowed"). Fix in lens.ts: not both neighbour labels, and at least one box on "system"/"stretch k" (or say in docs that extract may). **certain** (gap vs docs).

3. **The rule itself is written three ways, by three different notions of "which system":** review.ts 203–204 (the systems of the *images* the boxes are on), humanReview.ts 124–125 (`systemsOf`, i.e. `placesOf`'s overlap with tight box *or crop*, group 02 #3), and none for extract (2). The same clarification box near a system's edge counts as two systems for the human but one for a model. One `systemsRuleProblem(systems: number[])` (with 1's key rule, in notation) fed by one `systemsOf` (group 02 #3/#4). **certain**.

4. **"Is it the same answer?" has four rules:** review.ts 134 trim + lowercase (repeat → answer unusable), applyReview.ts 188 trim, case-sensitive (→ unusable), humanReview.ts 52 trim, case-sensitive ("case counts", chooses the existing answer), and HumanReviewCards.tsx 61 restates humanReview's rule inline to decide its own `pending` state (it breaks silently if `writeAnswer`'s rule changes). Decide one rule (case-insensitive is the safer for models: a review answer "C sharp" next to "c sharp" is the same) and export `sameAnswer` from the issues module; AnswerPicker should ask `writeAnswer`'s result (did it choose an existing key?) instead of re-deriving it. **certain** (four copies), **check** (which rule).

5. **"The issues as the stages before left them" is folded in four places, one an inline copy:** attribution.ts 79–94 `issuesAfter`, runApplyReview.ts 115–121, ExtractionView.tsx 113–116 (= `reviewedIssues(base, calls, review.done)` written out again: same sort, `applyEntries`, `withKept(changedBy)`), runReview.ts 111–115 `issuesBefore` (= `reviewedIssues(base, calls before n, false)`). And the loading before it (extractions + checks → issue map) in runReview 48–54, runApplyReview 88–93/115, attribution 83–85, ExtractionView 100–113. A pure `issuesAt(chain, loaded)` (or `foldIssues(base, stages)`) beside attribution's walk, used by runApplyReview and the view; ExtractionView calls `reviewedIssues`. Level 1 saw the view's folding as untested logic in a component: confirmed. **certain**.

6. **A stored code issue is built three times, with a deliberate difference hidden in the copies** — extract.ts 106–121 `codeIssue` (`applications` from "extract" when applied), runApplyReview.ts 371 and 395 (verbatim literals without `applications`, which per extract.ts 33–35 is intended: raised after the transcription was written). Plus the "fresh code issues → numbered" block twice in runApplyReview (361–364/388–391) and the places→boxes / warning mapping three times (extract.ts 77–79, 99–102, runApplyReview 213). One `codeIssue(issue, id, places, { writtenBy: "extract" | null })` and `storedWarning` in the issues module, and one `freshCodeIssues(codeIssues, existing, placeBox)` used by both apply items. **certain**.

7. **Code-issue identity is the question text + page boxes (answer to group 17 #10).** `isNewCodeIssue` (applyReview.ts 313–316) compares `question` and `canonicalJson(boxes)`; the texts are written in lens.ts (4 kinds), spans.ts and scoreChecks.ts (group 17 #10: one text twice). Rewording a question, or a layout change that moves a stretch's box by a rounding, re-raises every answered code issue as new on the next Apply review. Proposal: `CodeIssue` gets a stable `kind` (e.g. `first-stretch`, `continuation`, `stretch-class`, `open-mark:<mark>`) and its `StretchPlace`s, both stored on the `StoredIssue` (`code: { kind, places }`), and identity = kind + places; the text stays wording. Cheap now (no data to keep). **check** (design, for the owner).

8. **Issue numbering: the "reserve if any, else 1" idiom five times, and review numbers twice.** runExtract 171/187, runReview 196, runApplyReview 364/391: `count > 0 ? await reserveIssueNumbers(project, count, known) : 1` then `id++`. runReview additionally has `checkReview(parsed, ctx, 1)` number new issues from a dummy 1 (review.ts 148 `first`, used only by tests with 10), then renumbers them (197), and counts them with `newIssueCount` on the *raw* JSON (review.ts 187) instead of the checked entries (level 1's "two views of one answer"). Fix: `checkReview` returns new issues unnumbered (or `id: 0`), runReview counts `checked.entries`, and one `numberIssues(project, unnumbered, known)` in api.ts or the issues module. **certain** (duplication); the dual count agrees today.

9. **Three shapes of "a choice, maybe with a new answer", each appended by its own fold.** `ReviewEntry.choice` (`newAnswer: {key,text} | null`, `reason: string | null`), `StoredApplyCall.choices` (`newAnswer?: …`, `reason: string`), `StoredIssue.choices` (`by`, `kept?`, `reverted?`); `applyEntries` (review.ts 236–240) and `appliedIssues` (applyReview.ts 283–288) each do "answers + new one, choices + one". Also `latest(issue)` defined twice (review.ts 133, applyReview.ts 20) and inline twice (transcription.ts 258, runApplyReview.ts 283), and humanReview.ts 23 fakes a `StoredReview` (`system: 0`) to reuse `applyEntries` (as does runApplyReview 104 and ExtractionView 89). One `addChoice(issue, choice)` + `latest` in the issues module; `applyEntries(issues, entries, by)` taking entries. **certain** (small).

10. **The `StoredIssue` family belongs in its own module** (level 1 check, confirmed): `apps/web/src/issues.ts` with `StoredIssue`, `StoredWarning`, the choice shape (9), `latest`, `nextAnswerKey`/key rule and `systemsRuleProblem` (or re-exported from notation, 1/3), `sameAnswer` (4), `codeIssue`/`storedWarning` (6), `isNewCodeIssue`, `needsApplying`, the folds (5), and `placesOf`/`systemsOf` (group 02's box module feeds it). Today review.ts, applyReview.ts, humanReview.ts, transcription.ts, attribution.ts, runReview/runApplyReview and the views import the type from extract.ts and the folds from review.ts (humanReview → review, applyReview → review, attribution → review + humanReview). **certain** (structure).

11. **runApplyReview.ts (426 lines) and runReview.ts share their whole loading and request scaffolding** (level 1 and group 06/02 found the pieces: the transcription load, `imageRecipe`, marked crops (group 02 #9), the log with `cacheUpTo`). Small divergences show they drifted rather than chose: runReview's log skips calls with no entries (161), runApplyReview's doesn't (269; harmless, an apply call always has entries); runReview's request issues include those raised by earlier calls (drawn too, 136), runApplyReview draws and lists `startIssues` only (246, 274: consistent with "the issues when this stage started", fine). With 5, 8 and group 06 #1/#2 a `musicStage.ts` (load transcription + issues, marked crops, the log) would leave each runner its own calls. **certain** (structure).

12. **The model's two score views differ on purpose** (answer to group 10's "for level 3"): `reviewScore` (review.ts 46–75, used by review *and* apply_review's shared prefix) drops staff/voice descriptions per system and lists them once per piece; `systemView` (runApplyReview 416–426) keeps them for the window, because the model "needs them to name a new voice or staff" (its comment). Not a bug; the duplication is group 16 #5's `systemForModel(answer, { measureOf, descriptions })`; `measures()` (runApplyReview 408) = the `measureOf` loop (review.ts 50). Also `reviewIssues` sends `kept` but not `reverted` on choices (93): a revert reads to the next review as "chosen by Apply review" with a reason. **check** (whether the review should know a choice was a revert; prompt question).

13. **ExtractionView's review branch: a misleading placement step.** 117–119 append each call's new issues to the extraction of the call's system ("the new ones under the system whose call raised them"), but the note's home is then decided by `homeOf` from its boxes (252–258), so the placement only changes the order of notes within a home (and so the colour cycle). Either drop it (append to checks) or say what it does. **check** (minor).

14. **Tests at the seams:** each fold is unit-tested alone (review.test 139, applyReview.test 258, humanReview.test 33), and attribution.test walks extract → review → … with fixtures, but nothing composes extract → review → apply_review → human_review → apply_review on the pure functions and checks the issues (ids stable, choices appended only, `needsApplying` false after each apply); only the replay does it end to end, with the fake model. No test feeds a key set like "a", "c" (1), an extract issue over three systems (2), or the same box to `boxProblems` and `newIssue` (3). The view's fold (5) is untested. **certain** (gaps).

## For level 3
- **The issues are a component of their own** spread over a stage file (extract.ts), a sibling stage (review.ts, which every later stage imports for its folds), a view (ExtractionView, HumanReviewCards) and notation (lens.ts, the first validator). Its rules — key letters, the systems rule, same-answer, code-issue identity, append-only choices — each exist in two to five places with small differences; one module (10), with the systems/keys rules in notation so lens.ts can apply them to extract (1, 2), would make them one rule each.
- **"The state of the issues at stage X" is a pipeline-level question** (fold over the chain) answered four times (5); together with group 06's "latest stage of step X" and group 17's check chain, the music stages want one "music state at a stage" module that runners, views and attribution share.
- **Identity by content, again:** code issues by text and float boxes (7), like the cache keys by content (groups 01, 06). Any stable identity should be a field, not a derived text.

## Patterns
- **A rule restated by each stage that creates or edits issues** (answer keys ×5 with a collision, same-answer ×4, two-systems ×2 + 1 missing, `latest` ×4): 4 findings (1–4, 9). Likely cause: each issue-creating stage (extract, review, apply_review, human_review, its UI) written later than the type, by copying the one-liner it needed from the previous stage instead of a shared helper; the validator for extract lived in notation, so the later web checks never saw it.
- **A fold or builder copied into a caller instead of called** (`reviewedIssues` inline in the view, `issuesBefore`, code issues ×3, the reserve idiom ×5): 3 findings (5, 6, 8). Likely cause: the caller needed a variant (partial calls, no `applications`, a count first) and copied rather than adding a parameter.
- **A central type homed in the first module that needed it** (`StoredIssue` in extract.ts, folds in review.ts): 1 (10). Likely cause: extract was built first; later stages imported from it rather than moving it.
- **Identity derived from wording** (code-issue text): 1 (7). Likely cause: dedup added after the fact, keyed on what was at hand.
- **Misleading comment / no-op step in a view** (13): 1.
- **Seam tests missing where per-function tests are thorough** (14): 1. Likely cause: each stage's pure module tested when built; the chain only by the replay.
