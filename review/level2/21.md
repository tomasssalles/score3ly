## Map

- **web engrave.ts** (both steps' pure parts, five jobs, finding 10): `EngraveConfig`/`PAGE_SIZES`/`pageOptions`/`engraveConfigOf`; `engraveSources`, `latestMei`, `sourceIds`, `buildMeiStageKey`, `loadScore`, `meiText`, `meiMetadata` (stored metadata → `MeiMetadata`, via fixMetadata's `normalizeMetadata`); notes; file names; PDF byte fixes. **runBuildMei.ts** stores the MEI (item '', type `mei`, `application/xml`). **runEngrave.ts** stores the PDF's recipe (type `pdf`).
- **engraving.ts**: `pdfRecipe` {mei, config, verovio, rendering, pdf}, `engravedPdf` (OPFS cache by `keyOf(recipe)`, else Verovio pages → jsPDF + svg2pdf.js), `meiFile`, `saveFile`. **rendering.ts**: `renderMei` (Transcription systems), `renderPages` (engravings), SVG cache keyed by {mei, options, versions}; worker client (group 04). **renderWorker.ts / verovioRender.ts**: Verovio calls.
- **fixMei.ts**: `fix_mei`'s outputs `mei_base`/`mei_draft`/`mei`, `loadFixMei` (writes the base on first open while WIP), `finishFixMei` (checks the *stored draft*, stores it as `mei`). **meiChecks.ts** (ids, `linesChanged`, `changesNote`) + **meiSchema.ts** (libxml2 RelaxNG) behind meiCheckWorker/meiValidation (group 04).
- **Views**: EngravingView (build_mei's MEI view, read-only; engrave's PDF via PdfView), FixMeiView (the editor, `draftSaver`, Apply), MeiWorkspace (search, Go to, file ↔ score by `xml:id` = Verovio's `g[id]`, index from meiView.ts), MeiCode (CodeMirror). **downloads.ts**: the card's downloads and zip. **attribution.ts**: issue labels (group 18's topic; only its leftovers here).
- **eval engrave.ts**: its own Verovio → pdfkit path, a copy of `pageOptions`, its own `verovio.d.ts`.

Contracts: (a) the builder's file format (one element per line, `escapeAttr`, "a–b" measure ranges, `mdiv @n/@label`) ↔ meiView's line index and meiChecks' line regexes; (b) `xml:id` ↔ Verovio's SVG ids ↔ MeiWorkspace's click/selection mapping; (c) stored outputs: `mei` (build_mei, fix_mei), `mei_base`/`mei_draft`; `pdf` recipe written by `pdfRecipe`, read by steps.ts 495; (d) keys: build_mei's stage key, engrave's stage key `{step, version, recipe}`, the PDF cache key `keyOf(recipe)`, the SVG cache key; (e) stored metadata → `normalizeMetadata` → `meiMetadata` → `MeiMetadata` → header and `mdiv` labels; (f) `pageOptions` ↔ eval's `VEROVIO_OPTIONS`.

## Findings

1. **Finishing `fix_mei` loses the last edits and leaves the editor editable on a done stage** — `finishFixMei` (fixMei.ts 190–199) checks and applies the *stored* draft; the editor holds unsaved text for up to 250 ms (MeiCode 130) + 2 s (FixMeiView 15, `draftSaver`), and nothing flushes it before the card's Finish (ProjectView 340–360 fetches the pipeline and calls the finisher). Then the view stays mounted: ArtifactView 59 keys FixMeiView by `artifact.id` (`<stage>.mei`, unchanged by finishing), FixMeiView 35 reloads only on `stage.id`, and MeiCode creates its editor once (`useEffect(..., [])`, 113), so `editable` going false hides the tools but the CodeMirror stays editable (history, no `readOnly`) and shows the unsaved text, not the applied MEI. Typing on saves to a done stage, refused 409 "the stage isn't running" (pipeline.ts 556) → "The text couldn't be saved". The other editors switch branch in ArtifactView (`artifact.editor?.step`) and remount. Fix: flush the editor before finishing (a registry of pending saves the finish awaits, or Finish disabled while one is pending), key the view by `${artifact.id}:${stage.status}` (or MeiCode by `editable`), reload texts after finishing. **certain** (mechanism read in code; whether the artifact stays open on Finish: yes in the wide layout, the route doesn't change).
2. **`draftSaver` doesn't chain its saves, and there are two stacked debounces each with its own unmount flush** — FixMeiView 42–66: `save(text).catch(onError)` with nothing serializing it. At unmount, `saver.close()` (104) flushes the 2 s-pending text A, then MeiCode's cleanup (163–167) sends the 250 ms-pending text B → `changed` → flush: two `saveText` in flight, both `recordOutputs` with the same `X-Project-Version`; the second is refused `stale_version` → App's "changed on another device" dialog, and B (the latest typing) is lost. Typing, a pause under 2 s, typing, then leaving within 250 ms is enough. Apply (135) can also overlap a flush; and `saved.current = t` (97) is set by whichever save answers last, so an older save answering late leaves `saved` wrong. In development, StrictMode runs FixMeiView's effect twice, so `loadFixMei` saves `mei_base` twice at once on first open (fixMei.ts 179) → same 409. Same family as group 19 #1/#4 (its "one save queue per project" fixes this one too; FixMeiView is a fifth save chain). **certain** (mechanism), **check** (frequency).
3. **The PDF's keys don't contain what makes the PDF, and the stored recipe is never read back** — (a) `pdfRecipe` (engraving.ts 21) holds the page *size* name, not `pageOptions(config)` (engrave.ts 32: breaks, scale 40, footer…); a change to `pageOptions` changes the SVG cache key (rendering.ts 89, options in it) but not the PDF cache key nor engrave's stage key (runEngrave 268), so cached PDFs and done stages keep the old engraving while the MEI view shows the new one, unless someone remembers to bump `PDF_VERSION` or `RENDERING_VERSION`. Put `options: pageOptions(config)` in the recipe. (b) steps.ts 495–497 takes only `recipe.mei` and rebuilds the recipe from today's constants (`pdfRecipe(meiSha256, engraveConfigOf(stage.config))`, engraving.ts 31/36), and `config` from the stage, not the recipe: after a Verovio upgrade a done `engrave` stage shows and downloads a PDF its stored recipe doesn't describe, with no warning (images have fingerprints for this, §8.3; PDFs nothing). Read the stored recipe (typed `PdfRecipe`, not `as { mei?: string }`) and say when it can't be honoured. **certain** (a), **check** (b: what the docs want for a recipe the code can no longer make).
4. **`idProblems` refuses valid MEI, which blocks Apply and Finish** — meiChecks.ts 123–131 takes every attribute token starting with "#" as an id reference: `color="#ff0000"` (MEI's data.COLOR allows hex) or any label "#1" → "points to "#ff0000", but no element has that id". And both loops read only double-quoted attributes (117, 124): an `xml:id='n1'` written with single quotes (valid XML) isn't collected, so every `#n1` is reported missing. Fix: walk the document libxml2 already parsed (meiSchema.ts 199; nodes carry lines) and check only MEI's pointer attributes (`startid`, `endid`, `plist`, `facs`, `corresp`, `next`, `prev`, …, the builder's `refsOf` set at least). **certain**.
5. **`build_mei`'s stage key has no version of the MEI builder** — engrave.ts 107–118: the comment calls `lensVersion` "the MEI builder's (the format's) version", but `LENS_VERSION` (symbolic.ts 8) is the lens format's; a change to mei.ts or score.ts reaches the key only if `BUILD_MEI_VERSION` (apps/web) is bumped by hand, in another package. A `MEI_BUILDER_VERSION` beside `MEI_VERSION` in notation, in the key. (The Transcription's renderings are keyed by the MEI text, so they follow automatically.) **certain** (comment), **check** (adding the version).
6. **A piece's title read three ways** — mei.ts 115 `new Map(...)` keeps the *last* title for a system (header `componentList`), 384 `find` the *first* (the `mdiv @label`) — group 20 #3b, confirmed; and MeiWorkspace 255 `pieceName` falls back to "Untitled" where the header says "Piece N" (131), so several untitled pieces look alike in Go to. One `pieceTitle(metadata, system)` in mei.ts for both, and the picker's fallback "Piece n". **certain**.
7. **Dead code** — `meiNote` (engrave.ts 173–183) is used only by its test (`fix_mei`'s card uses `changesNote`), so "measure ranges parsed twice" is once in the app; `divideAtSystemBreaks` (mei.ts 58–60, 66; test 242) is used by nothing (`engrave` has Verovio's own breaks; the comment describes the dropped design); xml.ts `attr`/`setAttr` (mei.ts remaps by hand at 984, 1036 instead); attribution.ts `whoChose`/`whoApplied` (129–135). **certain**.
8. **The file format's small contracts restated on the reading side** — the measure range: written `${n}–${n+count-1}` (mei.ts 998), parsed by `split("–")` (meiView 84; dead meiNote 177): export `measureNumberText`/`measureRange` from mei.ts. meiView 10–12 `unescape` isn't the inverse of xml.ts `escapeAttr` (no `&#9;`, `&#13;`; a title with a tab shows raw in Go to): an `unescapeAttr` beside `escapeAttr`, round-trip tested. meiView 6 `name.replace(".", ...)` escapes one dot: latent (names used have none). **certain** (minor).

- **`core`/shared layout:** nothing here needs `core`; the shared modules proposed are web-local (`files.ts`, `engravePage.ts`, `pipeline.ts`'s `Engraving`, about.ts `APP_INFO`) plus notation exports for the file format (`measureRange`, `unescapeAttr`, `pieceTitle`, `MEI_BUILDER_VERSION`).

## Patterns

- **A flow missing its last step when two features meet** (1: Finish × the editor's debounce and mounting): 1. Likely cause: Finish built for editors that save every edit at once; fix_mei, the first with a delayed save and a view that survives finishing, was added without revisiting it.
- **Save chains written per editor, without the serialization the lock needs** (2): 1 here (5th in the app). Cause: as group 19: each editor's saving written from scratch; the optimistic lock's "one request at a time" rule lives in no shared helper.
- **A cache or stage key that leaves out an input** (3a, 5): 2. Cause: the key lists what was obvious when written (the config, the MEI), and options or code living in another module/package change without anyone seeing the key.
- **Stored data rebuilt instead of read back** (3b): 1. Cause: the artifact needs a `meiSha256` and takes the shortest path to it.
- **Regexes over a format that a parser already handles** (4, 8): 2. Cause: the line-based index was right for the builder's own files, and the hand-edited case reused it; libxml2 arrived later for the schema only.
- **Dead code left after a design change** (7: `meiNote`, `divideAtSystemBreaks`, `whoChose`/`whoApplied`, `attr`/`setAttr`): 4. Cause: features replaced (fix_mei's note became lines changed; engrave dropped the original's breaks) with the old helpers kept alive by their tests.
- **The same small thing restated per file** (8, 10, 12: `Engraving` ×3, the `mei` lookup ×3, app info ×4, zip wrapper ×2, page options ×2, verovio.d.ts ×2, `TITLES`): 7. Cause: each module written to need, with no shared home for app-wide bits (files, app info) and no habit of exporting a type where it is first declared.
- **Generic helpers placed in the first stage module that needed them** (10: `saveFile`, `fileBase`, `EXTRACTION_STEPS`): 3. Cause: written for `engrave`, later imported by unrelated modules instead of being moved.
- **Seams untested where each side has tests** (9): 1 (four seams). Cause: unit tests per module with hand-written inputs; the builder's output is never fed to its readers.
- **Comments naming the wrong file or meaning** (5, 11): 2. Cause: code moved or renamed (engraving.ts/engrave.ts, lens vs builder version) without searching the comments.
