# Level 2, group 06: Running a stage

## Map
- **Worker `pipeline.ts`, the run routes** (464–690): `start` (planned|failed|stale → running, or reuse of a done stage with the same `stage_key` by repointing the entry; records `stage_inputs` one `INSERT OR IGNORE` per id; closes calls left running), `outputs` (running: `INSERT OR IGNORE` per output + one statement per input id; WIP: upsert + `manual_saves`; refreshes `heartbeat_at`; returns ids by `(type, item)`), `heartbeat`, `finish` (running → done|failed; WIP → done), `stop` (outputs deleted, a planned copy in place). Each route opens with `entry()` + 404 (+ carried 409, + `anyRunning` 409 in the five structural routes). `resolve` (790) compares a carried stage's `stage_inputs` with the ids the browser says it would read now.
- **Worker `versions.ts`**: a second, hand-written table of the same routes (`whatOf`, by path segments) saying which are checked/raised; `outputs`/`finish` need a read of the stage's status for it.
- **Worker `llmRoutes.ts` 836**: `…/llm-calls/:callId/unusable` (an answer the stage can't use: `ok` → `unparseable`).
- **Web `api.ts` 175–245, 587**: the client side of those routes (`startStage`, `recordOutputs`, `sendHeartbeat`, `finishStage`, `stopStage`, `resolveStage`, `markUnusable`), `StageStart`, `NewOutput`; `putContent` (hash, PUT).
- **Web `stageRunner.ts`**: `runPlan(run, plan)`: start (return on reuse) → skip `(type, item)` already in `stage.outputs` → `timed(make)` → `recordOutputs` one by one → progress → heartbeat every 60 s → finish done/failed (errors inside are swallowed into a failed finish). `CannotStart`: thrown by a runner *before* `runPlan`, nothing recorded.
- **Web `runners.ts` / `finishers.ts`**: step id → runner / finisher; `ProjectView.run`/`finish` drive them (Auto chaining, abort on Stop or unmount, errors before start → panel error).
- **Web `run*.ts`**: each finds its inputs among the earlier stages, computes its stage key, preloads what a failed run recorded (analyze, extract, review, apply_review), and hands `runPlan` the items. **`finish*.ts`**: fill a manual stage's untouched items from its source stage, return the note.
- **Lookups of "the latest stage of step X before this one"**: steps.ts (10), musicInputs.ts (`latest`, + 3 lists), engrave.ts (`engraveSources`/`withOutput`, `latestMei`), run*.ts, finish*.ts, fixMei.ts — about 25 hand-written `slice/reverse/find`.
- **Contracts:** (a) `StageStart`/`NewOutput` ↔ the routes' hand validation; (b) the skip key `(type, item)` ↔ `UNIQUE (stage_id, item, type)` and the `outputs` route's id lookup; (c) the heartbeat period (web 60 s) ↔ `STALE_MS` (group 05); (d) what a stage records as its inputs at `start` ↔ what `carriedInputs`/`reviewInputIds` say it would read now (`resolve`); (e) the route list in `pipeline.ts` ↔ `whatOf` in versions.ts; (f) `markUnusable` ↔ the cache's "only usable answers" rule.

## Findings
1. **"The latest stage of step(s) X before this one" ~25 times, with step lists restated and diverging rules** — steps.ts 75/205/231/251/308/338/373/400/429/560, musicInputs.ts 40–49, engrave.ts 64–72/93, runLayout 31–34, runAnalyze 61, runSkewAnalysis 15–19, runBuildMei 14, runEngrave 15, finishFixSkew 17, finishFixLayout 18, finishFixMetadata 37, finishFixObservations 23, finishHumanReview 17, fixMei 48. Step lists: `LAYOUT_STEPS` ×3 (musicInputs 17, engrave 60, runAnalyze 55) + inline `layout || fix_layout` ×2 (steps 251, finishHumanReview 17); `PIECE_STEPS` = `METADATA_STEPS` (musicInputs 19, engrave 61) + inline in `reviewInputIds`; `OBSERVATION_STEPS` + inline; `EXTRACTION_STEPS`, `MEI_STEPS` in engrave.ts imported by unrelated modules; `LINE_STEPS` in runLayout. The rules differ by copy: musicInputs checks `status === "done"` on the layout, engrave doesn't (67); musicInputs `latest` finds the stage without the content condition then `!`s the output (46–48), engrave's `withOutput` checks both; `reviewInputIds` checks no status at all. They agree today only because "the first stage not done" keeps a later stage from running past a WIP fix. Each list is really "the steps that produce output type T" (layout: layout, fix_layout; pieces/metadata: fix_metadata, analyze; observations: fix_observations, analyze; extraction: extract, apply_review; mei: build_mei, fix_mei; lines: skew_analysis, fix_skew). Shared version: in web `steps.ts` (or a new `stageInputs.ts`, cf. group 05's split of steps.ts) a `PRODUCERS: Record<OutputType, StepId[]>` (or `produces` on each `STEPS` entry) and one `latestOutput(stages, beforeStageId, type, { done: true })` / `latestStage(…)` returning stage + outputs with content; `findLast` after a lib bump to ES2023. Used by every file above. certain.
2. **What a review reads is computed twice: once to run it, once to compare it when carried** — runReview takes its inputs from `musicInputs` + its own `reviewed` lookup (42–50), but records `inputIds` from `reviewInputIds` (steps.ts 556, runReview 118), a separate re-derivation of the same lookups (comment: "the same list runReview.ts records"). `resolve` keeps or drops a carried further review by comparing those ids, so if the two ever diverge, a review is dropped (or kept) wrongly; nothing pins them. runApplyReview builds its `inputIds` by hand a third way (196–202) — harmless today (an `apply_review` is never compared), but the same parts. Fix with 1: a pure `musicSources(earlier)` (stages and outputs, no fetching) used by `musicInputs` (which then fetches) and by `reviewInputIds`, as `engraveSources` already is for `build_mei` (pure, then `loadScore`, and `sourceIds` both records and would compare). certain (two derivations), check (no divergence found today).
3. **Notes counted only from the items made in this run** — `runPlan`'s `note()` closes over counters that only `make` fills, so a resumed run understates: runLayout 51–52/114–115 ("N systems on M pages" counts only the pages after the failure, `flagged` likewise), runSkewAnalysis 30/41 (said in a comment), runEngrave 19/26 ("0 pages" if the PDF item was recorded and only `finish` failed), runAnalyze 168/218 (`pieces` 0 likewise). extract, review and apply_review preload the recorded outputs and are right. Layout's is the visible one (a failed page is common: an unusable answer). Fix: the same preload for layout (its layouts are small JSON), or compute every note from the stage's final outputs after the loop (`runPlan` could pass the full output list to `note`, the runner fetching what it needs). certain.
4. **Unusable-answer handling written 8 times, and its failure swallowed** — runLayout 99, runAnalyze 152/162/202, runExtract 166, runReview 191, runApplyReview 310 (+ its local `unusable`): `markUnusable(...).catch(() => {})` then `throw`. If the mark fails (network blip), the call stays `ok`, the retry is served the same cached answer, fails the same way, and only then marks it. One helper in llm.ts, e.g. `unusable(run, answer, what, problem): never`, or better `ask(…, { check })` that marks and throws itself, so that a runner can't forget the mark; whether to retry the mark once is the helper's business. certain (duplication), check (the retry served the same answer: self-heals on the next retry).
5. **Content written as canonical JSON in 16 places by 5 helpers** — `json` consts (runAnalyze 57, runExtract 34, runReview 38, runApplyReview 66), inline (runLayout 116, runSkewAnalysis 51), `linesBytes` (finishFixSkew, used by SkewEditor), `layoutBytes` (finishFixLayout, used by LayoutEditor), `jsonBytes` (finishFixMetadata, used by finishFixObservations, finishHumanReview, ExtractionView). All then `putContent(…, "application/json")`. Consistent (all canonical, which the content hash needs), but `putJson(value)` in api.ts (beside `putContent`) would replace them all and make the editors stop importing from finishers. Also `JSON.parse(canonicalJson(x))` as "what a reload would read" 5× (runAnalyze 207, runApplyReview 313/350, runExtract 164, runReview 187/201): a `normalized()` in core keys.ts. certain.
6. **Preloading a failed run's outputs, the same block 4×** — runAnalyze, runExtract 66–72, runReview 104–108, runApplyReview: `new Map(stage.outputs.filter(type && content).map([item, o]))` + `Promise.all(fetchJsonContent)`. A `recordedContent<T>(stage, type): Promise<Map<item, T>>` beside `runPlan` (it already knows `stage.outputs`). certain.
7. **The LLM runners' start prologue 5× and partly a no-op** — runLayout 42–56, runAnalyze 81/172, runExtract 43/106, runReview 81/122, runApplyReview 146/221: `stageModelConfig(stage.config)`, `imageRecipe` literal, then `config: { ...stage.config, modelConfigId: config.id }` + `modelConfigId: config.id`. A `llmStart(stage, config)` in llm.ts, or drop the separate field. certain (small).
8. **Errors before `startStage` don't fail the stage; only `CannotStart` was meant to** — `ProjectView.run` 417–423 shows any error a runner throws before `runPlan` in the panel, and the stage stays ready; `CannotStart` is documented for that ("Nothing has been recorded"), but the runners also do fetches and checks there that are real failures: musicInputs/runReview/runApplyReview loading every extraction (a network error), runReview 64 "no longer passes the checks" (a `CannotStart`, though it is a failure of stored data after an app update), runBuildMei's `loadScore`. These never reach the stage's error, the failures statistics, or the run report. Decide the rule (only "a precondition isn't met" stays unrecorded) and move loading into the plan (a first item, or `runPlan` taking a `prepare` that runs after `start`). check (design).
9. **A failed stage retried after an app update mixes versions under the new key** — `start` (pipeline.ts 518–525) overwrites `step_version`, `config_json`, `stage_key` of a failed stage and keeps its outputs; `runPlan` skips every `(type, item)` already recorded (stageRunner 51). If a deploy changed the prompt or lens version between the failure and the retry, the old items stay, now labelled with the new key, and a later run with that key reuses the mix. extract catches part of it (it re-checks recorded answers, runExtract 92), the others don't. Fix: `start` compares the stored `stage_key` with the new one and, if they differ, drops the outputs (as `stop` does) and says so; or the browser skips only when `stage.stageKey === plan.stageKey`. check (needs a deploy between failure and retry).
10. **The run routes' prologue 12× on the Worker** (level 1) — `entry` + 404 (+ carried 409, + `anyRunning` 409) in every stage route; and versions.ts reads the same stage again for `outputs`/`finish`. A Hono middleware on `/api/projects/:pid/stages/:sid/*` that loads the entry once into `c.var` (404 there) would serve both, the guards becoming one-line checks. certain.
11. **The lock table restates the route list by hand** — versions.ts 23–41 classifies by path segments; a new stage route falls through to "neither checked nor raised" silently, and no test lists the routes (index.test.ts 1654–1722 tests three of them). Either declare the class where each route is registered (a `locked("checked", handler)` wrapper), or a test that walks Hono's `app.routes` under `/api/projects/:pid/` and fails on any route missing from an explicit table. certain (fragile, untested), check which.
12. **Many statements per request: one per input id** — `start` 521–523 (one `INSERT` per input: a review ≈ systems + 2·pages + 3), `outputs` 588–594 (per output, one per input id: extract's `score_checks` and every apply_review output carry the whole input list), also `fix`/`edit`/`human-review` (level 1). With D1's per-invocation query limit (50 on Workers Free, 1000 paid, if batch statements count individually — to verify), a 60-system score's review couldn't start. `INSERT OR IGNORE INTO stage_inputs SELECT ?, value FROM json_each(?)` (and the same for `output_inputs`) makes each one statement whatever the size — and the same `json_each` form fixes `resolve`'s 100-parameter bug (group 05, finding 9). check (the limit's counting), certain (the fix is simpler either way).
13. **`start` is read-decide-write; two simultaneous starts both run** (level 1) — 484–526: status read, then an unconditional `UPDATE … SET status = 'running'`; `start` is "raised", not checked (versions.ts 34). Two tabs clicking Run within the same moment both start and both pay. A conditional update (`… WHERE id = ? AND (status IN ('planned','failed') OR heartbeat_at < ?)`, check `meta.changes`) closes it, and is the natural place for group 05's run token (finding 10). check (narrow window).
14. **`config` route doesn't refuse while another stage runs** — 407–461 refuses only when *this* stage runs; `fix`, `edit`, `review`, `human-review`, `drop` refuse on `anyRunning`. Changing an earlier stage's config replaces the running one (`rewriteFrom`), the runner's later writes 404 and its calls are wasted. The UI's `busy` and the version check prevent it from the app; a request without the header (scripts) doesn't. One rule for "a structural change while a stage runs" (in the middleware of 10). check (small).
15. **itemTiming's global tracker is reset by an older item** (level 1 check, confirmed) — itemTiming.ts 30–36: `timed` sets `current` and its `finally` sets it to `null` unconditionally. After Stop (or leaving the project) the aborted item keeps running (image work isn't cancellable, stageRunner 58); if a new run's item starts meanwhile, the old `finally` nulls the new item's tracker, and its calls and images go uncounted (runTimes.ts `ranAnew` 48: an LLM item with `callsCached` 0 counts as really run, so a cached item would wrongly enter the run-time estimate; a rasterize item with `images` 0 counts as cached and drops out). Fix: `if (current === counts) current = null`. certain (race), small impact.
16. **Leaving a running project keeps the stage "running" for up to `STALE_MS`** — ProjectView 132 aborts only; `runPlan` returns without a word to the Worker (deliberately: `stop` would delete the outputs). Coming back at once, the stage shows running elsewhere and `start` refuses ("it is running") until the heartbeat is 3 min old. A "release" (finish as failed "interrupted", outputs kept) on abort-by-leaving, or `start` accepting a stage whose last heartbeat came from the same tab (group 05's run token), would remove the wait. check (design; cf. docs/database.md "Interrupted runs").
17. **Runners load all content before `start`, also when the stage is then reused** — musicInputs + each runner fetch every layout, extraction, review (runReview 51–52, runApplyReview 90–104, runBuildMei 16) before `runPlan` learns from `start` that a done stage with the same key exists (the "re-run with nothing changed" path, meant to be fast). ## For level 3
- **The web app has no "pipeline inputs" module.** What each stage reads is found by ~25 lookups spread over step modules, runners, finishers and the UI's artifacts; `musicInputs.ts` and `engraveSources` are two partial attempts. A level 3 component "stage inputs" (pure lookups over `ApiStage[]` + producer table, then fetching) would serve runners, finishers, `carriedInputs` and the artifacts alike; it pairs with group 05's shared `STEP_KINDS`.
- **The run protocol between browser and Worker is implicit:** no run identity (group 05, 10), unconditional status updates (13), the stale wait after leaving (16), mixed versions on retry (9). A level 3 look at the stage's lifecycle as one state machine (start → outputs → finish/stop/release, with a run id) would settle them together.
- **Route metadata in two places** (versions.ts vs the routes; also the request log's step lookup in `entry`): the Worker's routing could carry per-route facts (lock class, needs a stage) — relevant to groups 07 (errors) and 15 (projects' routes in index.ts).
- **D1 limits**: per-statement parameters (group 05) and per-invocation statements (12) — one Worker-wide decision (`json_each` for lists), and a test D1 that enforces them.

## Patterns
- **A lookup re-derived at each use** (~25 "latest stage of X", 2 input lists for review, 8 step lists): each runner and finisher written from the previous one's example, copying the lookup instead of moving it to a shared place; `musicInputs` was the moment it was noticed ("In one place, so that every stage finds them the same way") but only for three stages.
- **A small helper written per file** (5 JSON-bytes helpers, 8 unusable blocks, 4 preload blocks, 5 start prologues): the second stage's runner copied the first's local helper rather than lifting it into api.ts/llm.ts/stageRunner.ts; finishers exporting helpers that editors then import shows the lift happened to the nearest file, not the right one.
- **A swallowed error with a consequence** (2: `markUnusable().catch(() => {})`, errors before `start` only in the panel): `.catch(() => {})` used where "best effort" was meant, without checking what follows when it fails.
- **State carried in closures only filled by fresh work** (4 notes on resume): the resume path (skip recorded items) added to `runPlan` after the runners' notes were written; only the runners that needed recorded content for other reasons got right notes.
- **Route facts restated apart from the routes** (lock table, 12 copies of the prologue, one route missing the `anyRunning` guard): routes added one by one, each copying its neighbour's guards, the lock table updated by hand.
- **Concurrency of the run not designed** (4: double start, version mix on retry, global item tracker, the stale wait): the protocol designed for one tab running one stage to its end; Stop, leaving, retries and app updates added later around it.
- **Platform limits invisible locally** (1: statements per invocation, with group 05's parameters): SQLite in tests and on the desktop doesn't enforce D1's limits.
