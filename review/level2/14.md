Files: apps/worker/src/activity.ts, activeTime.ts, runTimes.ts, projectStats.ts, failures.ts (the Usage half, passed on by 05 and 13); apps/web/src/runTimes.ts, usage.ts, time.ts, chart.ts, effort.ts (passed on by 12), StatsPage.tsx (tabs, the fetch pattern), UsageTab.tsx, RunTimesTab.tsx, EffortTab.tsx, TimeChart.tsx, statsParts.tsx, ProjectFilter.tsx (`FinishedProjectsFilter`), api.ts (the four stats types, 417–482). Read beside them: core pageSelection.ts, worker pipeline.ts (start 468–520, `manual_saves` 600), web costs.ts (the calendar and labels it lends), the run*.ts `pageCount`s, index.test.ts 1515–1650, docs/statistics.md, docs/style.md 230.

## Map

- **Worker, four read-only routes, each one `db.batch` of SQL + a little JS:**
  - `GET /api/activity` (activity.ts): every call (start→end), stage start/end/last heartbeat, output, project creation, and `manual_saves` (gaps filled by activeTime.ts) floored to quarters → `[project, quarterMs][]` sorted, plus every project (picker).
  - `GET /api/project-stats` (projectStats.ts): projects {created, deleted, finished}; distinct (PDF, page) of done `rasterize` stages.
  - `GET /api/failures` (failures.ts): LLM calls per config × quarter × reason (`ok`, the four statuses, `error_kind`, `interrupted` past `ZOMBIE_MS`), fake provider out.
  - `GET /api/run-times` (runTimes.ts): finished projects (pages from their pipeline's rasterize config, final pipeline), their started stages (manual flag, active quarters, `replaces_stage_id`, item counts by kind from the item string), timed items `[stage, item, ms, calls, cached, images, cached]`, used configs, `RECIPE`.
  - activeTime.ts: `QUARTER_MS`, `filledQuarters`, `manualQuarters` (shared by activity and run-times). `manual_saves.quarter` is written by pipeline.ts 600 (ms, floored there).
- **Web:** api.ts restates the four shapes (`ActivityData`, `ProjectStats`, `FailureData`, `RunTimeData`); pure functions in usage.ts (Usage), runTimes.ts (Run times, also `duration` and `QUARTER_MS`), effort.ts (Effort, on run-times data); components UsageTab, RunTimesTab, EffortTab, StatsPage (tab bar + the whole Costs tab), statsParts (`Picker`, `StatHead`, `ProjectChecks`, `ChartModes`), TimeChart + chart.ts (`ticks`), ProjectFilter. The calendar (ranges, buckets, labels) and the notes/step titles come from **costs.ts**; dates from time.ts.
- **Contracts:** (a) quarters are ms floored to 15 min on the Worker, counted `/4` and by local day in the browser; (b) the item string (`""`, `p3`, `p3/s2`) parsed by SQL `LIKE` (runTimes.ts 34–36) and by web `kindOf` (runTimes.ts 45); (c) "finished" = last pipeline entry done; (d) the reason keys of failures.ts's CASE ↔ usage.ts `REASONS`; (e) every list arrives sorted by time (UsageTab takes element 0 as "first": activity 54, projectStats `ORDER BY created_at`, failures `ORDER BY t`); (f) `stages.page_count` as each runner reports it is the Run times' denominator.

## Findings

1. **runTimes.ts `duration` rounds a rest of 60** — web runTimes.ts 156–160: for 119.6 s it says "1 min 60 s" (`whole` floored, `rest` rounded), 3599.6 s "59 min 60 s", 59.6 s "60 s". Also its format ("3 min 12 s", spaces) breaks docs/style.md 230 ("8s", "3min 12s", "1h 5min"), which time.ts `duration` (seconds, 27–33) follows — with its own quirks ("3min 0s", "1h 0min", no days). A third and fourth format: testResult.ts 6 (`toFixed(1)} s`), web pipeline.ts 154 (card seconds via time.ts). One `duration(ms)` in time.ts (round to whole seconds first, then split; sub-second precision as an option for the per-page times, which are often < 1 s), used by StageCard, StageDetails, RunTimesTab, EffortTab, testResult. **certain** (bug + duplicate); tests lack the rounding edges.
2. **Run times' manual rows count an edited stage twice, Effort's once** — web runTimes.ts 94–99 `manualPerPage`: Σ active quarters of every *done* manual stage of the step ÷ Σ their `pageCount`. An edit (pipeline.ts 763) copies `page_count` into a new stage and the old one stays done, so one Fix layout edited once is two stages, its pages counted twice: the per-page time halves with every edit. Dropped (re-run) manual stages count too. effort.ts 35–48 walks the same chain (`replacesStageId`) into one piece of work over the project's pages, final pipeline only. The two tabs show a "Fix layout per page" for the same selection that disagree. Arithmetic **certain**; whether Run times should take Effort's rule (or show no manual rows, leaving them to Effort) is the owner's: **check**.
3. **`page_count` means different pages in different stages, and Run times divides by it** — extract reports the pages *with systems* (runExtract.ts 109), review and apply_review *all* layout pages (runReview.ts 125, runApplyReview.ts 224), rasterize/layout/analyze all selected pages, fix_metadata/fix_observations/human_review copy their predecessor's, fix_mei build_mei's, build_mei counts page images (runBuildMei.ts 22). A score with a cover page: extract's time per page is over 11 pages, review's over 12, and `estimatePerPage` (runTimes.ts 143–147) adds them up as if per the same page. Decide what a stage's `pageCount` is (the selected pages, everywhere; it is "the pages its inputs cover" in pipeline.ts 26) and set it in one place (a `pageCountOf(pipeline)` helper) — **certain** (inconsistency), small numeric effect.
4. **The quarter of an hour, six copies, and the floor four times** — Worker activeTime.ts 7 `QUARTER_MS`, costs.ts 20 `BUCKET_SECONDS` (comment admits it), web runTimes.ts 91 `QUARTER_MS` (imported by effort.ts 16), usage.ts 54/57 and runTimes.ts 63 `/ 4`, scripts/seedStats.ts 353; `Math.floor(t / Q) * Q` in activity.ts 28, 34, pipeline.ts 600, seedStats 355–356, and in SQL ×4 (finding 5). It is a contract between the Worker and the browser (quarters fit every time zone): `QUARTER_MS` and `quarterOf(ms)` in `@score3ly/core` (it runs everywhere and imports nothing), used by both sides and the seed; the SQL fragment built from it. **certain**.
5. **The Worker's statistics routes repeat their SQL and helpers** — (a) "finished" subquery ×3: projectStats.ts 16, runTimes.ts 21–23, costs.ts 81; (b) the bucket expression `(CAST(strftime('%s', c.started_at) …) / 900) * 900` ×4: failures.ts 21, costs.ts 43/54/65; (c) the rasterize-config page parse ×3: runTimes.ts 108–114, projectStats.ts 22–27, costs.ts 93–100; (d) the configs `SELECT id, name, provider, model_id, model_string, family, created_at, deleted_at` + `{ id, name, model: resolvedModel(m).model, ...modelGroupOf(m), createdAt, deletedAt }` ×3: failures.ts 36/44, runTimes.ts 44/101–103, costs.ts 85/129–138 (with `effort`). One `apps/worker/src/statsSql.ts` (`FINISHED`, `bucketOf(column)`, `rasterizedPages(configJson)`, `CONFIG_COLUMNS` + `configSummary(row)`), imported by the four routes. Besides, all four import `modelGroupOf`/`resolvedModel`/`ModelConfigRow` from llmRoutes.ts (1300 lines of routes) — those belong with the model names (llm/models.ts or group 12's names module). **certain**.
6. **Three rules for "a project's pages"** — costs.ts 89–100: the union of every *started* rasterize stage's selection, per project; projectStats.ts 19–27: every *done* rasterize stage, per PDF; runTimes.ts 28: the rasterize in the *final pipeline* (subquery without `LIMIT 1`, fine while there is one). Effort divides by the last, Costs by the first; `stages.page_count` exists beside them. Docs give each its reason (statistics.md 65, 80), so mostly on purpose; a failed rasterize counting in Costs' pages but not in Usage's is not explained. **check** (meaning), folds into 5(c).
7. **Run-times fields sent and never read; stale comments** — the web reads neither `stages[].kept` (an `EXISTS` subquery per stage, runTimes.ts 33), `createdAt` nor `finishedAt` (only the tests fill them: runTimes.test.ts 16–20, effort.test.ts 15, where `kept: false` reads as if it mattered but effort.ts uses pipeline membership). api.ts 459 "manual: timed from its creation to its finish" and index.test.ts 1574 the same: stale since manual stages count active quarters. Drop the three fields (or use `kept` in effort.ts instead of the pipeline walk, one of the two) and fix the comments. **certain**.
8. **Step facts restated by the statistics** — Worker runTimes.ts 16 `MANUAL` (and its `manual` SQL list 24 that also holds `ingest`, a misleading name); web runTimes.ts 24–42 `STEPS` (name clash with steps.ts), `MANUAL`, `LLM`; effort.ts 18 `MANUAL`; costs.ts 171 `STEPS` (the LLM steps again); costs.ts 167–169 `STEP_TITLES`, dead (all three steps are in steps.ts with the same titles; its comment is stale). Covered by group 05 #6 (`STEP_KINDS`/`RECIPE` in core) and group 06 #18; this group adds the costs.ts copies and the dead map. **certain**.
9. **Usage's reasons: the contract with the recorder, unpinned** — failures.ts 22–27 maps statuses and `error_kind` to reason keys, usage.ts 96–113 labels them, unknown keys shown raw (131). What makes the reasons wrong is upstream and already found: a live call 15–60 min old shown as "Interrupted" (`ZOMBIE_MS` 15 min vs 60-min timeouts, group 13 #3; failures.ts 11 is the second copy); "Aborted" lost to another kind (group 08 #8); the same event a different kind per provider (group 09 #4); "Wrong model" under `unexpected_model` here, `wrong_model` in Costs (group 13 #7). Add to group 13 #7's shared outcome vocabulary: the reason union typed in core, `FailureData.points`' reason typed by it, `REASONS` a `Record<Reason, string>` so a new kind fails the typecheck. **certain**.
10. **web costs.ts is also the statistics' calendar and label kit** — ranges, buckets, `axisLabel`/`bucketTitle` (8–112) used by UsageTab and ProjectFilter (`createdBefore`); `deletedNote`/`endedNote`/`stepTitle` used by runTimes.ts, effort.ts, UsageTab, ProjectFilter. `MONTHS` (89) duplicates time.ts 11, and `dateOf` (196) is time.ts `shortDate` always with the year. Split: `calendar.ts` (ranges, buckets, labels; `MONTHS` and a `fullDate` from time.ts) and the notes beside `shortDate` in time.ts; costs.ts keeps the cost groupings. **certain** (structure; level 1's check confirmed).
11. **The tabs' shells repeat themselves** — CostsTab (StatsPage 86–100), UsageTab 17–37, RunTimesTab 12–28, EffortTab 12–27: the same `useState` data/error + `useEffect` fetch with a fixed message (the error itself dropped: group 07). 17. **The item string's shape parsed in three places** — runTimes.ts 34–36 (SQL `LIKE '%/%'`), web runTimes.ts 45 `kindOf`, besides the writers (rasterize.ts 70 `pageItem`, musicInputs.ts 67 inline `p…/s…`) and scripts/callPlaces (group 15). `itemOf(page, system?)`/`itemKind(item)` in core beside `parsePages`. **check** (goes with groups 15, 17).

## For level 3

- **No shared types for the statistics' API** (group 05's general point): four more `Api*` mirrors cast from `res.json()`; the Worker's tests and the web's tests each build the shapes by hand, so dead fields (7) and stale comments survive on both. The statistics are a natural first case for `packages/core/src/api/` since they are read-only.
- **The statistics re-derive meaning from columns written elsewhere** — `status`/`error_kind`/`started_at` (the recorder, groups 08, 09, 13), `page_count` (each runner, group 06: 3), `item` (runners, 17), `manual_saves` (pipeline.ts), `replaces_stage_id` (edits). No module owns "what a row means for the statistics"; each SQL query restates it. The component review should pin the recorder's rows to what the tabs count (group 13's suggestion, extended to `page_count` and items).
- **A formatting module for the web** (time.ts grown): durations (one), dates (`shortDate`, `fullDate`, `MONTHS`), percentages, hours; with money.ts beside it. Groups 13 and 22 point the same way (`dollars`, `plural`).
- **Step facts in core** (group 05 #6) would remove four step lists here.

## Patterns

- **A constant or helper written again in the next module of the same feature** (quarter ×6, floor ×4+4 SQL, finished subquery ×3, bucket SQL ×4, pages parse ×3, config select/mapping ×3, `MONTHS`/`dateOf`, `value`, `selected`, tab shells ×4, group-by spread ×3): ~30. Cause: each tab was built in its own session, copying the previous tab's route or component rather than lifting the shared piece once a second user appeared.
- **Step lists restated** (5 in this group): written where needed instead of derived from the step definitions; one (`STEP_TITLES`) outlived the reason for it.
- **Stale comments and dead fields after a redesign** (manual stages timed by span → by active quarters; the review step built): 4 comments, 3 fields, 1 dead condition. Cause: the redesign changed the computation and its tests but not the shape's comments or the fields nobody reads any more; nothing flags an unread response field.
- **Two formats/rules for one notion** (durations ×4, "a project's pages" ×3, a stage's `pageCount` ×4 meanings, manual time per page ×2): 4 notions. Cause: each tab/runner decided locally what the notion meant, against the docs where they spoke (style.md's duration format) and without them where they didn't.
- **Rounding/edge bugs in hand-written formatters** (`duration` 60 s, `ago` 7d, `createdBefore` 29 days): 3. Cause: tests of the happy values only.
- **Small UI races/leaks** (TimeChart tap start): 1.
