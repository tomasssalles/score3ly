# Level 2, group 17: Score structure and linking

## Map
- **notation score.ts** (202): `buildScore(systems, pieceStarts)`: pieces, every voice parsed into runs, stretch lengths, the piece's staves/voices, measures from the stretch classes and their numbering (0 or 1); `stretchOffsets`, `tstamp`. Read by mei.ts, and in the web app by runReview, runApplyReview (review's score view), engrave.ts `loadScore`, transcription.ts `scoreOf`.
- **notation spans.ts** (191): `SpanTracker` (marks with two ends within a system, open/closed), `OpenMark`/`ClosedMark`, `describeMark`, `markName`, `sameMark`. Used by lens.ts `checkSystem` (per system), links.ts (closures), scoreChecks.ts (names).
- **notation links.ts** (145): `repeatStructure(piece)` (go-backs, endings and their neighbours, warnings) and `systemLinks(systems, pieceStarts)` (sentences per system for `review`/`apply_review`).
- **notation scoreChecks.ts** (83): `checkScore(systems, pieceStarts)`: piece ends (measure, marks, ending), repeat warnings (from links.ts), courtesy signatures. Called at the end of runExtract and runApplyReview.
- **web linking.ts**: a different layer: links the *observations'* spans (ottavas, endings) across pages, and builds each system's hints for `extract`. Only runExtract uses it.
- **web musicInputs.ts**: what extract/review/apply_review read: the lookups, the systems numbered across pages (via fixLayout `firstNumbers`), `bounds` (via extract.ts `pieceBounds`), `labelsOf`, `placeBox`, `straight`.
- **web fixLayout.ts `firstNumbers`, humanReview.ts `placedSystems`:** two ways to number systems top to bottom across pages.
- **Contracts:** (a) the piece starts (`StoredPieces`, written only through analyze.ts `piecesOf`, always with 1) ↔ four splitters; (b) the chain "check every system from its piece's start" (web, three copies) ↔ what `checkScore`/`systemLinks` take; (c) the ending and repeat structure read by lens.ts (strict), links.ts and mei.ts; (d) the system number ↔ the item `p<page>/s<index>` ↔ the stored `extraction.system`; (e) code-issue question texts ↔ `isNewCodeIssue` (identity by text and boxes).

## Findings

1. **The check chain is written five times.** "Check the systems in order, each from the state the one before left, a piece starting afresh": runExtract.ts 75–97 (`stateBefore`/`stateAfter`, lazy and memoized), runReview.ts 57–68 (a loop), applyReview.ts 199–211 `checkAll` (exported, tested, with `pieceStart` passed in as a parameter although it is notation's own export), links.test.ts 33 `linked`, scoreChecks.test.ts 34 `checked`. The check context `{ system, stretches: barLines.length + 1, firstOfPiece: bounds(n).first, images: labelsOf(s) }` is built three times (runExtract 76 `contextOf`, runReview 63, runApplyReview 126–132 `toCheck`), and the reset condition `bounds(n).first || !byNumber.has(n - 1)` three times. Then the results are re-mapped by hand into `LinkedSystem`/`CheckedScoreSystem` (runReview 66, runApplyReview 234, 385; runExtract 183). Shared: `checkSystems(answers, contexts)` in notation beside `checkScore`, returning `{ number } & CheckedSystem` in order or the first problem; its output goes straight into `checkScore`, `systemLinks` and (with the parsed `voices` it already holds) `buildScore`, which would stop parsing every voice again (group 16). `contextOf(s)` joins `labelsOf` in musicInputs. runExtract's recursion becomes the same call over the systems stored so far. **certain**.
2. **Piece splitting four ways.** score.ts 53–58 (a `Set` plus the first system), links.ts 106–111 and scoreChecks.ts 16–21 (`pieceStarts.includes`, identical), web extract.ts 63 `pieceBounds` (first/last), plus finding 1's reset condition. They agree because `piecesOf` (analyze.ts 42) always adds system 1 and the systems are numbered without gaps; score.ts alone would survive a `pieces` without 1. Shared: `splitPieces<T extends { number: number }>(systems, starts): T[][]` in notation (score.ts), used by all three notation files; `checkScore` and `systemLinks` could then take pieces. **certain**.
3. **Three readers of the ending/repeat structure disagree on "none" stretches and on a doubly reported start repeat.** lens.ts 219–232 checks endings over *all* stretches (a "none" stretch inside an ending must carry it); links.ts 30 drops "none" stretches before following endings; mei.ts `endingOf` (426–431) reads segments. An ending whose `endsHere` is on a "none" stretch (e.g. a courtesy stretch after the system's last bar line, which lens.ts 222 forces to carry an ending that runs on) passes lens.ts, but links.ts never sees the end: `next` stays −1, the following ending isn't linked, both get "stands alone" warnings and review's links omit the pair. Likewise a start repeat given both as the last stretch's `rightBarLine` and as the next system's `startRepeat`: links.ts 45/64 warns "Two start repeats", mei.ts 990–992 ORs them into one `rptstart`; the prompt (extract.ts 155, 172) says nothing about which to use. One walk over the piece's stretches (in notation, with "none" stretches kept for endings) for both links.ts and the MEI's endings, and a sentence in the prompt. **check** (needs those answers from a model; mechanism certain).
4. **"The first stretch that is part of a measure"** twice: links.ts 92 `firstMeasureStretch` = mei.ts 1022 `firstStretch`; scoreChecks.ts 63 computes the trailing counterpart (with `findIndex` called twice in one expression). Export one from score.ts (or lens.ts) beside a `trailingNoneStretches`. **certain**.
5. **System numbering across pages computed in six places,** with different filters: musicInputs.ts 55–68 (layout outputs with content and an image recipe, sorted, `firstNumbers`); runAnalyze.ts 66–75 (a copy of musicInputs 40–59, then `firstNumbers`); ArtifactView.tsx 229 and LayoutEditor.tsx 132 (`firstNumbers`, the latter counting 0 for a page without a loaded layout); humanReview.ts 146 `placedSystems` (its own counter and sort), fed by finishHumanReview.ts 17–23 (its own layout lookup, no image filter) and ExtractionView.tsx 173. They agree while every page has one layout output, which layout and fix_layout guarantee; the filters differ only in theory. Also runReview 75 and runApplyReview 111 map `MusicSystem` to `PlacedSystem` by hand though it already is one structurally. Shared: one pure, tested `numberSystems(pages: { page, systems }[]) → { number, page, item, layout, pageIndex }[]` in layout.ts; `firstNumbers` and `placedSystems` fold into it; the lookup part goes with group 06's "latest stage of step X". **certain** (duplication), divergence **dropped** (not reachable today).
6. **The system item `p<page>/s<index>` written once, parsed twice, and a second source for the system's number.** Written in musicInputs.ts 67; parsed with `split("/s")[1] ?? 1` in engrave.ts 130 and steps.ts 369 (a malformed item silently becomes system 1 or NaN). engrave.ts `loadScore` takes the number from the stored `extraction.system` and the layout from the item's index: two facts that must agree, kept apart. `systemItem(page, index)`/`systemOfItem(item)` beside rasterize.ts `pageItem`/`pageOfItem` (or in core, with group 14 #17's `itemOf`/`itemKind`). **certain**.
7. **Three types for "a checked system", and a type-only import cycle.** lens.ts 93 `CheckedSystem`, scoreChecks.ts 11 `CheckedScoreSystem` (number, answer, state), links.ts 97 `LinkedSystem` (+ closed); links.ts imports its type from scoreChecks.ts, which imports `repeatStructure` from links.ts. Define once in lens.ts as `{ number } & CheckedSystem` (finding 1's output) and let both take it. **certain**.
8. **`ScoreSystemInput` built by hand four times** — runReview.ts 71, runApplyReview.ts 136, engrave.ts 131, transcription.ts 76 (`{ number, page, box: layout.box, barLines: layout.barLines, answer }`). A `scoreInput(system, answer)` helper next to the numbering (5), or `buildScore` taking `{ number, page, layout, answer }`. **certain** (minor).
9. **Dead parts of `Score`:** `pieceOf` (score.ts 47, 79, 84) is used nowhere; `measureLengthOf` (195) likewise (group 16). **certain**.
10. **Code-issue texts duplicated where the text is an identity.** scoreChecks.ts 47 writes `Where does this ${markName} end?` by hand; spans.ts 56 has it as private `whereEnds`. `isNewCodeIssue` (applyReview.ts 313–316) recognizes a code issue by its question text and boxes, so the wording is part of a stored identity: a drift re-raises issues already answered. Export `whereEnds`/`whereStarts` from spans.ts. Also the ending's name written twice in links.ts (80, 120). **certain**.
11. **links.ts 131 dedups crossing marks by `${m.kind}/${JSON.stringify(m)}`** (property-order dependent, `kind` twice) while 129 already defines a mark's identity (`sameMark` + `from` + `fromStretch`). Use that. **certain** (minor).
12. **scoreChecks.ts 53–55 `repeats`** is a one-line wrapper. **certain** (trivial).
13. **web linking.ts ignores pieces.** `linkSpans` (44–82) follows an ottava or ending open at a page's end onto the next page's open-start item of the same kind and staff, even when a piece starts on that page; the hint then spans the boundary, against "nothing carries over a piece's boundary" (overview §6). Needs a model reporting both ends open, so rare. Pass the piece starts and stop at them. **check**.
14. **musicInputs.ts mixes fetching with pure logic:** numbering, `bounds`, `labelsOf`, `placeBox` are pure and untested (the file has no test because of `fetch`). Split with finding 5. **certain**.

## For level 3
- **notation lacks the "whole score" entry points the web app needs:** a `checkSystems` chain (1), `splitPieces` (2), one checked-system type (7). With them, runExtract, runReview and runApplyReview stop restating the chain and the shapes; the review/apply-review code gets thinner (group 18).
- **Structure readers in notation should share one walk** over a piece's stretches (endings, repeats, first measure stretch): lens.ts, links.ts, mei.ts each walk it with slightly different rules (3, 4). Same lesson as group 16's measure counting.
- **System identity has three representations** (the number, the item string, the page + index in the layout), converted ad hoc in the web app (5, 6). A small module in web (numbering + item) would be the single place; core if the Worker's statistics need the item's shape too (group 14).
- **Code-issue question texts are identities** (10): group 18 should decide whether identity by text is wanted, or whether code issues get a stable kind.

## Patterns
- **A chain or loop restated by each stage instead of shared** (check chain ×5, check context ×3, reset condition ×3, `ScoreSystemInput` ×4): 3 findings. Likely cause: each music stage written by copying the previous stage's setup; `checkAll` was added to applyReview.ts for its own needs and never moved down to notation or adopted by the others.
- **One rule split into near-identical helpers** (piece splitting ×4, first measure stretch ×2, system numbering ×6, item parsing ×2): 4 findings. Likely cause: a helper written private to its file (`firstMeasureStretch`, `placedSystems`) because the existing one lived in a module that felt unrelated (mei.ts, fixLayout.ts).
- **Readers of one structure with diverging rules** (endings over "none" stretches, start repeats): 1 finding, the only bug-shaped one. Likely cause: links.ts written for its own purpose with a filter that suited go-backs, then reused for endings.
- **Types restated per module, with a cycle** (checked system ×3): 1. Likely cause: each new file defined the shape it needed next to its function.
- **Text duplicated where it is an identity** (question text): 1. Likely cause: the text treated as wording, while `isNewCodeIssue` made it a key.
- **Dead exports** (`pieceOf`, `measureLengthOf`): 1. Likely cause: built ahead of a use that went elsewhere.
- **Pure logic inside a fetching module, untested** (musicInputs): 1.
