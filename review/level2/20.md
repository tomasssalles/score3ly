# Level 2, group 20: Analyze and its forms

## Map
- **prompts analyze.ts** (701 lines): the texts (page call, whole-score call), the stored-ish types (`Metadata`, `PageObservations`, `ScoreObservations`, `Place`, `Staff`, item types), flat ↔ nested conversion (`flatMetadata`/`nestedMetadata`, `flatObservations`/`nestedObservation(s)`, `nestedScore`), `withIds` ("p7-3"), the two schemas, `shapeProblem` (group 10 #2), the checks (`placeProblem`, `staffProblem`, `observationsProblem`, `stavesProblem` (exported, used by web), `metadataProblem`, `checkPageAnswer`, `checkScoreAnswer`), its own place text `placeName`.
- **web analyze.ts**: the stored types (`PageAnalysis`, `Stored<T>`, `StoredObservations`, `StoredPieces`, unused `StoredMetadata`), `piecesOf`, stage key, `pageResultsForScore`/`pageItems` (both via `withIds`), `placeOrder`/`firstPlace` (score order), `combineObservations` (applies the whole-score answer), `placeLabel`, `analyzeNote`, `ShownConfidence` + `CONFIDENCE_SYMBOLS`.
- **runAnalyze.ts**: per-page calls → `checkPageAnswer` → `analysis` outputs; one whole-score call → `checkScoreAnswer` → `combineObservations` → `stavesProblem` per page (here, not in prompts) → `metadata`, `observations`, `pieces` outputs.
- **fixMetadata.ts / MetadataView.tsx / finishFixMetadata.ts**: `ShownMetadata` (the stored form of `fix_metadata`: `analyze`'s plus `comments`, `confirmed`, nullable `page`/`confidence`), rows ↔ stored, `pieceProblem` (unique system), `changedFields` (multiset: metadata has no ids), the form, finishing (metadata + pieces). `normalizeMetadata` is also the reader of both forms of metadata for the MEI header (engrave.ts `meiMetadata`).
- **fixObservations.ts / ObservationsView.tsx / finishFixObservations.ts**: `ObsRow` (one row type for every list), rows ↔ `StoredObservations` (rebuilt per list: stray fields dropped), pickers' positions, staff add/remove, `obsProblem`/`pagesProblem` (`stavesProblem` again), `changedItems` (by id).
- **fieldList.tsx**: `useFieldList` (load, one edit at a time, commit, save chain, unmount save, module `saved` cache), `fieldActions`, `FieldStrip`, `Picker`, `Confidence`.
- **AnalysisView.tsx**: 12-line dispatch. **CheckList.tsx**: not part of this group at all (the statistics' and settings' filter list) → group 22.

Contracts: (a) the flat answer ↔ the nested lists (one module, round-trips both ways, tested). (b) `withIds` numbering ↔ `pageItems` ↔ `combineObservations` (same function, consistent). (c) the stored metadata: two writers (`runAnalyze`: `ScoreMetadata`; `fix_metadata`: `ShownMetadata`), every reader goes through `normalizeMetadata` (MetadataView, finishFixMetadata, engrave). (d) the stored observations: two writers, one type `StoredObservations`, readers: linking.ts (extract's hints), ObservationsView, finishFixObservations. (e) the rules on items: what `analyze`'s checks accept ↔ what the forms let a person save ↔ what linking/extract/MEI assume (findings 3–5). (f) `pieces`: `piecesOf` at both writers (group 17 contract a).

## Findings
1. **An item added in a form can vanish while it is being typed: the reload after an earlier save overwrites the rows.** fieldList.tsx 36–46: the load effect re-runs on every change of `source.sha256`, and the form's own sha changes after each save (steps.ts 310/341 `own ?? parent`, refreshed by `onEdited` → ProjectView refresh). ArtifactView keys the view by `artifact.id` (62), so it doesn't remount: the effect sets `rows` to `saved.get(stageId)`, the rows as last saved. Sequence: confirm or edit a field (save → `recordOutputs` → refresh GET), click "+" and start typing before the GET answers; the refresh replaces `rows` with the saved ones, which lack the new row, while `editing.index` still points past their end: the editor disappears from the list, and the next `commit` (`current.map`, 70) finds no row at that index, so the typed field is dropped and the rows saved without it. Two round trips on a phone's network is a realistic window. Fix: don't reload rows that came from this form (load once per stage; the `saved` cache and the effect's dependency are the same problem as group 19 #3), or keep `editing`'s added row when reloading. **certain** (mechanism), **check** (reproduce by hand).
2. **The unmount save restates `commit`** — fieldList.tsx 154–164 repeats 61–71's rules (empty, problem, unchanged, confirm) without the state updates; a change to one rule must be made twice. A pure `committed(rows, edit, rules): { rows } | { problem }` used by both. Also the "shift an index after a removal" arithmetic three times (84, 92 `after`, 136–139). The save chain is group 19 #4's. **certain**.
3. **What `analyze` accepts and what the forms refuse differ, so a person can't save an item the model gave without changing it.** (a) Spans that end before they start: refused by `obsProblem` (fixObservations.ts 325), accepted by `observationsProblem` (prompts analyze.ts 497–513; level 1's 501/503). linking.ts then builds a span with `to` before `from`. (b) Two pieces at one system: refused by `pieceProblem` (fixMetadata.ts 108), accepted by `metadataProblem` (analyze.ts 595). `piecesOf` dedups, but the MEI builder reads the titles twice, differently: mei.ts 115 `new Map(...)` keeps the *last* title for the header's `work`, 384 `find` the *first* for the `mdiv` label, so the header and the music name one piece differently. Fix: the checks in prompts refuse both (a span's order needs `placeOrder`, finding 6), so the rules live in one place and the forms call them. **certain**.
4. **A piece read on a page that doesn't hold its system makes the page's answer unusable, and the prompt doesn't say so.** `checkPageAnswer` checks pieces against the page's own systems only (`metadataProblem` 591 with `context.systems` = the page's, runAnalyze 199–200), but the shared prompt says only "piece: … the one where the piece starts" (analyze.ts 128) and the page text gives this page's system numbers (159–165). A contents page or a title page that lists the movements ("No. 2 … p. 5") invites a piece with a system the model can't know; the whole page answer is then refused (retried, at a cost). Either tell the page call "only pieces that start on this page's systems", or drop pieces whose system isn't on the page instead of refusing the answer. Related: a piece's `page` means "where it was read" in `analyze` (the score prompt: "the page it was read on") but "its system's page" in `fix_metadata` (fixMetadata.ts 26–27, `withSystem` 199), so a model's piece can show "p. 1" and jump to the system's page as soon as it is moved. **check** (how often models do it; the meaning of a piece's page is for the project owner).
5. **"startEndRepeat" in the observations, "bothRepeats" in the lens** — prompts analyze.ts 19/141/214, fixObservations.ts 170; lens.ts 14, extract.ts 172. linking.ts 119 passes `b.kind` verbatim into `extract`'s hints, so the model reads one name in the hints and must write the other. Rename the observation's kind to the lens's (prompt text and schema change: request keys change, re-paid once) or translate in `systemHints`. **certain** (two names), **check** (whether it confuses a model: probably not).
6. **Score order and place names live in the web, but the prompts' checks need them** — `placeOrder`/`firstPlace` (web analyze.ts 83–96) sort the lists and drive `obsProblem`'s order check; the prompts can't use them (finding 3a). Place labels four ways: prompts `placeName` ("the start of system 17", analyze.ts 467, in unusable reasons), web `placeLabel` ("system 17, start"), fixObservations `positionLabel` (the same without "system n, ", 218–220), linking `placeFor` (in the lens's terms, on purpose). Shared: `placeOrder`, `placeLabel` (built on `positionLabel`) and `samePlace` beside `Place` in prompts analyze.ts (or a small `places.ts` there); `placeName` replaced by `placeLabel` (unusable reasons only: no request key changes). Also `positionsIn(…, barLinesOnly)` (fixObservations.ts 208) restates `BAR_LINE_PLACES`, which fixObservations imports and never uses (6): filter by it. **certain**.
7. **The whole-score check is in three places, the last untested** — `checkScoreAnswer` (prompts), `combineObservations` (web analyze.ts), then the staves check on the combined pages inline in runAnalyze 155–164 (with its own `markUnusable`). The prompts' comment (641) says the staves are checked "on the pages as corrected", which happens only in runAnalyze; analyze.test.ts 106 shows the disagreement "as the run checks" but no test runs the check. One pure `scoreObservations(pages, json, context): StoredObservations & {metadata…} | Problem` in web analyze.ts (check, combine, staves), tested; runAnalyze calls it once. Also, `combineObservations` is part of `analyze`'s result but changing it raises neither `ANALYZE_PROMPT_VERSION` (its comment names "the checks") nor necessarily `ANALYZE_VERSION`; one comment saying which version covers what. **certain** (structure), **check** (versioning comment).
8. **Conflicting edits in the whole-score answer are resolved silently** — the same id corrected twice (Map, last wins: analyze.ts web 103) or corrected and removed (removal wins, 108); `checkScoreAnswer` doesn't refuse either (level 1's 650–674). Deterministic and harmless; a refusal would cost a paid retry for nothing. Keep, with a comment saying so. **certain** (behaviour), no fix needed.
9. **The note's piece count isn't the stored pieces'** — runAnalyze 218/227/236 count `answer.metadata.pieces.length`, while `pieces` stores `piecesOf(...)` (system 1 added, duplicates merged): one named piece starting at system 5 gives "12 pages" for two pieces; two titles at one system give "2 pieces" for one. Count `piecesOf(answer.metadata).length`. Folds into the three identical blocks (213–239, one loop over `[type, value]`, level 1) and group 06 #3 (resumed runs). **certain** (minor).
10. **Confidence shown three ways** — `shownConfidence` twice, identical (fixMetadata.ts 50, fixObservations.ts 143), and linking.ts `stateOf` (14), the same value but with "no confidence" read as confirmed; `ShownConfidence` = `ItemState` (analyze.ts 138, linking.ts 12). They agree only because the forms make every user-added item `confirmed: true` and forbid unconfirming it (`fieldActions` 197). One `ShownConfidence` + `shownConfidence(item)` in web analyze.ts with `stateOf`'s rule, used by both forms, `Confidence` and linking. **certain**.
11. **The two forms' views are one view written twice** — list shell (MetadataView 117–142 / ObservationsView 144–172), row (`Field` 151–176 / `Item` 243–260), editor-row shell (Escape, Enter, blur, Done, problem line: 203–226 / 288–296, 518–545), layouts loaded for the systems (60–71 / 72–83). The systems' loading is two more copies of the system numbering across pages (`pageOf` / `ScoreSystems`, MetadataView 65, ObservationsView 77) → add to group 17 #5's `numberSystems`. **certain**.
12. **The stored metadata has two types, one unused** — `StoredMetadata = ScoreMetadata` (web analyze.ts 29) is imported nowhere; `fix_metadata` stores `ShownMetadata` (nullable page and confidence, `confirmed`, `comments`). Make `ShownMetadata` the one stored type (renamed `StoredMetadata`, in analyze.ts beside `StoredObservations`) and `normalizeMetadata` its reader; drop the other. Normalizing is also uneven: `people` rebuilt field by field, the other lists spread whole (fixMetadata.ts 42–45), while observations are rebuilt per list (fixObservations `itemOf`). **certain** (minor).

## Patterns
- **A rule written twice, once per side, diverging** (model's checks vs the form's: span order, unique piece systems; the unmount save vs commit): 3. Likely cause: the forms were built after `analyze`, writing their checks for what a person can do, without reusing or extending the prompts' checks; the prompts couldn't take the web's ordering helper, so the order check was written only where it was handy.
- **A helper or type written again** (`shownConfidence` ×2 + `stateOf`, place labels ×4, `StoredMetadata` beside `ShownMetadata`, two form views, systems numbered twice more): 5. Likely cause: the second form copied the first rather than extracting; each stage's labels written where first needed.
- **Async state overwritten by a reload of one's own save** (finding 1): 1 here, 3 in group 19. Likely cause: the forms and editors refresh the pipeline after every save and treat a new content hash as new data, without telling their own saves apart.
- **Two names for one thing across stages** (`startEndRepeat`/`bothRepeats`; a piece's `page` meaning two things): 2. Likely cause: analyze's vocabulary was designed before the lens's was fixed, and never reconciled.
- **Prompt and check disagreeing** (pieces on other pages): 1. Likely cause: the check was written for the whole-score call's context and reused for the page call.
- **A derived count from the wrong source** (pieces note): 1. Likely cause: the note written before `piecesOf` added system 1 and deduplication.
- **Stale or misleading comments** (the prompts' "staves checked on the pages as corrected", versions' coverage): 2.
