# Level 2, group 03: Page images and the image cache

## Map
- **imaging (pure, browser/Worker/Node):** `image.ts` (RGBA type, luminance, stable trig); `pdfPages.ts` (`openPdf` with our decoders forced, `pageImage`: embedded scan taken as is, else `renderPage` at a DPI on a given canvas; no version constant); `png.ts` (`encodePng` RGBA or gray, `decodePng` → always RGBA); `rotate.ts` (`rotate`, `deskew`, `paperColor`; `ROTATE_VERSION`); `scale.ts` (`shrinkToFit`, `CLAUDE_IMAGE_LIMIT`; `SCALE_VERSION`); `skew.ts` (`findSkew`, `deskewAngle`, `DESKEW_VERSION`; private `rotateGray`); `fingerprint.ts` (`fingerprintOf`, `asStored` = what `decodePng(encodePng(x, gray))` gives, `compareFingerprints`); `testPages.ts` (test helpers).
- **core:** `pdf.ts` (`drawPage` on a DOM canvas at DPR, `PDFJS_DATA` relative URLs), `pdfjsAssets.ts` (Vite plugin serving/emitting the same four folders).
- **web, recipe → pixels → OPFS:**
  - `rasterize.ts`: `PageRecipe {step, version, pdf, page, dpi, pdfjs}`; `runRasterize.ts` makes each page via `pageImages.pageImage` and records `recipeKey`.
  - `pageImages.ts` (main thread): RPC client of `pageImageWorker.ts`; recipe types nesting `Page ⊂ Straight ⊂ ModelPage/Crop ⊂ Drawn/Layout/MarkedCrop`; `cachedOr` (key → OPFS → else worker `derive` → cache → `made`); fingerprints kept as `<key>.fingerprint.json`, checked against `GET /api/fingerprints/<key>` when made; `differing` set + listeners; `keepFingerprints` → `POST /api/fingerprints`.
  - `pageImageWorker.ts`: pdf.js (legacy, OffscreenCanvas factory, absolute `/pdfjs/...` URLs), `derive` = deskew → crop → shrink → draw → encode(gray?) and fingerprint of `asStored(image, gray)`.
  - `imageCache.ts`: OPFS `cache/pdf-<sha>/<key>.png|.json` (+ top-level SVGs, engrave PDFs, `lru.json`), in-memory fallback; `cacheLru.ts`: `toEvict`, limit setting, `formatSize`.
  - Views: `ImagesDiffer.tsx` (banner by page recipe key), `PdfView.tsx` + `pdf.ts` (`usePdf`, `pdfUrl`, lazy `loadPdfjs`) on the main thread; `apps/eval/src/PdfPane.tsx` its sibling.
- **Contracts:** (1) recipe key = `keyOf(recipe)`, the same object built in ~12 places (below), names the OPFS file, the fingerprint row and the image in LLM requests (group 01). (2) Worker request/response union typed once (`PageImageRequest`/`Response`), imported as types by the client. (3) `asStored` ↔ `decodePng` (gray expanded the same way) so a fingerprint made in the worker equals one recomputed from the cached PNG; pinned by fingerprint.test's gray round trip. (4) pdf.js data folders: `pdfjsAssets` FOLDERS ↔ `PDFJS_DATA` ↔ the worker's own list. (5) The PDF's URL `/api/pdfs/<sha>/file`: `pdfUrl` (pdf.ts 23) and api.ts 724 `fetchPdf`.

## Findings

1. **Page images have no code version in their recipe** — `PageRecipe` (rasterize.ts 55) has `pdfjs` and `RASTERIZE_VERSION` but nothing for imaging's own `pdfPages.ts` (embedded-scan detection, 1-bit unpacking, orientation, nearest-neighbour resampling, `renderPage`'s white fill), unlike every other operation (`CROP_/DRAW_/ROTATE_/SCALE_/DESKEW_VERSION`, in imaging). A fix there (e.g. `parseColor` or the 1-bit loop, level 1) changes pixels under unchanged keys: cached images are served stale, and freshly made ones mismatch stored fingerprints (a false "images differ" on the same device). Same pattern as group 01's finding 9 (`findSkew`). Add `PAGE_IMAGE_VERSION` in pdfPages.ts, put it in `pageRecipe`. certain (inconsistency; bites on the next pdfPages change).
2. **The memory fallback written to but never read when OPFS exists** — imageCache.ts 96–97: a failed OPFS write (quota, Safari's lock on a second `createWritable`) calls `remember`, but `cachedFile` (57–59) reads memory only when `folder()` is null. The blob sits in memory unread (up to 200 MB), is counted by `cacheUsage` (189) in Settings, and the image is remade on every request. Either `cachedFile` falls back to `recall` after an OPFS miss, or the catch drops the blob. certain (bug, minor).
3. **No in-flight dedupe of image making** — pageImages.ts `cachedOr` 118–128 and `pageImage` 79–90: two concurrent requests for the same recipe (a view and the running stage; ExtractionView's crops while `extract` runs; `straightPage` called by both `modelPage` and an editor) both miss, both make the image in the worker, both write the same OPFS file and both `fetchFingerprint`. `openPdfForImages` already dedupes with a promise Map (`opened`, 30); the same `Map<key, Promise<Blob>>` in `cachedOr` would do. check (wasted work; concurrent `createWritable` on one file may throw in some browsers → finding 2's path).
4. **`pageImage` repeats `cachedOr`, and its `computed` flag is unused** — pageImages.ts 79–90 vs 118–128 (level 1 certain); `computed` (79) is read by no caller (all take `.png`: ArtifactView 137, SkewEditor 104/117, runSkewAnalysis 47, runLayout 68, runRasterize 31, straightPage 212). With it gone, `pageImage` = `cachedOr(recipe, () => askPage(recipe))` returning a Blob like its siblings. certain.
5. **Unused fields in the worker's answers** — pageImageWorker.ts 52/55: `width`, `height`, `source`, `dpi` of `page`, `width`/`height` of `derived` are posted and never read (pageImages takes `png` and `fingerprint` only). `source`/`dpi` (embedded or rendered, the scan's real DPI) would be useful in the rasterize note or the run report; otherwise drop. certain (dead contract fields).
6. **The `StraightRecipe` literal built by hand in 8 places** — `{ page, angle, deskew: DESKEW_VERSION, rotate: ROTATE_VERSION }` in runLayout 70, runAnalyze 93, musicInputs 84, ArtifactView 257, ExtractionView 150, LayoutEditor 122 and 195; and `CropRecipe` `{straight, box, crop: CROP_VERSION, limit, scale: SCALE_VERSION}` in runExtract 126, runReview 145, runApplyReview 253, ExtractionView 149–155. These must be identical for the cache, fingerprints and LLM request keys to match; a field added in one place silently splits the cache. Constructors beside the types in pageImages.ts (`straightRecipe(page, angle)`, `cropRecipe(straight, box, limit)`, also `modelPageRecipe`) would be the one place. The `imageRecipe` objects for stage keys (runLayout 43, runAnalyze 84, runExtract 44, runReview 86, runApplyReview 150) restate the same versions again: one `IMAGE_VERSIONS` const in pageImages.ts. certain.
7. **The Transcription's crops aren't always the ones the model saw** — ExtractionView.tsx 153 uses `limit: CLAUDE_IMAGE_LIMIT`; runExtract 124 uses `imageLimitFor(config, labels.length)`, smaller when a request has many images (llm.ts 59). For such systems the view makes and caches a second crop (another key), and its banner checks a recipe with no stored fingerprint. Boxes are fractions, so they still fit. check (by design? if so, a comment; else use the same constructor, finding 6).
8. **Fingerprints stored under a key that is never checked** — LayoutEditor.tsx 122–123 keeps the fingerprint of `straight` even when `layout.angle` is null; `straightPage` then returns the page image (pageImages.ts 212) without `cachedOr`, so no `made` ever checks that key (the page image is checked under its own key). Harmless rows, plus a worker round trip to fingerprint the PNG. Normalize: a null-angle straight recipe *is* the page recipe (have `straightRecipe` return the page recipe's key, or `keepFingerprints` map it). check (minor).
9. **Gray → RGBA expansion three times, and two of them form a contract** — png.ts 89–92 (`decodePng`), fingerprint.ts 66–68 (`asStored`), skew.ts 95–99 (`rotateGray`). `asStored` must equal `decodePng`'s output exactly, or a gray image's fingerprint made in the worker differs from one recomputed from its PNG. One `grayToRgba(gray, width, height)` in image.ts, used by all three (`asStored` = `grayToRgba(luminance(image))`), makes the contract structural. Also removes the per-pixel `data.set([…])` allocation (level 1). certain.
10. **pdf.js data folders listed three times** — pdfjsAssets.ts 11 `FOLDERS`, core pdf.ts 34–39 `PDFJS_DATA`, pageImageWorker.ts 106–107 (plus Node paths in imaging pdfPages.test.ts 16–19 and imaging scripts/common.ts 16–21). One table in core pdf.ts (`{wasmUrl: "wasm", …}`), `PDFJS_DATA` derived from it, `pdfjsAssets` importing its values (pdf.ts has no top-level DOM use, so the Node plugin can import it), the worker mapping `PDFJS_DATA` through `new URL(v, self.location.origin)`. certain (level 1 certain, confirmed).
11. **The PDF fetched three ways** — `usePdf` (pdf.ts 36, error `HTTP <status>`), `openPdfForImages` (pageImages.ts 65, its own message), `fetchPdf` (api.ts 724, `checked`, URL written again instead of `pdfUrl`). One `fetchPdf(sha256)` in api.ts on `pdfUrl`, used by the other two (`usePdf` takes a URL only because PdfView is keyed by it; it could take the sha256). certain.
12. **PdfView/usePdf vs eval's PdfPane: three copies** — `useSettledWidth` identical (PdfView 64–81, PdfPane 245–264), `drawPages` near-identical (PdfView 50–60, PdfPane ~81–92), and the load effect (fetch → `getDocument({data, ...PDFJS_DATA})` → destroy on cleanup) in usePdf 32–54 and PdfPane 43–70. Core already hosts `drawPage` for both; `drawPages(doc, width, isCancelled)` and a `loadPdf(url, getDocument, signal)` belong there too (no React). `useSettledWidth` needs React, which core doesn't depend on: either a React peer dependency for a `@score3ly/core/react` entry, or accept two copies. check (plan decides where the hook goes).
13. **PdfView draws every page at device pixels, eagerly** — PdfView 50–60 with `drawPage` (core pdf.ts 84: width × DPR): a 50-page PDF on a 3× phone is ~50 × 7–8 MB of canvases, and a resize draws a second set before the first is replaced (cancelled sets aren't released, `canvas.width = 0`). docs/images.md §8.5 warns that mobile Safari limits total canvas memory. Lazy drawing near the viewport (as ArtifactView's pages do with IntersectionObserver, 125) would bound it. check (to try on a phone; the release checklist's "Tried … on a phone").
14. **Worker keeps every opened PDF for the page's life** — pageImageWorker.ts 116 `docs` and pageImages.ts 30 `opened`: never released, not even when a project is deleted (DeleteProjectDialog deletes the cache folder only). A session through several large projects holds them all in the worker. An LRU of one or two docs, or a `close` request on leaving a project. check (memory; level 1 check confirmed as real but low).
15. **`changeConfig` opens the whole PDF in the image worker to learn its page count** — ProjectView.tsx 492. The PDF's page count isn't stored with the project (only stages' page counts, docs/database.md "page counts"), so configuring `rasterize` fetches and parses the PDF. Storing the PDF's page count at ingest (the browser has the PDF then) would make it free. check (for group 05/15).
16. **`pngSize` reads PNG headers outside the PNG module** — pageImages.ts 272–275 assumes IHDR at byte 16; the format knowledge lives in imaging png.ts (`decodePng` parses IHDR, 52). Move as `pngSize(bytes)` beside it. certain (small).
17. **`DESKEW_VERSION` in the straightened page's recipe is redundant with `angle`** — skew.ts 162–164 says the deskew decision's version is part of straightened pages' recipes; but the recipe already carries the decided `angle` (and later stages read the stored `layout.angle`), and the rotation itself is `ROTATE_VERSION`. Bumping it changes every straight/crop key, so every LLM request key, while the pixels for a given angle are the same. It belongs in `layout`'s stage key (where the angle is decided: runLayout 43 has it), not in the image recipe. check (design; ask before changing, the docs decided it).
18. **Two LRU evictions in one cache** — imageCache.ts 23–32 (memory Map order, re-summing all sizes per write) vs cacheLru.ts `toEvict` (OPFS index). They needn't behave identically (fixed 200 MB vs the setting), but `remember` could feed `toEvict` (`used` = insertion order) and drop the second algorithm. certain (small duplication); fix with finding 2.
19. **`deleteCachedPdf` reopens the root by hand** — imageCache.ts 211 instead of `folder()` (level 1 certain, confirmed); and it leaves a project's top-level files (Transcription SVGs, engrave PDFs, both keyed by content, not PDF) to LRU eviction. Fine for keys shared across projects; worth a comment against docs §4 "as if it never existed". certain (the reopen) / check (the leftovers).
20. **`DEFAULT_DPI` twice** — imaging pdfPages.ts 52 and rasterize.ts 15 (`dpi: 300`); `rasterize` always passes its own, so imaging's is used only by Node scripts/tests. rasterize.ts could import it. certain (trivial).
21. **`usePageDiffers(page: PageRecipe | null)`: the null case is dead** — every caller passes a recipe (ExtractionView 547, ArtifactView 159, LayoutEditor 423, SkewEditor 303), so level 1's stale-key-on-null worry can't happen; narrow the type. certain (trivial).

## Tests at the seams
- `asStored` ↔ `decodePng`: pinned (fingerprint.test gray round trip). `encodePng` ↔ `decodePng` and ours ↔ other programs: pinned.
- Worker `derive` (the order deskew → crop → shrink → draw → gray) has no unit test; covered end to end only by the replay's request snapshots (recipe keys, not pixels) and the screenshots.

## For level 3
- The recipe nesting (`Page ⊂ Straight ⊂ …`) is the image cache's real schema, but its constructors are spread over the run*/view files (finding 6); a recipe module (in pageImages.ts or its own `recipes.ts`) is the component boundary between "stage logic" and "images".
- Versioning of imaging code is by hand-bumped constants in imaging, collected by hand in the web's recipes and stage keys; two operations (`findSkew`, group 01; page extraction, finding 1) are missing. A level 3 rule: every pixel-producing or pixel-measuring function has a version constant, and recipes/keys take them from one `IMAGE_VERSIONS` object.
- A damaged cached PNG (or fingerprint JSON) is never remade: `cachedOr` returns whatever the cache has, and a decode failure fails the caller. Nothing deletes a cache entry on a decode error. For the "errors" group (07) or the plan: on decode failure, delete and remake.
- The PDF's page count isn't stored (15): touches groups 05/15.
- Main thread pdf.js (PdfView) and the worker's pdf.js parse the same PDF separately; fine (different jobs), but both stay in memory (13, 14).
- The worker RPC itself (ids, errors, termination) is group 04's.

## Patterns
- **A literal object rebuilt at each use instead of a constructor** (1 big case: recipes ×12, plus `imageRecipe` ×5). Cause: each stage written by copying the previous stage's runner; the recipe type was exported, its constructor never written, and TypeScript accepts any structurally equal literal.
- **A version constant missing for one operation** (1, plus group 01's 9). Cause: versions added per module as each was written; pdfPages predates the convention or was thought covered by the pdf.js version.
- **The same small helper written in two or three modules** (gray→RGBA ×3, pdf.js folders ×3, PDF fetch ×3, `useSettledWidth`/`drawPages`/load ×2, `DEFAULT_DPI` ×2, `pngSize` outside png.ts, two LRUs: 7). Cause: a module written without looking for the helper the neighbouring module has, sometimes because the helper was private (`draw.ts fill`, png.ts's expansion) or in a package the code couldn't import (imaging ↛ core; core ↛ React).
- **Dead or unread contract fields** (`computed`, the worker's `width/height/source/dpi`, the null page, the never-read memory write: 4). Cause: fields added for a use that was planned or later moved elsewhere, never removed since nothing fails.
- **Concurrency and resource lifetime not considered** (no in-flight dedupe, docs kept forever, eager canvases: 3). Cause: code written and tried with one view and one stage at a time on a desktop, where duplicate work and memory don't show.
- **Redundant key part** (`DESKEW_VERSION` in image recipes: 1). Cause: "anything that could change the image goes into its recipe" applied to a decision whose result is already in the recipe.
