## Map

- **Stored:** `model_configs` (0001 l.37): one row per config, never edited but for its name and `deleted_at` (and `convertAddedConfigs`, which turns a hand-added model into a listed one when a new list has its string). CHECKs restate the code's rules: provider/family/effort/routing/account/pricing_kind enums, routing iff Bedrock, project only Vertex, account iff OpenRouter, EU only Business, provider pricing only OpenRouter, reference only for added models. Unique live names `COLLATE NOCASE`. Seed: `fake-model`, the default.
- **Worker, llmRoutes.ts:** `ModelConfigRow` (the row) → `toModelConfig` → `ModelConfig` (the browser's shape: resolved model, `unsupported` reason, `price`). `configProblem` validates a creation body; `unsupportedOf` = `configProblem(bodyOf(row))` + `unsupportedReason` for words. Naming: `configName` (given, or `configBaseName` + `firstFreeName`). `sameValues` (refuses a second config with the same values, 409 `same_values` + the config). Routes: list, one (deleted too), create/clone (`replaces`), rename, delete (not the default), Test (`sendCall` with `TEST_REQUEST`), settings (`defaultModelConfigId` refused if unsupported), `/api/models` (`modelOptions`: the form's pickers, with `SECRETS` sets), `/api/secrets` (names), price range.
- **Other Worker readers of the row:** pipeline.ts 287/969 (a stage's config rebuilt from `mc_*` aliases → `unsupportedOf`), the start and config routes (deleted/unsupported refusals), projectFile.ts (`sameConfig`, inserts imported rows).
- **Web:** api.ts restates `ModelConfig`, `Settings`, `ModelOptions`, `NewModelConfig` (= the body `configProblem` reads), `TestResult` (a subset of `CallAnswer` + `durationMs`), `WorkerRefusal`. configForm.ts: the form's pure logic (`settled`, pickers, `missing` ≈ the web's `configProblem`, `requestOf`, `defaultName` ≈ `configBaseName`, `firstFreeName`, `sameValues`). NewModelConfig.tsx: the dialog, submit flow (same values → offer rename, confirmations, create, make default). SettingsPage.tsx: the cards, filter (configList.ts), actions (Test, Make default, Rename, Clone, Delete), the default picker. TestConfigDialog + testResult.ts. ConfigDialog.tsx: a stage's "Change config", fed by ProjectView `modelConfigsFor` (`{id, name, deleted, unsupported: boolean}`) and checked by steps.ts `LLM_CONFIG.check`.
- **effort.ts is not in this group's subject:** it computes the statistics' Effort tab (manual work), not effort levels; nothing here. To group 14.

## Findings

1. **Cloning a config unchanged, or making one with the values of an existing config under "Use default", offers to rename it to its own numbered name.** NewModelConfig.tsx 95–96: `shownDefault = firstFreeName(name, taken)` counts every live config as taken, the one with the same values too; so when that config has the default name ("… · high"), `finalName` is "… · high (1)", `offerRename` (122) doesn't see the names as equal, and asks "Rename "… · high" to "… · high (1)" instead?". The simplest case: Clone on any config with a default name, change nothing, Save. Fix: in `offerRename`, compute the default name without `same` among the taken names (renaming frees its name), and treat "same values, would get its own default name" as "already exists". The decision logic (submit, `offerRename`'s three texts) lives untested in the component; moved into configForm.ts it could be tested (finding 13). **certain** (bug).
2. **Provider names: four copies, three spellings.** Worker `PROVIDER_NAMES` (models.ts 29: "Fake", "Fake (dev)"), which reach the form's picker and the default names ("X (Fake (dev))") through `ModelOptions`; web costs.ts 174 (same as the Worker's); SettingsPage.tsx 397 ("Fake (no network, no costs, for trying the app)", "Fake with costs (for development)"), from which the filter's label is cut by regex (`providerName`, 395, "Fake with costs"); the Worker's own refusal says "Fake with costs" (llmRoutes 731). So the same provider is "Fake (dev)" in the form and the config's name, "Fake with costs (for development)" on its card. One map, shared (group 11's handoff: models.ts's names to `@score3ly/core`), with the long explanation as a separate hint where the card wants it; `providerName`'s regex and `configList`'s `providerName` parameter go. **certain**.
3. **Secret field labels three times, and a comment naming a table that doesn't exist.** configForm.ts 318 `SECRET_LABELS` (exported, used only in `missing`), NewModelConfig.tsx 39 `FIELD_LABELS`, SettingsPage.tsx 410 `FIELD_LABELS` with `region`/`projectId` added so that `Fact` can label non-secret facts by a made-up field name; its comment says "the Worker's FIELDS" (it is `SECRETS`, llmRoutes 52). Keep configForm's `SECRET_LABELS`; `Fact` takes its label as text. **certain**.
4. **Place labels twice, and a raw id in text.** Routing: configForm `routingLabel` (226, with geography) vs SettingsPage `ROUTINGS` (407, without, so the card says "Geographic" where the form said "Geographic (EU)"); `missing()` prints the raw id ("(geographic routing)", configForm 341). Region: `regionLabel` (NewModelConfig 547: "" → "Global", "eu" → "EU") vs the card's inline "eu" → "EU" (SettingsPage 561); Vertex's region is "Location" in the form (293), "Region" on the card and in `missing()`. One `placeLabels` pair in configForm.ts for form, card and `missing`. **certain** (dup); the Location/Region wording **check** (style.md says "Region").
5. **"Same config" decided three times.** Worker `sameValues` (llmRoutes 1267: refuses a create), projectFile.ts `sameConfig` (246: reuses on import; group 01 #6 for sharing it with `sameValues`), and the web's `sameValues` (configForm.ts 384: finds it before the pricing confirmation, to offer a rename first). Compared field by field today, the web's agrees with the Worker's (trimmed string, `project` "" → absent → null, reference only for "list"). The web's is untested and the only one a person sees the effect of first; the Worker's 409 is the backstop (`create` handles `same_values`). Keep it, test it against a few Worker-made rows, or drop it and ask the Worker first (a dry run). The level 1 doubt on its hand-made canonical secrets is dropped: both sides of that comparison are computed by the same function, nothing needs byte equality with the Worker's `secrets_json`. **certain** (dup), **check** (keep or drop).
6. **`secrets_json` parsed in five places, guarded in two, and the import writes it unchecked.** `bodyOf` 153 and `unsupportedReason` 202 guard; `toModelConfig` 263 and `sameValues` 1269 (twice) don't. Creation always stores core's `canonicalJson`, but `importProject` (projectFile.ts 277) inserts the file's `secrets_json` as it is (and runs no `configProblem`-like check on it): one imported config with a non-JSON `secrets_json` makes `GET /api/model-configs` and every `POST /api/model-configs` (`sameValues` over all live rows) fail with a 500. Fix: the import checks and canonicalizes `secrets_json` (group 15); one `secretsOf(row)` that parses once. **certain** (mechanism), low practical risk (a corrupt or hand-edited `.s3l`).
7. **pipeline.ts rebuilds a `ModelConfigRow` from aliased columns** (287: `m.name AS mc_name, …` for eleven columns; 969 `stageModelConfig` maps them back with defaults, `pricing_kind ?? "unpriced"`, and a cast that hides the missing `id`/`created_at`). A column added to `model_configs` must be added there too, or `unsupportedOf` judges a different config than `/api/model-configs` does, silently (the cast). Select the config rows of the pipeline's stages separately (`SELECT * FROM model_configs WHERE id IN …`) and reuse `ModelConfigRow`. Also `stages.model_config_id` and `config_json.modelConfigId` hold the same fact (group 06 #7). **certain** (fragile), **check** (worth the extra query).
8. **The config's shapes, restated.** Worker `ModelConfig`/web `ModelConfig` (api.ts 318; web inlines the effort, routing and price literals instead of `Routing`/`ModelPrice`, level 1), `Settings` both sides, `ModelOptions` both sides (`ModelPrice` = `Price`), web `NewModelConfig` vs the Worker's untyped body (`configProblem(body: Record<string, unknown>)`, `newConfigRow`'s casts), `TestResult` ⊂ `CallAnswer` + `durationMs`; and two summaries `{name, model, deleted, unsupported: boolean}` (pipeline.ts 969) and `{id, name, deleted, unsupported: boolean}` (ProjectView 718, steps.ts 39), where `ModelConfig.unsupported` is the reason text. 9. **The enums restated in the migration's CHECKs, and inline in `configProblem`.** Provider, family, effort, routing, account, pricing kind: 0001 l.41–51, models.ts/types.ts, the web's api.ts, schema.json (group 11 #14); `configProblem` writes the routings (llmRoutes 335) and the non-provider pricing kinds (386) as inline arrays instead of a `ROUTINGS`/`PRICING_KINDS` constant. ## For level 3

- **The config vocabulary belongs in `@score3ly/core`:** the enums and names (group 11), `ModelConfig`, `NewModelConfig`, `ModelOptions`, `Settings`, the config summaries (8), with the labels the UI needs (provider, secret fields, region, routing: 2–4) beside or in the web. Today the Worker owns it and the web restates it in four files.
- **The rules of a valid config live in four places:** the migration's CHECKs, `configProblem`/`unsupportedReason`, the web's `settled`/`missing`, and `listProblems` (for the list's places). The form's `missing()` and the Worker's `configProblem` say the same refusals in different words ("The app no longer supports X on Y" in three). Nothing tests that a form `missing()` accepts yields a body `configProblem` accepts; configForm.ts imports only types, so a Worker-side test could import it with `modelOptions(LIST)` and check the round trip.
- **Import of configs** (6, 9) crosses into group 15: the only path that writes a config row without the create route's checks.
- **Error texts:** the deleted/unsupported sentences (group 08 #11), the cap sentence (12), `same_values` handled by code (group 07 #8).

## Patterns

- **Labels and names restated per screen** (2, 3, 4, 17): count 4. Cause: the settings card, the form and the costs view written in different sessions, each adding the map it needed where it was, including a fourth spelling of the same provider; the exported `SECRET_LABELS` was never looked for.
- **Types and enums restated across the API and the schema** (8, 9): count 2 (about ten types). Cause: the web cannot import the Worker, and no shared package was set up for API types, so each new response was typed again on the web; the migration restates the enums by nature, with no test pinning it.
- **One rule written on both sides** (5, 15, and `missing` vs `configProblem`): count 3. Cause: the form wants to answer before asking the Worker (rename offer, shown default name), so the Worker's rule is re-implemented in the browser instead of asked for (a dry run) or shared as pure code.
- **Logic in components, untested, where the bug was** (1, 11, 13): count 3. Cause: the submit flow grew inside NewModelConfig.tsx, while configForm.ts got the tests; the case "the same config already has the default name" wasn't thought through.
- **A row read in several places by hand** (6, 7): count 2. Cause: each reader (pipeline's join, import, `sameValues`) parses or rebuilds the row itself, so a guard or a column added in one isn't in the others; the import path was written as a copy of rows, not through the create path's checks.
- **Coupling by wording** (12, `providerName`'s regex in 2): count 2. Cause: a message adjusted after the fact by editing its text instead of building it from parts.
- **Wrong text for a case** (10): count 1. Cause: written when "no cost" meant only "unpriced", before OpenRouter's priced-by-provider configs.
