# Level 2, group 04: Web Worker RPC

## Map
- **Three clients, each a module singleton** (lazy `new Worker(new URL("./x.ts", import.meta.url), {type:"module"})`, `nextId` counter, `pending: Map<id, {resolve, reject}>`, a `message` listener that resolves by id), never terminated, living as long as the page:
  - `pageImages.ts` 21–58 → `pageImageWorker.ts`: `ask(request, transfer)`, request type `Unsent` (Omit `id` on each union member); answers discriminated by `type`, errors as `{type:"error", message}`. On the Worker's `error` event: rejects all pending, clears `opened` (the PDFs open in the worker), drops the reference. Five callers each check the answer's `type` and throw "Unexpected answer…".
  - `rendering.ts` 47–75 → `renderWorker.ts`: `ask(mei, options, allPages, pageWidth)` → `string[]`; request built with `satisfies RenderRequest`; errors as `{id, error}`. `error` event: rejects all pending, drops the reference.
  - `meiValidation.ts` 8–34 → `meiCheckWorker.ts`: the worker is a `Promise<Worker>` resolved by a `{listening:true}` handshake (libxml2-wasm loads with a top-level await, `node_modules/libxml2-wasm/lib/libxml2.mjs:3`, so a message sent before the module has run could be lost); errors as `{id, error}`. **No `error` listener.**
- **Three workers:** `pageImageWorker.ts` (pdf.js + imaging; `handle(request)` with a `.catch` posting `{type:"error"}`; transfers PNG buffers back), `renderWorker.ts` (Verovio WASM loaded on the first request into `toolkit ??=`; try/catch per message), `meiCheckWorker.ts` (schema fetched and compiled once in `ready()`, reset to null on failure so the next check retries; try/catch per message; posts `listening` last).
- **Contracts:** request/response unions are declared in each worker file and imported as types by its client (compile-time only; good, one definition each). Ids are per client, so no collisions. Nothing else is shared: three response conventions, three error paths, two retry policies.
- pdf.js's own worker (main-thread `pdf.ts`, and the one inside `pageImageWorker`) is pdf.js's RPC, not ours: out of scope.

## Findings
1. **`checkMeiText` can wait forever** — meiValidation.ts 12–25: no `error`/`messageerror` listener and no timeout. If the worker fails to load (its chunk 404s, or libxml2's WASM top-level await rejects, which fails module evaluation), `listening` never comes, the cached `worker` promise never settles, and every later check waits on it too. Concrete: an open tab after a new deploy (Workers static assets serve only the current version's hashed chunks) → Apply in FixMeiView (130) stays "applying" for good, and `finishFixMei` (fixMei.ts 66–67) never returns, so Finish of `fix_mei` hangs instead of failing. The other two clients reject on `error` and retry with a new worker. Fix: as rendering.ts, plus reject the handshake promise and reset `worker`. certain (level 1 certain, confirmed with the scenario).
2. **The RPC client written three times, diverging** — pageImages.ts 26–58, rendering.ts 47–75, meiValidation.ts 8–34: same id counter, pending Map, message dispatch; they differ only in (a) the handshake (meiValidation), (b) the error handling (finding 1), (c) the error shape. They must behave the same (reject on failure, retry with a fresh worker, terminate the dead one). One `apps/web/src/workerClient.ts`: `workerClient<Req, Res>(create: () => Worker, { handshake?: boolean })` → `{ ask(req, transfer?) }`, handling `error`/`messageerror`, `terminate()`, reset and retry, and one error convention. Constraint: Vite only bundles a worker from a literal `new Worker(new URL("./x.ts", import.meta.url), …)` at the call site, so the client takes a factory, not a URL. Web-only (browser), no package needed. certain.
3. **The worker side repeated too** — pageImageWorker.ts 69–74, renderWorker.ts 14–25, meiCheckWorker.ts 25–34: each wraps its handler in try/catch and posts `{id, error: err instanceof Error ? err.message : String(err)}` (pageImageWorker as `{type:"error", message}`). A `serve(handler)` beside the client (handler returns `{response, transfer?}`), so both sides share one error shape. certain (small; goes with 2).
4. **Two error conventions** — `{id, type:"error", message}` (pageImageWorker 56) vs `{id, error}` (renderWorker 10, meiCheckWorker 10), and two ways of telling them apart (`type === "error"` vs `"error" in data`). Unify with 2–3. certain.
5. **Untyped answers checked by hand five times** — pageImages.ts 69, 86, 96, 114, 189: "Unexpected answer from the page image worker." The response type depends on the request type; a typed `ask<T extends Unsent["type"]>(request): Promise<Extract<PageImageResponse, {type: ResponseOf<T>}>>` (a small request→response type map), or one checked helper, removes the five throws. certain (level 1 certain, deferred here by group 03).
6. **Two lazily loaded WASM workers, two retry policies** — renderWorker.ts 18 keeps a rejected `toolkit` promise for good (a failed Verovio load, or a toolkit left broken by an Emscripten abort, fails every later rendering until reload), while meiCheckWorker.ts 18–20 resets `validator` on failure so the next check retries. renderWorker should do as meiCheckWorker (`.catch(e => { toolkit = null; throw e })`). Whether a Verovio abort leaves the toolkit unusable: check. certain (inconsistency), check (the abort case).
7. **Dead workers not terminated** — pageImages.ts 42–48, rendering.ts 61–65: the reference is dropped, not `terminate()`d. Low in practice: both workers catch every error of a request, so an `error` event means a load failure (the worker is already dead); but an uncaught error in a running worker doesn't kill it, and then it would keep its memory (pageImageWorker's open PDFs, group 03 #14) and keep answering into a pending Map that was cleared. Goes into 2. certain (hygiene, low).
8. **pageImages: `opened` and the worker can disagree after a restart** — pageImages.ts 84–85: `pageImage` awaits `openPdfForImages` and then asks for the page; if the worker is replaced between the two (finding 7's path), the new worker answers "The PDF isn't open." (pageImageWorker 147–148). Rare (needs a worker `error` mid-run); the stage's retry recovers. Tying `opened` to the worker instance, or reopening on that answer, would close it. check (minor).
9. **No `messageerror` listener anywhere** — a message that fails to deserialize leaves its request pending forever in all three clients. The payloads are plain data and ArrayBuffers, so unlikely; folded into 2. check (low).
10. **No cancellation** — none of the clients can drop a request: renderings of systems scrolled away (ExtractionView 636–646 only ignores the result), images of a stopped stage, keep the worker busy, and requests queue behind them (one worker each; a long `renderPages` delays every system rendering behind it). Acceptable now; a shared client makes a later `AbortSignal` cheap. check (design, for level 3).
11. **No in-flight dedupe of renderings** — rendering.ts 78–95: like group 03 #3 for images, two concurrent `renderMei` of the same key both render and both write the cache. Lower cost than images (cache hit after the first). check (minor).
12. **`allPages` optional in `RenderRequest` but always sent** — renderWorker.ts 9 vs rendering.ts 73; and the `pageWidth` branch ignores `allPages`. Trivial; make it required. certain (trivial).
13. **`ask` named like llm.ts's `ask`** — pageImages.ts 52, rendering.ts 69 (and llm.ts): three module-private functions with the same name doing different things; disappears with 2. certain (naming, minor).

## Tests at the seams
- No test of any client or worker shell (all browser-only). The request/response types are shared by import, so the shapes can't drift at compile time; the behaviour around them (handshake, error, retry) is untested, which is exactly where the copies diverged (1, 6).
- A shared `workerClient` would be testable in Node with a fake Worker (an `EventTarget` with `postMessage`): answers by id, rejection on `error`, retry with a new worker, handshake, termination. The worker handlers are already testable through their pure parts (verovioRender.test, meiChecks.test, imaging's tests).

## For level 3
- **Stale tab after a deploy:** every lazily loaded chunk (the three workers, `import("./meiValidation")`, `lazy()` screens, Verovio) 404s in a tab opened before a new deploy. Here it turns into a hang (1) or an error per request; nowhere is the user told to reload. A component-wide answer (the app noticing its version changed, e.g. from `/api/info`, and asking for a reload) would cover all of them. Also `FixMeiView` 107's `import(...).then(...)` has no catch (an unhandled rejection in that case).
- Cancellation (10) belongs with the stage runner's Stop (group 06) and the views' unmounting.
- Worker lifetimes: all three live for the page; memory held by pageImageWorker's PDFs is group 03 #14.

## Patterns
- **A piece of infrastructure written again for each feature** (1: three RPC clients, with three worker shells). Likely cause: each worker added for a new need (page images, then Verovio, then the MEI schema) by copying the previous client's shape into the new module instead of extracting it; nothing prompted the extraction since each copy was small.
- **Copies drifting apart in their error handling** (3: meiValidation without an `error` listener, renderWorker without the retry meiCheckWorker has, two error shapes). Cause: the copy made from memory of the pattern, not from the code, and the failure paths never exercised (no tests, browser-only).
- **Untyped protocol checked by hand at each call** (1 pattern, 5 sites). Cause: a request/response union without a request→response type map, so each caller narrows itself.
- **Missing cleanup on failure** (2: no `terminate()`). Cause: the happy path written first; failure handling added as "drop and recreate" without thinking of the old instance.
- **No timeouts or cancellation on async boundaries** (2: worker requests, the handshake). Cause: requests assumed to always answer; hangs only show when a load fails, which development never hits (the dev server always serves the chunk).
