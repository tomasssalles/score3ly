# Level 2, group 23: Routing, navigation, the desktop shell

Files: apps/web/src/route.ts (+test), navigation.ts, history.ts (+test), useHash.ts, App.tsx, Menu.tsx, ProjectView.tsx (the routing, leaving and structure parts), ArtifactView.tsx, StageDetails.tsx, leaveGuard.ts (+test); apps/desktop/src/main.ts, leaving.ts (+test). Read alongside: StatsPage.tsx and SettingsPage.tsx (their tabs), PageView.tsx (passed on by group 19), pipeline.ts (`nextStaleAt`, `findArtifact`).

## Map

- **route.ts:** the hash grammar, pure: `parseRoute` (`#/projects/<id>[/artifacts|stages/<id>]`), `pageFromHash` (`#/<page>[/<tab>]`), the `hashFor*` builders, `PAGES`, `STATS_TABS`, `SETTINGS_TABS`, `TABS_OF`, two `*TabFromHash`. Imports nothing.
- **useHash.ts:** the hook that owns the URL: state `hash`, a `hashchange` listener, and the *hold*: each history entry is numbered in `history.state.score3lyIndex`, so a held change is undone by `history.go(-delta)`; `go(hash)` navigates past the hold (`allowed`). Its invariant: **an entry's number is its position in the history**.
- **leaveGuard.ts:** module state "the project this device runs" (`setRunningProject` by ProjectView's effect, `runningProject` read by App at `hashchange` time) and `leavesProject(hash, id)` (route.ts).
- **App.tsx:** the router and the shell: `useHash` with the hold (→ "Leave the project?" dialog), `navigate` (in-app links, held the same way), `selectArtifact`/`showStage` (set `location.hash`), `closeArtifact` (`history.back()` or `location.replace`), the project list (`current` = list ∩ route), the file pick / import / create flows (group 15), and every app-level dialog.
- **ProjectView.tsx:** receives `artifactId`/`stageId` from the route; sets the leave guard and `beforeunload` while `local` runs; narrow mode overlays `ArtifactView` with `onClose`; also the run controller, toasts, confirmations (726 lines).
- **ArtifactView.tsx:** the artifact pane, the dispatcher `ArtifactContent`, and generic views (`PageImageView`, `LayoutFilmstrip`, `Filmstrip`, the last used by ExtractionView and MetadataView too).
- **StageDetails.tsx:** a stage's details; exports `KIND_LABELS` (used by StageCard).
- **navigation.ts:** `useBackForward` (Navigation API's `canGoBack/Forward`, else both true) and `useNoBrowserBar` (matchMedia). Header's buttons call `history.back()/forward()`: they go through `useHash`'s hold.
- **Menu.tsx:** links `hashForPage(page)`.
- **StatsPage / SettingsPage:** each calls `useHash()` a second (third) time for its tab, and switches tabs with `location.replace(hashFor…Tab)`.
- **desktop main.ts:** Electron shell: back/forward keys, mouse buttons and swipes → `webContents.navigationHistory` (same-document traversals, so they reach `useHash`'s hold too); `will-prevent-unload` → native question (leaving.ts). **leaving.ts:** that question's text.
- **Contracts:** (1) the hash grammar, written by route.ts's builders and parsed by route.ts — but also built by hand in App 260 (`"#/"`); (2) `useHash`'s numbering ↔ every way the app changes the URL; (3) `runningProject` set by ProjectView ↔ read by App's hold; (4) the leave text: web App 281 ↔ desktop leaving.ts 11 ↔ docs (project-view.md 99, desktop.md 34); (5) `beforeunload` in ProjectView ↔ `will-prevent-unload` in main.ts; (6) `WindowTheme` web api.ts 105 ↔ desktop server.ts / main.ts 45 (group 24's side).

## Findings

1. **A `location.replace` breaks the history numbering, and a held back/forward then lands in the wrong place.** useHash.ts 23–41: an entry without a number is taken for a *new* entry (`isNew`, `index += 1`). A fragment navigation starts with a null `history.state`, `location.replace` included, so every replace is numbered one past the entry it replaced, and from then on numbers and positions differ (the gap is permanent in the replaced entry's state). Four sites replace: the tabs (StatsPage 70, SettingsPage 93; StatsPage 48 says replacing is on purpose), `closeArtifact` (App 188), after deleting (App 260). Concrete: project A → Settings → click "Model configs" (Settings now numbered 2 at position 1) → back to A (0) → Run → Forward: `delta = 2`, held, `history.go(-2)` from position 1 goes before the app's first entry: nothing happens (or another site is loaded); the URL now says `#/settings/configs` while the view still shows A with its "Leave the project?" dialog; Cancel leaves URL and view disagreeing (docs: "Cancel leaves the URL and the history as they were"), Leave runs `history.go(2)`, which does nothing (or leaves the app). Same with an artifact URL typed or reloaded, then closed (App 188), then back while running. **certain** (logic; the null state after a fragment replace is the spec's behaviour, worth a one-line browser check). Fix: one way to change the URL — `useHash` returns `go(hash, { replace })`, which for a replace calls `history.replaceState({ score3lyIndex: index }, "", hash)` and sets the state itself (no `hashchange` fires); every site uses it (App's `navigate`, `selectArtifact`, `showStage`, `closeArtifact`, delete, the tabs). Test it with a fake `history`/`location` (below, 3).

2. **Five ways of changing the URL; only `go` knows the hook's rules.** `go`/`navigate` (App 54–61), `location.hash =` (App 172, 178), `location.replace` (App 188, 260; StatsPage 70; SettingsPage 93), `history.back()` (App 186, navigation.ts 37), plus `<a href>` links (Menu, Header's wordmark, Home's cards). The links and `history.back` are fine (they reach the hold through `hashchange`); the replaces are finding 1; the direct `location.hash =` in `selectArtifact`/`showStage` works only because they never leave the project (level 1 check confirmed). With finding 1's fix, App's navigation (`holds`, `navigate`, `selectArtifact`, `showStage`, `closeArtifact`, `openedArtifactHere`, the leaving dialog's state) moves into one hook, e.g. `useAppNavigation()` in useHash.ts or a `navigation.ts` merged with it, and App keeps the layout. **certain** (structure).

3. **`useHash` is used three times, each instance numbering the history on its own.** App 48, StatsPage 58, SettingsPage 61: every instance registers a `hashchange` listener, keeps its own `index` and, for an unnumbered entry, writes `score3lyIndex` (19, 40). Today they agree only because the later listener reads the number the earlier one just wrote (and SettingsPage, mounted with the app on `#/settings`, registers *before* App's, so App then sees a numbered entry and computes `delta` from it — it still works, by luck of `delta = 1`). The pages need only the hash: pass `hash` down from App (PageView takes it) or put it in a context, so exactly one instance owns the history. And the hook is untested: the numbering, hold and `go` are pure enough to test with a fake `history` (a list, a position, `go`, `replaceState`, a dispatched `hashchange`); none of finding 1 would have survived such a test. **certain**.

4. **The Statistics page's first tab has two URLs; Settings' has one.** route.ts 63–75: `hashForSettingsTab("general")` = `#/settings`, `hashForStatsTab("costs")` = `#/stats/costs`, while the menu opens `#/stats` (Menu 22). And the two `*TabFromHash` are one function for two pages. Shared: `tabFromHash(page, hash)` / `hashForTab(page, tab)` over `TABS_OF` (already there, line 48), the first tab without a suffix for both (as Settings). **certain** (level 1's duplication and inconsistency, both confirmed).

5. **A created or imported project first shows "This project doesn't exist (any more)."** App 148/161 navigate before `refresh()` (154/166), and `current` comes from the list (65). Group 15 #14 confirmed it; the routing side: the same message also stays for good when the URL names a project made on another device after this tab loaded its list (a pasted link, KnownPdfDialog's `open` refreshes only after `markOpened`): the "doesn't exist" branch (341–346) could refresh once before saying so. Fix in the navigation hook of finding 2: add the returned project to the list (or `await refresh()`) before navigating. **certain** (flash), **check** (the pasted-link case: minor).

6. **The new project is created before the leave question is asked.** App 157–161 (and 147–148 for an import): `createProject` runs, then `navigate` holds if a stage runs; on Cancel the project exists, unopened and unmentioned (it appears in the picker after `refresh`). Asking before creating (`holds(hashFor…)` can't be known before the id, but `holds("#/projects/new")` — any project hash but the running one — can) would match the docs' "+ New project" asks first (project-view.md 99). **check** (rare: picking a PDF while a run goes; decide whether the order matters).

7. **The "leave while running" consequence is written twice in code and twice in the docs.** App 281 and leaving.ts 11 ("What is done so far is kept, and Run picks up from there; an answer from a model still on its way is lost, although it is paid for."), restated in ProjectView 158's comment; nothing pins them together. The desktop main process is bundled by esbuild (build.ts) and can import from `@score3ly/core` like the server does from the worker: a `LEAVING_A_RUN` constant in core (or leaving.ts exporting it and App importing it — web importing from desktop is the wrong way round, so core). **certain** (minor).

8. **`leavesProject`'s first clause is redundant, and `projectIdFromHash` is used only by its test.** leaveGuard.ts 22: a page hash never parses as a route, so `parseRoute(hash)?.projectId !== projectId` already says true; route.ts 19 `projectIdFromHash` is exactly that expression — use it in `leavesProject` (`projectIdFromHash(hash) !== projectId`) or delete it and its test cases. **certain**.

9. **ProjectView does four jobs, and the pure ones are untested.** (a) the run controller: `run`, `finish`, `resolveCarried`, `stop`, the abort, `local` (338–455) → `usePipelineRun(project, stored, setStored)`; (b) the toasts' gathering and timers (192–224) → `useToasts(snapshot, covered)` beside toasts.ts; (c) **`replacesWork`, `replacesLater`, `fixReplaces`** (240–263): pure functions of the stage list that decide whether the re-run confirmation appears (a decided rule, §5.5) — into pipeline.ts with tests; (d) the screen. ## Patterns

- **An invariant kept by one function, broken by code that bypasses it** (1: the history numbering vs four `location.replace` sites and two direct `location.hash` writes). Likely cause: the hold (2026-11-03) was added to `useHash` after the navigation sites existed, and the tab switching (replace "on purpose") later, each written against the browser's API rather than the hook's; nothing tested the hook.
- **A hook owning global state instantiated more than once** (1: `useHash` ×3). Cause: the pages needed "the hash" and called the hook that gives it, without seeing that it also writes `history.state`.
- **Two near-identical functions drifting apart** (1: the tab hash functions, one dropping the first tab, one not). Cause: the second page's tabs copied from the first and adjusted.
- **Text or rules duplicated across processes or with the docs** (1: the leave text ×2 in code + 2 in docs). Cause: the desktop question was written to match the web dialog by copying, with no shared home for UI text across apps.
- **Pure logic buried in a component, untested** (2: the re-run confirmation rules; the toasts' gathering). Cause: written where first needed, in a file that grew to 726 lines.
- **Generic parts exported from a view file** (2: `Filmstrip` and the page views from ArtifactView, `KIND_LABELS` from StageDetails). Cause: as groups 21/22, a helper placed in the first file that needed it.
- **Async order in a flow** (2: navigate before the list knows the project; create before asking to leave). Cause: each step written as "do it, then show it", without the route depending on the list.
- **Unhandled startup failure** (1: Electron's `whenReady` chain). Cause: the happy path written first, the shell never failing in development.
- **Stale or orphaned comments and pointers** (4: ArtifactView 22, ProjectView 57, main.ts "§3", Help text). Cause: code moved between files and docs split after the comments were written.
- **Dead or redundant code** (2: `projectIdFromHash`, `leavesProject`'s first clause).
