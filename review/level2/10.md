# Level 2, group 10: JSON Schemas and validating answers

## Map
- **Schemas, one per LLM stage,** in `packages/prompts/src`: `LAYOUT_SCHEMA` (layout.ts 36, a hand-written literal, `as const`), `ANALYZE_PAGE_SCHEMA`/`ANALYZE_SCORE_SCHEMA` (analyze.ts 400ff), `EXTRACT_SCHEMA` (extract.ts 293) built from `LENS_SCHEMA_PARTS` (extract.ts 219), which `REVIEW_SCHEMA` (review.ts 87) and `APPLY_REVIEW_SCHEMA` (applyReview.ts 82) reuse. Each module builds them with its own copy of `str`/`int`/`object`/`described`/`nullable` (level 1, 02).
- **The model's form ↔ code's form** (lensForm.ts): `*FromModel` (sentinels `""`/`-1` → null, `new-…` → class + kind, ending enum + label → object) and `*ForModel` (back). Stage wrappers: `lensFromExtract` (lensForm.ts), `reviewFromModel` (review.ts 149), `applyReviewFromModel` (applyReview.ts 182); analyze has its own flat↔nested conversion (`nestedMetadata`, `nestedObservations`, analyze.ts 247–340).
- **Validating an answer**, five different ways:
  - `layout`: `checkLayoutAnswer` (layout.ts 77), fields checked by hand.
  - `analyze`: `shapeProblem` (analyze.ts 556), a generic validator of the schema subset, run against the schema itself, then semantic checks.
  - `extract`: `lensFromExtract` then `checkSystem` (notation lens.ts 105): top-level arrays checked, the rest trusted while it checks semantics.
  - `review`: `reviewFromModel` then `checkReview` (apps/web/src/review.ts 148): top-level `entries` checked, the rest trusted.
  - `apply_review`: `applyReviewFromModel` then `checkPatch` (apps/web/src/applyReview.ts 110): four top-level arrays checked, the rest trusted.
- **Worker side:** the schema travels as `jsonSchema` (web `PlannedRequest` → `llmRoutes` 497, which checks only "is an object" → each adapter hands it to the provider). `apps/worker/src/llm/jsonSchema.ts` (`schemaProblems`) is a second validator, used only by `scripts/generate-model-list.ts` and its test (group 11). `apps/worker/scripts/probe-schemas.ts` sends the stage schemas to Anthropic to see which it accepts. `llm/fake.ts` recognizes stages by schema property names and parses the request text (group 08, item in its "checks settled").
- **Contracts:** schema ↔ the TS answer types (`LayoutAnswer`, `FlatPageAnswer`/`FlatScoreAnswer`, `ReviewAnswer`, `ApplyReviewAnswer`, notation's `LensSystem` after `lensFromExtract`), restated by hand and pinned by nothing; schema ↔ the validator (only analyze validates against its own schema); schema ↔ Anthropic's limits (docs/llm.md, "Claude's limit on schemas"); the schema's emitted JSON ↔ the request key and the replay snapshots (any change in what a builder emits re-pays calls and changes `fixtures/replay/*/requests/`).

## Findings

1. **An answer of the wrong nested shape crashes the check instead of being marked unusable, and so stays cached and fails the same way on every retry.** `checkSystem`, `checkReview`, `checkPatch` and `checkLayoutAnswer` check only the top level and then read nested fields as typed: `s.changes`/`s.voices` iterated (lens.ts 160, 172), `n.boxes.length` (web review.ts 191), `u.staves.map` (web applyReview.ts 133), `s.left` on a null entry (layout.ts 84). A missing field is a `TypeError`; only `Unusable` is caught (lens.ts 108), and the run*.ts files call `markUnusable` only on a returned `problem` (runExtract 165, runReview 190, runApplyReview 314, runLayout 98). The call stays `ok` in `llm_calls`, so Retry serves the same answer from the cache and throws again, with a stack-trace message, until the config changes. Also `checkPatch` stores a stretch unit without checking `changes` is a list (applyReview.ts 140–147), which later throws in `stretchForModel` (lensForm.ts 104) while writing the log. Triggers: a provider that doesn't enforce the schema fully (Gemini's `responseJsonSchema`, an OpenRouter model), or a replayed answer recorded under an older schema. **certain** (mechanism), **check** (how likely). Fix: one full shape check against the stage's own schema before `*FromModel`, as analyze does (finding 2), so every malformed answer becomes a `problem`.
2. **Two hand-written validators of the same JSON-Schema subset, each missing what the other has.** `shapeProblem` (analyze.ts 556: `anyOf`, enum, object, array, string, integer, boolean, null; ignores `additionalProperties`, `number`, `required` as such) and `schemaProblems` (worker jsonSchema.ts 24: type lists, enum, required, `additionalProperties: false`, pattern, minimum, minLength; no `anyOf`, so it can't check the review or analyze schemas). One validator covering the union, with the user-facing messages `shapeProblem` writes ("… isn't one of …"), in `@score3ly/core` (no dependencies, runs in browser, Worker and Node; prompts would add a dependency on core), used by every stage's check (finding 1) and by generate-model-list. A package (`@cfworker/json-schema`, no deps, runs everywhere) is the alternative, but its messages would reach the user as the unusable reason. **certain** (duplication), placement **check**.
3. **`shapeProblem` ignores `additionalProperties: false`,** so an extra key passes and is carried by `...rest` into stored items (analyze.ts 268, 303, 654). Harmless under constrained output; folds into 2. **certain**.
4. **Four copies of the schema builders, already diverging:** `nullable(schema, description)` in analyze.ts 357 vs `nullable(schema)` in applyReview.ts 72; `described` exported by extract.ts 211 and redefined in analyze.ts 355 with its comment copied word for word; `number(description)` in layout.ts 34; layout's schema written out by hand with its `required` list typed separately from its properties (layout.ts 36–64). One small module (`schema.ts` in prompts: `str`, `int`, `num`, `bool`, `enumOf`, `object`, `described`, `nullable`, `list`, and a `JsonSchema` type) used by all five stages. Safe to refactor: the replay's request snapshots pin every emitted schema, and the emitted JSON must stay deep-equal or every request key changes. **certain**.
5. **The schemas are untyped, hence `as unknown as Record<string, unknown>` five times** (runLayout 79, runAnalyze 119/196, runExtract 156, runReview 182, runApplyReview 304; flagged by group 06). The builders' inferred types are probably assignable to `Record<string, unknown>` already (type aliases have implicit index signatures; `readonly` doesn't block it), so the casts may be plain noise; a shared `JsonSchema` type (finding 4) on `PlannedRequest.jsonSchema` and the builders removes them either way. `probe-schemas.ts` 86 uses `any` for the same lack; `jsonSchema.ts`'s `Schema` lacks `anyOf`, `description`, `$defs`, so it isn't the type to use. **check** (typecheck without the casts).
6. **Answer types restated beside their schemas, nothing pinning them:** `ReviewAnswer` (review.ts 134–151), `ApplyReviewAnswer` and units (applyReview.ts 146–176), `FlatPageAnswer`/`FlatScoreAnswer` (analyze.ts 434), and the cast `lensFromExtract(...) as LensSystem` in `checkSystem`. They agree today (checked field by field). Options: derive the types from the schemas (`json-schema-to-ts`'s `FromSchema`, types only, no runtime), or define each schema once in Zod and emit the JSON Schema (`z.toJSONSchema`), which would also replace finding 2's validator and finding 4's builders; both must keep the emitted JSON identical (finding 4) and within Claude's limits. **check** (the plan decides).
7. **The docs say Zod; there is no Zod.** overview §3 ("Structured LLM output … validated with Zod", "Schema validation: Zod (or similar)"), §5.1 ("A config schema (Zod), which is also the source of its UI controls"), §7.1 ("validated by a Zod schema"), docs/stages/analyze.md 59 ("its Zod schema exists anyway"). No `package.json` has it. Either the docs say "JSON Schema, validated by our own checks", or finding 6's Zod option is taken. **certain** (docs drift).
8. **The schema strictness test covers analyze only.** analyze.test.ts 257 walks both analyze schemas (every object `additionalProperties: false`, `required` = all properties); `layout`, `extract`, `review` and `apply_review` aren't walked, and layout's `required` is a hand-written list. The documented explicit limits (no optional properties, at most 16 properties with `anyOf` or a type list, across the request; docs/llm.md 94) are pinned only piecewise (extract.test 34: no `anyOf`; lensForm.test 52: one `null` in apply_review). One test over all six schemas, strictness plus a count of unions ≤ 16, would catch an Anthropic refusal offline, before `llm:probe-schemas` is needed. **certain** (gap).
9. **The model form of issues and choices is written inline in apps/web, not in lensForm.ts.** lensForm.ts has `issueFromModel` but no `issueForModel`; web review.ts 90–96 and 115–126, runApplyReview.ts 288 and web extract.ts 88 write `?? ""` and spread `lilypond` by hand. And not quite the form the model writes: a reading issue's tokens are left out (`...(i.lilypond ? …)`), where the model writes `lilypond: []`, against "every model sees one form, the one it writes" (lensForm.ts header). Add `issueForModel` (and a choice's) beside `issueFromModel`. **certain** (placement), **check** (whether the omitted `lilypond` matters).
10. **The lens's model form is split over two modules:** its conversions in lensForm.ts, its schema parts (`LENS_SCHEMA_PARTS`, `described`) and the `MUSIC`/`lensRecap` texts in extract.ts, so review.ts and applyReview.ts import "extract" for what is the shared lens form. `LENS_SCHEMA_PARTS` belongs with lensForm.ts (the model's form: schema and conversions in one place); `MUSIC`/`lensRecap` in a shared prompt-text module. Confirms level 1's check. **certain**.
11. **analyze.ts does three jobs in 700 lines:** prompt texts (≈ 1–240), flat↔nested conversion and schemas (247–434), validation and semantic checks (436–701). With `shapeProblem` moved out (finding 2), the checks are a module of their own (`analyzeChecks.ts`), the prompts another. **certain** (structure).
12. **review.ts and web review.test.ts test the code form only:** every `checkReview` test feeds nulls (`choice(…, null)`, review.test 74), never the model form (`key: ""`, `newAnswer: ""`, `lilypond: []`), so `reviewFromModel`'s conversion isn't tested anywhere, and the test inputs are answers no schema-constrained model could give. `applyReviewFromModel` is tested through `checkPatch` in model form (applyReview.test 171–217). Seam test: feed each check a model-form answer, and check test answers (and the fake model's answers) against the stage's schema with the shared validator, which pins answer fixtures, schema and check together. **certain** (gap).
13. **`probe-schemas.ts` doesn't send what the adapter sends,** and reaches into prompts by relative path. It builds its own `output_config` (100–104) instead of `toParams` (anthropic.ts), so a change in the adapter's params (adaptive thinking, effort) isn't probed; the worker doesn't depend on `@score3ly/prompts` (80–84). Reduced to "every stage's schema, through `toParams`", it would fit beside `try-llm.ts` using `createProvider`, with prompts added as a dev dependency of the worker. **check** (the plan).
14. **`{ problem: string }` spelled 13 times;** `Problem` is a private type in analyze.ts 93. With one validator and stage checks returning the same shape, one exported `Problem` (prompts or core) would do. **certain** (minor).

## For level 3
- **The "answer → problem or value" contract** spans prompts (schemas, `*FromModel`), notation (`checkSystem`), apps/web (`checkReview`, `checkPatch`, the run*.ts files' `markUnusable`) and the Worker (what is cached as `ok`). Finding 1 shows the seam: an exception in a check is neither recorded as unusable nor kept out of the cache. Level 3 should decide one rule for all stages (shape check against the schema first; checks never throw on input; run*.ts treat a thrown check as unusable too).
- **Issue validation exists twice** (extract's issues in lens.ts 238–257, review's new issues in web review.ts 195–213, answer keys "single letters, unique" vs "a, b, c in order") → group 18.
- **The score written for the model twice** (web review.ts 55–70 strips staff descriptions, runApplyReview.ts 415–425 keeps them) → group 18.
- **Any refactor of schemas or their builders changes request keys** unless the emitted JSON stays deep-equal: the replay snapshots are the guard, and a prompt version bump is the price otherwise.
- **The fake model is coupled to the schemas' property names and the request texts' separators** (group 08); a schema refactor must keep both.

## Patterns
- **A helper written again in each new stage module** (schema builders ×4 with diverging signatures, `each` ×2, `{ problem: string }` ×13): 3. Likely cause: each stage's prompt module written by copying the previous one's preamble rather than importing it, with no shared "schema" module to find.
- **Validation written per stage, to a different depth each time** (five ways, one generic validator not reused by the other four, a second generic validator elsewhere): 2. Likely cause: analyze's full shape check came from its own incident (the big schema, before constrained output fit), and the stages built later relied on constrained output without deciding it as a rule; the model-list validator was written for a Node script without looking for the one in prompts.
- **Types restated beside the schema they describe:** 4 answer types (plus `LensSystem` by cast). Likely cause: schemas as plain objects give no types, and no derivation was set up.
- **Tests on one side of a seam only** (strictness walk for analyze alone; review's checks fed code form, never model form): 2. Likely cause: tests written for the stage being built, not for the shared contract.
- **Docs describing a tool that was never adopted** (Zod, four places): 1. Likely cause: the architecture written before the code; the docs weren't revisited when JSON Schema by hand was chosen.
- **Dev scripts reaching around package boundaries / left from a finished investigation** (probe-schemas): 1. Likely cause: a one-off investigation script kept as a tool without being trimmed.
