# LLM providers and model configs

How the Worker calls the providers (Anthropic, Vertex AI, Bedrock, Google AI Studio, the fake one; for the first release Claude on the first three and Gemini on Vertex AI and Google AI Studio, decided 2026-11-03), how calls are recorded, cached and priced, what a model config is and which one a stage uses, and the discussion of supported models and prices. What each LLM stage asks is in `docs/stages/`; costs and the spending cap are below ("Costs"). § numbers here are `docs/overview.md`'s sections.

## Calling the providers
Built: `apps/worker/src/llm/`. One small request and response shape for every provider (`LlmProvider`, §3): a system prompt, messages of text and images, a maximum of output tokens, an effort, and optionally a JSON schema the answer must follow (the provider's schema-constrained output, §7.1; the answer is then parsed). The response says which model answered, the text (and parsed JSON), why it stopped (finished, cut off, refused) and the tokens. Errors are typed and say whether retrying can help.
- **The chosen model answers, or the call fails.** No fallback to another model, not even Anthropic's server-side fallback on refusals: a refusal comes back as a refusal.
- **Several images in one request are labelled** with a text block right before each ("System 3:", "System 3, stretch 2:"): content is an ordered list of text and images for both Anthropic and Gemini, and the adapters keep the order. Neither API passes a file name to the model. Anthropic's vision docs recommend this way of labelling.
- **Anthropic** (Claude API), with the official SDK. Requests are streamed, so long answers don't hit timeouts. Thinking is left at the model's default (adaptive on current models), and effort maps directly. As a sanity check, an answer that names another model than the one asked is an error (`unexpected_model`).
- **Google** (Gemini API, keys from AI Studio), with the official SDK. Effort maps to Gemini's thinking levels (low, medium, high), which exist from Gemini 3 on; older Gemini models want a token budget and would refuse a level. Thinking tokens count as output, cached ones apart from the rest. Gemini names the exact version that answered, which can differ from the name asked for (an alias, a dated version), so there is no model check.
- **Claude on Google Cloud's Vertex AI** (for processing in the EU, §10), with Anthropic's official Vertex client: the same Messages API, so the same adapter code as for Anthropic's API, sanity check included. Configured with a service account's key file (a secret), a region (`eu` for the EU multi-region, a single region such as `europe-west1`, `us` or `global`) and optionally a project (default: the key file's).
  - **Tokens without Google's auth library,** which expects Node (files, child processes, the metadata server) and doesn't run in a Worker. Our own small token source signs Google's service-account claim with WebCrypto, exchanges it for an access token, and reuses the token until a minute before it expires. A refused service account is an `auth` error.
  - **Billing** goes through Google Cloud, after the fact. Google Cloud now has enforced spending caps per project; the project owner's project ("score3ly") has a monthly cap of €30, with the Vertex AI API enabled. What is left to set up is a task (§15).
- **Claude on Amazon Bedrock** (for processing in the EU: Opus 5.5 isn't offered on Vertex AI in Europe, and Anthropic has no servers there), with Anthropic's official Bedrock client for Bedrock's Messages API endpoint ("Mantle"): again the same adapter code, sanity check included. Configured with a region (e.g. `eu-central-1`) and either a Bedrock API key or an AWS access key pair (a key ID and a secret), both secrets; with a key pair, requests are signed with AWS Signature V4. The client runs in a Worker as it is, given the credentials explicitly (it would otherwise look for them in the environment and AWS's files). The model is Bedrock's own ID for it, e.g. an `eu.` inference profile.
  - **Setting up an AWS account for it** (for the user guide): a new account must first be verified (up to 24 hours), then the AWS Marketplace agreement for the model signed, then Anthropic's use-case form submitted; before that, requests are refused with "not available for this account". The project owner's account is in this process (2026-10-09), with 100 USD of starter credits valid for six months.
  - **The sanity check compares the two model strings as they are;** whether Bedrock answers with the string that was asked is checked on the first real call (§15).
  - **Spending:** AWS has no hard spending cap as far as known: budgets alert, and a budget action can at most attach a deny policy. The app's spending cap (§10) and the IAM user's permissions are the limits.
- **Gemini on Google Cloud's Vertex AI** (built 2026-11-03; provider `google-vertex`, `VertexGeminiProvider` in `apps/worker/src/llm/google.ts`), configured as Claude on Vertex AI: a service account's key file (a secret), a location (`region`: a single region such as `europe-west4`, `eu` or `us` for a multi-region, or `global`) and optionally a project (default: the key file's). Vertex's REST API is called directly (`generateContent`, with the same body as the Gemini API's: the system instruction and the generation config apart), because Google's SDK authenticates with Google's auth library, which doesn't run in a Worker; the token comes from our own token source, the same as Claude's on Vertex AI (`googleServiceAccount.ts`). The answer is read as the Gemini API's (`fromResult`), so the thinking levels, refusals, thought summaries left out and cached tokens counted apart are the same. The endpoint is Anthropic's Vertex SDK's rule: `aiplatform.googleapis.com` for `global`, `aiplatform.eu.rep.googleapis.com` (and `.us.`) for the multi-regions, `<region>-aiplatform.googleapis.com` otherwise. Not yet tried with a real call (§15, "Try the app with Gemini 3.1 Pro on Vertex AI"): which locations offer which Gemini models, and whether every field of the request (`responseJsonSchema`, `thinkingLevel`) is accepted on Vertex's `v1`, are to see then. No prices yet, as for Gemini on Google AI Studio: a config needs the free-tier mark until the prices are in ("Supported models, prices and the config form").
- **Prompt caching** (decided and built, 2026-10-31): a request can mark parts of its prompt, "cache up to here" (`cacheUpTo: true` on a part of a message, text or image), when later requests will start with the same prefix, e.g. `review`'s calls, which all start with the whole score and the issues (`docs/stages/music.md`, `review`). The provider then bills that prefix at its cache-write price once, and at its cache-read price, a fraction of the input price, each time a later request starts with it.
  - **Provider-neutral:** the mark says where, each adapter decides how. **Claude** (Anthropic's API, Vertex AI, Bedrock): a cache breakpoint (`cache_control`) on that part, with the default lifetime, 5 minutes from the last use (1 hour is possible, at twice the input price to write instead of 1.25 times: a task, §15, "The cache's lifetime for Claude"); a prefix shorter than the model's minimum is simply not cached. **Gemini:** the mark is ignored. Gemini caches matching prefixes by itself (implicit caching, without a guarantee), and reports what it read from the cache, which is counted as cache reads; its explicit caching (a cached-content resource created first, with a lifetime and a storage charge) isn't used. The fake providers ignore it.
  - **At most 4 marks per request** (Anthropic's limit of breakpoints); the Worker refuses more.
  - **Not part of the request key** (§5.2): the marks change what a call costs, not what the model is given, so moving them doesn't make paid calls run again. The recorded request keeps them, as it was sent.
  - **Used by `review`** (built): after the issues and warnings, and after the last block of the log (`docs/stages/music.md`, "`review`, built"). Whether `extract` gains from a mark after the part all its calls share (the instructions and the observations) is to be seen.
- Tested without network, with a fake `fetch`, and run inside the local Workers runtime. `npm run llm:try -w apps/worker -- <anthropic|anthropic-vertex|anthropic-bedrock|google> <model> <image> "<question>" [--json]` sends one image and a question with real credentials, from environment variables.
- **Wired into the Worker** (built, `apps/worker/src/llmRoutes.ts`), as Block 1 of the LLM stages:
  - **`POST /api/projects/<id>/stages/<stage id>/llm`** takes one request of a running stage (system prompt, messages of text and images, base64, an optional JSON schema and maximum of output tokens). The model config is the stage's (set when it starts, from the stage's choice or the default setting, "Which config a stage uses"). **The item-level cache comes first** (decided): an earlier successful call with the same request key, not deleted, is served at no cost, even when the spending cap is reached. Only then: the price, the spending cap, the secrets, the call. The request key is the hash of the request, with each image replaced by its recipe key (§5.2, "Only recipes"), and of the model's provider, model and effort.
  - **The browser asks first without the images** (built, `ask` in `apps/web/src/llm.ts`): each image named only by its recipe key. A cached call is served then; otherwise the answer is `{ imagesNeeded: true }`, and only then does the browser make the images (from the device's cache, or from their recipes), check the request's size against the provider's limits, and send it again with them. So a re-run on another device makes no images for calls already paid for. A stage builds its requests with each image as its recipe and the function that makes it (`requestImage`); every image sent has a recipe, `layout`'s drawings for its check rounds included (cached now, like the others).
  - **Requests must be built the same way in a run and in a retry:** an answer that later requests are built from (a page's analysis, a system's extraction) is used as it reads back from storage, canonical JSON, also in the run that got it; otherwise the order of its keys differed and the whole-score `analyze` request missed the cache after a retry (found while building this).
  - **Every call is recorded** in `llm_calls`, with its tokens (cache reads and writes apart, migration 0008) and cost. The request is stored in R2 as canonical JSON **with images replaced by their recipe keys and hashes** (decided, built): images are never stored (§2); a cached request is found and served without them, and the images of a request can be rebuilt from the stored outputs when someone needs to look at them (inspection and debugging aren't ordinary use). The response (text, parsed JSON, stop reason, the provider's raw answer) is stored as JSON.
  - **Statuses:** `ok`; `cut_off`, `refused`, `unparseable` and `error` are recorded but never served from the cache. `unparseable` is first the JSON itself: an answer that isn't valid JSON, although the provider was asked for schema-constrained output. The provider's response around it is fine, so the adapter returns it with its usage (`invalidJson` says what is wrong), and its tokens and cost are recorded like any other call's (decided, built).
  - **Why a call threw** is kept with it (migration 0020): `error_kind`, the adapter's kind of error (`auth`, `rate_limit`, `overloaded`, `bad_request`, `server`: the provider answered with an HTTP error; `network`: no connection; `timeout`; `aborted`; `unreadable_response`: the provider answered, but its response couldn't be read, broken JSON or a stream that ended without a message; `unexpected_model`: another model answered than the one asked, not thrown but recorded with its tokens and cost, since it was billed; `unknown`), and `http_status`, the HTTP status the provider answered with, if any (today only an HTTP error's: an unreadable response after a 200 has none). A call that didn't throw has neither.
  - **A known gap in the costs: calls with no readable response** (decided, accepted). When the provider's response itself can't be read (its outer JSON broken, a stream cut off midway), the client library throws, no token counts are known, and the call is recorded as `error` with no cost. The provider may still have billed it, so the costs underestimate by such calls. They are rare; errors with no answer at all (a refused connection, an overload, a timeout before any answer) aren't billed anyway.
  - **Calls of unknown cost** (decided): calls with no recorded tokens, unless the provider answered with an HTTP error status (`http_status` 400 or above; a successful status, or none, leaves the cost unknown) or the error is `auth` without a status (the credentials failed before anything was sent: a service account key that can't be read, Bedrock given both kinds of credentials), and calls still `running` that started more than 15 minutes ago (decided: such a call will never answer; the tab was closed while it waited, and the provider may well have answered and billed). A call running for less may still answer, and isn't counted yet. Some cost nothing (no connection), some were billed; the count says how far the costs may fall short. An HTTP error (401, 429, 529 …) is the provider refusing the call, which isn't billed. (A refused service account is `auth` with the HTTP status of Google's token endpoint, not the provider's: nothing was sent either.)
  - **Answers the stage can't use** although their JSON is fine (LilyPond in `extract`'s answer that doesn't parse, a `layout` box outside the page): the stage marks the call unusable (`POST …/llm-calls/<call id>/unusable` with the reason), which records it as `unparseable`, so it isn't served from the cache again; its cost stays recorded.
  - **Free-tier configs are always allowed:** no spending cap needed, no known price needed, and they don't count towards the cap.
  - **Errors the stage acts on** carry a code: `spending_cap`, `no_price`, `no_model_config`, `missing_secret`. The stage fails with the message, and a retry later asks only what is missing.
  - **Model configs** (`/api/model-configs`) and **settings** (`/api/settings`: the default model config, the spending cap and the run mode for new projects) have endpoints; the settings page shows the run mode, the spending cap and the model configs (read-only) so far. Each provider's form is checked: which secrets (by the Worker secret's name) and which plain values it needs.
  - **A fake provider** (`provider: "fake"`) answers without network: the simplest JSON its schema allows, tokens counted from the request's size; some model names make it fail on purpose. **It costs nothing** (decided, built), whether its config is marked free tier or not: it ships with the app, installed by default, for trying the app without paying, and never shows in the statistics of costs. **`fake-dev`** answers the same with made-up prices, for developing and testing the costs and the spending cap. Two steps get more, so the pipeline runs end to end: `layout` two systems on every page, each with three bar lines, and `extract` the stretches asked for, a voice per staff with a whole-measure rest in 4/4, a made-up doubt on every system and a format issue on the first (§6, `extract`). For tests, and for trying the pipeline without paying.
  - **In the browser** (`apps/web/src/llm.ts`): the stage's model config, the part of the stage key that depends on it (provider, model, effort), images as request content, and asking the model.

## Model configs
- **A model config** is a stored, named combination of provider, model, thinking effort and the provider's authentication. The user can keep several. They live in D1 and are managed in the settings: created, renamed, cloned and deleted, never edited ("Managing model configs", below).
- **The model is the provider's own string** (to be replaced by picking from the supported models, see "Supported models, prices and the config form" below), entered as the provider spells it (`claude-opus-5-5` on Anthropic's API, an `anthropic.`-prefixed ID or an `eu.` inference profile on Bedrock, ...). The app doesn't translate between providers' names, and the sanity check compares the answer's model with that string as it is ("Calling the providers").
- **A name** for each model config, shown on the stage cards (§5.6), shortened in the middle when it doesn't fit, like project and file names (§5.7). **Required, and unique ignoring case** among the configs that aren't deleted (decided and built 2026-11-02: the Worker gives the name and refuses a taken one with 409, `configName` in `llmRoutes.ts`; migration 0024 named the configs that had none, and a unique index keeps names unique): the field in the create and clone forms may be left empty, and its label says that the name is then made from the model and the effort, e.g. "claude-opus-5-5 · high" (the model alone where the effort is the model's default), with " (1)", " (2)", … for the first free one if that is taken, like project names (§4). **To change with the supported models** (decided 2026-11-05): "Claude Opus 5.5 (Bedrock) · high" ("Supported models, prices and the config form", "Configs"). A rename to a name that is taken is refused, like a project's.
- **Each provider declares its own form:** which fields are secrets and which are plain values. The plain Anthropic and Google APIs take one key; Google Vertex AI wants a service-account file plus a project and a region, AWS Bedrock an access key pair plus a region. The form is generated from a schema, like a step's config (§3).
- **A secret field is a dropdown of the Worker's secrets, by name** (§10). The config stores the name, never the value. Several keys per provider are possible, e.g. a free-tier key and a paid one.
- **A missing key:** if a secret was removed or renamed, the configs pointing to it are broken. **The stage fails when a call needs the secret** (decided 2026-11-02: no checking of configs everywhere, a clear message where it fails is enough), with a message that names the config and the secret and says where secrets are set: "The model config "Opus" needs the secret ANTHROPIC_KEY, which isn't set. Set it where the app's secrets are kept (Settings, "Secrets"), then retry." (`missingSecretMessage` in `llmRoutes.ts`). Calls served from the record need no secret, so a stage whose calls are all recorded still runs. Possible later, if it turns out to be needed: the settings page marking a config whose secrets aren't set (the Worker can list the names it was given, an endpoint the config form needs anyway).

## Which config a stage uses
Decided 2026-11-02 (the project owner's proposal), to build. The goal: the user always knows which config each stage will run with, and can change it for one stage or for many in a few clicks. Before this, a stage took the default when it started and was tied to the config it started with from then on, which the cards didn't show: a re-run after a new default still ran on the old config, and a stage that failed because of its config (no price, a broken config) could only be left behind with a new project (found 2026-11-01).
- **Every LLM stage names its model config from the moment it is created** (decided; built 2026-11-02: the Worker gives it when it creates the stage, `newStageConfig` in `apps/worker/src/pipeline.ts`, for a new project, the planned copies a change or a stop makes, and a config set without one; the browser uses only the config the stage names, `stageModelConfig` in `apps/web/src/llm.ts`): no stage means "the default" and looks it up later. **The default is given to every LLM stage when it is created:** the stages of a new project, and stages added to a project later (a further review and its `apply_review`, the `apply_review` after a `human_review`). **Stages that already exist keep theirs:** a retry runs with the stage's config, and the planned copies a re-run makes (§5.5) take the config of the stage they replace.
- **The cards show it for every LLM stage** (built 2026-11-02), planned and ready ones included (dimmed with the rest of a planned card), so the pipeline panel says what will run before it runs (`docs/project-view.md`).
- **A stage whose config was deleted can't start** (decided and built 2026-11-02): the browser refuses before it starts, and the Worker refuses the start too (`deleted_model_config`), with the message ""Layout" can't run: its model config, "Opus", was deleted." **Its card says so early** (decided and built 2026-11-02), so that the user fixes it before running: the name with " (deleted)", in red on a stage that still has to start with it (planned, ready, failed); on a stage that ran, the suffix only. (Missing secrets, unlike this, are only found when a call needs them: "A missing key", above.)
- **"Change config" in an LLM stage's "⋮"** picks another config for that stage, with a checkbox **"Apply to the remaining stages planned in this pipeline"** (decided 2026-11-02; it doesn't name them): every LLM stage after it in the pipeline (carried further reviews included), never one before it; unticked at first, and hidden when no LLM stage comes after it. It adds no runs of its own: a new config already replaces everything after the stage (§5.5), and the checkbox only decides whether those stages run again on their own configs or on the new one. With nothing run yet, it sets the planned stages in place, without a confirmation. Changing the first LLM stage's config with the checkbox switches the whole project, so there is no separate action for that. The confirmation before a re-run (`docs/project-view.md`) says so when the box is ticked: "This stage will have to run again with the new config. The remaining stages planned in this pipeline will use it too.", then the usual text. Built 2026-11-02: the model config is a field of every LLM stage's config (`LLM_CONFIG` in `apps/web/src/steps.ts`; a further setting of an LLM step would be a field beside it), picked in the same "Change config" dialog as other steps' settings, labelled just **"Model"** (decided 2026-11-02: shorter, if less precise), with its picker below the label across the whole row like the other steps' inputs (decided 2026-11-02, after trying it on the label's row: below is consistent with the other fields, and suits further settings beside it; the name shortened in the middle, the list as wide as the field), from the configs that aren't deleted (the stage's own deleted one shows as current, marked, and Save is refused until another is picked); the checkbox is grouped under the picker, and changes only `modelConfigId` in the later stages' configs (`applyModelConfigToLater` on `PUT …/config`, `rewriteFrom`). Ticked with nothing else changed, only the later stages change (this one is replaced by itself, served from the record). The runners keep the rest of a stage's config when they record the one they used.
- **The settings page:** a row in the settings list, like "Run mode for new projects": **"Default model config for new LLM stages"** (decided 2026-11-02; "LLM", as in a stage's kind and "Paid LLM calls" on the same page), a drop-down of the configs by name (built 2026-11-02, `SettingsPage.tsx`: a pick is saved at once), with the hint **"Given to every LLM stage when it is created: in a new project, or when one is added to a project. Stages that already exist keep theirs; change them with "Change config" in a stage's ⋮."** The default's card keeps its "Default" badge. The default is changed only here and by "Make default" in the create and clone forms ("Supported models, prices and the config form", below). (One day perhaps a config per kind of work in the advanced settings, §15, "Model configs per kind of work": the same rule, a more specific default.)
- **A further review takes the default** like every other new stage (decided 2026-11-02): adding one doesn't open the config picker; "Change config" is there for another model. Like every change made by hand, adding it doesn't start a run, in Auto mode either: only finishing a manual stage carries an Auto run on by itself (`ProjectView.tsx`).
- **Changing the config of a stage that already ran** is a change in the middle (§5.5): confirmation, then everything after it runs again.
- **The key is not part of a stage's inputs.** Using another key for the same model doesn't count as a change and doesn't make paid stages run again.

## Managing model configs
Decided 2026-11-02, to build (it replaces the earlier design, where editing a config added a new row and marked the old one deleted). **A config's values never change:** provider, model, effort, region and other plain values, the names of its secrets, and the free-tier mark. Changing any of them would change what a stage that names the config does, and which version a stage would get is exactly the kind of arbitrary rule that confuses. So there is no editing of values at all; there is cloning. What the user can do:
- **Create** a config.
- **Rename** a config. A real edit: the name is in no key and changes no result, so the new name shows everywhere at once, in past runs too (a run report downloaded later has the new name; one saved earlier is a file and keeps the old). **Names are required and unique, ignoring case** ("Model configs", above): a card or a picker showing two configs of the same name says nothing.
- **Clone** a config, adjusting its values in the cloning form. A clone must differ from every existing config in more than its name:
  - **The same values and the same name as an existing config:** refused, saying why; nothing is deleted.
  - **The same values as the original, another name:** not created; the message offers to rename the original instead ("A config with these settings already exists: "Claude". Rename "Claude" to "Opus 5.5" instead?"). This is also what happens when only the name was changed.
  - **The same values as another config than the original, another name than both:** not created; the message offers to rename that config instead, naming it.
  - **"Delete the original"** (a checkbox in the cloning form) makes replacing a config one workflow, with the same confirmation as a delete, and it still reads as a new config, not an edit. With the box ticked, the offers above say so: "Rename "Claude" to "Opus 5.5" instead of deleting it?", and "Rename "Sonnet" to "Opus 5.5" and delete "Claude"?".
- **Delete** a config. Nothing changes in existing stages: those that ran keep naming it, marked as deleted; planned and ready ones show it in red with " (deleted)", can't start while they name it, and say why ("Which config a stage uses", above); another config is picked with "Change config", with its checkbox for the stages after it. **The default can't be deleted** until another config is the default (built 2026-11-02: the Worker refuses with 409, `default_model_config`, naming it). **A config deleted while a stage runs with it** stops the stage at its next request (built 2026-11-02: the Worker checks the config before every request, before the cache too, and refuses with `deleted_model_config`: "The model config "X" was deleted while the stage ran. Pick another with "Change config" in the stage's ⋮, then retry.").
- **Secrets:** a new value under the same secret name (an expired key replaced, in the Cloudflare dashboard or the desktop app's secrets file) is simply used from then on, by re-runs of old stages too: the config names the secret, not its value. Moving to other secret names (another key, another AWS account) is a clone with the new names, with "Delete the original" ticked, then "Change config" with the checkbox on the first stage that still names the old one. A config whose secret is missing is marked as such on the settings page ("A missing key", above).
- **The free-tier mark** is a value like the others: changing it means a clone. Calls made with a config were counted towards the cap, or not, by that config's mark, for good; editing it would suggest that old calls no longer count.
- **Stored:** a row per config; its name and `deleted_at` are the only columns that change. Built so far (2026-11-02): no editing (the earlier `PUT /api/model-configs/<id>` and the column `supersedes_id` are gone, migration 0025), names required and unique; rename and clone are to build. A stage and each of its calls refer to the row they used, which never changes in what it does. The secrets' names are part of the row; a secret's value isn't recorded in any way.

## Supported models, prices and the config form
**Decided, not built** (2026-11-03 to 2026-11-05, the project owner's design): the plan below. Where it disagrees with "Model configs" above or with §10 (a model string typed by hand, the price table in `llm/prices.ts`), this section is the newer thinking. What is still open is in §15 ("Decide the model configs").

- **Why:** the code has to know which kind of model it talks to, not only the provider. Today the provider ids carry the model family (`anthropic-vertex` and `anthropic-bedrock` are Claude; `google` is Gemini on Google AI Studio), and the Worker's adapter, the effort levels (Gemini has three, quietly mapped from our five), the image limits (`apps/web/src/llm.ts`) and the prices all follow from that. And a model without a price in the code's table can't be used at all unless marked free tier, which hides its spending from the cap: a new model (an Opus 5.6) can't even be tried without a new version of the app.

### Providers and families
- **Providers are platforms,** a fixed list in the code, named in the UI as people call them: **Anthropic, Bedrock, AI Studio, Vertex AI** (and Fake, with Fake (dev) for development); ideally the code's ids are the same four, not today's five ids that mix in the family.
- **Model families** are a second fixed list: **Claude, Gemini** (and Fake). **The adapter is picked by the pair (provider, family):** Claude on Anthropic, Bedrock and Vertex AI; Gemini on AI Studio and Vertex AI. The pair also says which secrets and plain values the form asks for, and which effort levels it offers (for Claude "Model's default" and low to max, for Gemini "Model's default", low, medium, high; a level a single model rejects is found by the Test button, below). Only pairs the code can call exist.
- **A model from the list brings its family;** for a model the user adds, the user picks the family ("Models the user adds", below).

### The list of models and prices: code, generated
- **The supported models and their prices are a TypeScript module, not tables** (decided 2026-11-05): nothing the user adds goes into them (what users add lives in the configs, below), so they are exactly the shipped list. It is **generated by a script from the providers' published price lists** (AWS publishes its as public JSON files; Google's catalog needs credentials), **run at release time and spot-checked before the release,** and reviewed like any other code: filling a list of this size by hand invites mistakes that make the cap undercount. **Never updated by the app** (decided): no button, no update when deploying. A live update would skip the spot-check, and its failures are silent (a provider moving its price list, changing its shape or its way of pricing would make the cap wrong without anyone noticing). New prices come with a new version of the app. The first thing to build of the model configs (§15, "Generate the shipped price list"). The list's date is the "prices as of" on the About page (§10, "How costs are computed and kept").
- **Models,** one entry per model, independent of the provider:
  - a **stable id** (`claude-opus-5-5`), which configs refer to and which survives later versions of the list; a model that leaves the list stays in it, marked retired, so configs naming it still work;
  - its **name for people** ("Claude Opus 5.5"), shown in the pickers and the default config names, and one more way to group and filter the statistics: by the actual model, whatever the provider (§15, "Statistics by model");
  - its **family;**
  - **its model string for each provider,** as that provider spells it, empty where the provider doesn't offer it. On Bedrock's Messages API endpoint, which the code uses, a model string is `anthropic.` followed by Anthropic's own model ID (`anthropic.claude-opus-5-5`, checked 2026-11-04 on Anthropic's page "Claude in Amazon Bedrock"): a documented table, not a stated rule, so the list holds the strings rather than a formula. AWS's price list names models by their names for people, so the script maps them itself.
- **Prices,** one entry per model, provider, region and routing:
  - the **region:** empty for Anthropic and AI Studio, which have none; on Vertex AI, the location as Vertex spells it, one string that decides both where a request runs and its price (`global`, a multi-region such as `eu`, or a region such as `europe-west1`); on Bedrock, the AWS region the request is sent to (the URL's);
  - the **routing,** Bedrock only, in AWS's own terms: **Global, Geographic** (EU, US, JP, AU: AWS's "inference profiles") **or In-region.** On Bedrock's older integration it is a prefix on the model ID (`global.`, `eu.`, none); how the Messages API endpoint asks for it is still open (§15). Prices differ by it: in `eu-central-1`, Opus 5.5 costs $4 per million input tokens routed globally and $4.40 routed regionally or within the EU (AWS's price list, 2026-11-04; Vertex AI's regional and multi-region locations carry the same 10% premium over `global`);
  - **four prices in US dollars per million tokens: input, output, cache read, cache write.** Cache prices aren't a fixed ratio of the input price (a cache hit is 2.5% of it on Fable 5.1, 5% on Opus and Sonnet 5.5, 10% on others). **The four fit every provider and family for our usage** (decided 2026-11-04): Claude's cache write is the 5-minute one (the only time-to-live the adapter asks for; the 1-hour one costs more); Gemini's implicit caching has no write price (0) and reports its hits as `cachedContentTokenCount`; thinking is output for both. **Short-context prices only** (decided 2026-11-04): some prices go up once a prompt passes a threshold (Gemini's Pro models above 200K tokens, Claude's long-context variants on Bedrock, Haiku 5.5 above 100K); the list has the prices below the threshold, and whether our prompts ever pass one is a task of its own (§15, "Do our prompts reach long-context prices?").
- **A price is always looked up at call time** (decided): a config doesn't pin a price; each call records the prices it was billed at (§10), so history stays as it was when a new list changes them.

### Configs
A row per config in D1, as now ("Model configs", "Managing model configs" above), with these columns:
- `id`, `name` (unique ignoring case; the default name below), `created_at`, `deleted_at`;
- `provider`;
- **the model, one of two shapes, never both** (decided 2026-11-05, so that the config and the list can't contradict each other; a CHECK keeps them apart):
  - **a listed model:** `model_id`, the list's id; the model string and the family come from the list, for the config's provider;
  - **a model the user added:** `model_string` and `family`, no `model_id`;
- `effort`;
- `region`, and `routing` (Bedrock only);
- `project` (Vertex AI only, Claude and Gemini alike);
- the **names of its secrets** (never their values, §10);
- **`pricing_kind`: from the list, free or unpriced,** and **`pricing_reference`,** a model id or none:
  - **from the list,** with no reference: the price of the config's own model, provider, region and routing;
  - **from the list, with a reference:** priced as that model, for the config's provider, region and routing ("Models the user adds");
  - **free:** the free-tier mark (§10), which listed models can have too (e.g. Gemini on AI Studio's free tier, whose price is known but whose calls cost nothing);
  - **unpriced:** calls of unknown cost ("Models the user adds").
- **When a new list has a string the user added,** for the config's provider, the Worker converts the config to a listed one: it sets `model_id` and clears the string and the family; the pricing kind stays as the user set it, and later calls get the listed price. **When a provider renames a listed model's string** (Vertex adding an `@` version, say), configs follow the new list by themselves; their requests then miss the cache once, rightly, since they are different requests.
- **The default name** (decided 2026-11-05): the model's name for people, the provider's in parentheses, and the effort after a centred dot: **"Claude Opus 5.5 (Bedrock) · high"**; the effort left out where it is the model's default; a model the user added shows its string in place of the name. Taken already: " (1)", " (2)", … like project names (§4). A second config that differs only in its region is rare, and its user renames it.

### The settings page
- **"Model configs" has a "+" on the heading's line** (like the forms' "+", §6), and each card a "⋮" with Rename, Clone and Delete (refused for the default until another config is the default): no Edit ("Managing model configs", above), and no "Make default" (decided 2026-11-02: the default is picked in its row on the settings page, or with the forms' checkbox).
- **Each card shows a compact price label,** input and output per million tokens, e.g. "$4 / $20 per MTok", or "priced as Claude Opus 5.5", "unpriced", "free tier". Money is shown here, in a stage's details and in the costs view, never in the pipeline panel (§5.6).
- **Creating a config: everything is picked, nothing typed** but the name (which may be left empty for the default name) and, for a model the user adds, its string: the provider; then the model and the region (with the routing on Bedrock, and the project on Vertex AI); the effort, from the family's levels; each secret from a drop-down of the Worker's secret names (a new endpoint listing the names of its text bindings, never their values); the pricing kind where there is a choice; the free-tier checkbox with its confirmation (§10); and a **"Make default"** checkbox (decided 2026-11-02), in the clone form too. Cloning the default with "Delete the original" ticked ticks "Make default" and keeps it ticked: the default can't be deleted unless another config becomes the default.
- **For a listed model, model and region filter each other:** the region picker lists only the regions (and routings) the list has a price for with the chosen model, and the model picker only the models served in the chosen region, so a user who wants their data in Europe picks it first and sees what is available there. A combination without a price can't be picked.
- **For a model the user adds,** the regions are the provider's (a list in the code), or, priced as another model, those where that model has a price. A region where the model isn't served is found at the first call, which fails with the provider's error (acceptable, decided 2026-11-05).
- **A "Test" button** on a config sends a minimal request through the Worker, to show that the model, region and key work before a long run. A hint says what it does and that it costs money (a fraction of a cent, counted towards the cap).
- **Pre-installed:** a new database has a config for the Fake model named "Fake model" (on the cards, a plain "Fake" read unclearly), which is the default (decided; built, migration 0014; free tier: it is for users to try the app, so it costs nothing and never meets the cap), and a spending cap of $1 (built, §10).

### Models the user adds, and their prices
Decided 2026-11-03, for the first release (the project owner's proposal, "option 2.5"). **Why:** new models come out all the time, and users (the project owner first) want to try one in the app the day it comes out, without waiting for a release, which may also mean building the desktop app again or deploying again. But a price the user types can be wrong in ways the app can't see (euros instead of dollars, per thousand tokens, cache prices guessed), and the cap and the costs would then be trusted and wrong. So the user adds a model, but never types a price.
- **What the user enters:** a new model string, with its family, for a provider and regions that already exist (the code's lists): the family picks the adapter and the effort levels. Nothing new for the code to learn: a model string the provider doesn't know, or doesn't serve in the region, fails at the call, with the provider's error shown as it is.
- **How it is priced, one of three:**
  - **Priced as another model:** the user picks a model of the same provider and family from the table, and the new model borrows its prices, region by region; only the regions where the reference has a price can be used. E.g. `claude-opus-5-6` priced as Opus 5.5. Every price still comes from the shipped table, so no sanity checks of typed prices are needed. **Usually close, not always right:** a point release tends to keep its predecessor's price (Opus 4 to 4.1, Sonnet across several versions), but a new generation has moved prices by a factor of 3 either way (Opus 4.5 a third of Opus 4.1's; Haiku up from 3 to 3.5). A cheaper model makes the cap stop early (safe); a dearer one makes it undercount, by that factor at most, which is still far better than counting nothing.
  - **Unpriced:** the app has no price. Its calls are recorded as calls of unknown cost (§10, "Calls of unknown cost"), which the costs view counts apart ("the total may be far higher"), and they don't count towards the spending cap, which can't stop them. Not "free tier": the app doesn't pretend they cost nothing.
  - **Free tier:** the user's account really doesn't pay for it (the mark as it is, §10, with its confirmation).
- **Said plainly when the config is created:** "priced as" gets a short confirmation ("The costs and the spending cap use Opus 5.5's prices for this model; check the provider's price page"); "unpriced" a stronger one ("The spending cap can't limit this model's calls, and the costs won't include them. Check your charges with the provider."). **Shown afterwards:** the config's card says "priced as Opus 5.5" or "unpriced"; the costs view marks the costs computed from a borrowed price as estimated from another model's.
- **The real price wins when it ships:** once the shipped list has the model's string for the config's provider, the config becomes a listed one ("Configs", above) and its real price replaces the borrowed one (or none), by itself, and the card's mark goes. **For later calls only** (decided 2026-11-03): every call keeps the cost and the prices it was recorded with (§10, "How costs are computed and kept"), so the costs and statistics already seen don't change; calls made unpriced stay calls of unknown cost, and calls priced as another model stay marked as estimated from its price.
- **Not built, and not planned for now:** prices typed by the user (with range checks against the family's prices, cache prices required rather than guessed, and typed prices marked wherever prices are shown), only if users ask for it; and updating the prices from inside the app (above, "The list of models and prices").
- **In every case, the user guide says to set a budget at the provider:** the app's cap is against bugs and its costs are estimates; the provider's budget is the real limit.

## Costs

### How costs are computed and kept
- **The app computes the cost itself:** the providers' APIs report token counts per call, not money. Cost = tokens × a price table per model, kept in the code (to move into the database, under discussion: `docs/llm.md`, "Supported models, prices and the config form").
- **Currency: US dollars** for everything, since that is how the providers publish their prices. The amounts are estimates, not the invoice: the bill may be in another currency, with tax or discounts. The app doesn't convert.
- **The cost is stored with each call, when it is made,** so a later price change doesn't rewrite history.
- **So are the prices it was computed with** (decided, built): each call records the price table's entry for its model and the date the table was collected (`price_json`, migration 0009). The table's date (`PRICES_AS_OF` in `apps/worker/src/llm/prices.ts`) is shown on the About page, marked once it is older than three months, so stale prices are noticed and a new version updates them. The costs view (docs/statistics.md, "Costs") may show the prices behind a cost where it doesn't clutter.
- **Costs and statistics come from the rows of the calls and the stages** (§5.8), with no ledger of their own: each call has its cost, each stage its start and end time and its page count (§5.8). Those rows survive everything that removes outputs:
  - stages replaced by re-running from an earlier stage (§5.5), which are no longer visible in the pipeline;
  - stopped stages (§5.6);
  - deleted projects (§4): their project, stage and call rows are kept, marked as deleted.
- **The Statistics page** shows them: the Costs tab (the costs view and the average cost per page) and the other statistics (run times, manual work, failed calls, from the same rows and from the outputs' timings and the manual stages' saves), all in docs/statistics.md.
- **Free-tier configs:** the user can mark an LLM config as free tier, behind a confirmation dialog, since the app can't check it: a response says nothing about whether the call was billed. Calls with such a config are shown as "$0.00" (in a stage's details).
- **The spending cap** sums the costs of the calls started in the last 24 hours, deleted projects included.

### Spending cap
- **Purpose: protection against bugs,** not against a user who transcribes too much. A bug in the app must not be able to burn a lot of money on a handful of scores.
- **A setting: at most $X within any 24 hours** (a rolling window, not the calendar day, so a runaway just before midnight doesn't get two budgets). Once reached, the app refuses every further request that costs money.
- **Always set** (decided): a new database has a cap of $1, and it can be changed but never removed, so there is no way to run without one. (Migration 0012 removes a cap stored as unset, so the $1 applies.)
- **On the settings page** (built): an amount in US dollars ("$ 1.00"), saved when the field is left or Enter is pressed; anything but an amount above $0 isn't saved and says so. It can't be cleared: an empty field isn't saved, and Escape brings back the cap.
- **Why a day and not a month:** with a monthly budget the user picks a large number ("about $30 a month"), and a bug can spend all of it in a day before anything stops. A daily budget makes them pick a small one ("$1 a day"), so a bug is stopped after a small sum.
- **Why not per project:** scores differ a lot in length, and re-running stages adds cost legitimately.
- **Enforced by the Worker,** which makes the LLM calls. A second tab or a stale page can't get around it.
- **The cap can be overshot** by the cost of the calls in flight when it is reached, because a call's cost is only known when it returns. Sequentially that is one call, a few cents. **If requests ever run in parallel, revisit this:** the overshoot could be far too much.
- **Free-tier configs stay usable** after the cap is reached, and don't count towards it. A config wrongly marked as free spends money the cap doesn't see; a spend limit set at the provider is the backstop. **So do unpriced ones** (decided 2026-11-03, "Models the user adds"), whose calls the cap can't count, as their creation said.
