# LLM providers and model configs

How the Worker calls the providers (Anthropic, Vertex AI, Bedrock, Google AI Studio, OpenRouter, the fake one; for the first release Claude on Anthropic, Bedrock and OpenRouter, and Gemini on Vertex AI, Google AI Studio and OpenRouter; Claude on Vertex AI is not supported, below), how calls are recorded, cached and priced, what a model config is and which one a stage uses, and the discussion of supported models and prices. What each LLM stage asks is in `docs/stages/`; costs and the spending cap are below ("Costs"). § numbers here are `docs/overview.md`'s sections.

## Calling the providers
Built: `apps/worker/src/llm/`. One small request and response shape for every provider (`LlmProvider`, §3): a system prompt, messages of text and images, a maximum of output tokens, an effort, and optionally a JSON schema the answer must follow (the provider's schema-constrained output, §7.1; the answer is then parsed). The response says which model answered, the text (and parsed JSON), why it stopped (finished, cut off, refused) and the tokens. Errors are typed and say whether retrying can help.
- **The chosen model answers, or the call fails.** No fallback to another model, not even Anthropic's server-side fallback on refusals: a refusal comes back as a refusal.
- **Several images in one request are labelled** with a text block right before each ("System 3:", "System 3, stretch 2:"): content is an ordered list of text and images for both Anthropic and Gemini, and the adapters keep the order. Neither API passes a file name to the model. Anthropic's vision docs recommend this way of labelling.
- **Anthropic** (Claude API), with the official SDK. Requests are streamed, so long answers don't hit timeouts. Thinking is left at the model's default (adaptive on current models), and effort maps directly. As a sanity check, an answer that names another model than the one asked is an error (`unexpected_model`). First real calls (2026-11-07): `llm:try` with Sonnet 5.5, and from the app a config's Test and a whole `layout` with Opus 5.5 (excellent results). The account needs prepaid credits (at least $5) before it answers at all.
- **Google** (Gemini API, keys from AI Studio), with the official SDK. Effort maps to Gemini's thinking levels (low, medium, high), which the listed models take from Gemini 2.5 on (Google's page "Gemini thinking", 2026-11-06; older ones wanted a token budget). Thinking tokens count as output, cached ones apart from the rest. Gemini names the exact version that answered, which can differ from the name asked for (an alias, a dated version), so there is no model check. First real calls (2026-11-07): `llm:try` with Gemini 3.8 Flash, and from the app a config's Test and a whole `layout`. Even with billing set up, a paid account answers only from a prepaid balance in AI Studio (at least €5; otherwise 429, "Your prepayment credits are depleted").
- **Not supported: Claude on Google Cloud's Vertex AI** (removed 2026-11-09, the project owner: nothing untested is released, and it couldn't be tested).   - **Enabling the model** (Opus 5.5) is a purchase on Google Cloud Marketplace, after a form about the intended use (a business website, an industry, who uses it). It was refused on the project's first billing account: a free trial's credits don't pay for partner models. It went through on a second, paid billing account, linked to the project. The console's "Claude models" page (under "Agent Platform", "Models", "Partner Services") also has APIs of its own to enable, "Claude API" (`claude.googleapis.com`) and "Anthropic Managed Claude", which made no difference.
  - **The quota stays 0:** every Claude model's requests and tokens per minute, at `global`, `eu` and `us` (read from the Service Usage API), so every call fails with 429, in `llm:try` and in Google's own console alike. Every request to raise it, each with a reason, was refused automatically.
  - **The conclusion:** Google Cloud is built for large businesses, and for a person's own instance the way to Claude is long and may be closed. Claude in the EU goes through Bedrock, or OpenRouter's EU host. Gemini on Vertex AI works and stays.

Configured with a region (e.g. `eu-central-1`) and either a Bedrock API key or an AWS access key pair (a key ID and a secret), both secrets; with a key pair, requests are signed with AWS Signature V4. **Both are kept** (2026-11-08): removing the key pairs was decided and done, then undone the same day, since a personal AWS account can't use long-term Bedrock API keys (it belongs to an organization AWS runs, which doesn't allow them), so the project owner uses an access key pair.   - **Setting up an AWS account for it** (for the user guide): a new account must first be verified (up to 24 hours), then the AWS Marketplace agreement for the model signed, then Anthropic's use-case form submitted; before that, requests are refused with "not available for this account". The project owner's account is in this process (2026-10-09), with 100 USD of starter credits valid for six months.
  - **`bedrock-runtime`, not the Messages API endpoint ("Mantle", `bedrock-mantle`)** (decided 2026-11-08, the project owner): the app first used Mantle, Anthropic's page presenting it as the integration for Opus 4.7 and later, with no reason recorded. But Mantle refused `eu.anthropic.claude-haiku-4-5` as a model that doesn't exist, and documents no way to choose global or geographic routing; AWS's pages recommend `bedrock-runtime` for most work, Mantle only for a few niche things. On `bedrock-runtime` the routing is an inference profile, the model ID with a prefix: `global.`, or the geography's (`eu.`, `us.`, `jp.`, `au.`, …); in-region routing sends the model ID alone, where a model allows it (`bedrockModel`, `llm/index.ts`). Anthropic's page on that integration ("Claude on Amazon Bedrock (Opus 4.6 and earlier)") says the newer models are reachable through `InvokeModel` too, served by the same infrastructure. Not supported there: automatic prompt caching (a top-level `cache_control`), which the app doesn't use. **The sanity check takes the answer's model as Bedrock names it:** the first real call (2026-11-08) asked `eu.anthropic.claude-sonnet-4-6` and was answered by `claude-sonnet-4-6`, Anthropic's own name; so the check takes the string as sent, without the routing's prefix, or Anthropic's name (for a dated model with or without its date; `bedrockNames`, `llm/anthropic.ts`).
  - **Spending:** AWS has no hard spending cap as far as known: budgets alert, and a budget action can at most attach a deny policy. The app's spending cap (§10) and the IAM user's permissions are the limits.

Each answer says who ran it (`servedBy`, kept in the stored response) and what it cost (`usage.cost`, in US dollars of credits, always included): **OpenRouter's configs are priced by the provider** ("Configs", `pricing_kind`). Tokens: `prompt_tokens` counts the cache reads and writes too (OpenAI's convention), so the input tokens are what is left. **An account per config** (`account`): its plan, Standard or Business, sets the fee on credit purchases (5.5% or 8%, `ACCOUNT_FEES` in `models.ts`), added to every call's cost; **only Business may use the EU** (region `eu`: `eu.openrouter.ai`, which serves in Europe only and fails rather than leaving it; region `""` is everywhere). The form asks for the region only with a Business account. One secret: the API key. **The list** has OpenRouter's models without prices, only where it offers them (everywhere, the EU), from its models API on both hosts (`gather/openrouter.ts`).
  - **Found in its docs and API** (2026-11-08): `usage.cost` is in every answer, in credits (US dollars), the total charged (the old `usage: {include: true}` is deprecated and does nothing); prices differ by who runs the model (Opus 5.5: $4 / $20 per million tokens on global endpoints, $4.40 / $22 on regional ones, $8 / $40 on Anthropic's `fast` tier, which only a request asks for), and OpenRouter picks by cost and speed, so a global call may be served regionally; `/api/v1/models/<id>/endpoints` lists every provider's prices, `/api/v1/models` the lowest. The EU host fails rather than leaving the EU (EU/EEA, UK, Switzerland) and has its own models API with EU prices. Claude's cache marks get sticky routing to the same provider, to keep cache hits. The models API gives each model's `reasoning.supported_efforts`.
  - **The fee and taxes** (found with a real purchase, 2026-11-09): the fee is added on top of a purchase (100 USD of credits cost 108 USD on Business), so a call's cost × (1 + fee) is what it really cost; it is at least $0.80 per purchase, so buying less than 10 USD of credits is wasteful. VAT is added on top of credits and fee together (19% in Germany: 128.52 USD for 100 USD of credits), as with every other provider (§15, "VAT in the costs").
  - **Tried with real calls** (the project owner, 2026-11-09): Claude Opus 5.5 at low effort on the EU host and Gemini 3.1 Pro Preview at medium effort globally (a config's Test each), and `layout` and `analyze` on Claude. The answer names the model by its id (`anthropic/claude-opus-5.5`). Not checked yet: that the reported costs agree with the tokens and the prices of who ran the call, and that the input tokens come out right. The total agrees with OpenRouter's dashboard as far as can be told: 10 calls and $0.67 there (credits used, without the fee); the app's 9 finished calls reported $0.6317, and the 10th, an `extract` call on Gemini stopped by the user, was billed but has no cost in the app (its row stays `running`), which would account for the rest. Claude in the EU was run by Google (Vertex AI). `extract` on Claude fails like on Anthropic's API, its schema refused (below, "Claude's limit on schemas").
  - **A provider's refusal** comes as "Provider returned error", with the provider's own error in `error.metadata` (`provider_name`, and `raw`, the provider's body): the error message includes both ("Provider returned error (Google): The compiled grammar is too large, …"; `errorMessage` in `openrouter.ts`, found 2026-11-09, when only the generic message was kept).
- **Gemini on Google Cloud's Vertex AI** (built 2026-11-03; provider `google-vertex`, `VertexGeminiProvider` in `apps/worker/src/llm/google.ts`), configured with a service account's key file (a secret), a location (`region`: a single region such as `europe-west4`, `eu` or `us` for a multi-region, or `global`) and optionally a project (default: the key file's). Vertex's REST API is called directly (`generateContent`, with the same body as the Gemini API's: the system instruction and the generation config apart), because Google's SDK authenticates with Google's auth library, which doesn't run in a Worker; the token comes from our own token source instead (`googleServiceAccount.ts`), which signs Google's service-account claim with WebCrypto, exchanges it for an access token, and reuses the token until a minute before it expires, across requests (one per service account; a refused service account is an `auth` error). Billing goes through Google Cloud, after the fact; Google Cloud has enforced spending caps per project (the project owner's, "score3ly", has a monthly cap of €30). The answer is read as the Gemini API's (`fromResult`), so the thinking levels, refusals, thought summaries left out and cached tokens counted apart are the same. The endpoint is Anthropic's Vertex SDK's rule: `aiplatform.googleapis.com` for `global`, `aiplatform.eu.rep.googleapis.com` (and `.us.`) for the multi-regions, `<region>-aiplatform.googleapis.com` otherwise. First real calls (2026-11-06, `llm:try`): Gemini 3.1 Pro Preview at `global`, with and without `--json`, so `responseJsonSchema` is accepted on Vertex's `v1`; and from the app (2026-11-07), a config's Test with Gemini 4 Argon at `eu` and effort medium, so `thinkingLevel` is accepted too. Its prices and the locations serving each model come from the list of models ("Supported models, prices and the config form").
- **Authentication stays in the Worker's own code** (reviewed 2026-11-06, after a second opinion from Gemini, which saw problems where there are none):
  - **Bedrock's signing** (AWS Signature V4, with an access key pair) is done by Anthropic's Bedrock client, not by our code; a Bedrock API key needs no signing at all. Gemini claimed Bedrock has no API keys: it has had them since 2025.
  - **Vertex AI's token exchange** (a JWT signed with the service account's key, exchanged for an access token) is our own small token source, built and tested, with WebCrypto and without `nodejs_compat`. Its RSA signature is native code, well under a millisecond of CPU time, so it doesn't matter for the Workers free plan's limit of 10 ms; what may matter is the handling of large requests (§15, "Measure the Worker's CPU time per LLM request").
  - **A service account's key file fits in a Worker secret** (about 2.3 KB; a secret may have up to 5 KB), and `wrangler secret put NAME < key.json` takes it from a file, line breaks and all.
  - **Other model families on Bedrock** (Mistral, DeepSeek, GLM, …) can't use Anthropic's client, which only speaks Claude's Messages API. A new family needs its own adapter anyway (the pair of provider and family); with a Bedrock API key it is a plain `fetch` with the key as a bearer token (believed to work with Bedrock's Converse API, not checked), with a key pair it needs signing, with a small library made for Workers (`aws4fetch`) rather than AWS's own SDK, which is heavy.
- **Not used: Cloudflare AI Gateway** (decided 2026-11-06). It would hold the providers' keys and sign or authenticate the requests itself, and it logs and caches calls. Not for us: it is Cloudflare-only beyond D1, R2 and the secrets, so the desktop app would need a Cloudflare account, against the rule that keeps it cheap (`docs/desktop.md`); its cache duplicates our records and is worse for us (it keys on the request's bytes, so the images would have to be made before a lookup, where ours keys on recipes); its logs are one more place where prompts and score images are stored, with a jurisdiction we don't know; and the work it would take over is already done. Gemini's other suggestion, that the desktop app call the providers directly and keep the Worker for the hosted version, is what the desktop app already does, with one code path: the Worker's own app runs in Electron's main process and calls the providers from the user's machine, with the secrets in a local file (`docs/desktop.md`).
- **Prompt caching** (decided and built, 2026-10-31): a request can mark parts of its prompt, "cache up to here" (`cacheUpTo: true` on a part of a message, text or image), when later requests will start with the same prefix, e.g. `review`'s calls, which all start with the whole score and the issues (`docs/stages/music.md`, `review`). The provider then bills that prefix at its cache-write price once, and at its cache-read price, a fraction of the input price, each time a later request starts with it.
  - **Provider-neutral:** the mark says where, each adapter decides how. **Claude** (Anthropic's API, Bedrock): a cache breakpoint (`cache_control`) on that part, with the default lifetime, 5 minutes from the last use (1 hour is possible, at twice the input price to write instead of 1.25 times: a task, §15, "The cache's lifetime for Claude"); a prefix shorter than the model's minimum is simply not cached. **Gemini:** the mark is ignored. Gemini caches matching prefixes by itself (implicit caching, without a guarantee), and reports what it read from the cache, which is counted as cache reads; its explicit caching (a cached-content resource created first, with a lifetime and a storage charge) isn't used. The fake providers ignore it.
  - **At most 4 marks per request** (Anthropic's limit of breakpoints); the Worker refuses more.
  - **Not part of the request key** (§5.2): the marks change what a call costs, not what the model is given, so moving them doesn't make paid calls run again. The recorded request keeps them, as it was sent.
  - **Used by `review`** (built): after the issues and warnings, and after the last block of the log (`docs/stages/music.md`, "`review`, built"). Whether `extract` gains from a mark after the part all its calls share (the instructions and the observations) is to be seen.

- **Wired into the Worker** (built, `apps/worker/src/llmRoutes.ts`), as Block 1 of the LLM stages:
  - **`POST /api/projects/<id>/stages/<stage id>/llm`** takes one request of a running stage (system prompt, messages of text and images, base64, an optional JSON schema and maximum of output tokens). The model config is the stage's (set when it starts, from the stage's choice or the default setting, "Which config a stage uses"). **The item-level cache comes first** (decided): an earlier successful call with the same request key, not deleted, is served at no cost, even when the spending cap is reached. Only then: the price, the spending cap, the secrets, the call. The request key is the hash of the request, with each image replaced by its recipe key (§5.2, "Only recipes"), and of the model's provider, model and effort.
  - **The browser asks first without the images** (built, `ask` in `apps/web/src/llm.ts`): each image named only by its recipe key. A cached call is served then; otherwise the answer is `{ imagesNeeded: true }`, and only then does the browser make the images (from the device's cache, or from their recipes), check the request's size against the provider's limits, and send it again with them. So a re-run on another device makes no images for calls already paid for. A stage builds its requests with each image as its recipe and the function that makes it (`requestImage`); every image sent has a recipe, `layout`'s drawings for its check rounds included (cached now, like the others).
  - **Requests must be built the same way in a run and in a retry:** an answer that later requests are built from (a page's analysis, a system's extraction) is used as it reads back from storage, canonical JSON, also in the run that got it; otherwise the order of its keys differed and the whole-score `analyze` request missed the cache after a retry (found while building this).
  - **Every call is recorded** in `llm_calls`, with its tokens (cache reads and writes apart) and cost. The request is stored in R2 as canonical JSON **with images replaced by their recipe keys and hashes** (decided, built): images are never stored (§2); a cached request is found and served without them, and the images of a request can be rebuilt from the stored outputs when someone needs to look at them (inspection and debugging aren't ordinary use). The response (text, parsed JSON, stop reason, the provider's raw answer) is stored as JSON.
  - **Statuses:** `ok`; `cut_off`, `refused`, `unparseable` and `error` are recorded but never served from the cache. `unparseable` is first the JSON itself: an answer that isn't valid JSON, although the provider was asked for schema-constrained output. The provider's response around it is fine, so the adapter returns it with its usage (`invalidJson` says what is wrong), and its tokens and cost are recorded like any other call's (decided, built).
  - **Why a call threw** is kept with it : `error_kind`, the adapter's kind of error (`auth`, `rate_limit`, `overloaded`, `bad_request`, `server`: the provider answered with an HTTP error; `network`: no connection; `timeout`; `aborted`; `unreadable_response`: the provider answered, but its response couldn't be read, broken JSON or a stream that ended without a message; `unexpected_model`: another model answered than the one asked, not thrown but recorded with its tokens and cost, since it was billed; `unknown`), and `http_status`, the HTTP status the provider answered with, if any (today only an HTTP error's: an unreadable response after a 200 has none). A call that didn't throw has neither.
  - **A known gap in the costs: calls with no readable response** (decided, accepted). When the provider's response itself can't be read (its outer JSON broken, a stream cut off midway), the client library throws, no token counts are known, and the call is recorded as `error` with no cost. The provider may still have billed it, so the costs underestimate by such calls. They are rare; errors with no answer at all (a refused connection, an overload, a timeout before any answer) aren't billed anyway.
  - **Calls of unknown cost** (decided): calls with no recorded tokens, unless the provider answered with an HTTP error status (`http_status` 400 or above; a successful status, or none, leaves the cost unknown) or the error is `auth` without a status (the credentials failed before anything was sent: a service account key that can't be read, Bedrock given both kinds of credentials), and calls still `running` that started more than 15 minutes ago (decided: such a call will never answer; the tab was closed while it waited, and the provider may well have answered and billed). A call running for less may still answer, and isn't counted yet. Some cost nothing (no connection), some were billed; the count says how far the costs may fall short. An HTTP error (401, 429, 529 …) is the provider refusing the call, which isn't billed. (A refused service account is `auth` with the HTTP status of Google's token endpoint, not the provider's: nothing was sent either.)
  - **Answers the stage can't use** although their JSON is fine (LilyPond in `extract`'s answer that doesn't parse, a `layout` box outside the page): the stage marks the call unusable (`POST …/llm-calls/<call id>/unusable` with the reason), which records it as `unparseable`, so it isn't served from the cache again; its cost stays recorded.
  - **Free-tier configs are always allowed:** no spending cap needed, no known price needed, and they don't count towards the cap.
  - **Errors the stage acts on** carry a code: `spending_cap`, `no_model_config`, `deleted_model_config`, `unsupported_model_config`, `missing_secret`. The stage fails with the message, and a retry later asks only what is missing.
  - **Model configs** (`/api/model-configs`) and **settings** (`/api/settings`: the default model config, the spending cap and the run mode for new projects) have endpoints; the settings page shows the run mode, the spending cap and the model configs (read-only) so far. Each provider's form is checked: which secrets (by the Worker secret's name) and which plain values it needs.
  - **A fake provider** (`provider: "fake"`) answers without network: the simplest JSON its schema allows, tokens counted from the request's size; some model names make it fail on purpose. **It costs nothing** (decided, built), whether its config is marked free tier or not: it ships with the app, installed by default, for trying the app without paying, and never shows in the statistics of costs. **`fake-dev`** answers the same with made-up prices, for developing and testing the costs and the spending cap. **It is offered only with the Worker's `DEV_PROVIDERS`** (decided 2026-11-06): `npm run dev:worker -- --var DEV_PROVIDERS:true` (Wrangler; or `DEV_PROVIDERS=true` in `.dev.vars`), `--dev-providers` for the desktop server (`node dist/server.js --dev-providers`, `npm run desktop -- --dev-providers`). With it, Fake (dev) is an ordinary provider in the config form (with its listed fake model and its prices), cloned like any; without it, it isn't offered, and creating a config on it is refused ("Fake with costs is a provider for development: start the Worker with DEV_PROVIDERS=true to use it."). Configs already made on it stay usable and show as usual, in the settings and the statistics; cloning one without the flag says its provider isn't offered now. For developers only; the user guide doesn't mention it. Two steps get more, so the pipeline runs end to end: `layout` two systems on every page, each with three bar lines, and `extract` the stretches asked for, a voice per staff with a whole-measure rest in 4/4, a made-up doubt on every system and a format issue on the first (§6, `extract`). For tests, and for trying the pipeline without paying.
  - **In the browser** (`apps/web/src/llm.ts`): the stage's model config, the part of the stage key that depends on it (provider, model, effort), images as request content, and asking the model.

## Claude's limit on schemas
**The problem** (found 2026-11-07, the first `analyze` on Anthropic's API): Anthropic refuses most of our stages' JSON schemas for schema-constrained output, with a 400 before the model runs (so the call isn't billed). The limit doesn't depend on the model (Opus 5.5 and Sonnet 5.5 refuse the same schemas), and is the same on Bedrock as far as known (the same Messages API; not tried). Gemini takes all of them. So a run on Claude can't finish today.

| Schema | Anthropic's answer |
|---|---|
| `layout` | accepted (it ran) |
| `review` | accepted |
| `analyze`, per page | "The compiled grammar is too large, which would cause performance issues." |
| `analyze`, whole score | the same |
| `extract` | the same |
| `apply_review` | "too many parameters with union types (18 …; limit: 16)" |

(The table is the first probe, before the changes under "Being tried" below: `analyze` and `apply_review` are accepted now.)

**What the grammar is.** Constrained decoding: Anthropic compiles the schema into a grammar, rules describing every text that is valid JSON for it, and while the model writes, masks out at each step the tokens that would break the rules; so the answer is guaranteed to follow the schema, not just likely to. A schema `{"type":"object","properties":{"at":{"enum":["start","end"]}},"required":["at"]}` becomes roughly

```
root ::= "{" ws "\"at\"" ws ":" ws at ws "}"
at   ::= "\"start\"" | "\"end\""
ws   ::= [ \t\n]*
```

and every object, property, array, enum and `anyOf` adds rules. The grammar is compiled on Anthropic's servers and never shown.

**How its size is measured** isn't documented. Anthropic's page on structured outputs gives explicit limits (at most 20 strict tools, 24 optional properties, 16 properties with `anyOf` or a type array, across all the request's schemas) and "additional internal limits on the compiled grammar size", where optional properties, unions, nested objects and the number of tools "interact", plus a compilation timeout of 180 seconds. What is usually measured in constrained decoding isn't the rules but what they compile into: a state machine checked against the whole vocabulary (about 100k tokens) at every step. Sequences of fields add to it; alternatives (an optional or nullable field) roughly double a part of it, hence the explicit limits on those; arrays and nested objects add states of their own. So not characters or depth as such: the best proxy is the number of distinct places in the JSON where the decoder must know what may come next.

**What the probes found** (2026-11-07, `npm run llm:probe-schemas -w apps/worker -- [model] [name prefix]`, `apps/worker/scripts/probe-schemas.ts`: a short text-only request per schema and variant; about $0.10 for some 30 probes on Sonnet). Our schemas have no optional properties (everything is `required`, `null` where empty); `analyze`'s page schema has 5 nullable fields, 30 enums, 31 objects and 16 arrays of objects, in 7.3 KB.
- **The size adds up:** the metadata alone is accepted; the observations are accepted with up to 6 of their 7 lists (each list alone too) and refused with all 7.
- **The usual fixes barely help:** without enums, or without `anyOf`, the page schema is still refused; without both, the observations alone pass, but metadata and observations together don't. Shared definitions (`$defs` and `$ref` for the objects that occur more than once) change nothing, so what a definition holds is compiled at every use.
- **Splitting can't save the whole-score `analyze`:** it holds the observations twice (corrections and additions), each already at the limit.
- **The threshold is unknown and can change** on Anthropic's side without notice, so a schema just under it is fragile.

**The options** (to decide: §15, "Decide how Claude's schemas fit"):
1. **No constraint on Anthropic for the schemas that don't fit:** the schema goes in the prompt, our own checks (`shapeProblem` and each stage's checks) validate the answer, and a wrong shape is retried. Simple; these calls lose the guarantee of the shape, so wrong shapes cost retries. Changes §7.1 ("the provider's schema-constrained output").
2. **Schemas redesigned to fit:** least likely to work (the page schema fails even without enums and `anyOf`), and fragile near an undocumented limit. Would do for `apply_review` alone (two nullable fields fewer).
3. **Requests split into several calls:** more calls and cost, and no help for the whole-score `analyze`.
4. **Constrained first, unconstrained on this 400:** the first try is free, but the behaviour is implicit, inside the adapter.

The leaning (Claude's recommendation, not decided): 1, chosen explicitly per request rather than by catching the error; 2 for `apply_review`.

**Being tried** (2026-11-07, on branch `claude/friendly-curie-wb7w4w`, not merged): option 2 for `analyze`, its answer flat (`docs/stages/analyze.md`, "The answer's shape"). The page schema: 2.3 KB, 8 objects, 7 enums, 4 nullable fields (was 7.3 KB, 31, 30, 5). Probed (2026-11-07, Sonnet 5.5): **the page schema is accepted,** with room (also without enums or `anyOf`, and its halves alone). **The whole score's, at first 4.7 KB, 16, 15, 7, was still refused,** but only just: accepted without its additions, and accepted with `$defs` (which made no difference on the old schemas). So corrections and additions became one list (`edits`), holding the observations once: now 3.1 KB, 10 objects, 10 enums, 4 nullable fields (was 13.8 KB, 55, 52, 10), **accepted** by the probe, and `analyze` (both calls) ran in the app on Claude (2026-11-07). And for `apply_review`, its texts with no value "" instead of null (`docs/stages/music.md`, `apply_review`): 4 properties with unions instead of 18 (the limit is 16): **accepted** by the probe (2026-11-07); not yet run in the app (the run stopped at `extract`). **`extract` was still refused** ("compiled grammar is too large"), in the app too. So (2026-11-09) its schema lost every nullable field, 13 of them (`docs/notation.md`, "The lens": `""` and `-1` for no value, a stretch's class and kind merged into one enum, its ending an enum and a label instead of an object or null): no `anyOf` left, and one nested object fewer per stretch. **Not probed yet** (no key in the session where it was made).

## Model configs
- **A model config** is a stored, named combination of provider, model, thinking effort and the provider's authentication. The user can keep several. They live in D1 and are managed in the settings: created, renamed, cloned and deleted, never edited ("Managing model configs", below).
- **The model is the provider's own string** (to be replaced by picking from the supported models, see "Supported models, prices and the config form" below), entered as the provider spells it (`claude-opus-5-5` on Anthropic's API, an `anthropic.`-prefixed ID on Bedrock, ...). The app doesn't translate between providers' names, and the sanity check compares the answer's model with that string as it is ("Calling the providers").
- **A name** for each model config, shown on the stage cards (§5.6), shortened in the middle when it doesn't fit, like project and file names (§5.7). **Required, and unique ignoring case** among the configs that aren't deleted (decided and built 2026-11-02: the Worker gives the name and refuses a taken one with 409, `configName` in `llmRoutes.ts`, and a unique index keeps names unique): the field in the create and clone forms may be left empty, and its label says that the name is then made from the model and the effort, e.g. "claude-opus-5-5 · high" (the model alone where the effort is the model's default), with " (1)", " (2)", … for the first free one if that is taken, like project names (§4). **To change with the supported models** (decided 2026-11-05): "Claude Opus 5.5 (Bedrock) · high" ("Supported models, prices and the config form", "Configs"). A rename to a name that is taken is refused, like a project's.
- **Each provider declares its own form:** which fields are secrets and which are plain values. The plain Anthropic and Google APIs take one key; Google Vertex AI wants a service-account file plus a project and a region, AWS Bedrock an access key pair plus a region. The form is generated from a schema, like a step's config (§3).
- **A secret field is a dropdown of the Worker's secrets, by name** (§10). The config stores the name, never the value. Several keys per provider are possible, e.g. a free-tier key and a paid one.
- **A missing key:** if a secret was removed or renamed, the configs pointing to it are broken. **The stage fails when a call needs the secret** (decided 2026-11-02: no checking of configs everywhere, a clear message where it fails is enough), with a message that names the config and the secret and says where secrets are set: "The model config "Opus" needs the secret ANTHROPIC_KEY, which isn't set. Set it where the app's secrets are kept (Settings, "Secrets"), then retry." (`missingSecretMessage` in `llmRoutes.ts`). Calls served from the record need no secret, so a stage whose calls are all recorded still runs. Possible later, if it turns out to be needed: the settings page marking a config whose secrets aren't set (the Worker can list the names it was given, an endpoint the config form needs anyway).

(Missing secrets, unlike this, are only found when a call needs them: "A missing key", above.)
- **"Change config" in an LLM stage's "⋮"** picks another config for that stage, with a checkbox **"Apply to the remaining stages planned in this pipeline"** (decided 2026-11-02; it doesn't name them): every LLM stage after it in the pipeline (carried further reviews included), never one before it; unticked at first, and hidden when no LLM stage comes after it. It adds no runs of its own: a new config already replaces everything after the stage (§5.5), and the checkbox only decides whether those stages run again on their own configs or on the new one. With nothing run yet, it sets the planned stages in place, without a confirmation. Changing the first LLM stage's config with the checkbox switches the whole project, so there is no separate action for that. Ticked with nothing else changed, only the later stages change (this one is replaced by itself, served from the record). The runners keep the rest of a stage's config when they record the one they used.
- **The settings page:** a row in the settings list, like "Run mode for new projects": **"Default model config for new LLM stages"** (decided 2026-11-02; "LLM", as in a stage's kind and "Paid LLM calls" on the same page), a drop-down of the configs by name (built 2026-11-02, `SettingsPage.tsx`: a pick is saved at once), with the hint **"Given to every LLM stage when it is created: in a new project, or when one is added to a project. The code that handles a missing default or a stage without a config (the Worker's `no_model_config`, a "—" in the pickers) stays, as a guard against a database edited by hand. ## Managing model configs
Decided 2026-11-02, to build (it replaces the earlier design, where editing a config added a new row and marked the old one deleted). **A config's values never change:** provider, model, effort, region and other plain values, the names of its secrets, and the free-tier mark. Changing any of them would change what a stage that names the config does, and which version a stage would get is exactly the kind of arbitrary rule that confuses. So there is no editing of values at all; there is cloning. What the user can do:
- **Create** a config.
- **Rename** a config. A real edit: the name is in no key and changes no result, so the new name shows everywhere at once, in past runs too (a run report downloaded later has the new name; one saved earlier is a file and keeps the old). **Names are required and unique, ignoring case** ("Model configs", above): a card or a picker showing two configs of the same name says nothing.
- **Clone** a config, adjusting its values in the cloning form. A clone must differ from every existing config in more than its name:
  - **The same values and the same name as an existing config:** refused, saying why; nothing is deleted.
  - **The same values as the original, another name:** not created; the message offers to rename the original instead ("A config with these settings already exists: "Claude". Rename "Claude" to "Opus 5.5" instead?"). This is also what happens when only the name was changed.
  - **The same values as another config than the original, another name than both:** not created; the message offers to rename that config instead, naming it.
  - **"Delete the original"** (a checkbox in the cloning form) makes replacing a config one workflow, with the same confirmation as a delete, and it still reads as a new config, not an edit. With the box ticked, the offers above say so: "Rename "Claude" to "Opus 5.5" instead of deleting it?", and "Rename "Sonnet" to "Opus 5.5" and delete "Claude"?".
- **Delete** a config. Nothing changes in existing stages: those that ran keep naming it, marked as deleted; planned and ready ones show it in red with " (deleted)", can't start while they name it, and say why ("Which config a stage uses", above); another config is picked with "Change config", with its checkbox for the stages after it. **The default can't be deleted** until another config is the default (built 2026-11-02: the Worker refuses with 409, `default_model_config`, naming it). **A config deleted while a stage runs with it** stops the stage at its next request (built 2026-11-02: the Worker checks the config before every request, before the cache too, and refuses with `deleted_model_config`: "The model config "X" was deleted while the stage ran. Pick another with "Change config" in the stage's ⋮, then retry.").
- **Secrets:** a new value under the same secret name (an expired key replaced, in the Cloudflare dashboard or the desktop app's secrets file) is simply used from then on, by re-runs of old stages too: the config names the secret, not its value. Moving to other secret names (another key, another AWS account) is a clone with the new names, with "Delete the original" ticked, then "Change config" with the checkbox on the first stage that still names the old one. A config whose secret is missing is marked as such on the settings page ("A missing key", above).
- **The free-tier mark** is a value like the others: changing it means a clone. Calls made with a config were counted towards the cap, or not, by that config's mark, for good; editing it would suggest that old calls no longer count.
- **Stored:** a row per config; its name and `deleted_at` are the only columns that change. Built so far (2026-11-02): no editing (the earlier `PUT /api/model-configs/<id>` and the column `supersedes_id` are gone), names required and unique; rename and clone built 2026-11-05 (below, "The settings page"). A stage and each of its calls refer to the row they used, which never changes in what it does. The secrets' names are part of the row; a secret's value isn't recorded in any way.

  - **the effort levels it takes** (decided 2026-11-06), none for some (Claude Haiku 4.5 and the older 4.x models): the form then offers only "—", with "Claude Haiku 4.5 takes no effort level: it runs as it is." under the picker, and the Worker refuses an effort for it; left out, all of its family's (a model added by hand always gets those). **And whether the adapter must ask for adaptive thinking** (`thinking: "adaptive"`): Claude Opus 4.7 and 4.8 think only when asked, where the 5.x models think by themselves. Both kept by hand in `gather/claude-models.json`, from Anthropic's documentation (checked by the project owner, 2026-11-06);
  - **its model string for each provider,** as that provider spells it, empty where the provider doesn't offer it. On Bedrock's `bedrock-runtime`, which the code uses, a model string is the model ID the inference profiles are named after, without their prefix (`anthropic.claude-opus-5-5`; dated for the older models, `anthropic.claude-haiku-4-5-20251001-v1:0`), from each model's card on AWS (2026-11-08): a documented table, not a stated rule, so the list holds the strings rather than a formula. AWS's price list names models by their names for people, so the script maps them itself.
- **Regions,** one entry per provider and region (decided 2026-11-05: collected with the models and prices, nothing about regions known by the code): the region, and on Bedrock the routings it offers and its geography (EU, US, JP, AU, for geographic routing). A model the user adds is offered its provider's regions; a listed model is offered the places where it has a price.
- **Prices,** one entry per model, provider, region and routing:
  - the **region:** empty for Anthropic and AI Studio, which have none; on Vertex AI, the location as Vertex spells it, one string that decides both where a request runs and its price (`global`, a multi-region such as `eu`, or a region such as `europe-west1`); on Bedrock, the AWS region the request is sent to (the URL's);
  - the **routing,** Bedrock only, in AWS's own terms: **Global, Geographic** (EU, US, JP, AU, …: AWS's "inference profiles") **or In-region.** On `bedrock-runtime` it is a prefix on the model ID (`global.`, `eu.`, none). Prices differ by it: in `eu-central-1`, Opus 5.5 costs $4 per million input tokens routed globally and $4.40 routed regionally or within the EU (AWS's price list, 2026-11-04; Vertex AI's regional and multi-region locations carry the same 10% premium over `global`);
  - **four prices in US dollars per million tokens: input, output, cache read, cache write.** Cache prices aren't a fixed ratio of the input price (a cache hit is 2.5% of it on Fable 5.1, 5% on Opus and Sonnet 5.5, 10% on others). **The four fit every provider and family for our usage** (decided 2026-11-04): Claude's cache write is the 5-minute one (the only time-to-live the adapter asks for; the 1-hour one costs more); Gemini's implicit caching has no write price (0) and reports its hits as `cachedContentTokenCount`; thinking is output for both. **Short-context prices only** (decided 2026-11-04): some prices go up once a prompt passes a threshold (Gemini's Pro models above 200K tokens, Claude's long-context variants on Bedrock, Haiku 5.5 above 100K); the list has the prices below the threshold, and whether our prompts ever pass one is a task of its own (§15, "Do our prompts reach long-context prices?").
- **A price is always looked up at call time** (decided): a config doesn't pin a price; each call records the prices it was billed at (§10), so history stays as it was when a new list changes them.

### Models the user adds, and their prices
Decided 2026-11-03, for the first release (the project owner's proposal, "option 2.5"). **Why:** new models come out all the time, and users (the project owner first) want to try one in the app the day it comes out, without waiting for a release, which may also mean building the desktop app again or deploying again. But a price the user types can be wrong in ways the app can't see (euros instead of dollars, per thousand tokens, cache prices guessed), and the cap and the costs would then be trusted and wrong. So the user adds a model, but never types a price.
- **What the user enters:** a new model string, with its family, for a provider and regions that already exist (a pair the app supports, the list's regions): the family picks the adapter and the effort levels. Nothing new for the code to learn: a model string the provider doesn't know, or doesn't serve in the region, fails at the call, with the provider's error shown as it is.
- **How it is priced, one of three:**
  - **Priced as another model:** the user picks a model of the same provider and family from the table, and the new model borrows its prices, region by region; only the regions where the reference has a price can be used. E.g. `claude-opus-5-6` priced as Opus 5.5. Every price still comes from the shipped table, so no sanity checks of typed prices are needed. **Usually close, not always right:** a point release tends to keep its predecessor's price (Opus 4 to 4.1, Sonnet across several versions), but a new generation has moved prices by a factor of 3 either way (Opus 4.5 a third of Opus 4.1's; Haiku up from 3 to 3.5). A cheaper model makes the cap stop early (safe); a dearer one makes it undercount, by that factor at most, which is still far better than counting nothing.
  - **Unpriced:** the app has no price. Its calls are recorded as calls of unknown cost (§10, "Calls of unknown cost"), which the costs view counts apart ("the total may be far higher"), and they don't count towards the spending cap, which can't stop them. Not "free tier": the app doesn't pretend they cost nothing.
  - **Free tier:** the user's account really doesn't pay for it (the mark as it is, §10, with its confirmation).
- **Said plainly when the config is created:** "priced as" gets a short confirmation ("The costs and the spending cap use Opus 5.5's prices for this model; check the provider's price page"); "unpriced" a stronger one ("The spending cap can't limit this model's calls, and the costs won't include them. Check your charges with the provider."). **Shown afterwards:** the config's card says "priced as Opus 5.5" or "unpriced"; the costs view marks the costs computed from a borrowed price as estimated from another model's.
- **The real price wins when it ships:** once the shipped list has the model's string for the config's provider, the config becomes a listed one ("Configs", above) and its real price replaces the borrowed one (or none), by itself, and the card's mark goes; a free one stays free. **The form says so** (decided 2026-11-05): the "i" of the pricing choices says that the pricing changes that way when the app's list of models is updated. **For later calls only** (decided 2026-11-03): every call keeps the cost and the prices it was recorded with (§10, "How costs are computed and kept"), so the costs and statistics already seen don't change; calls made unpriced stay calls of unknown cost, and calls priced as another model stay marked as estimated from its price.
- **Not built, and not planned for now:** prices typed by the user (with range checks against the family's prices, cache prices required rather than guessed, and typed prices marked wherever prices are shown), only if users ask for it; and updating the prices from inside the app (above, "The list of models and prices").
- **In every case, the user guide says to set a budget at the provider:** the app's cap is against bugs and its costs are estimates; the provider's budget is the real limit.

## Costs

### How costs are computed and kept
- **The app computes the cost itself:** the providers' APIs report token counts per call, not money. Cost = tokens × a price table per model, kept in the code (to move into the database, under discussion: `docs/llm.md`, "Supported models, prices and the config form").
- **Currency: US dollars** for everything, since that is how the providers publish their prices. The amounts are estimates, not the invoice: the bill may be in another currency, with tax or discounts. The app doesn't convert.
- **The cost is stored with each call, when it is made,** so a later price change doesn't rewrite history.
- **So are the prices it was computed with** (decided, built): each call records the price table's entry for its model and the date the table was collected (`price_json`). The list's date (`asOf` in the list of models, `apps/worker/src/llm/modelList.ts`) is shown on the About page, marked once it is older than three months, so stale prices are noticed and a new version updates them. The costs view (docs/statistics.md, "Costs") may show the prices behind a cost where it doesn't clutter.
- **Costs and statistics come from the rows of the calls and the stages** (§5.8), with no ledger of their own: each call has its cost, each stage its start and end time and its page count (§5.8). Those rows survive everything that removes outputs:
  - stages replaced by re-running from an earlier stage (§5.5), which are no longer visible in the pipeline;
  - stopped stages (§5.6);
  - deleted projects (§4): their project, stage and call rows are kept, marked as deleted.
- **The Statistics page** shows them: the Costs tab (the costs view and the average cost per page) and the other statistics (run times, manual work, failed calls, from the same rows and from the outputs' timings and the manual stages' saves), all in docs/statistics.md.
- **Free-tier configs:** the user can mark an LLM config as free tier, behind a confirmation dialog, since the app can't check it: a response says nothing about whether the call was billed. Calls with such a config are shown as "$0.00" (in a stage's details).
- **The spending cap** sums the costs of the calls started in the last 24 hours, deleted projects included.

### Spending cap
- **Purpose: protection against bugs,** not against a user who transcribes too much. A bug in the app must not be able to burn a lot of money on a handful of scores.
- **A setting: at most $X within any 24 hours** (a rolling window, not the calendar day, so a runaway just before midnight doesn't get two budgets). Once reached, the app refuses every further request that costs money.
- **Always set** (decided): a new database has a cap of $1, and it can be changed but never removed, so there is no way to run without one. (Migration 0012 removes a cap stored as unset, so the $1 applies.)
- **On the settings page** (built): an amount in US dollars ("$ 1.00"), saved when the field is left or Enter is pressed; anything but an amount above $0 isn't saved and says so. It can't be cleared: an empty field isn't saved, and Escape brings back the cap.
- **Why a day and not a month:** with a monthly budget the user picks a large number ("about $30 a month"), and a bug can spend all of it in a day before anything stops. A daily budget makes them pick a small one ("$1 a day"), so a bug is stopped after a small sum.
- **Why not per project:** scores differ a lot in length, and re-running stages adds cost legitimately.
- **Enforced by the Worker,** which makes the LLM calls. A second tab or a stale page can't get around it.
- **The cap can be overshot** by the cost of the calls in flight when it is reached, because a call's cost is only known when it returns. Sequentially that is one call, a few cents. **If requests ever run in parallel, revisit this:** the overshoot could be far too much.
- **Free-tier configs stay usable** after the cap is reached, and don't count towards it. A config wrongly marked as free spends money the cap doesn't see; a spend limit set at the provider is the backstop. **So do unpriced ones** (decided 2026-11-03, "Models the user adds"), whose calls the cap can't count, as their creation said.
