# The database

The D1 schema and how the Worker records a pipeline: the tables, the requests while a stage runs and for manual stages, carrying manual stages through a re-run, interrupted runs, what deleting a project deletes and keeps, page counts and settings. The schema itself is in `apps/worker/migrations`, with comments on the columns. § numbers here are `docs/overview.md`'s sections.

## Tables and rules

The D1 schema for the pipeline (decided; built in `apps/worker/migrations/0001_initial.sql`, which has the columns and their comments. The earlier migrations were squashed into it on 2026-11-06 and again on 2026-11-09, while no data needed keeping; later changes are migrations 0002 onwards). Artifacts have no table: a step's code defines them as views over its outputs (§5.2), and an artifact that is stored for convenience (the MEI file) is an output for the whole score.

| Table | One row per | Holds |
|---|---|---|
| `projects` | project | Besides §4: the run mode (§5.1), a version for optimistic locking (§4), the number the next issue gets (§6, "Issue ids"), `deleted_at`, and `importing` while its import is unfinished (migration 0006, "Exporting and importing a project"), and its PDF's page count (`page_count`, migration 0007, "Page counts" below). |
| `pipeline_entries` | stage in a pipeline | Project, position (1, 2, 3, ... without gaps) and the stage. Nothing else: the pipeline is a list of pointers. |
| `stages` | stage, planned ones included | The project it was created in, the step and its version, the status (`planned`, `running`, `failed`, `done`, `wip`, `stopped`), the step's config, the model config (LLM stages), the stage key, its page count, error, a short result, the stage it replaces (an edited manual stage, §5.4), whether it is the recipe's (`in_recipe`, below), times, a heartbeat, its current or last run's id and start, its run time (`run_ms`, below), `deleted_at`. |
| `stage_inputs` | input of a stage | The outputs a stage read. |
| `outputs` | item a stage produced | The stage, the item, the type (`pdf`, `layout`, `lens`, `mei`, ...), the content's hash (stored, in R2) or the recipe and its key (computed), the corrected output (manual), the call that produced it (LLM), and for an item of a running stage how long it took and what it found in the caches (below). One per stage, item and type. |
| `output_inputs` | input of an output | The outputs an output was made from (§5.2). |
| `manual_saves` | manual stage and quarter of an hour | How many times the stage was saved in that quarter : its active time, for the statistics (docs/statistics.md, "Active time"). |
| `llm_calls` | LLM call | The stage, the model config, the request key, the call's place (`item` and `round`, migration 0004, docs/overview.md §12; required since migration 0009: below), the call it was served from (`served_from`, migration 0009: "Calls served from the record" below), the model the response names (`response_model`), the full request and response (in R2), the status (`running`, `ok`, `error`, `unparseable`, `refused`, `cut_off`), the error, and for a call that threw its kind and the provider's HTTP status (`error_kind`, `http_status`, docs/llm.md), tokens (output tokens include thinking: Gemini reports thinking apart, and its adapter adds it), the cost, times, `deleted_at`. |
| `model_configs` | model config | Name (required, unique ignoring case among the configs that aren't deleted), provider, model, effort, plain parameters (region, project, and OpenRouter's account), secrets as `{field: secret name}` (Bedrock with a key pair needs two), the free-tier mark, `deleted_at`. Only the name and `deleted_at` ever change: values are never edited, a config is cloned instead (`docs/llm.md`, "Managing model configs"; decided 2026-11-02; the editing endpoint and the column of the row an edit superseded were removed). |
| `import_ids` | row an unfinished import mapped | The import's project, the kind (config, stage, output, call), the exported id and the row here, whether the import made it, and a revived call's deletion time and import mark (migration 0006): for the import's next requests and for removing it. Emptied when it finishes. |
| `image_fingerprints` | image from which a stored result was computed (§8.3) | Its recipe key, its PDF, and the fingerprint (§8.3): dimensions, the hash of the raw pixels, the thumbnail. |
| `settings` | user setting | A key and a JSON value. |

- **Planned stages have a row** (status `planned`), so all there is to know about a stage lives in `stages`, and a pipeline entry is only a pointer. A planned stage is unfinished, so it may change: its config is NULL until a config is set (a step with a config form), or what the user picked for it; **an LLM stage's config names its model config from the moment it is created** (`{ modelConfigId }`, the default then unless it is given one, also in `model_config_id` so that the card shows it; `newStageConfig` in `apps/worker/src/pipelineRules.ts`, the steps of kind `llm` in core's `STEP_KINDS`; `docs/llm.md`, "Which config a stage uses"). When it starts, its config is the resolved one (what it actually used), and its version and stage key are set. "Ready" isn't stored: it is the first planned stage after the done ones.
- **Whether a stage is the recipe's or the user's addition** (decided, built, `stages.in_recipe`), for the costs view, which tells the default pipeline from what the user added to it (§10): the recipe's `review` and its `apply_review` from further reviews and theirs, which the step alone can't, and which the position can't either, since replaced and stopped stages have none. The mark belongs to the place in the pipeline and is passed on with it:
  - **the recipe's:** the stages a new project gets (`RECIPE`, Ingest included);
  - **the user's:** every stage the user adds: manual stages (`fix`), further reviews and the `apply_review` that comes with each, and the `apply_review` added after a `human_review` (with the reviews, §6);
  - **passed on:** a stage that takes another's place takes its mark: the planned stage of a config change, the planned stage that replaces a stopped one, the planned copies of a change in the middle, an edited manual stage's WIP copy. So a recipe stage run again with another config is still the recipe's, and a further review re-run after a change upstream still the user's;
  - **a reused stage keeps its own mark:** when a stage key finds a finished stage, the pipeline points to that row as it is (recipe and user stages with the same key would need the same inputs, which doesn't happen);
  - the column's default is 1, so a later migration that gives old projects a new recipe stage needn't set it, but the Worker sets it on every stage it creates.
- **The kind isn't stored:** it follows from the step, declared in code (§5.1). A step's kind never changes, which a unit test guarantees (§15).
- **Stages are shared, not owned by a pipeline.** A fork (§15) copies the pipeline entries up to its stage, and the issue counter, and no stages or outputs. `created_in` says which project a stage was created in.
- **Item names:** `''` for the whole score, `p3` for page 3, `p3/s2` for the second system on page 3. A system's number in the whole score (system 17) is derived, not stored.
- **A manual stage has an output for every item** of what it corrects, not only for the items changed: an unchanged one points to the same content (the same hash, so nothing is copied in R2). The next stage's inputs are then simply the outputs of the stages before it, with no falling back to an earlier stage per item.
- **Running a stage:** resolve its config and inputs and compute the stage key. If a stage that is done and not deleted has that key, the entry points to it and nothing runs. Otherwise the stage runs, each item first looks in the cache (`llm_calls` for an LLM request, a successful call with the same request key that isn't deleted and was sent, not served; the device's image cache for an image), and each output's row is written as soon as it is done.
- **Calls served from the record** (decided 2026-11-17, the owner's dec. 15 of the code review, E4; built by its batch 32, migration 0009, `recordServed` in `apps/worker/src/llmCalls.ts`): a request answered from the cache gets a row of its own, for the stage it was served to: `served_from` names the call whose answer it is (always a call that was sent: the lookup reads only those), with that call's request and response, the request's place, the stage's model config, no tokens, a cost of 0, `ok`. The browser gets that row's id, which the stage's outputs name. So **every stage has a row for each call it consumed, and exactly one row per call made carries its cost:** a stage's export, its replay and a deletion elsewhere all read its own rows. Before, a hit wrote nothing: a `layout` served from another project's calls named only its last round in its output, so its earlier rounds were in no export (a replay of the file failed at round 1) and deleting the project that paid them marked them (the other project then paid them again). An answer marked unusable through a served row marks the call it was served from too. The statistics count these rows apart ("From the cache" in Usage, in no count of calls made or paid: `docs/statistics.md`).
- **Places are required** (decided 2026-11-17, the owner's dec. 17; migration 0009): two triggers refuse a new call, or a place written, with the placeholders of migration 0004 (`"?"` and 0). Calls that still have them (made before 0004, which the one-time script, removed by batch 32, couldn't place) are kept as they are: read, counted and served like any, but **a project with one isn't exported** (409 `unplaced_calls`, "The project can't be exported: one of its LLM calls was recorded before calls had a place, which couldn't be told afterwards."). The migration changes no row, so it applies on a database that still has them.
- **Retry** runs the failed stage again in the same row: the items already saved stay, the missing ones run. Unless the failed run had another stage key (the app was updated in between: another step version or prompt): then `start` drops its outputs and what it read, and every item runs again (found 2026-11-17, the code review), so that no stage holds items of two versions under one key for a later run to reuse; the browser is told (`keptOutputs`).
- **Stop** marks the stage `stopped` and takes it out of the pipeline. Its outputs are deleted; its calls stay, for the costs and the cache, and one still marked running is closed as stopped, of unknown cost (`docs/llm.md`, "Stopped calls"). The call itself is cancelled too, down to the provider, where the runtime passes the browser's going away on.
- **A change in the middle** (§5.5) points the later entries to new planned stages, each with the config of the stage it replaces (a re-run follows the pipeline as it was). The replaced stages stay as they are, for the stage key to find; a dropped manual stage's entry is removed.
- **An interrupted run** (a tab closed mid-stage) leaves a stage `running`. A running stage writes a heartbeat **once a minute**, no more: each one is a write to the remote database. A running stage whose heartbeat is older than about three minutes counts as interrupted, and is resumed like a failed one.
  - **Each run has an identity** (decided 2026-11-17, review dec. 2–3; built 2026-11-18, migration 0005): `start` gives the run an id (`run_id`), which the run sends with its outputs, heartbeats and end; a request of a run that is over (interrupted, then started again on another device or in another tab) is refused, so a device that comes back after three minutes can't write into the new run, nor make its stage look alive with a heartbeat. `start` claims the stage in one statement (`UPDATE … WHERE` it is planned, failed or interrupted), so of two starts at once (two tabs), one runs and the other is refused.
  - **Leaving a project mid-run releases the stage** (`POST release`, with the run's id): failed, "Interrupted: the project was left while this stage ran.", its outputs kept, so it can run again at once instead of looking like it runs until its heartbeat is old. It counts as interrupted wherever a stale run does (`wasInterrupted`). Stop isn't a release: Stop throws the run's outputs away. Closing the tab sends nothing; the heartbeat rule covers it.
  - **An error before a run's start is the stage's failure** (decided 2026-11-17, review dec. 3): a runner that can't get ready (its inputs can't be loaded, say) records it (`POST fail`, on a stage that could start), so the card, the statistics of failures and the run report have it, and Retry. Not recorded: a precondition the user has to meet first (`CannotStart` in the web app: a stage before it isn't done, a deleted model config, …) and the Worker's refusal of the start itself; those show in the panel.
  - **A stage's run time** (`run_ms`; decided 2026-11-17, review dec. 41) is the summed time of its runs, each from its start to its end, or to its last heartbeat for one interrupted: what the card, the stage's details and the run report show. A manual stage has no runs: it shows the time from its start to its Finish. **Losing an LLM answer that was paid for** when the tab is closed or a phone suspends the page mid-call is **accepted** (decided), even if its cost doesn't reach the records; while this device runs a stage, closing or reloading the tab asks first (built; browsers show their own wording, not ours).
- **The requests while a stage runs** (built, `apps/worker/src/pipeline.ts`, by the rules in `pipelineRules.ts`; the browser does the work, the Worker records it), all under `/api/projects/<id>/stages/<stage id>/`, each of which first reads the stage's entry in the pipeline, once (`stageEntries`), and refuses a stage that isn't in the live project's pipeline (404) before anything else:
  - `PUT config`: sets a stage's config. A planned stage gets it in place; a stage that has run is replaced by a new planned one, and every stage after it by a planned copy of itself. Refused while a stage of the pipeline runs, as every other change of the pipeline is (until 2026-11-17 only while the stage itself ran: a request without the app's guards could replace a later stage under its run).
  - `POST start`: the browser sends what it resolved (the step's version, the resolved config, the stage key, the page count and the outputs it reads). If a finished stage that isn't deleted has the same key, the entry points to it, the planned stage's row is deleted (nothing ran in it), and nothing runs. A planned, failed or interrupted stage can start (claimed in one statement); a running one can't. Answers the run's id, and whether an earlier run's outputs were kept.
  - `POST outputs`: records outputs as each is done; an item recorded already is left as it is (a retry skips them anyway).
  - `POST heartbeat`, `POST finish` (done with a short result, or failed with the error), `POST release` (leaving the project), `POST stop`. `outputs`, `heartbeat`, `finish` and `release` of a running stage carry the run's id.
  - `POST fail` with an error, on a stage that could start: it failed before its run started.
- **Manual stages** (built, same file), under the same path:
  - `POST fix` with the step (and its version, page count and inputs), on a done stage: adds a WIP stage right after it. Refused if the next stage is already that step, or if a stage is running.
  - `POST outputs` while WIP: saves outputs as the user works; a WIP stage's item saved again is overwritten (a running stage's is left as it is). Outputs name their parent (the output they correct).
  - `POST finish` on a WIP stage: done, with a short result.
  - `POST edit` on a done manual stage: a new WIP stage takes its place, with the same outputs and inputs, and `replaces_stage_id` pointing to the old one, which stays as it was (§5.4).
  - `POST drop` on a manual stage, WIP or done: its entry is removed and the later ones move up.
  - Each of them, like a config change, replaces the stages after it: a planned one stays as it is, one that ran gets a planned copy.
  - **A manual stage after a change is carried** (built, `pipeline_entries.carried`): it stays in the pipeline, WIP or done, as it is, and waits for its turn. Then it is kept if what it would read now holds what it read (the same items and types, each with the same content hash or recipe key: `stage_inputs`), and dropped otherwise, with the stages after it moving up (`POST resolve` with the outputs it would read now, as when it was added: `carriedInputs` in `steps.ts`, the outputs of the stage it fixes). A kept stage keeps its status: a WIP one stays WIP (decided). While it waits, it looks like a planned stage (dimmed, the wrench, no artifacts; decided), it can be dropped, and it can't be edited, saved or finished. Its turn comes when every stage before it is done: it is resolved at once, in Auto and Manual mode alike (decided), and an Auto run carries on. Tried in Chromium: a `fix_skew` kept after `rasterize` ran again on a scan at another resolution (the same lines), and dropped on a vector PDF (other lines).
  - **A further review is carried the same way once it has run,** except after a config change that gives the stages after it a model config ("for every model stage after it"): then it is replaced by a planned copy with the new config, like any LLM stage that ran (decided and built 2026-11-09, `rewriteFrom` in `apps/worker/src/pipelineRules.ts`; docs/overview.md §5.5).
  - Which steps are manual, and which stages can be dropped (a manual one, or a further review: `isDroppable`), is declared once, in core (`STEP_KINDS`, `packages/core/src/steps.ts`), for the Worker's rules and the web app's cards alike; the web app declares the rest of each step (title, config form, artifacts) by the same ids, every one of them (`STEPS` in `apps/web/src/steps.ts`).
  - **The recipe's stages are listed in the Worker** (`RECIPE`), which creates them, planned, with every new project.
- **A stage that seems to run, but not on this device** (another device, or this one before a reload) shows as running, without progress, and can be stopped. Once its heartbeat is about three minutes old it shows as failed ("Interrupted"), and can run again. **The Worker decides it, on its own clock** (review A10, 2026-11-18): it sends `interrupted` with each stage of a pipeline and with a project's position in the list (`isStale` in `apps/worker/src/pipelineRules.ts`), so a device whose clock is off shows what the Worker would do (a clock some minutes ahead used to show a live run as interrupted, whose start the Worker then refused). The panel fetches the pipeline every 5 seconds while a stage runs elsewhere, so it turns "Interrupted" without a reload, within 5 seconds of the limit.
- **Progress isn't stored:** only the device that runs a stage knows it (§5.1). Another device sees the stage running, without a bar.
- **Each item's timing** (built, `apps/web/src/itemTiming.ts`): the stage runner times every item of a running stage in the browser, from its start to its output (making its images, its model calls, its checks), and counts the model answers it asked for (`calls`) and how many were served from the record (`calls_cached`), and the images it looked up on the device, those an image is made from included (`images`), and how many were found in its cache (`images_cached`). Stored on the output (`duration_ms` and the four counts); NULL for manual outputs and older ones. For the statistics of run times: a fresh run is estimated from the items that really ran, item by item, so a stage run a few minutes a day, half from the cache, still counts for what it did. A failed attempt leaves no output, so no timing: the calls' own records hold those. An item of a step with no item of its own per page (`analyze`'s whole score: its `metadata` output holds the call's time, `observations` and `pieces` are derived from it at no cost). An image looked up meanwhile by a view, not by the item, is counted with it too: views mostly find their images in the cache.
- **Deleting a project** (§4) marks rows instead of deleting them, for the costs and statistics, and every cache lookup ignores marked rows (partial indexes `... WHERE deleted_at IS NULL`). Marking in the rows, rather than filtering every lookup by the projects that aren't deleted, keeps the rule in one place. When project P is deleted:
  - a stage is marked if no other project that isn't deleted has it in its pipeline, and it was created in P or in a project already deleted. A stage a fork still uses stays, and is marked when that fork is deleted; a stage created in a project that isn't deleted is never marked;
  - the calls of a marked stage are marked with it;
  - the outputs of marked stages, the content of stages and calls that nothing else uses, and the fingerprints of a PDF nothing else uses are deleted (§4).
- **Each stage records its page count** (decided), when it starts, and it never changes: **the selected pages, for every stage** (the code review's dec. 40, 2026-11-25; before, `extract` counted the pages with systems, `review` and `apply_review` the layouts): `rasterize` its resolved selection, every later stage the page images of the latest `rasterize` before it (`pageCountOf` in `apps/web/src/stageInputs.ts`), a manual stage the same when it is added (and its edit copies it). So the per-page times of the steps (docs/statistics.md, "Run times") are over the same pages and add up, and the run report says the same count for each. Pages without music (a cover, say) aren't discounted: pages aren't classified (§6, `layout`). NULL for Ingest, which doesn't read the PDF.
  - **Why on the stage, and not the project's:** the selection of pages can change within a project (`rasterize`'s config, then a re-run), and the replaced stages keep their statistics. A replaced `extract` is no longer in any pipeline, so "the `rasterize` stage in the same pipeline" can't give its count. Following its inputs back to its `rasterize` (`stage_inputs`, `output_inputs`) would, but for every statistics query; a column makes per-page averages one query over `stages` (§10).
- **The project records its PDF's page count** (`projects.page_count`, migration 0007; the code review's dec. 20, built 2026-11-25): counted by the browser when the PDF is picked, as it opens it for its page images anyway, and sent with the create; exported and imported with the project's row. Setting `rasterize`'s pages checks the selection against it without opening the PDF; where it is NULL (a PDF pdf.js couldn't open, a project made or exported before), the browser counts them there, as before. Unlike the stages' counts, it never changes: a project's PDF never does.
- **Two kinds of settings:** the user's, in the `settings` table (the default model config, the run mode for new projects, the spending cap, ...), and the device's, in the browser (`localStorage`), for what may differ between a phone and a laptop: screen size, touch or mouse, bandwidth. The collapsed pipeline panel (§5.6) is the first device setting. Every key the browser keeps is listed once, in `apps/web/src/deviceStorage.ts`, which reads and writes them (a storage that is missing or refuses reads nothing and keeps nothing).

## Deploying

How an instance on Cloudflare is made and upgraded (decided and built 2026-11-09; the desktop app applies the migrations itself when it starts, `docs/desktop.md`). For users, step by step from a new Cloudflare account: `apps/worker/README.md` (the account, a payment method, R2, the workers.dev subdomain, Zero Trust, the setup, the deployment without keys, Access for the score3ly Worker, the keys; decided 2026-11-10, checked against Cloudflare's docs: worker-level Access covers all the Worker's addresses, previews included, and needs the deployed Worker, so the app is open for the minutes between deploying and locking, without keys; account-wide Access (*Protect all Workers*) would close that gap, but would make every other Worker of the account private too, and many users have other projects on their account, so the guide offers it only as the alternative; set after deploying, it covers the Worker too, which falls back to it while it has no rule of its own: the project owner's instance is protected that way, 2026-11-10).
- **Once per Cloudflare account:** `npx wrangler login`, then `npm run setup:cloudflare -w apps/worker -- --jurisdiction <eu|fedramp|none>` (`apps/worker/scripts/setup-cloudflare.ts`): the R2 bucket `score3ly-pdfs` and the D1 database `score3ly`, both in the jurisdiction given, which can only be set at creation (§14) and so must be given, with no default (decided 2026-11-10: the EU is the project owner's choice, not every user's; `fedramp` needs Cloudflare Enterprise; `none` lets Cloudflare choose; D1 also has `us`, R2 doesn't, so it isn't offered). Last, it writes `apps/worker/cloudflare.env` (`CLOUDFLARE_JURISDICTION`, `CLOUDFLARE_D1_ID`), not committed, which is never overwritten: the setup refuses to run where it exists. A setup that fails before writing it can be run again; what it created is kept. Then the secrets the model configs name (`npx wrangler secret put <NAME> -c wrangler.deploy.jsonc` in `apps/worker`, or the dashboard, §10), and Cloudflare Access in front of the app (`apps/worker/README.md`).
- **Wrangler's configs are generated, never committed or edited** (decided 2026-11-10; `apps/worker/scripts/config.ts`). The committed `apps/worker/wrangler.jsonc.template` is the only place the app's configuration is changed. **There is no `wrangler.jsonc`,** so every Wrangler command names its config with `-c`, and one that doesn't fails rather than reaching the wrong database (Wrangler names the local database's file after the database's id, so a config with the real id would open another local database than `dev`'s; found 2026-11-10). Each config is generated again before every use, so a change to the template always takes effect:
  - **`wrangler.local-dev.jsonc`:** the template as it is, never reading `cloudflare.env`. For `dev`, `migrate:local`, the tests (in memory, apart from dev's data), the screenshot and seed scripts (each in a state folder of its own), and local commands typed by hand (`npm run config -w apps/worker` makes both configs first).
  - **`wrangler.deploy.jsonc`:** the template with the database's id and the bucket's jurisdiction from `cloudflare.env`; it can't be made without that file. For `deploy` and every command on the deployed Worker (`secret put`, `d1 … --remote`).
- **cadenza uses neither:** it reads only the Worker's `migrations/` folder (`docs/desktop.md`).
- **Every deployment, the first and every upgrade, is `npm run deploy`:** it builds the web app, generates `wrangler.deploy.jsonc`, applies the migrations the remote database doesn't have yet (`wrangler d1 migrations apply score3ly --remote`, which asks for confirmation when a person runs it), and only then deploys the Worker with the web app's files. **To upgrade to a new version:** pull it (`git pull` on `main`, §11), `npm ci`, `npm run deploy`. The secrets and the data stay as they are.
- **Or from GitHub** (built 2026-11-12, `.github/workflows/deploy.yml`, the workflow "Deploy"): the same `npm run deploy` on GitHub's runner, **started only by hand** (Actions → Deploy → Run workflow, from the branch picked there), one at a time. It runs in the GitHub environment `deployment` (2026-11-12; the project owner's allows `main` and `dev` only), whose secrets and variable it reads. It writes `cloudflare.env` from the secret `CLOUDFLARE_D1_ID` and the variable `CLOUDFLARE_JURISDICTION` (a variable: not sensitive, and a secret `eu` would be masked inside every word of the logs; each id a secret of its own, so GitHub masks it wherever the public logs print it; the app's address isn't masked, decided 2026-11-12: it is guessable from the GitHub username, and Access protects the app) and gives Wrangler `CLOUDFLARE_API_TOKEN` (a token from the template "Edit Cloudflare Workers" plus D1 Edit) and `CLOUDFLARE_ACCOUNT_ID`; Wrangler applies the migrations without asking, as it does wherever no one can answer. How to set the secrets: `apps/worker/README.md`, "Deploying from GitHub". It doesn't run the tests first; the web app's build typechecks it. **First deployed this way 2026-11-12** (the project owner, from a phone); the first try failed on the migrations with Cloudflare's 7403 ("The given account is not valid or is not authorized to access this service"), because the token lacked D1 Edit. **A personal convenience, not a release channel** (decided 2026-11-12, the project owner): score3ly's code is released to its users through `main`, and each user deploys their own instance; the workflow lets the project owner deploy any branch, experimental states included, from a phone. **Not Cloudflare's Workers Builds** (considered the same day): it deploys on every push to one branch, which doesn't fit deploying a chosen state by hand (a dedicated branch to push to would, at the cost of moving a branch to deploy); its private logs and secrets kept in Cloudflare weren't worth that.
- **Bindings are part of the config, and a deployment applies them:** a Worker's bindings (`DB` for D1, `STORE` for R2) are uploaded with its code by `wrangler deploy`, from the generated config, so renaming one in the template takes effect with the next `npm run deploy`, and nothing has to be changed in the dashboard. The R2 binding was `PDFS` until 2026-11-25 (renamed `STORE`, the code review's dec. 4: it holds every stored object, not only the PDFs); the bucket (`score3ly-pdfs`) and what is in it stay the same, only the name the code uses changed. The local data (Wrangler's state, the desktop's folder) is kept under the bucket's name, so it stays too.
- **Migrations come before the new code,** so for a few seconds the old code runs on the new schema. A migration must keep the code before it working, or the gap accepted (an instance has one user, who is the one deploying).
- **The migrations are squashed into one before the first deployment** (done 2026-11-09, OpenRouter's two rebuilds of `model_configs` folded in; a migration added before the first deployment is folded in the same way): a remote database records the migrations it was given (`d1_migrations`), so squashing after it has them would need the database made anew. Local databases made before a squash (Wrangler's `.wrangler/state`, the desktop app's data folder) are made anew, since their `d1_migrations` names migrations that no longer exist.

## The Worker's logs

**Workers Logs is on** (`observability` in `wrangler.jsonc.template`): the Worker's Logs tab in Cloudflare's dashboard lists every request with its wall time and CPU time. **Cloudflare replaces the parts of a URL that look like ids with "REDACTED"** (found 2026-11-12; nothing found says it can be turned off), so the Worker adds a log line of its own to every API request (built 2026-11-12, `apps/worker/src/requestLog.ts`), shown under the request beside its CPU time, as an object whose fields can be filtered on:
- `request`: the method and the path, **every id in it (a UUID, a SHA-256) shortened to its first 7 characters,** without dashes, followed by `...` to show it is cut, e.g. `POST /api/projects/3f2a1b9.../stages/88ac1d0.../llm` (the project owner's idea): short enough not to look like an id, long enough to find the row (`SELECT … WHERE id LIKE '3f2a1b9%'`);
- `status`, and `bytes`, the request body's size (its `Content-Length`);
- what the route adds (`logFields`): a stage's `step` (every request about a stage); on `/outputs`, the number of `outputs` and their `items`; on `/llm`, the `label` the browser names the call by ("System 12", "Page 3", "The whole score"; sent beside the request, not part of it or its key), the number of `images` it carries, the `answer` (`cached`, `images needed`, or `sent`, with the `provider`, the call's `status` and its `outputTokens`, or `refused` with the code); on every refusal (`refuse`, `apps/worker/src/refusals.ts`), `refused` (its code, or the status) and the `reason` it gave; on anything a route throws (the app's `onError`), the `error`, answered as JSON with the code `internal` (docs/style.md, "Error texts").

A streamed answer's line (a stage's call that was sent, `docs/llm.md`, "A call's progress") is written when the stream ends, not when the route returns, so it has the answer's status and tokens (`deferLog`).

Only where Workers Logs collects them: when the Worker runs on Cloudflare's runtime (deployed, and `wrangler dev`, whose terminal shows them), not in the tests or cadenza's Node server, which run the same app. One `console.log` of a small object per request costs microseconds of CPU time, nothing against the 10 ms limit.

## Exporting and importing a project

A project as one file, to bring it back after deleting it (to free storage, R2's free 10 GB, §2), to move it to another instance, or to replay a real run locally, for free, from its records (decided 2026-11-11 with the project owner; built the same day: `apps/worker/src/projectFile.ts`, `apps/web/src/projectFile.ts`, `ExportDialog.tsx`).
- **The file:** `<project name>.s3l`, a plain zip, no format of our own: `manifest.json` (the export format's version, the app's version and commit, the date, the project's name, each content object's media type), `project.json` (the rows, below), `pdf/<sha256>.pdf`, and `content/<sha256>`, every object the rows refer to (outputs, the calls' requests and responses). Images stay out: they are made again from their recipes. It can be unzipped (renamed to `.zip`, or on the command line), but imports take the zipped file, with the extension `.s3l`. Made and read in the browser (fflate): zipping is too much work for a Worker's CPU limit; the Worker hands out the rows (`GET /api/projects/<id>/export`) and takes them back (in several requests, below).
- **The export format has its own version** (`format`, `EXPORT_FORMAT` in `@score3ly/core`, which the Worker and the app both read; only that format is read, no older one: decided 2026-11-17), raised when an export can't be read the same way any more, apart from the app's. A file of a format the app doesn't read is refused with a message (a newer one: "update the app"). **Historical exports** are kept in `fixtures/exports/`, and a test imports each, so that a change that breaks an old format fails a test, not a user's import.
- **What is exported: exactly the current pipeline,** every stage in it whatever its state (done, failed, stopped, WIP, carried, planned), with its outputs, their inputs, its calls (its own rows, those served from the record included; a row served from a call outside the file goes as that call, with its model config, request, answer, tokens, cost and times, under the row's own id, stage and place, once per call, the other rows served from it naming that one; export format 2, the code review's batch 32), its manual saves, the model configs of those stages and calls, and the PDF's fingerprints. Not replaced stages, nor the cards of dropped stages: links to anything outside the pipeline are cut (an edited manual stage's `replaces_stage_id`, the parent or inputs of an output from an earlier attempt). So after a full run, a project exported while a manual stage is WIP pays again for the stages after it once it continues (their earlier runs stay behind); the export dialog says that earlier attempts stay out (its text: the project owner's, 2026-11-11). Including every earlier attempt would bring configs and costs the pipeline doesn't show, and whether one would ever be reused can't be known at export.
- **Calls' places** (`docs/overview.md` §12, "Each call records its place") go with them. A project with a call that still has the placeholders of migration 0004 isn't exported (above, "Places are required"). A file with a call without a valid place is refused ("The file can't be imported: the LLM call … has no place …"), at the chunk that holds it: the unfinished import stays hidden until a retry or "Free up storage" removes it. Files of format 1 (before served rows and required places) are refused like any other format.
- **Export:** "Export" in the project's "⋮" opens a dialog: the file's name, what it holds, what stays out, then "Export" ("Exporting…" with a bar while the content is fetched); the file is saved like a download. Refused while a stage runs, here or on another device, as deletion is.
- **Import:** "+ New project" takes `.pdf` and `.s3l` files (no folders). A project file gets its exported name, numbered if taken, like a new project. If its PDF already has projects here, the dialog of a known PDF lists them, its last item "→ Import as a new project". "Importing "<name>"…" shows meanwhile, with a bar over the uploads and the chunks of rows (the code review's E23, built 2026-11-25; indeterminate while the PDF and the head go).
- **The import goes in several requests** (built 2026-11-25, the code review's batch 11, after E1: the owner imported Liszt's Consolations, 132 systems and a 15.8 MB `project.json`, into the deployed instance, and the one request with all the rows took 543 ms of the Worker's CPU, against the free plan's 10 ms; `content/missing` with 200 hashes took 60–75 ms). Each request stays far within a Worker's CPU time and D1's limits (100 bound parameters per statement, 50 statements per request on the free plan: a table's rows go in as one JSON value, `INSERT … SELECT … FROM json_each(?)`), and the Node host's tests enforce those limits (`docs/overview.md` §12). The browser (`importArchive`):
  1. checks the PDF and every content object against their hashes (fflate checks no CRC: a damaged object would be stored under another hash than the rows name; the code review's E7, built 2026-11-25): "The file is damaged: …", before anything is sent; then stores the PDF (`PUT /api/pdfs/<sha256>`);
  2. sends the **head** (`POST /api/projects/import`: the project, its model configs, stages and pipeline, and the file's key, the SHA-256 of its rows as read, so that the same file always gives the same key): the Worker first removes an unfinished import of the same file (below), then maps the configs and stages and makes the project, marked `importing` (migration 0006) with the key. **The file's model configs are checked first** (the code review's E7, C14, built 2026-11-25, `storedConfigProblem` in `modelConfigs.ts`): one this version can't store or read (a provider, family, effort, routing, account or pricing kind it doesn't know, a model given both or neither way, secrets that aren't a JSON object of names) refuses the import with a 409, before anything is removed or made ("The file can't be imported: its model config "X" can't be stored here. Details: …"); a config the app no longer supports is imported, and shown so, as at home. A config created keeps its secrets as canonical JSON, as a create does. A name taken meanwhile, a project's or a created config's, makes the head look again (`insertProject`);
  3. asks which content the Worker doesn't have (`POST /api/content/missing`, **at most 20 hashes a request**, about 0.3 ms of CPU each, looked up in R2 at once: the owner, "stay on the safe side") and uploads it. **An object no row names counts as missing** (the code review's E9, built 2026-11-25): it is an orphan, which a deletion elsewhere may collect before the import's rows name it; uploaded again, it is young, and safe from collection for an hour. Which rows name it is one statement (`contentNamed`, `storage.ts`, the same rule as the orphan collection's; indexes on the hashes, migration 0008). After the head, not before: removing an unfinished import may collect content (below), and the import trusts this check, without looking at each object again;
  4. sends the other rows a table at a time (calls, outputs with parents first, their inputs, the stages' inputs, the saves, the fingerprints), in chunks of at most 150 kB or 500 rows (`importChunks`, core; `POST /api/projects/<id>/import/rows`); the Worker maps each row's ids through `import_ids`, the import's own map (what it made, what it found here);
  5. ends it (`POST /api/projects/<id>/import/finish`): the mark and the map go, and the project shows.
- **An unfinished import** (a closed tab, a failed request: the import is no longer one request's all or nothing) stays marked, and **hidden** (the owner, 2026-11-24): the home, the project picker, the known-PDF dialog and every statistics tab leave it out, the spending cap doesn't count its calls, and neither cache serves its stages or calls. Its name stays taken. **Importing the same file again removes it, then starts over** (no resuming). **Removed, not deleted** (the owner, 2026-11-24, during the batch): marking it like a deleted project would keep the calls it added, with their costs, under a project nobody saw, and the retry would bring them back to life with their cost there. So what it made goes for good (the project, its pipeline, the stages it copied, their outputs, inputs, saves and calls, the model configs it created that nothing uses by now), and what it only pointed to is left as the usual deletion leaves it: the live stages and configs it matched stay, a call it brought back to life is deleted again, with its old deletion time (kept in `import_ids`). The content goes by the usual orphan collection, with its hour (so content the first attempt uploaded less than an hour before is found by the retry's check; older content is uploaded again). The retry then imports as if the first attempt had never been, and the costs land under the real project. An unfinished import that is never retried is removed by **"Free up storage"** (the settings) once it began a day ago or more (`imported_at`; built 2026-11-25, the code review's batch 14). **The gap of an orphan** (one over an hour old, reported present by the content check, collected by a deletion running at the same time before the import's rows name it) **is closed:** an object no row names counts as missing (step 3).
- **An import is looked up like a run,** stage by stage, then call by call, under the rule of "Deleting a project" (what a live project uses stays alive; costs stay where they were paid):
  1. **a done stage with the key of a live done stage here** is that stage: the imported pipeline points to it, nothing copied (as reusing a stage from the cache);
  2. **any other stage is copied,** with a new id, and each of its calls becomes a row of the imported stage, looked up first: **one the file says was served from another of its calls** is served from what that one became here; else by its request key, **a live call that was sent** serves it (a row served from it, cost 0); **a deleted one** is brought back to life (its request and response stored again, its cost where it was paid, under the deleted project: nothing counts twice, and deleting the imported project marks it again) and serves it; **a call found nowhere** becomes a new row, with its cost, counted in the costs, the statistics and the spending cap. The imported outputs name the imported stage's rows. Calls that didn't succeed are never served from the cache: always new rows, as in a run. Deleted stages aren't brought back as stages (their outputs are gone), only their calls.
  Stages, outputs and saves count in the statistics like a run's. **Original times are kept** (calls, stages, saves), so costs show on the days they happened. **The spending cap never refuses an import:** it stops calls being sent, and an import sends none, it records calls already paid; with original times only those of the last 24 hours count towards it.
- **Model configs:** one with the same values (all but the id, the name and the dates; the secrets' names included) among those not deleted is used; else one is created, numbered if its name is taken (deleted if it was deleted where it came from). A copied stage names the config it was mapped to, in its column and in its config (`modelConfigId`, which the browser runs it with). A secret missing here makes it invalid, as any config.
- **Rows are copied with new ids;** content in R2 is stored under its hash, so never twice. No id is part of a cache key (both levels are content only), so an imported project's records serve this instance's identical requests.
- **`imported_at`** (migration 0002) on projects (it came in by import, on that date; work done on it later isn't marked), stages and calls (those the import added or brought back to life; not live calls it reused). Nothing reads it yet: room for later choices, e.g. a toggle in the costs view.

## Optimistic locking
Two devices, or two tabs, changing the same project at once (§4; built 2026-11-06, `apps/worker/src/versions.ts`; decided with the project owner the same day):
- **The version** (`projects.version`) **is raised by every change a person makes to the project:** a stage's config ("Change config"), adding a manual stage, a further review or a human review, editing a finished manual stage, dropping a stage, stopping one, dismissing a dropped stage's card, a manual stage's saves and its Finish, the project's name and run mode. **Such a change is refused** (409, `stale_version`) **when the browser sends an older version** than the project has: someone changed it elsewhere since this page read it.
- **The browser** keeps the last version it saw of each project (`projectFetch` in `apps/web/src/api.ts`), sends it with every request about the project in the `X-Project-Version` header, and takes the new one from every answer, which carries it in the same header (the GET of the pipeline too, so the 5-second refresh while a stage runs elsewhere keeps it current). **The version it keeps only goes up** (an answer that comes late, such as a refresh read before a save, never takes it back), and **a page's requests that change a project go one after the other** (every request about the project but a GET, LLM calls apart), each with the version the one before it brought: so the page's own changes (an editor's saves, a run's outputs, two debounced saves at once) never refuse each other (found 2026-11-17, the code review, A4). A request without the header isn't checked: scripts, tests, the manual tests' `curl`.
- **A refusal shows "Changed elsewhere"**, over whatever is open: "This project was changed on another device or in another tab since this page loaded it, so your last change wasn't made. Reload to see the project as it is now, then make the change again.", with Reload (the page) and Cancel.
- **The rule of thumb:** the version is **raised by everything that changes what a page shows of the pipeline or the project**, and **checked on what a person asks for**, since only a person decides from what their page shows, which may be stale. So three cases:
  - **checked and raised:** a person's changes (the list above);
  - **raised, not checked:** what changes the pipeline without a person asking: a stage's start and end (its release and a failure before its start too) (decided 2026-11-06: a page still showing a stage as planned can't then change its config after it ran, which would replace it and the stages after it without the confirmation that page would have shown), and a carried manual stage kept or dropped at its turn. Not checked, because nobody decided it from a view: the run goes on by itself, and the pipeline's own rules guard it (a running stage can't be started again or changed). The page that ran it takes the new version from the answer, so its own changes never conflict with its own run (tried: a whole run, then a rename);
  - **neither:** what changes nothing another page could act on: a running stage's outputs and heartbeats, the LLM calls, opening a project.
- **Each route declares its class where it is registered** (`lock("checked")` and so on, a middleware before its handler; 2026-11-17, the code review), and a test walks the Worker's routes and fails on one about a project that declares none, so a new route can't be left out silently.
- **A manual stage's saves raise the version on every save:** that is what catches two devices editing the same stage (the second device's save, made on boxes it read before the first device's saves, is refused instead of silently overwriting them); the device that saves takes the new version from each answer, so its own saves never conflict.
- **The check and the raise are one statement** (2026-11-18, the code review, A11; until then two around the change, so two changes within milliseconds of each other could both pass): a checked change claims the version before it is made (`UPDATE projects SET version = version + 1 WHERE id = ? AND version = ?`), and a change then refused gives it back.

## Deleting a project

Apart from the costs and statistics, it must be **as if the project had never existed** (decided). In particular, a new project with the same PDF, name and config runs every stage from scratch and finds nothing of the deleted one in the cache.
- **Deleted:** the project's stage outputs (their rows and their content), the full requests and responses of its LLM calls, its PDF and the PDF's image fingerprints, in D1, R2 and the device cache, unless another project that isn't deleted still uses them. That is checked with a query at deletion time, not with stored reference counts, which can drift.
- **"Free up storage"** (the settings' General tab, section "Storage"; the code review's dec. 18, built 2026-11-25; `POST /api/storage/free`, `freeUpStorage` in `deletion.ts`): the same collection at once, without deleting a project, after removing the imports abandoned a day ago or more (three at a time, within D1's statements per request), and a line says what it removed ("Removed 12 files (3 MB) and 1 unfinished import.", or "Nothing to remove."). Not scheduled (no cron trigger, nothing at the desktop's start-up: the owner's decision).
- **Orphans in R2 are collected then too:** objects that no row in D1 refers to any more, from any project. They are left behind when a manual stage in progress is saved again (the new content is a new object, §2) or when an upload isn't followed by its row in D1. Nothing else deletes them: a save doesn't delete the object it replaces. This lists the whole bucket and compares it with D1, which is acceptable because deleting a project is rare.
- **Kept, but marked with a deletion time (`deleted_at`):** the project's row, its stages and their LLM calls, for the costs and statistics (§10). Every cache lookup ignores marked rows (§5.8), so they are never reused. A stage that a fork which isn't deleted still uses is not marked (§5.8).
- **What a live project uses stays alive** (decided 2026-11-11, the project owner; built the same day, `LIVE_CALLS` in `deletion.ts`: before, a call was marked with its stage even when a live output named it, which then no longer served the cache, so a live project re-running the same request would have paid again): a stage stays unmarked while a live project's pipeline points to it (built), and **a call stays unmarked while a live stage has a row served from it** (`served_from`, since migration 0009) **or a live output names it** (`call_id`: a project run before served rows), and keeps serving the cache. The served rows carry the call's request and response, so the orphan collection and the import's content check (`collectOrphans`, `contentNamed`) keep its content by the same rule. **Costs stay where they were paid:** under the stage, and so the project, that made the call, deleted or not. **The marks are a state, worked out at every deletion:** a call is marked when its stage is marked and no live stage uses it, so when the last project using it is deleted, it is marked then. An import that names a marked call brings it back to life the same way (the task "Export a project before deleting it, and import it again").
- **An unfinished import isn't deleted this way:** it is removed for good, as if it had never been started (`removeUnfinishedImports`, "Exporting and importing a project").
- A deleted project never appears in the UI again, except in the costs view. Picking its PDF again doesn't trigger the "already based on this file" dialog, unless other projects use that PDF.
- Uniqueness of names only counts projects that aren't deleted: a partial unique index (`... WHERE deleted_at IS NULL`). *Built*.
- **Behind one dialog** (decided): it shows the project's full name, says what is deleted, and the user has to type the name, exactly (case included); pasting or dropping text into the field doesn't count. "Delete project" stays disabled until the name matches.
- **Refused while a stage of the project runs,** here or on another device (an interrupted one doesn't count), with a message saying so.
- **Its text** (the project owner's): "The project and all its files will be deleted, along with any data cached on this device (with the exception of files still in use by other projects). Only its costs will still be reported in the Statistics page. This action cannot be undone."
- **Afterwards** the app shows a screen like the one without a project, saying that "<name>" was deleted from this device and from the remote storage; the URL is `#/` (the project's URL is replaced, so going back doesn't land on it), and a reload shows the usual empty screen.
- **Built** (`apps/worker/src/deletion.ts`, `DELETE /api/projects/<id>`; the orphan collection, `collectOrphans`, in `storage.ts` with the keys of every stored object; `apps/web/src/DeleteProjectDialog.tsx`): marking as above; the outputs of marked stages are deleted unless a stage that isn't marked read them, or an output of one was made from them or corrects them (with the provenance rows of marked stages that point to them); the PDF's fingerprints when no project left uses the PDF. Content in R2 is deleted by collecting orphans: every object no row refers to (a stored output's content, the request or response of a call that isn't marked or that an output names, the PDF of a project that isn't deleted), **if it was uploaded more than an hour ago**: content is uploaded before the row that refers to it, e.g. by a stage running on another device, and must not be collected in between. On the device, the images made from the PDF are deleted when no project left uses it: they are cached in a folder per PDF (§8.6). Renderings of the Transcription and the engraving (SVG, keyed by the MEI's hash) stay until the cache's size limit is built. Tried in Chromium at both widths.
