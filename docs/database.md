# The database

The D1 schema and how the Worker records a pipeline: the tables, the requests while a stage runs and for manual stages, carrying manual stages through a re-run, interrupted runs, what deleting a project deletes and keeps, page counts and settings. The schema itself is in `apps/worker/migrations`, with comments on the columns. § numbers here are `docs/overview.md`'s sections.

## Tables and rules

The D1 schema for the pipeline (decided; built in `apps/worker/migrations/0001_initial.sql`, which has the columns and their comments. The earlier migrations were squashed into it on 2026-11-06 and again on 2026-11-09, while no data needed keeping; later changes are migrations 0002 onwards). Artifacts have no table: a step's code defines them as views over its outputs (§5.2), and an artifact that is stored for convenience (the MEI file) is an output for the whole score.

| Table | One row per | Holds |
|---|---|---|
| `projects` | project | Besides §4: the run mode (§5.1), a version for optimistic locking (§4), the number the next issue gets (§6, "Issue ids"), `deleted_at`. |
| `pipeline_entries` | stage in a pipeline | Project, position (1, 2, 3, ... without gaps) and the stage. Nothing else: the pipeline is a list of pointers. |
| `stages` | stage, planned ones included | The project it was created in, the step and its version, the status (`planned`, `running`, `failed`, `done`, `wip`, `stopped`), the step's config, the model config (LLM stages), the stage key, its page count, error, a short result, the stage it replaces (an edited manual stage, §5.4), whether it is the recipe's (`in_recipe`, below), times, a heartbeat, `deleted_at`. |
| `stage_inputs` | input of a stage | The outputs a stage read. |
| `outputs` | item a stage produced | The stage, the item, the type (`pdf`, `layout`, `lens`, `mei`, ...), the content's hash (stored, in R2) or the recipe and its key (computed), the corrected output (manual), the call that produced it (LLM), and for an item of a running stage how long it took and what it found in the caches (below). One per stage, item and type. |
| `output_inputs` | input of an output | The outputs an output was made from (§5.2). |
| `manual_saves` | manual stage and quarter of an hour | How many times the stage was saved in that quarter : its active time, for the statistics (docs/statistics.md, "Active time"). |
| `llm_calls` | LLM call | The stage, the model config, the request key, the model the response names (`response_model`), the full request and response (in R2), the status (`running`, `ok`, `error`, `unparseable`, `refused`, `cut_off`), the error, and for a call that threw its kind and the provider's HTTP status (`error_kind`, `http_status`, docs/llm.md), tokens (output tokens include thinking: Gemini reports thinking apart, and its adapter adds it), the cost, times, `deleted_at`. |
| `model_configs` | model config | Name (required, unique ignoring case among the configs that aren't deleted), provider, model, effort, plain parameters (region, project, and OpenRouter's account), secrets as `{field: secret name}` (Bedrock with a key pair needs two), the free-tier mark, `deleted_at`. Only the name and `deleted_at` ever change: values are never edited, a config is cloned instead (`docs/llm.md`, "Managing model configs"; decided 2026-11-02; the editing endpoint and the column of the row an edit superseded were removed). |
| `image_fingerprints` | image from which a stored result was computed (§8.3) | Its recipe key, its PDF, and the fingerprint (§8.3): dimensions, the hash of the raw pixels, the thumbnail. |
| `settings` | user setting | A key and a JSON value. |

- **Planned stages have a row** (status `planned`), so all there is to know about a stage lives in `stages`, and a pipeline entry is only a pointer. A planned stage is unfinished, so it may change: its config is NULL until a config is set (a step with a config form), or what the user picked for it; **an LLM stage's config names its model config from the moment it is created** (`{ modelConfigId }`, the default then unless it is given one, also in `model_config_id` so that the card shows it; `newStageConfig` in `apps/worker/src/pipeline.ts`, the Worker's list `LLM_STEPS`; `docs/llm.md`, "Which config a stage uses"). When it starts, its config is the resolved one (what it actually used), and its version and stage key are set. "Ready" isn't stored: it is the first planned stage after the done ones.
- **Whether a stage is the recipe's or the user's addition** (decided, built, `stages.in_recipe`), for the costs view, which tells the default pipeline from what the user added to it (§10): the recipe's `review` and its `apply_review` from further reviews and theirs, which the step alone can't, and which the position can't either, since replaced and stopped stages have none. The mark belongs to the place in the pipeline and is passed on with it:
  - **the recipe's:** the stages a new project gets (`RECIPE`, Ingest included);
  - **the user's:** every stage the user adds: manual stages (`fix`), further reviews and the `apply_review` that comes with each, and the `apply_review` added after a `human_review` (with the reviews, §6);
  - **passed on:** a stage that takes another's place takes its mark: the planned stage of a config change, the planned stage that replaces a stopped one, the planned copies of a change in the middle, an edited manual stage's WIP copy. So a recipe stage run again with another config is still the recipe's, and a further review re-run after a change upstream still the user's;
  - **a reused stage keeps its own mark:** when a stage key finds a finished stage, the pipeline points to that row as it is (recipe and user stages with the same key would need the same inputs, which doesn't happen);
  - the column's default is 1, so a later migration that gives old projects a new recipe stage needn't set it, but the Worker sets it on every stage it creates.
- **The kind isn't stored:** it follows from the step, declared in code (§5.1). A step's kind never changes, which a unit test guarantees (§15).
- **Stages are shared, not owned by a pipeline.** A fork (§15) copies the pipeline entries up to its stage, and the issue counter, and no stages or outputs. `created_in` says which project a stage was created in.
- **Item names:** `''` for the whole score, `p3` for page 3, `p3/s2` for the second system on page 3. A system's number in the whole score (system 17) is derived, not stored.
- **A manual stage has an output for every item** of what it corrects, not only for the items changed: an unchanged one points to the same content (the same hash, so nothing is copied in R2). The next stage's inputs are then simply the outputs of the stages before it, with no falling back to an earlier stage per item.
- **Running a stage:** resolve its config and inputs and compute the stage key. If a stage that is done and not deleted has that key, the entry points to it and nothing runs. Otherwise the stage runs, each item first looks in the cache (`llm_calls` for an LLM request, a successful call with the same request key that isn't deleted; the device's image cache for an image), and each output's row is written as soon as it is done.
- **Retry** runs the failed stage again in the same row: the items already saved stay, the missing ones run.
- **Stop** marks the stage `stopped` and takes it out of the pipeline. Its outputs are deleted; its calls stay, for the costs and the cache.
- **A change in the middle** (§5.5) points the later entries to new planned stages, each with the config of the stage it replaces (a re-run follows the pipeline as it was). The replaced stages stay as they are, for the stage key to find; a dropped manual stage's entry is removed.
- **An interrupted run** (a tab closed mid-stage) leaves a stage `running`. A running stage writes a heartbeat **once a minute**, no more: each one is a write to the remote database. A running stage whose heartbeat is older than about three minutes counts as interrupted, and is resumed like a failed one. **Losing an LLM answer that was paid for** when the tab is closed or a phone suspends the page mid-call is **accepted** (decided), even if its cost doesn't reach the records; while this device runs a stage, closing or reloading the tab asks first (built; browsers show their own wording, not ours).
- **The requests while a stage runs** (built, `apps/worker/src/pipeline.ts`; the browser does the work, the Worker records it), all under `/api/projects/<id>/stages/<stage id>/`:
  - `PUT config`: sets a stage's config. A planned stage gets it in place; a stage that has run is replaced by a new planned one, and every stage after it by a planned copy of itself.
  - `POST start`: the browser sends what it resolved (the step's version, the resolved config, the stage key, the page count and the outputs it reads). If a finished stage that isn't deleted has the same key, the entry points to it, the planned stage's row is deleted (nothing ran in it), and nothing runs. A planned, failed or interrupted stage can start; a running one can't.
  - `POST outputs`: records outputs as each is done; an item recorded already is left as it is (a retry skips them anyway).
  - `POST heartbeat`, `POST finish` (done with a short result, or failed with the error), `POST stop`.
- **Manual stages** (built, same file), under the same path:
  - `POST fix` with the step (and its version, page count and inputs), on a done stage: adds a WIP stage right after it. Refused if the next stage is already that step, or if a stage is running.
  - `POST outputs` while WIP: saves outputs as the user works; a WIP stage's item saved again is overwritten (a running stage's is left as it is). Outputs name their parent (the output they correct).
  - `POST finish` on a WIP stage: done, with a short result.
  - `POST edit` on a done manual stage: a new WIP stage takes its place, with the same outputs and inputs, and `replaces_stage_id` pointing to the old one, which stays as it was (§5.4).
  - `POST drop` on a manual stage, WIP or done: its entry is removed and the later ones move up.
  - Each of them, like a config change, replaces the stages after it: a planned one stays as it is, one that ran gets a planned copy.
  - **A manual stage after a change is carried** (built, `pipeline_entries.carried`): it stays in the pipeline, WIP or done, as it is, and waits for its turn. Then it is kept if what it would read now holds what it read (the same items and types, each with the same content hash or recipe key: `stage_inputs`), and dropped otherwise, with the stages after it moving up (`POST resolve` with the outputs it would read now, as when it was added: `carriedInputs` in `steps.ts`, the outputs of the stage it fixes). A kept stage keeps its status: a WIP one stays WIP (decided). While it waits, it looks like a planned stage (dimmed, the wrench, no artifacts; decided), it can be dropped, and it can't be edited, saved or finished. Its turn comes when every stage before it is done: it is resolved at once, in Auto and Manual mode alike (decided), and an Auto run carries on. Tried in Chromium: a `fix_skew` kept after `rasterize` ran again on a scan at another resolution (the same lines), and dropped on a vector PDF (other lines).
  - **A further review is carried the same way once it has run,** except after a config change that gives the stages after it a model config ("for every model stage after it"): then it is replaced by a planned copy with the new config, like any LLM stage that ran (decided and built 2026-11-09, `rewriteFrom` in `apps/worker/src/pipeline.ts`; docs/overview.md §5.5).
  - The Worker knows which steps are manual (`MANUAL_STEPS`): a step's kind is declared in the web app's code, but the Worker needs it for these rules.
  - **The recipe's stages are listed in the Worker** (`RECIPE`), which creates them, planned, with every new project.
- **A stage that seems to run, but not on this device** (another device, or this one before a reload) shows as running, without progress, and can be stopped. Once its heartbeat is about three minutes old it shows as failed ("Interrupted"), and can run again. The panel fetches the pipeline again at the moment its heartbeat would be too old (a heartbeat may have come meanwhile), so it turns "Interrupted" without a reload (built: `nextStaleAt` in `pipeline.ts`).
- **Progress isn't stored:** only the device that runs a stage knows it (§5.1). Another device sees the stage running, without a bar.
- **Each item's timing** (built, `apps/web/src/itemTiming.ts`): the stage runner times every item of a running stage in the browser, from its start to its output (making its images, its model calls with the providers' own retries, its checks), and counts the model answers it asked for (`calls`) and how many were served from the record (`calls_cached`), and the images it looked up on the device, those an image is made from included (`images`), and how many were found in its cache (`images_cached`). Stored on the output (`duration_ms` and the four counts); NULL for manual outputs and older ones. For the statistics of run times: a fresh run is estimated from the items that really ran, item by item, so a stage run a few minutes a day, half from the cache, still counts for what it did. A failed attempt leaves no output, so no timing: the calls' own records hold those. An item of a step with no item of its own per page (`analyze`'s whole score: its `metadata` output holds the call's time, `observations` and `pieces` are derived from it at no cost). An image looked up meanwhile by a view, not by the item, is counted with it too: views mostly find their images in the cache.
- **Deleting a project** (§4) marks rows instead of deleting them, for the costs and statistics, and every cache lookup ignores marked rows (partial indexes `... WHERE deleted_at IS NULL`). Marking in the rows, rather than filtering every lookup by the projects that aren't deleted, keeps the rule in one place. When project P is deleted:
  - a stage is marked if no other project that isn't deleted has it in its pipeline, and it was created in P or in a project already deleted. A stage a fork still uses stays, and is marked when that fork is deleted; a stage created in a project that isn't deleted is never marked;
  - the calls of a marked stage are marked with it;
  - the outputs of marked stages, the content of stages and calls that nothing else uses, and the fingerprints of a PDF nothing else uses are deleted (§4).
- **Each stage records its page count** (decided), when it starts, and it never changes: the number of pages its inputs cover. `rasterize`: the pages selected; `layout` and `analyze`: the same; per-system stages (`extract`, `review`, `apply_review`): the pages their systems are on; `engrave`: all selected pages, since it also builds the header from the metadata, which `analyze` read from every page, cover included. Pages without music aren't discounted: pages aren't classified (§6, `layout`). NULL for Ingest, which doesn't read the PDF.
  - **Why on the stage, and not the project's:** the selection of pages can change within a project (`rasterize`'s config, then a re-run), and the replaced stages keep their statistics. A replaced `extract` is no longer in any pipeline, so "the `rasterize` stage in the same pipeline" can't give its count. Following its inputs back to its `rasterize` (`stage_inputs`, `output_inputs`) would, but for every statistics query; a column makes per-page averages one query over `stages` (§10).
- **Two kinds of settings:** the user's, in the `settings` table (the default model config, the run mode for new projects, the spending cap, ...), and the device's, in the browser (`localStorage`), for what may differ between a phone and a laptop: screen size, touch or mouse, bandwidth. The collapsed pipeline panel (§5.6) is the first device setting.

## Deploying

How an instance on Cloudflare is made and upgraded (decided and built 2026-11-09; the desktop app applies the migrations itself when it starts, `docs/desktop.md`). For users, step by step from a new Cloudflare account: `apps/worker/README.md` (the account, a payment method, R2, the workers.dev subdomain, Zero Trust, the setup, the deployment without keys, Access for the score3ly Worker, the keys; decided 2026-11-10, checked against Cloudflare's docs: worker-level Access covers all the Worker's addresses, previews included, and needs the deployed Worker, so the app is open for the minutes between deploying and locking, without keys; account-wide Access (*Protect all Workers*) would close that gap, but would make every other Worker of the account private too, and many users have other projects on their account, so the guide offers it only as the alternative; set after deploying, it covers the Worker too, which falls back to it while it has no rule of its own: the project owner's instance is protected that way, 2026-11-10).
- **Once per Cloudflare account:** `npx wrangler login`, then `npm run setup:cloudflare -w apps/worker -- --jurisdiction <eu|fedramp|none>` (`apps/worker/scripts/setup-cloudflare.ts`): the R2 bucket `score3ly-pdfs` and the D1 database `score3ly`, both in the jurisdiction given, which can only be set at creation (§14) and so must be given, with no default (decided 2026-11-10: the EU is the project owner's choice, not every user's; `fedramp` needs Cloudflare Enterprise; `none` lets Cloudflare choose; D1 also has `us`, R2 doesn't, so it isn't offered). Last, it writes `apps/worker/cloudflare.env` (`CLOUDFLARE_JURISDICTION`, `CLOUDFLARE_D1_ID`), not committed, which is never overwritten: the setup refuses to run where it exists. A setup that fails before writing it can be run again; what it created is kept. Then the secrets the model configs name (`npx wrangler secret put <NAME> -c wrangler.deploy.jsonc` in `apps/worker`, or the dashboard, §10), and Cloudflare Access in front of the app (`apps/worker/README.md`).
- **Wrangler's configs are generated, never committed or edited** (decided 2026-11-10; `apps/worker/scripts/config.ts`). The committed `apps/worker/wrangler.jsonc.template` is the only place the app's configuration is changed. **There is no `wrangler.jsonc`,** so every Wrangler command names its config with `-c`, and one that doesn't fails rather than reaching the wrong database (Wrangler names the local database's file after the database's id, so a config with the real id would open another local database than `dev`'s; found 2026-11-10). Each config is generated again before every use, so a change to the template always takes effect:
  - **`wrangler.local-dev.jsonc`:** the template as it is, never reading `cloudflare.env`. For `dev`, `migrate:local`, the tests (in memory, apart from dev's data), the screenshot and seed scripts (each in a state folder of its own), and local commands typed by hand (`npm run config -w apps/worker` makes both configs first).
  - **`wrangler.deploy.jsonc`:** the template with the database's id and the bucket's jurisdiction from `cloudflare.env`; it can't be made without that file. For `deploy` and every command on the deployed Worker (`secret put`, `d1 … --remote`).
- **cadenza uses neither:** it reads only the Worker's `migrations/` folder (`docs/desktop.md`).
- **Every deployment, the first and every upgrade, is `npm run deploy`:** it builds the web app, generates `wrangler.deploy.jsonc`, applies the migrations the remote database doesn't have yet (`wrangler d1 migrations apply score3ly --remote`, which asks for confirmation when a person runs it), and only then deploys the Worker with the web app's files. **To upgrade to a new version:** pull it (`git pull` on `main`, §11), `npm ci`, `npm run deploy`. The secrets and the data stay as they are.
- **Or from GitHub** (built 2026-11-12, `.github/workflows/deploy.yml`, the workflow "Deploy"): the same `npm run deploy` on GitHub's runner, **started only by hand** (Actions → Deploy → Run workflow, from the branch picked there), one at a time. It writes `cloudflare.env` from the repository secret `CLOUDFLARE_D1_ID` and the repository variable `CLOUDFLARE_JURISDICTION` (a variable: not sensitive, and a secret `eu` would be masked inside every word of the logs; each id a secret of its own, so GitHub masks it wherever the public logs print it; the app's address isn't masked, decided 2026-11-12: it is guessable from the GitHub username, and Access protects the app) and gives Wrangler `CLOUDFLARE_API_TOKEN` (a token from the template "Edit Cloudflare Workers" plus D1 Edit) and `CLOUDFLARE_ACCOUNT_ID`; Wrangler applies the migrations without asking, as it does wherever no one can answer. How to set the secrets: `apps/worker/README.md`, "Deploying from GitHub". It doesn't run the tests first; the web app's build typechecks it. **A personal convenience, not a release channel** (decided 2026-11-12, the project owner): score3ly's code is released to its users through `main`, and each user deploys their own instance; the workflow lets the project owner deploy any branch, experimental states included, from a phone. **Not Cloudflare's Workers Builds** (considered the same day): it deploys on every push to one branch, which doesn't fit deploying a chosen state by hand (a dedicated branch to push to would, at the cost of moving a branch to deploy); its private logs and secrets kept in Cloudflare weren't worth that.
- **Migrations come before the new code,** so for a few seconds the old code runs on the new schema. A migration must keep the code before it working, or the gap accepted (an instance has one user, who is the one deploying).
- **The migrations are squashed into one before the first deployment** (done 2026-11-09, OpenRouter's two rebuilds of `model_configs` folded in; a migration added before the first deployment is folded in the same way): a remote database records the migrations it was given (`d1_migrations`), so squashing after it has them would need the database made anew. Local databases made before a squash (Wrangler's `.wrangler/state`, the desktop app's data folder) are made anew, since their `d1_migrations` names migrations that no longer exist.

## The Worker's logs

**Workers Logs is on** (`observability` in `wrangler.jsonc.template`): the Worker's Logs tab in Cloudflare's dashboard lists every request with its wall time and CPU time. **Cloudflare replaces the parts of a URL that look like ids with "REDACTED"** (found 2026-11-12; nothing found says it can be turned off), so the Worker adds a log line of its own to every API request (built 2026-11-12, `apps/worker/src/requestLog.ts`), shown under the request beside its CPU time, as an object whose fields can be filtered on:
- `request`: the method and the path, **every id in it (a UUID, a SHA-256) shortened to its first 7 characters,** without dashes, followed by `...` to show it is cut, e.g. `POST /api/projects/3f2a1b9.../stages/88ac1d0.../llm` (the project owner's idea): short enough not to look like an id, long enough to find the row (`SELECT … WHERE id LIKE '3f2a1b9%'`);
- `status`, and `bytes`, the request body's size (its `Content-Length`);
- what the route adds (`logFields`): a stage's `step` (every request about a stage); on `/outputs`, the number of `outputs` and their `items`; on `/llm`, the `label` the browser names the call by ("System 12", "Page 3", "The whole score"; sent beside the request, not part of it or its key), the number of `images` it carries, the `answer` (`cached`, `images needed`, or `sent`, with the `provider`, the call's `status` and its `outputTokens`, or `refused` with the code).

Only where Workers Logs collects them: when the Worker runs on Cloudflare's runtime (deployed, and `wrangler dev`, whose terminal shows them), not in the tests or cadenza's Node server, which run the same app. One `console.log` of a small object per request costs microseconds of CPU time, nothing against the 10 ms limit.

## Exporting and importing a project

A project as one file, to bring it back after deleting it (to free storage, R2's free 10 GB, §2), to move it to another instance, or to replay a real run locally, for free, from its records (decided 2026-11-11 with the project owner; built the same day: `apps/worker/src/projectFile.ts`, `apps/web/src/projectFile.ts`, `ExportDialog.tsx`).
- **The file:** `<project name>.s3l`, a plain zip, no format of our own: `manifest.json` (the export format's version, the app's version and commit, the date, the project's name, each content object's media type), `project.json` (the rows, below), `pdf/<sha256>.pdf`, and `content/<sha256>`, every object the rows refer to (outputs, the calls' requests and responses). Images stay out: they are made again from their recipes. It can be unzipped (renamed to `.zip`, or on the command line), but imports take the zipped file, with the extension `.s3l`. Made and read in the browser (fflate): zipping is too much work for a Worker's CPU limit; the Worker hands out the rows (`GET /api/projects/<id>/export`) and takes them back (`POST /api/projects/import`).
- **The export format has its own version** (`format`, `EXPORT_FORMAT` in the Worker, `EXPORT_FORMATS` in the app, kept in step by a test), raised when an export can't be read the same way any more, apart from the app's. A file of a format the app doesn't read is refused with a message (a newer one: "update the app"). **Historical exports** are kept in `fixtures/exports/`, and a test imports each, so that a change that breaks an old format fails a test, not a user's import.
- **What is exported: exactly the current pipeline,** every stage in it whatever its state (done, failed, stopped, WIP, carried, planned), with its outputs, their inputs, its calls, the calls its outputs were served from (a call served from another project belongs, in the file, to the stage of the first output naming it), its manual saves, the model configs of those stages and calls, and the PDF's fingerprints. Not replaced stages, nor the cards of dropped stages: links to anything outside the pipeline are cut (an edited manual stage's `replaces_stage_id`, the parent or inputs of an output from an earlier attempt). So after a full run, a project exported while a manual stage is WIP pays again for the stages after it once it continues (their earlier runs stay behind); the export dialog says that earlier attempts stay out (its text: the project owner's, 2026-11-11). Including every earlier attempt would bring configs and costs the pipeline doesn't show, and whether one would ever be reused can't be known at export.
- **Export:** "Export" in the project's "⋮" opens a dialog: the file's name, what it holds, what stays out, then "Export" ("Exporting…" with a bar while the content is fetched); the file is saved like a download. Refused while a stage runs, here or on another device, as deletion is.
- **Import:** "+ New project" takes `.pdf` and `.s3l` files (no folders). A project file gets its exported name, numbered if taken, like a new project. If its PDF already has projects here, the dialog of a known PDF lists them, its last item "→ Import as a new project". The browser stores the PDF (`PUT /api/pdfs/<sha256>`) and the content the Worker doesn't have yet (`POST /api/content/missing`, at most 200 at a time, a request may only make so many calls to R2), then sends the rows; "Importing "<name>"…" shows meanwhile.
- **An import is looked up like a run,** stage by stage, then call by call, under the rule of "Deleting a project" (what a live project uses stays alive; costs stay where they were paid):
  1. **a done stage with the key of a live done stage here** is that stage: the imported pipeline points to it, nothing copied (as reusing a stage from the cache);
  2. **any other stage is copied,** with a new id, and each of its calls looked up by its request key: **a live call** is used (no row: the imported outputs name it); **a deleted one** is brought back to life (its request and response stored again, its cost where it was paid, under the deleted project: nothing counts twice, and deleting the imported project marks it again); **a call found nowhere** becomes a new row, with its cost, counted in the costs, the statistics and the spending cap. Calls that didn't succeed are never served from the cache: always new rows, as in a run. Deleted stages aren't brought back as stages (their outputs are gone), only their calls.
  Stages, outputs and saves count in the statistics like a run's. **Original times are kept** (calls, stages, saves), so costs show on the days they happened. **The spending cap never refuses an import:** it stops calls being sent, and an import sends none, it records calls already paid; with original times only those of the last 24 hours count towards it.
- **Model configs:** one with the same values (all but the id, the name and the dates; the secrets' names included) among those not deleted is used; else one is created, numbered if its name is taken (deleted if it was deleted where it came from). A copied stage names the config it was mapped to, in its column and in its config (`modelConfigId`, which the browser runs it with). A secret missing here makes it invalid, as any config.
- **Rows are copied with new ids;** content in R2 is stored under its hash, so never twice. No id is part of a cache key (both levels are content only), so an imported project's records serve this instance's identical requests.
- **`imported_at`** (migration 0002) on projects (it came in by import, on that date; work done on it later isn't marked), stages and calls (those the import added or brought back to life; not live calls it reused). Nothing reads it yet: room for later choices, e.g. a toggle in the costs view.

## Optimistic locking
Two devices, or two tabs, changing the same project at once (§4; built 2026-11-06, `apps/worker/src/versions.ts`; decided with the project owner the same day):
- **The version** (`projects.version`) **is raised by every change a person makes to the project:** a stage's config ("Change config"), adding a manual stage, a further review or a human review, editing a finished manual stage, dropping a stage, stopping one, dismissing a dropped stage's card, a manual stage's saves and its Finish, the project's name and run mode. **Such a change is refused** (409, `stale_version`) **when the browser sends an older version** than the project has: someone changed it elsewhere since this page read it.
- **The browser** keeps the last version it saw of each project (`projectFetch` in `apps/web/src/api.ts`), sends it with every request about the project in the `X-Project-Version` header, and takes the new one from every answer, which carries it in the same header (the GET of the pipeline too, so the 5-second refresh while a stage runs elsewhere keeps it current). A request without the header isn't checked: scripts, tests, the manual tests' `curl`.
- **A refusal shows "Changed elsewhere"**, over whatever is open: "This project was changed on another device or in another tab since this page loaded it, so your last change wasn't made. Reload to see the project as it is now, then make the change again.", with Reload (the page) and Cancel.
- **The rule of thumb:** the version is **raised by everything that changes what a page shows of the pipeline or the project**, and **checked on what a person asks for**, since only a person decides from what their page shows, which may be stale. So three cases:
  - **checked and raised:** a person's changes (the list above);
  - **raised, not checked:** what changes the pipeline without a person asking: a stage's start and end (decided 2026-11-06: a page still showing a stage as planned can't then change its config after it ran, which would replace it and the stages after it without the confirmation that page would have shown), and a carried manual stage kept or dropped at its turn. Not checked, because nobody decided it from a view: the run goes on by itself, and the pipeline's own rules guard it (a running stage can't be started again or changed). The page that ran it takes the new version from the answer, so its own changes never conflict with its own run (tried: a whole run, then a rename);
  - **neither:** what changes nothing another page could act on: a running stage's outputs and heartbeats, the LLM calls, opening a project.
- **A manual stage's saves raise the version on every save:** that is what catches two devices editing the same stage (the second device's save, made on boxes it read before the first device's saves, is refused instead of silently overwriting them); the device that saves takes the new version from each answer, so its own saves never conflict.
- **Not atomic:** the check and the raise are two statements around the change, so two changes within milliseconds of each other could both pass. Accepted: a person on each device.

## Deleting a project

Apart from the costs and statistics, it must be **as if the project had never existed** (decided). In particular, a new project with the same PDF, name and config runs every stage from scratch and finds nothing of the deleted one in the cache.
- **Deleted:** the project's stage outputs (their rows and their content), the full requests and responses of its LLM calls, its PDF and the PDF's image fingerprints, in D1, R2 and the device cache, unless another project that isn't deleted still uses them. That is checked with a query at deletion time, not with stored reference counts, which can drift.
- **Orphans in R2 are collected then too:** objects that no row in D1 refers to any more, from any project. They are left behind when a manual stage in progress is saved again (the new content is a new object, §2) or when an upload isn't followed by its row in D1. Nothing else deletes them: a save doesn't delete the object it replaces. This lists the whole bucket and compares it with D1, which is acceptable because deleting a project is rare.
- **Kept, but marked with a deletion time (`deleted_at`):** the project's row, its stages and their LLM calls, for the costs and statistics (§10). Every cache lookup ignores marked rows (§5.8), so they are never reused. A stage that a fork which isn't deleted still uses is not marked (§5.8).
- **What a live project uses stays alive** (decided 2026-11-11, the project owner; built the same day, `LIVE_CALLS` in `deletion.ts`: before, a call was marked with its stage even when a live output named it, which then no longer served the cache, so a live project re-running the same request would have paid again): a stage stays unmarked while a live project's pipeline points to it (built), and **a call stays unmarked while a live project's output names it** (`call_id`), and keeps serving the cache. **Costs stay where they were paid:** under the stage, and so the project, that made the call, deleted or not. **The marks are a state, worked out at every deletion:** a call is marked when its stage is marked and no live output names it, so when the last project using it is deleted, it is marked then. An import that names a marked call brings it back to life the same way (the task "Export a project before deleting it, and import it again").
- A deleted project never appears in the UI again, except in the costs view. Picking its PDF again doesn't trigger the "already based on this file" dialog, unless other projects use that PDF.
- Uniqueness of names only counts projects that aren't deleted: a partial unique index (`... WHERE deleted_at IS NULL`). *Built*.
- **Behind one dialog** (decided): it shows the project's full name, says what is deleted, and the user has to type the name, exactly (case included); pasting or dropping text into the field doesn't count. "Delete project" stays disabled until the name matches.
- **Refused while a stage of the project runs,** here or on another device (an interrupted one doesn't count), with a message saying so.
- **Its text** (the project owner's): "The project and all its files will be deleted, along with any data cached on this device (with the exception of files still in use by other projects). Only its costs will still be reported in the Statistics page. This action cannot be undone."
- **Afterwards** the app shows a screen like the one without a project, saying that "<name>" was deleted from this device and from the remote storage; the URL is `#/` (the project's URL is replaced, so going back doesn't land on it), and a reload shows the usual empty screen.
- **Built** (`apps/worker/src/deletion.ts`, `DELETE /api/projects/<id>`; `apps/web/src/DeleteProjectDialog.tsx`): marking as above; the outputs of marked stages are deleted unless a stage that isn't marked read them, or an output of one was made from them or corrects them (with the provenance rows of marked stages that point to them); the PDF's fingerprints when no project left uses the PDF. Content in R2 is deleted by collecting orphans: every object no row refers to (a stored output's content, the request or response of a call that isn't marked or that an output names, the PDF of a project that isn't deleted), **if it was uploaded more than an hour ago**: content is uploaded before the row that refers to it, e.g. by a stage running on another device, and must not be collected in between. On the device, the images made from the PDF are deleted when no project left uses it: they are cached in a folder per PDF (§8.6). Renderings of the Transcription and the engraving (SVG, keyed by the MEI's hash) stay until the cache's size limit is built. Tried in Chromium at both widths.
