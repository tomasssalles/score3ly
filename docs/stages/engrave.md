# The last stages: `build_mei`, `fix_mei`, `engrave`

What the user takes away: the full score's MEI, its engraving as a PDF, and a report of the run; and the one place where the MEI can be edited by hand. Their place in the pipeline and the rules all stages follow are in `docs/overview.md` (§5, §6); the MEI itself (what the builder writes, and why) is in `docs/overview.md` `docs/notation.md`, "MEI"; § numbers here are `docs/overview.md`'s sections.

**What they read and write** (built 2026-11-03, when `build_mei` took the MEI over from `engrave`):
- `build_mei` reads the latest extraction (`docs/stages/music.md`), the latest layout (`docs/stages/layout.md`), the latest metadata and `pieces` (`docs/stages/analyze.md`). It writes one `mei` output for the whole score.
- `fix_mei` reads `build_mei`'s MEI, its parent, like every fix; it writes `mei_base` (where it started), `mei_draft` (the text being edited) and `mei` (the applied version).
- `engrave` reads the latest MEI: `fix_mei`'s right before it, else `build_mei`'s. Its one output is the PDF's recipe; the PDF is cached on the device.
- **Who reads them:** nothing after `engrave`, always the last stage. The user downloads the files from the download card after it.

## `build_mei` (Build MEI)

A recipe stage right before `engrave` (decided 2026-11-03), kind computed, no config: it builds the full score's MEI from the latest extraction (the frame from the structure and the metadata, the header, the facsimile, measures joined across system breaks, the pieces as `mdiv`s) and stores it. It exists, without a config or a decision, because it creates an output a manual stage fixes (§6, "A stage exists where…"): "Fix MEI manually" is in its "⋮", and `fix_mei` reads its MEI as every fix reads its parent.
- **Output:** item `''`, type `mei`, the file with how it was made (score3ly, the app's version, the repository). The card's result: "96 measures", or "13 pieces · 412 measures".
- **Artifact:** the MEI view (below), the file beside the score engraved from it at the default page size: that engraving is for finding one's way in the file; the PDF with the chosen page size is Engrave's.
- **Icon:** a placeholder for now (its kind's, computed); the project owner decides it.
- **Built** (`apps/web/src/runBuildMei.ts`, `engrave.ts`): its stage key is the step, its version, the lens's version and the content of what it reads. No migration gives existing projects one (CLAUDE.md, "Existing data").

## `engrave` (Engrave)

The last stage, always; a review, `human_review` or `fix_mei` added later goes before it, and it runs again. Kind computed: it engraves the latest MEI (`fix_mei`'s right before it, else `build_mei`'s) with Verovio and makes the PDF (decided 2026-11-03; before, it built the MEI too, and the PDF was made only when downloaded).
- **Its output is a recipe, like Rasterize's page images:** item `''`, type `pdf`, the recipe (the MEI's hash, the config, Verovio's version, our rendering and PDF code's versions) and its key; nothing stored. The PDF is cached on the device under the key, and made again from the recipe where it is missing; the view then says "Regenerating the PDF…", never "Engraving…": for the user the engraving already happened. Its time is the stage's run time, where it belongs: it was hidden behind the download button before, and it is significant. The card's result: "3 pages".
- **The same recipe gives the same bytes:** jsPDF always writes a creation date, which is overwritten with spaces (every offset in the file stays right), and the file's id is taken from the recipe's key instead of jsPDF's random one.
- **Artifact:** the PDF, the file itself, drawn by pdf.js like the original PDF (`PdfView`), not Verovio's SVG pages: the conversion changes things (fonts, the metronome glyphs added by hand), so the app shows exactly what is downloaded.
- **Config:** the page size; later more of what Verovio lets adjust (finer details of the engraving).
- **No "as in the original" breaks** (decided, replacing an earlier decision): the engraving always has Verovio's own breaks, of the MEI file as it is, so the PDF always engraves exactly the MEI it comes with. The MEI is the product; the engraving is a convenience the user could make with other free software, and one that doesn't match the file next to it would mislead. Matching the original system by system matters earlier, for the review (`human_review`), not for the export. The MEI builder's `divideAtSystemBreaks` (each measure split by a system break divided there, `@metcon="false"`, the first part ending with an invisible bar line) stays for that.
- **Icons** (decided): the card's is the inverse of `extract`'s (a quarter note turning into a letter): a letter turning into a quarter note (`EngraveIcon`): notes are printed, engraved music, letters are its source code. The MEI artifact's tile (`build_mei`'s) is the PDF's sheet with "MEI" on it (`MeiIcon`).
- **The download card** (decided 2026-11-03): downloads are on a card after Engrave, which isn't a stage, so it has no config, title, icon, "⋮" or status, and doesn't count in the progress: only the usual accent-coloured "Download" button, disabled whenever the pipeline isn't finished, during a re-run too. The pipeline is done when Engrave is done: downloading has nothing to do with it. The usual use is "let it run, take the final MEI and leave" (§5.6).
- **Built** (`apps/web/src/engrave.ts`, `runEngrave.ts`, `engraving.ts`, `EngravingView.tsx`, `meiView.ts`; migration 0015 adds it, planned, at the end of existing pipelines, and the Worker's `RECIPE` has it). Tried in Chromium at both widths, with the fake model. Decisions made while building it (to confirm):
  - **What `build_mei` reads:** the latest `extract` or `apply_review`, the latest `layout` or `fix_layout`, the latest metadata and `pieces` (`fix_metadata` or `analyze`). Its page count, and `engrave`'s, is the pages selected in `rasterize`.
  - **Config:** the page size (A4, the default, or US Letter), a picker (the config dialog's choice fields). No staff size: Verovio's staves are 7.2 mm on the page whatever its `scale`, which only sizes the SVG. A change of config re-runs the stage (it is in the stage key), which takes a moment.
  - **The engraving:** Verovio renders every page in the Web Worker, cached on the device like the Transcription's renderings; the PDF is made from the pages' SVG with jsPDF and svg2pdf.js (loaded only then). svg2pdf.js doesn't scale the SVG Verovio nests each page in, so the nested one becomes a scaled group first.
  - **The artifact:** "PDF" (a sheet with "PDF", `PdfIcon`, as the original's).
  - **Downloads** (decided): the "Download" button (under the card's facts) opens a menu: "Bundle (.zip)" first, then each file on its own: "MEI source (.mei)", "Re-engraved score (.pdf)", "Report (.json)". It says "Preparing…" while the files are made: the PDF comes from the device's cache (made again if it was evicted); only the report is made for the download, never stored. Files are named after the project, marked as score3ly's: `<name>.s3l.zip` holding `<name>.s3l.mei`, `<name>.s3l.pdf` and `<name>.s3l.report.json`, the same names as on their own. The marker keeps the engraving from overwriting the original PDF (the project's name is often the original's), and the four sort together. The zip is made in the browser (fflate, loaded only then).
  - **The run report** (decided; `runReport.ts`): JSON, so that programs can read it back. score3ly's version, commit and whether there were uncommitted changes, the repository; the project's name; the original PDF's file name and SHA-256; the MEI's SHA-256 (the one Engrave engraved: `fix_mei`'s, else `build_mei`'s); the engraving's config and Verovio's version; and every stage of the pipeline up to `engrave`: position, step, title, kind, version, status, config, the model config of an LLM stage (name, provider, model, effort, region, free tier; never its secrets), page count, start, end, seconds, cost and the card's result; and the total cost.
  - **The MEI view** (decided): the file and the score engraved from it (the engraving's pages, as the PDF has them), split: the score below the file on narrow screens, on its right on wide ones (the view at least 900 px wide). A toggle hides the score (a note, `MusicIcon`, remembered per device).
    - **The file:** in CodeMirror (`MeiCode.tsx`, read-only here, editable in `fix_mei`): only what is in view is drawn, numbered, highlighted (colours after GitHub's dark theme), elements can be folded.
    - **Between the two:** a click on the score selects the line of the smallest element of the file whose box holds the point (a stem is its note's, a staff line its measure's; Verovio's SVG keeps the file's `xml:id`s; a hollow notehead would otherwise let the click through to the staff line under it), and the file scrolls to it. A click on a line selects it, and the innermost element of the score it is part of is marked (amber) and scrolled to. Whatever is gone to (a match, a measure, the top) is selected the same way, on both sides. Scrolling puts the selection in the middle of the view.
    - **The toolbar:** a magnifying glass that opens the search (collapsed at first; the box, "2 / 16", the arrows; Enter and Shift + Enter, Escape closes it; case ignored). Going to a measure: a picker of the piece (by name only, when there are several; picking one goes to its start), "measure:", the number, "Go"; a number that doesn't exist says so. Measures by their `@n`, from `mdiv` and `measure @n`. No pages or systems: those are the original's, not this engraving's. Then "Back to the top" and the score's toggle. The magnifying glass, "Go" and the toggle look like the Transcription's boxes toggle. **Where the view covers the app** (narrow screens, with the close button floating at the top right) the toolbar is laid out in rows (built 2026-11-02, `styles.css`): the search alone on the first, with room for the close button on its right; the piece on a row of its own (beside the measure from 600 px); the measure and "Go", with "Back to the top" and the score's toggle at the right edge; Fix MEI's Apply last. Before, the close button's room was kept on every wrapped row, so they ended short of the edge, and the row with the piece overflowed on a phone.

## `fix_mei` (Fix MEI)

Optional and manual: the user edits the MEI as text, in the MEI view (see `engrave`, "The MEI view") made editable. Pure text editing, much simpler than the reviews.
- **Its name** (decided): "Fix MEI", and "Fix MEI manually" in the "⋮", like every manual stage ("Fix skew", "Fix layout", "Fix metadata", "Fix observations"). Its id is `fix_mei`.
- **No replacing the MEI by an upload** (decided): a file edited in another program (MuseScore reads and writes MEI) can lose in the round trip the ids that tie measures to the original.
- **Its place:** after `build_mei`, right before `engrave`, and nothing else can come after it: the issues, which a direct edit makes unreliable, are no longer needed. `engrave` then engraves its MEI.
- **Where it is offered** (decided 2026-11-03): in `build_mei`'s "⋮", the stage that creates the MEI, as every "Fix X manually" is in the "⋮" of the stage that creates X. Not twice in a row.
- **What it starts from:** `build_mei`'s MEI, its parent; it is carried through a re-run and kept if that MEI comes out the same.
- **A change before it drops it,** with every edit (the confirmation before a re-run says so, §5.5). Keeping the edits by rough patching, measure by measure, is a task (§15).
- **Saving:** the text is saved automatically, about 2 s after typing stops and when the editor closes, overwriting the stage's draft.
- **Apply** (a button, decided): checks the text and, if it passes, makes it the applied version and engraves the score pane again. The score is engraved only on Apply, never while typing. Disabled while the text is the applied version. The checks: well-formed XML; valid against MEI 5.1 (the full schema: our files go beyond MEI Basic, see `docs/notation.md`, "MEI"); every `xml:id` unique; every `#id` reference pointing to an element that exists (the schema doesn't catch a slur whose note was deleted). If it fails, the errors are listed with their line numbers and nothing is applied. The toolbar shows when the text differs from the applied version.
- **Why the schema** (decided): Verovio is no check. It loads MEI the schema refuses and silently leaves out what it doesn't understand (in a test, an unknown element and attribute and a nested layer: 45 notes engraved became 38, without an error).
- **The schema is compiled once** (decided): libxml2 (`libxml2-wasm`) in a Web Worker started when the editor opens, which compiles MEI 5.1's RelaxNG schema (about a second) and keeps it. Each check then takes what the file needs: about 60 ms on a short score in the browser, about 0.55 s for 660 measures (720 KB) in Node. xmllint-wasm, tried first, compiles the schema on every call (1.2 s even for two systems). A risk: libxml2 plans to remove RelaxNG (`libxml2-wasm` marks its validator deprecated); the tests still use xmllint-wasm for the builder's output.
- **Undo goes on past an Apply** (decided): undoing after an Apply changes the text again, which then needs another Apply. (Clearing the history would make a mistaken Apply impossible to undo.)
- **Finish** applies the text first; a text that doesn't pass can't be finished.
- **No list of commits** (decided, for now): only the start, the draft and the applied version are stored (item `''`, types `mei_base`, written when the editor first opens, what "lines changed" counts against; `mei_draft`; `mei`), the last two overwritten; earlier applied versions are left in R2 as orphans. Going back to an earlier applied version is an optional task (§15).
- **Anything can be deleted,** a note with an `xml:id` too. What refers to it fails the reference check. A deleted measure leaves its zone in the facsimile unused: harmless, but that music can no longer be traced to the original.
- **The card and the run report:** "14 lines changed": the MEI it started from against its final one, line by line, a changed line counting once.
- **Icons** (decided): the card's is the wrench, like every manual stage's; its artifact's tile is the MEI's (`MeiIcon`), the editor while WIP.
- **The editor** (decided): CodeMirror 6, for the MEI artifact of `build_mei` too (read-only there), loaded with the view: it draws only what is in view, works with touch, and has XML highlighting, folding and undo. The toolbar, going to a measure and the link between the lines and the score stay ours.
- **Built** (`apps/web/src/fixMei.ts`, `FixMeiView.tsx`, `MeiWorkspace.tsx`, `MeiCode.tsx`, `meiChecks.ts`, `meiSchema.ts`, `meiCheckWorker.ts`, `meiValidation.ts`; the Worker knows it as a manual step). The score pane is engraved from the applied text at the default page size. CodeMirror is its own chunk (about 107 KB gzipped), loaded with the view. The checking worker loads libxml2 with a top-level await, so the workers are built as ES modules (`worker.format`), and it says when it listens before anything is sent to it (a message sent earlier was lost). Tried in Chromium at both widths, with the fake model: added after `extract`, edited, the draft kept across a reload, Apply disabled without changes, refused (an unknown element or attribute, a tag left open, a duplicate id, a reference to a missing id; each problem goes to its line) and accepted, Finish ("2 lines changed"), and `engrave` taking the file as it is ("8 measures"); the production build too.
