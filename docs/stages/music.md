# The music stages: `extract`, `review`, `apply_review`, `human_review`

The stages that read and correct the music, system by system, and the artifact they share, the Transcription. Their place in the pipeline and the rules all stages follow are in `docs/overview.md` (§5, §6); the format they write and read (the lens, the symbolic format), the issues and the warnings are in `docs/overview.md` §6 too; § numbers here are `docs/overview.md`'s sections.

**What they read and write:**
- `extract` reads the latest layout (`docs/stages/layout.md`), the latest observations and `pieces` (`docs/stages/analyze.md`) and the model config; it writes one `extraction` output per system (the answer in the lens, its issues and warnings) and one `score_checks` output for the whole score (what the checks of the whole score found).
- `review` reads the latest extraction before it (from `extract` today; from an `apply_review` once further reviews exist), its issues and warnings, and the same crops as `extract`; it writes issues only (new ones, and choices on existing ones), one output per call (see `review`, "How it stores what it does").
- `apply_review` reads the latest extraction and the issues that need applying; it writes a new version of the extraction (only what changed, per stretch), with its issues and warnings.
- `human_review` reads the latest extraction and issues; it writes the user's answers and issues, and is always followed by an `apply_review`.
- **Who reads them:** each next review stage, and `engrave` (`docs/stages/engrave.md`), which builds the MEI from the latest extraction.

## `extract` (Extraction)

One call per system, with:
- the system crop and its stretch crops, both with margins code adds to the tight boxes (see `layout`), the stretch crops with generous ones (e.g. half a measure on each side), so that a slur crossing a bar line shows where it ends (in the manual run, with 25 px margins, every missed slur crossed a bar line or a system break);
- the crops of the previous and the next system;
- **all the observations** (decided: global, the whole document from `analyze` or `fix_observations`, not a part per system), each item with its state: low, medium or high confidence, or confirmed. The prompt says what the states mean: confirmed items were checked by a person and can be relied on; the others are the model's bird's-eye guesses, a guide that may be close but not exact, to be checked against what the crop shows;
- **what is in effect on the system,** pre-linked by code from the observations (`docs/stages/analyze.md`, "Code links when the links are needed"): an 8va or an ending that continues from the previous system, the repeat an ending belongs to;
- the stretches it must classify and fill, and the special bar lines and the staves `analyze` saw, as a starting point;
- whether the previous system's extraction ended with a measure that continues into this system;
- the marks left open by the previous system (slurs, ties, hairpins, 8va, pedal, per staff and voice), worked out by code from its extraction (see "Loose ends across systems" below);
- the state the system begins with (clefs, keys, time signature), carried by code from the previous system's extraction;
- **where the pieces start** (the `pieces` output of `analyze` or `fix_metadata`; decided), not the rest of the metadata. **Everything is reset at a piece's boundary:** at a piece's first system, code shows no previous system and carries over no state, no open marks, no continuing measure and no staves or voices (their lists start empty); at a piece's last system, it shows no next system. Otherwise the last system of one piece would be shown as if the next one continued it;
- later, zoom crops on request (see "Zooming in").

The model classifies each stretch (see `docs/notation.md`, "Bar lines, stretches and measures"), extracts the music printed in each stretch, says whether the system's last measure continues into the next system, states every bar line's kind, the clefs, key and time signatures, staff labels, groups and endings as printed (full statements, not corrections; see `docs/notation.md`, "The lens"), and reports its doubts as issues. **It can't add or drop a stretch:** code rejects an answer that doesn't cover exactly the stretches asked for. **The extraction is stored per stretch** (its classification and its music), not per measure: stretches are fixed structure, so two versions of an extraction always match stretch by stretch, however the measures were regrouped (`apply_review`); code joins a measure's stretches into one MEI measure, divided only where a bar line is printed inside it (see `docs/notation.md`, "MEI"). **Each system's answer is checked as soon as it arrives,** not at the end: if the model can't handle the score, that shows early, and an hour of calls isn't paid for answers that turn out not to parse. It tells the user to step in earlier in the pipeline, or to use a stronger model.
- **Models write music in the symbolic format, wrapped in JSON** (decided; `docs/notation.md`, "The lens" and "The symbolic format"), never MEI: code builds the MEI. So MEI's schemas are checked in our tests, as a check on our converter, not at run time (see `docs/notation.md`, "MEI").
- **Checks after each system's answer,** on the system alone (code wraps it with the running state where needed):
  - **parsing:** the answer is valid JSON in our schema, and its LilyPond parses;
  - **durations:** each voice in each measure, its stretches joined, adds up to the time signature (incomplete and unmeasured measures excepted);
  - **the stretches** are exactly the ones asked for.
- **First version: a single turn per system** (decided), no follow-up rounds. A duration mismatch becomes a warning (see `docs/notation.md`, "Warnings"), which `review` sees, and the stage goes on. An answer that doesn't parse (the JSON itself is guaranteed by the provider's schema-constrained output, the LilyPond inside it isn't) **stops the run there** (decided): the stage fails, and the rest of the score isn't extracted. The answers so far stay in the cache, the broken one doesn't (§5.2). The card shows the stage as failed, with Retry, and an error that says exactly what happened, e.g. "Couldn't parse the answer for system 17. The answers for systems 1–16 are kept." A retry is an ordinary run of the stage, with the cache used exactly as in any run: with the same config, systems 1–16 come from the cache and the requests start again at system 17; with another model config, nothing matches and every system is asked again.
- **Later, perhaps: a failed check goes back to the model** in the same call, with the place and the problem, as one more round of the conversation, with a configurable cap: most slips might be fixed for the price of a short follow-up. Whether it pays off over `review` seeing the warnings is measured then.
- **Loose ends across systems are matched by code** (decided), from the lens alone; the model lists nothing extra:
  - code parses each system's answer and finds the marks still open at its end: slurs, ties, hairpins, 8va, pedal, trill spans and glissandos, per staff (by the score's staff numbers, see `docs/notation.md`, "The lens") and voice;
  - the next system's request says what is open ("slur 2 in staff 1, voice 1 continues from the previous system"), as it says whether the last measure continues; the model closes it on the note where it ends. The lens allows a closing mark without an opening one at the start of a system, where the request says it is open, and an opening mark left open at the end of a system;
  - code matches both sides: what was left open must be closed in the next system, or still be open for marks that can run longer (8va, pedal, trill spans). the checks that end `extract` and `apply_review` cover the whole score;
  - **ties:** on the page, a tie and a slur are the same kind of curve, and the symbolic format has only curves (`docs/notation.md`, "The symbolic format"): code decides which are ties, from the notes the model wrote, also across a system break, once both sides are parsed. A curve meant as a tie whose second note has another letter or octave is simply a slur, so a misread pitch under a tie doesn't show as an inconsistency; it is left to `review`. **A tie to nothing,** "let ring" (*l.v.*, common in piano music, e.g. an arpeggio held with the pedal), has its own notation (LilyPond's `\laissezVibrer`), so it isn't taken for an open curve;
  - a mismatch becomes an issue raised by code, with boxes at the end of one system and the start of the next ("where does this slur end?"), within the 2-system rule;
  - what code can't catch is a slur ended too early on both sides (m31→32 in the manual run): the pairing looks consistent. That is left to `review`'s attention to spanners.
  - The number of voices isn't matched: it changes from measure to measure, and is content.
- **No list of long marks in advance** (decided; Claude's suggestion in the manual run): `extract` sees the whole system, closer than `analyze` does, plus the neighbouring systems and the marks left open, so planning ahead is a line in its prompt, not an extra pass. Instructions that aren't marks with two ends ("sempre staccato", "simile", "con pedale", "cresc. poco a poco" over a long passage) are in `analyze`'s observations already.
- **The prompt,** besides what is musical (see `docs/notation.md`, "Musical content and typesetting"), carries the lessons of the manual run (§13):
  - **Doubts as alternatives with evidence for each** ("dot near the A♭: staccato or smudge?"), raised as issues, not decided silently. In the manual run, 6 of the 11 errors were at least partly in the model's list of doubts, so a review that gets them sees them for free.
  - **What comes from the previous system is a hint, not ground truth:** whether its last measure continues, the marks it left open, and the state carried by code are the current best guess, given to help. Where the page clearly says otherwise, the model trusts its own eyes. A mistake in one system then doesn't spread to the next, and it doesn't go unnoticed either: code compares both sides and raises an issue on a mismatch (above, and `docs/notation.md`, "Bar lines, stretches and measures").
  - **Plan ahead within the system:** follow every long mark (slur, hairpin, 8va, pedal) to its end before writing it down.
  - **Read first, compare afterwards:** a stretch is transcribed from the image before any supposed repeat is looked at; the differences from the repeat are then things to look at again, never a reason to copy (m13 was copied from m9 because of a hint, and was wrong).
  - **No unprinted tuplets:** if the durations don't add up, read again; if they still don't, raise an issue (an invented note in m9 produced an odd rhythm, which was "fixed" with a tuplet that isn't printed).
  - **A checklist per note:** accidental, dots, accents, fingering, where slurs start and end.
  - **Only the main text, no alternatives** (until alternatives are supported, §15): an ossia or another alternative version of a passage is ignored, in `extract` and in `review`.
  - **Telling marks from smudges** is the hard part, not keeping or dropping marks by default: "keep every printed mark" was rejected, since several of the model's omissions were right (a stray dot in m2, a dot beside a note in m15).

## `extract`, built

(`apps/web/src/runExtract.ts`, `extract.ts`, `linking.ts`, `ExtractionView.tsx`; the prompt and schema in `packages/prompts/src/extract.ts`; the parser and the checks in `packages/notation`), tested with unit tests and with the fake provider, not yet with a real model (the prompt is a draft):
- **The recipe's sixth stage,** after `analyze` (migration 0013). It reads the latest layout (`layout` or `fix_layout`), the latest observations (`fix_observations` or `analyze`) and the latest `pieces` (`fix_metadata` or `analyze`); a fix of the analysis that is still WIP stops it from starting.
- **One call per system,** in the score's order. Its images, each after its label: the system ("System 17:"), each stretch ("System 17, stretch 2:"), the previous and the next system, not across a piece's boundary. The labels issue boxes name are "system", "stretch k", "previous system", "next system".
- **Margins** (`MARGINS` in `extract.ts`, in the images' recipes): 1% of the page's width at the system's ends, 15% of the system's height above and below (at least 0.5% of the page's), and for a stretch half of each neighbouring stretch. Crops are cut from the straightened page at its resolution, then shrunk to the provider's limits (`cropImage`, cached under its recipe).
- **The request:** the system's number and page, its number of stretches, whether it begins or ends a piece, whether the previous system's last measure continues, the piece's staves and voices so far, the signatures in effect, the marks left open (each with a description), whether an ending runs on, the hints for the system (its staves and instruments, the items on it, the spans in effect on it, linked across pages, its page's notes; every item with its state: low, medium, high or confirmed) and the whole observations document.
- **Checks,** as soon as an answer arrives (`checkSystem`): the structure (an unusable answer stops the run, the answers before it kept); then issues raised by code (a continuation that doesn't match across a system break, a piece's first stretch read as continuing, a stretch of no measure before stretches of one, a printed number on a stretch that doesn't start a measure, marks with two ends that don't match) and warnings (durations, the offset of printed measure numbers, a stretch of no measure with notes, a change in the order of the staves).
- **Decisions made while building it** (to confirm): curve numbers are per voice (a curve in voice 1 and one in voice 2 may have the same number); hairpins, trill lines and glissandos are per voice, ottavas and the pedal per staff (the staff the voice is on where they are written); all voices of a stretch must last the same (a stretch spans one stretch of time), and a measure is the sum of its stretches; a mismatch of marks is an issue raised by code with no answers and `applied` null, its box the stretch where it was found; a staff or a voice from the list given a description makes the answer unusable, as does a new one without (decided).
- **Outputs:** one per system, item `p<n>/s<k>`, type `extraction`: the answer as the model gave it, its issues (the model's with their boxes on the pages, then code's, numbered from the project's counter, `POST /api/projects/<id>/issue-numbers`) and its warnings (with the boxes of their stretches). What a system leaves to the next is worked out again from the stored answers when a retry needs it, not stored. Then one output for the whole score, item `''`, type `score_checks`: what the checks of the whole score found (see "The checks of the whole score, built" below), its issues numbered from the same counter. The card's result counts both: "54 systems · 12 issues · 3 warnings".
- **The artifact:** "The Transcription", as decided below; built (`ExtractionView.tsx`, `transcription.ts`, `rendering.ts`, `renderWorker.ts`).
- **The fake provider** answers an `extract` request (recognized by its schema) with the piece's staves, or two, a voice per staff and a whole-measure rest in 4/4 in every stretch, and a `layout` request with two systems per page, so the pipeline runs end to end without a model (§7.2).
- **Not done:** zoom crops, follow-up rounds for failed checks. Ties, the sounding pitches and the ottavas are worked out by the MEI builder (see §6, "MEI, built"), the 0-or-1 numbering of a pickup by the score model (`packages/notation/src/score.ts`).
- **The checks of the whole score, built** (`packages/notation/src/scoreChecks.ts`), run once every system is in, on the stored answers and the state each system leaves:
  - **a piece that ends with its last measure read as continuing:** an issue raised by code ("Does the piece end with the measure at the end of system 12?");
  - **marks with two ends still open where a piece ends** (curves, hairpins, ottavas, pedal, trill lines): an issue, "Where does this slur or tie end?" (the mark by its name on the page: slur or tie, hairpin, trill line, glissando, ottava line, pedal mark); and **an ending still open there:** a warning;
  - **the repeat structure:** two start repeats without an end repeat between them (repeats don't nest), a start repeat never closed in its piece; an end repeat without a start before it is fine (it goes back to the previous end repeat, or to the piece's start);
  - **endings:** one that another ending follows must end with an end repeat (it goes back); an ending with no other right before or after it stands alone. Both warnings;
  - **courtesy signatures:** a key or time on a stretch of no measure at a system's end that doesn't match the next system's start: a warning, with boxes on both.
  - Measures split across systems and the offset of printed measure numbers are checked system by system already (the state carries the open measure and the offset).

## The Transcription

(decided): the artifact of `extract`, and the base of `review`'s, `apply_review`'s and `human_review`'s views (the form of the human review). A filmstrip of the systems, each with its crop of the original and, below it, its music:
- **rendered** from a small MEI of the system alone, with Verovio's `breaks: "none"`, so it is one system whatever its width; a measure split across systems is half a measure in each (`@metcon="false"`). The small MEI and its rendering are views (made when the system scrolls into view, cached on the device), not stored;
- **or raw:** a toggle (♪ | `</>`, icons only, like the editors' modes) shows the lens instead, called "the raw source (LilyPond-based)": the elements the artifact had before renderings (the staves at the system's start, then each stretch's head and a line per voice); for debugging, not ordinary use;
- **issues and warnings as boxes on the crops,** in the layout's 7 colours (`fix_layout`), in turn in the order their texts are shown, the label inside the box's top left corner as the layout's system labels, the text's card edged in the same colour: issues numbered, in solid boxes; warnings in dashed boxes with "!"; a hint says what they are ("Numbered boxes are questions about what the page says. Dashed boxes mark places where the transcription doesn't add up."), and their text is below the system, in the cards the artifact already had for issues, which warnings use too (a dashed edge, "! · warning", the explanation). A toggle shows or hides the boxes (a staff with two boxes, `BoxesIcon`), so the score can be seen clearly. No separate Issues artifact. Boxes are stored on the pages and drawn on each crop they fall on, so a box on a neighbouring system shows on that system; tapping a box brings its text into view. A note's text goes below the first system its first box falls on. Both toggles are remembered per device (§5.8, device settings).
- **An issue's card** (decided, 2026-11-01): its id and its class in words that say what the problem is, "[unclear]" (`reading`) or "[cannot be encoded]" (`format`); its location and question; its answers, all in the text's colour and none in bold, with small muted suffixes in brackets, at most two on an answer (decided 2026-11-03): **one for the application,** on the applied answer, saying who put it in the transcription: "[written by Extract]", "[applied by Apply review 1]", or, for an issue raised after the transcription was written (a review's new issue, an issue code raised on an Apply review's transcription), "[in this transcription]", the honest phrasing there, also on an answer Apply review added to revert an issue that had no applied answer (`apply_review`, "When an answer can't be applied as given"); none when `applied` is null. **One for the choice,** on the latest choice when a stage other than Extract or a person made it: "[chosen by Review 2]", "[kept by Review 2]" (a review's agreement, added by code), "[chosen by Apply review 1]" (a revert: Apply review's choice of the applied answer, a choice like any other, not a change of the score; not "reverted to", which says the score went back) or "[confirmed by Human review 1]" (later "[applied by Apply review N]" after it). **A resolved issue's card** (decided 2026-11-03) is like any other's, with its "[confirmed by Human review N]" suffix. **The stage a suffix names is in bold** ("written by **Extract**", "chosen by **Review 2**"; decided 2026-11-03): in plain text it reads as ordinary words. The suffixes don't pile up: earlier choices and applications are in the Choices line and in the stored history. **Applications are kept as a history,** like choices (`applications` on a stored issue: who applied which answer, in order; Extract's for its own issues and the issues its checks raised), with no line of its own on the card; for a format issue "LilyPond equivalent: `\harmonic`"; and, when anyone has chosen, a line "Choices: Extract → a • Review 1 → b • Human review 1 → c" (bullets between them, not middle dots, which are too small here), each stage by its title and, for reviews and human reviews, its number among them (always numbered, never the model). Built (the reviews' choices tried with a mock until the reviews exist).
  - **Which stage chose:** a choice names its stage by the stage's id; the view numbers reviews and human reviews by their order in the pipeline.
  - **Reasons are shown, but only on request** (decided, 2026-11-01): every choice with a reason can show it, behind a control, not by default. They are written for the later reviewers, which might otherwise miss the detail that led to a choice and go back and forth between two answers; a person mostly sees the right answer on the page. No exceptions: `apply_review`'s reasons for reverting an answer it couldn't apply are shown the same way. The control (decided and built, 2026-11-01): a small "i" (`InfoIcon`, as on the Statistics page) right after each choice in the "Choices" line that has a reason; tapping it shows the reason on a line below the line ("Review 1: …"), and tapping again hides it. The "i" has the line's muted colour, open or not (the view has colour enough). The line stays one line where no choice has a reason, which is most of the time.
- **Only what the stage changed** (decided and built, 2026-11-01): in the Transcription of a later stage (a review's today; `apply_review`'s and `human_review`'s later), a toggle with a delta (Δ, `ChangesIcon`) next to the boxes' toggle shows only the issues the stage changed, or everything. Not in `extract`'s, where everything is new.
  - **Changed:** for a review, the issues it raised or made a choice on, not those it kept; for `apply_review`, the issues it applied or reverted, and those its checks raised.
  - **Only the changes when the view opens,** not remembered on the device.
  - **Exactly the unchanged issues are hidden,** their cards and their boxes; nothing else (systems, warnings, answers, choices stay). Numbers and colours stay as with everything shown: the colours are given over all the issues, so toggling never changes those already in view.
  - **The scroll position holds:** the first system part or changed issue's card in view before the toggle is put back at the same height after it.
- **Built:** the boxes of the checks of the whole score are among them. The renderings are made in a Web Worker (Verovio's WASM, about 8 MB, loaded only when the first rendering is needed), one system per call (`breaks: "none"`, no header or footer), shown at their own size (narrower where the view is, never blown up), black on white like the paper above them, and cached on the device as SVG under the hash of the MEI, the options, Verovio's version (a test keeps `VEROVIO_VERSION` equal to the installed one) and our rendering code's (`RENDERING_VERSION`). **Every rendering starts from Verovio's default options** (`resetOptions`, `verovioRender.ts`): the worker's one toolkit keeps options from call to call, and an engraving made after the Transcription's systems kept theirs (no title, a page shrunk to the music; found 2026-11-01, fixed 2026-11-02, with `RENDERING_VERSION` 2 so the wrong renderings cached meanwhile aren't used again). Tried in Chromium at both widths, with the fake model.
- **The rendering** (Verovio) can follow the original's layout or not: its `breaks` option `encoded` uses the page and system breaks in the MEI (`docs/notation.md`, "MEI"), so the rendering has the same systems as the original and the two can be compared system by system, as in `human_review`; `auto` computes its own breaks for the page size and ignores the encoded ones.

## `review` (Review)

One call per system, with the same input as `extract`, plus the extraction (in the lens, decided, not MEI: see `docs/notation.md`, "The lens") and the issues of the whole score, and what is in effect on the system pre-linked from the current extraction (as for `extract`, see `analyze`). The model reviews the extraction, changes the chosen answers of unresolved issues, and adds an issue for every correction it wants, **never one about what a resolved issue settled** (decided 2026-11-03: a person's answer is the truth; said in the prompt, not checked by code, which can't tell that two questions are the same); such an issue has at least two answers, the present state and the one the reviewer thinks is right, and possibly other reasonable ones. Zoom crops and the crops of other systems on request (see "Zooming in") come in a later version. **The review doesn't change the MEI and doesn't propose patches:** issues are its only output. **Its prompt names the common mistakes** to pay attention to, foremost slurs and other spanners crossing bar lines and system breaks (every missed slur in the manual run, §13; no separate tracing pass).
- **The whole score goes into every call** (decided), so the model can check consistency across the score. It is sent in the compact format the models write the music in (the "lens", `extract`), not as MEI.
- **Each call sees what the calls before it in the stage changed,** and the cost stays close to linear in the score's length, by prompt caching. A call's prompt is, in this order:
  1. the whole score;
  2. the issues as they were when the stage started, and the warnings of the version being reviewed (see `docs/notation.md`, "Warnings"); each call is also told which warnings touch its own system, and its crops show the part of each warning's box that falls on them;
  3. the changes made by the stage's earlier calls, one entry per change, in the order of the calls (e.g. "review of system 7: chose answer 2 for issue 12", or a new issue). Entries are only ever appended, never rewritten, like `choices` in an issue;
  4. the system's own part: its crops, its extraction, the neighbouring systems' crops.

  Parts 1 to 3 of a call are the start of the next call's prompt, so with a cache mark at the end of part 3 (`docs/llm.md`, "Prompt caching") each call pays the full price only for the entries added by the call before it, and the rest is read from the cache. Without the append-only log, every change to the issues would break the cache, and the cost would grow with the score's length times the number of issues, which is itself roughly proportional to the length. The calls run one after another (§10), so the cache stays warm between them.

- **Decided while preparing it** (2026-10-31):
  - **Choices only on the issues of its own system** (those with a box on it): a call doesn't choose on issues of other systems, although it sees the whole score. Issues raised by code are issues like any other: a review chooses on them too.
  - **At most one new answer per existing issue,** and only as its new choice.
  - **Its crops have the issues' boxes drawn on them;** no clean copies for now (an optional task, §15, "`review`'s crops without boxes too").
  - **Its only config is the model config.** Further reviews are added from an `apply_review`'s "⋮" (see `apply_review`).
  - **Built before `apply_review`:** added to the recipe alone first, so for now it has no effect on the MEI.
  - **The card's result:** the number of proposed changes, new issues plus new choices on existing ones ("15 proposed changes").
  - **What it reviews:** always the latest transcription before its own place in the pipeline: the extraction, its issues and its warnings as the latest stage that produces the extraction left them. Today that is always `extract`; once `apply_review` exists, it can be an `apply_review`.
  - **The score as text** (decided, 2026-11-01):
    - **One JSON document for the whole score,** in the field names of `extract`'s answer, so the model reads what it already knows how to write, and fully compact (no indentation, no line breaks): it goes into every call.
    - **Per piece:** its staves and voices with their descriptions, once, not on every system. **Per system:** its number, page, staves, groups, `startRepeat`, `lastMeasureContinues` and stretches. **Per stretch:** what `extract` wrote, plus code's measure number, so that the model and the log mean the same measure by "m. 23".
    - **The issues,** after the score, the same in every call: each with its id, source and class, its place as systems and stretches (worked out by code from its boxes: page coordinates mean nothing to the model), its location, question and answers, the choices so far with their reasons, `applied` and `resolved`. **The warnings** after them, each with its message and places.
    - **The log:** one line of JSON per entry, in the order of the calls, e.g. `{"by":"review of system 7","choice":{"issue":12,"key":"b","reason":"…"}}`, or a new issue. The entries are the earlier calls' stored outputs, as they read back from storage, so a retry builds the same text.
    - **The call's own part:** the same images as `extract`'s, labelled the same way, the crops with the issues' boxes drawn on them, each labelled with its issue's id.
    - **No format is asked for in the answer** (decided): each model writes its JSON as it likes, indented or not; it is parsed, and whatever goes into later prompts is written out by code.
  - **The answer** (decided, 2026-11-01): **one list of entries, in any order,** each either a choice or a new issue, as in the log: `{ entries: [{ choice: … } | { newIssue: … }] }`.
    - **A choice:** `{ issue, key, newAnswer, reason }`, exactly one of `key` (an existing answer) and `newAnswer` (its text; code gives it the next letter); `reason` null unless it adds something. **It must change the chosen answer:** repeating the current one isn't a choice.
    - **A new issue:** as `extract`'s (boxes on the labelled images, location, question, answers, class, `lilypond`), plus `applied` (the present state) and `chosen` (what the reviewer thinks is right), which must differ, and an optional `reason`. **At least one box on the call's own system;** others may be on the previous or the next system, within the 2-system rule (`docs/notation.md`, "Issues"): the call's system is the main character of the issue, which may involve the notation of a neighbour.
    - **Code's checks** (a failure makes the answer unusable and stops the run, as in `extract`): every issue an entry names exists, has a box on the call's system and isn't resolved; every key exists and no new answer repeats an existing one; a new issue keeps the 2-system rule, has a box on the call's system, and its `applied` and `chosen` differ.
  - **Agreement counts** (decided, 2026-11-01): when the stage is done, every unresolved issue it made no choice on, whose latest choice is a model's, gets a choice from the review that repeats the current one (none after a person's choice: the issue is resolved, and a model's agreement adds nothing to it), as if the reviewer had agreed: a further reviewer who saw the issue and left it is weight for the answer. It is marked as such (`kept`), has no reason, and isn't counted among the proposed changes. Not stored: it is a pure function of the stage's outputs and the issues it reviewed, so the view of the issues as the review leaves them adds it.
  - **Linking from the current extraction** (decided, 2026-11-01): at the start of the stage, code works through the transcription it reviews, and each call's own part gets a list of links for its system, each item a place in the score: each end repeat on the system with where it goes back to (a start repeat, an earlier end repeat, or the piece's start); each ending with its repeat and the endings next to it; each mark crossing into or out of the system with where it opens or closes on the other side ("slur 2, staff 1, voice 1: opens at system 6, stretch 4, closes here at stretch 1"); what is still open at the system's end. Not stored: worked out again from the stored extraction when needed. The whole score is in the prompt anyway; the links point the model at the places that belong together.
    - **One piece of code for the links** (decided): most of it exists. `checkSystem` carries the marks left open, a measure that continues, an ending that runs on and the signatures from system to system (`spans.ts`); the checks of the whole score pair end repeats and endings (`scoreChecks.ts`); the MEI builder pairs curves across system breaks. What is new is links in both directions (`extract` only needed what comes in from before) and handing the pairings on as places instead of only warning or carrying state. That is done by making the existing code report what it works out, used by `extract`, the checks of the whole score, `review`, `apply_review` and the MEI builder alike, not by writing the pairing again for each.
  - **How it stores what it does** (decided): **one output per call,** holding exactly that call's entries for the append-only log: its new issues (numbered by code as soon as the answer is stored, from the project's counter, like `extract`'s) and its choices on existing issues (each with its optional reason, and its new answer where it adds one). The issues as the review leaves them are a view: the issues of the transcription it reviewed with its entries applied, in the order of the calls. So a failed or interrupted run resumes system by system, as `extract` does, and the log of a call's prompt is the earlier calls' outputs as they read back from storage.

## `apply_review` (Apply review)

(decided):
- **Which issues:** those that need applying (below). Systems with none aren't called.
- **One call per system where at least one such issue begins** (its first system), applying all issues that begin there. The call's window is that system and, for an issue that reaches it, the next one (an issue spans at most 2 consecutive systems, see `docs/notation.md`, "Issues"). Calls run in score order; each sees the earlier calls' changes through the append-only log, so a system changed by one call is up to date when the next call's window includes it. Chained issues (systems 1–2, 2–3, 3–4, …) are applied one call each, and no window is ever larger than 2 systems.
- **Input, laid out like `review`'s calls so the cache works the same way:**
  1. the whole score in the lens, as it was when the stage started (the same bytes as `review`'s prefix, so right after a `review` even the first call may read it from the cache);
  2. the append-only log of what the stage's earlier calls changed;
  3. the call's own part: the crops of its window (systems and stretches, with the issues' boxes drawn), its current extraction (per stretch, with the continuation flags), what is in effect on its systems pre-linked from the current extraction (as for `review`), the issues to apply (question, location, boxes, chosen answer, the stretches under the boxes), the other issues on those systems, which are not to be changed, and the extraction of the systems just before and after the window.
- **Answer: a typed patch, only what it changes** (decided), each unit replaced whole, in exactly the lens's schema: a voice of a stretch (`{ stretch, voice, staff, description, music }`, the string replaced whole, or `music: null` to remove the voice from the stretch, e.g. an invented one; every staff still needs a voice in every stretch), the other fields of a stretch (classification, kind, measure numbers, signatures, ending, bar line), and the fields of a system (`startRepeat`, the staves, the groups, whether the last measure continues). Nothing unchanged is copied, so nothing can be miscopied or hallucinated there, and the model doesn't rewrite a whole system around one note. **Not JSON Patch** (RFC 6902): its paths point into arrays by index, which shift and are easy to get wrong, and its values are untyped, so the provider's structured output couldn't hold them to the schema; our units are named by stretch and voice, and every value is typed. **Merging and splitting measures** are a changed classification ("these two stretches are one measure": the second goes from "new" to "continues"), so they are first-class without anything extra, and nothing but regrouping the fixed stretches is possible.
- **It follows orders** (decided, 2026-11-01): decisions belong to `extract`, the reviews and the user; `apply_review` only carries them out. It is a model and not code only because the lens is complicated and the issues and answers have to be understood. It never judges whether a chosen answer is right, never refuses one because it disagrees with it, and the prompt says so: a cheap model applying an expensive reviewer's decisions must not overrule them.
- **When an answer can't be applied as given** (decided and built, 2026-11-02): it doesn't fit the transcription (the slur is to end on a G the measure doesn't have), two chosen answers conflict (one makes a note a quarter, another a dotted quarter), the format can't express it, or a user's answer is too vague to act on. Failing the stage would be a dead end (a retry asks the same, and no stage before it lets anyone choose again). So the model **reverts** the issue: it reports a choice exactly as a review does (`{ issue, key, reason }`), whose key is the issue's `applied` answer, with a reason ("the reviewer asked for these two changes, but they're incompatible"). Code checks that the key is the one applied and that the reason is given; the issue then no longer needs applying, and the next review sees why and doesn't make the same mistake.
  - **An issue with no applied answer** (decided and built 2026-11-03, `checkPatch`, `appliedIssues`; `applied` null, unresolved: in practice a question of code's, "where does this slur end?", whose answer the transcription reflects isn't known, and a review chose one that can't be applied): there is nothing to revert to, so the revert chooses the answer that matches what the transcription has: an existing one if one matches, otherwise a new one the model adds with it, describing what is there ("On the E of the next measure"; like every answer, about the page, never mentioning the transcription). Code sets `applied` to that key, so the issue no longer needs applying. The new answer's suffix is "[in this transcription]", not "[written by Apply review N]": Apply review wrote the answer's text, not the music it describes, and who wrote that isn't known. Code checks: a revert of an issue with an applied answer chooses that answer; one of an issue without chooses an existing answer other than the latest choice, or adds one.
  - **A resolved issue** (decided and built 2026-11-03, `runApplyReview`: the call is recorded, the stage fails with "The answer Human review 1 gave to issue 12 can't be applied: <the reason> Edit Human review 1 to answer it again."; a retry gets the same answer from the cache; a person's answer, which no model may change; a user's own issue is one, though its `applied` is null too): no revert. The stage fails, saying which answer couldn't be applied and why, and that the human review can be edited to answer again. Unlike a model's choice, a person's has a stage before it where it can be changed, so this isn't a dead end. Code checks that no revert touches a resolved issue.
  - **Shown:** the choice's suffix is "[chosen by Apply review 1]", as any choice's (decided 2026-11-03), and its reason is shown on request like every choice's. The view of `apply_review` opens with a block at the top, in the colour of errors, listing the issues it couldn't apply; its card says so ("4 changes applied, 2 reverted").
  - **Every other issue that needed applying counts as applied:** code sets its `applied` to its latest choice. Code's checks (below) catch what they can, as warnings.
  - **Code never reverts** (decided): it doesn't undo a change of the model's, even when the result fails its checks (e.g. two issues on the same stretches whose changes together don't add up). What it finds is reported as issues and warnings, as always.
- **Changes beyond the boxes:** the model may also change stretches of the systems just before and after its window, not only those under the boxes of the issues it applies, e.g. when an issue says a slur doesn't end at the box but continues into the next system, whose start then changes too. Every stretch changed outside the boxes comes with a reason. Every such change is accepted and becomes a warning, with the reason or without one, so a person sees what changed beyond the boxes and why. (Once failed checks go back to the model, `extract`'s "Later, perhaps", a change without a reason goes back once.)
- **Further reviews are added from an `apply_review`'s "⋮"** (decided; the only config of a review is its model config), from any `apply_review`, and **go right after it** (decided, 2026-11-02), with an `apply_review` of their own. Added after one that isn't the last, it is a change in the middle like any other: the stages after it run again, after the confirmation (§5.5).
- **Its crops have the issues' boxes drawn on them;** no clean copies for now (decided, 2026-11-02, as for `review`).
- **Checks:** those of `extract` (parsing; durations of the affected measures; continuations consistent across systems), handled as in `extract` (a single turn in the first version); then the comparison before and after (below). Code then rebuilds and renumbers the measures, choosing the 0-or-1 start anew.
- **Model config:** like every LLM stage's (§7.2).

## `apply_review`, built

(`apps/web/src/runApplyReview.ts`, `applyReview.ts`; the prompt and schema in `packages/prompts/src/applyReview.ts`), built 2026-11-02, tested with unit tests and with the fake provider, not yet with a real model (the prompt is a draft):
- **The recipe's eighth stage,** right after the review and before `engrave`. No migration gives existing projects one (no data to keep yet, CLAUDE.md); a new project has it.
- **What it reads:** the latest transcription before it (as `review` does), the review between that transcription and it (its stored calls, applied to the issues as the review's view applies them, with its agreements), and the same layout, observations and pieces. `review` and `human_review` are its reviewing steps (`REVIEWING_STEPS`).
- **The calls** (`applyCalls`): one per system where an issue that needs applying begins (the first system its boxes cover), with its issues in the order of their ids; the window is that system and the next when an issue reaches it. The systems a call may change are the window and the systems right before and after it, within the piece.
- **A call's prompt,** in one user message: the score as it was when the stage started, the same text as `review`'s (`reviewScoreText`), with the observations; the issues as the review left them and the warnings, marked "cache up to here"; the log, one text block per earlier call (its units without their reasons, its reverts, the ids it applied), the last one marked too; then the images, each after its caption: the previous system, each window system and its stretches, the next system, all with the issues' boxes drawn and labelled with their ids (no clean copies); then the request: the window, its systems as they are now (with the earlier calls' changes, each stretch with code's `measure`, the descriptions included), the systems right before and after it, the links of the window's systems, the issues to apply (places, location, question, answers, the chosen key and who chose it, `applied`), the ids of the other issues on the window, the warnings on it.
- **The answer** (`APPLY_REVIEW_SCHEMA`): four lists, `voices` (a voice of a stretch: its music replaced whole, null removes it), `stretches` (all the fields of a stretch but its voices), `systems` (`startRepeat`, `staves`, `groups`, `lastMeasureContinues`), each unit with a `reason`, and `choices`, the reverts, `{ issue, key, reason }`. A stretch's or a system's fields are replaced as a unit, all of them: with structured output, "unchanged" can't be told from null in a nullable field, and the units are small.
- **Code's checks** (`checkPatch`, then `checkAll`), each failure making the answer unusable and stopping the run there, the calls before it kept: the units on the systems the call may change, each unit once, stretches that exist, a removed voice that is there; reverts only of the call's own issues, each of its `applied` answer, with a reason. A description the model left null where the voice or staff had one is kept. Then the patched transcription is checked again system by system, from the start of each piece (`extract`'s checks): a patch that breaks any system, the call's or a later one, is unusable.
- **What a call stores** (item of its system, type `apply_review`): its window, the patch as checked, the reverts, the ids it applied (the issues it didn't revert), the stretches it changed (`changedStretches`: compared before and after stretch by stretch; a change of a system's fields counts as its first stretch), and its warnings (`callWarnings`): a stretch changed outside the boxes of the issues it applied, with the reason given or saying there was none ("Apply review changed stretch 2 of system 7 (m. 23), beyond the boxes of the issues it applied: …"), and an issue applied whose stretches didn't change.
- **Once every call is in,** the new transcription is stored as `extract` stores one, so every later stage (a further review, `engrave`, `fix_mei`) reads it the same way: an `extraction` per system (the answer patched, its issues, the warnings of the checks and of the calls) and a `score_checks` (the checks of the whole score run again). The issues: every reverted one gets the stage's choice of its applied answer, marked `reverted`, with the reason; every other issue a call applied gets its latest choice as `applied` (`appliedIssues`). Each issue is stored with the first system its boxes cover (the views place them by their boxes anyway); those of the checks of the whole score stay there. An issue code raises again on the new transcription is added only if no issue raised by code asks the same about the same places (`isNewCodeIssue`). Warnings are all computed anew.
- **The card's result:** "4 changes applied, 2 reverted" (the issues applied and reverted; "0 changes applied" when nothing needed applying, and then no call is made).
- **The artifact:** the Transcription of the new transcription. The Δ toggle shows only the issues it applied or reverted; a block at the top, in the colour of errors, lists the answers it couldn't apply as given, each with its reason and a link to its card. **The measures it changed** are tinted in the renderings, in violet (`--changed`, decided 2026-11-03): every measure holding a stretch a call changed (a change of a system's fields counts as its first stretch), and only where the printed change is: a changed time signature tints the measure it is printed at, not the measures it affects, on each system a measure split across systems has a part on. A reverted answer has the suffix "[chosen by Apply review 1]" beside "[written by Extract]" (or the application before it).
- **Further reviews** (`POST …/stages/<apply_review>/review`): "Add Review" in any Apply review's "⋮" adds a review and its Apply review right after it, planned, with the default model config, both marked as the user's (`in_recipe` 0); after an Apply review that isn't the last, the stages after them are replaced, after the confirmation. A further review has "Drop stage", which drops its Apply review too; the recipe's review and any Apply review can't be dropped. A further review that has run is carried through a re-run like a manual stage (its Apply review gets a planned copy, which the stage key finds again when the review is kept), kept at its turn if it would read the same, and dropped otherwise, with its Apply review and one card.
- **`fix_mei`** is offered in an Apply review's "⋮" (the latest one), no longer in a review's.
- **The fake provider** applies each issue on a window that starts on an odd system by writing a C in the first voice of the first stretch under it, and reverts every issue on a window that starts on an even one, with a made-up reason (a made-up new answer where none is applied); a person's answers (resolved) are applied on either, so a human review gets through.
- **Not done:** zoom crops.

## `human_review` (Human review)

**Its name** (decided, 2026-11-03): "Human review", not "Fix X" like the other manual stages. It isn't a fix of something before it: not of `apply_review` or of the review, and only indirectly of the extraction; it also creates issues of its own, so neither "Fix issues" nor "Fix choices" covers it. And a fix is final, while a human review can be followed by another review, another human review, and so on. It is a review like `review` in every way except who performs it. So it is added with **"Add Human review"** in an `apply_review`'s "⋮" (like "Add Review"), not "Human review manually". Like every manual stage, its icon is the wrench.

The user picks another answer for an issue, or writes one that isn't in the list ("none of these, but ..."). The user also adds issues of their own to correct something no model raised.
- **Adding a correction:** the user draws one or more boxes on the original score, with the box tool of `fix_layout` (tap, tap at two opposite corners), and writes the correction as free text ("this should be a C flat"). It becomes an issue like any other (below).
- **The warnings of the version being reviewed** are shown too (see `docs/notation.md`, "Warnings"). The user never sees MEI or LilyPond.
- **The screen:**
  - **Two panels at most,** side by side or stacked as in the evaluation viewer (§13): the original on the left or at the top, the rendering of the current extraction on the right or below. Zooming is a must. The side-by-side view is mainly for finding problems nobody raised; resolving an issue mostly needs only the original, since issues are about what is hard to read on it.
  - **No list of issues:** the boxes of all issues sit on the original, dimmed, and can be clicked. The selected one is no longer dimmed, and a panel with the issue (its question, location, answers, choices) covers the rendering panel; the original stays visible. Closing it dims the box again. Where the rendering is needed, the panel is opened and closed as often as needed.
  - **Warnings use the same UI:** their boxes are on the original too, in their own style (e.g. dashed, a warning colour); their panel shows the explanation, with nothing to answer. The rendering matters more for warnings than for issues.
  - **Arrow buttons** go from one box to the next (issues and warnings, in score order), scrolling the original to it, with the panel staying open.
  - **The original can be hidden,** to look at the rendering alone, and **the boxes can be hidden,** to see the original cleanly.
  - **A "⋮" menu** takes over once the toolbar gets busy: show or hide the boxes, show or hide the original, create a new issue. Creating one: the box tool of `fix_layout` is on for the original, and the panel opens with the new issue, whose answer the user writes; boxes can be adjusted or added while it is open, within the 2-system rule.
  - **Scrolling and zooming are linked** between the two panels by default, with a small button to unlink them. Verovio's engraving won't match the original's heights and spacing (staff size, distances between staves and systems, room for titles, lyrics and dynamics), even with options such as `spacingSystem` and `spacingStaff`; widths can come close, rendering each page at the original page's width. But with the encoded breaks, systems correspond one to one, and both sides have their systems located (the original from the layout, the rendering from the system elements of Verovio's SVG). So the link maps positions system by system, piecewise linear (40% into system 12 on one side is 40% into system 12 on the other, gaps interpolated alike), and the zoom is linked so that the same system has the same width on both sides. Re-linking aligns the rendering to the original.
- **Every correction is applied by `apply_review`,** an LLM call (decided). Applying answers by code doesn't work in general: a measure can have several issues, and an answer would have to come with a replacement for every combination of answers; and many corrections reach beyond one measure ("this slur continues the one in the previous system" touches two systems, perhaps two pages).
- **Code checks what `apply_review` did:** it compares the extraction before and after, **stretch by stretch** (not the MEI by measure: measures can be merged or split, stretches can't), the rendering highlights the measures whose stretches changed, and a changed stretch outside the boxes of the issues being applied needs a reason and is flagged (see `apply_review`). The stretches of an issue are the ones under its boxes (see `docs/notation.md`, "Issues").
- **So `applied` is what the model says, checked only roughly by code.** A model's account of what it did isn't reliable (`docs/evaluation.md`, "The manual run").
  - **Code catches,** as warnings: a missing change (an issue said to be applied, whose stretches didn't change; its `applied` stays as the model said, since the extraction may already have matched the answer), a change beyond the boxes (above), and a change where none was due (the chosen answer is the present state).
  - **Code can't tell** whether the change is the chosen answer: the right stretch changed the wrong way passes. Where several issues share stretches, a change can't be credited to one of them.
  - **The answer itself** can only be verified by a model or the user looking at the result, e.g. in a later review.
- **No editing of the source and no replacing it by an upload** (decided). Either would make the issues unreliable: after a direct edit, nobody knows which answer of each issue the MEI reflects. Direct editing comes only at the end, in `fix_mei` (§6), after which nothing needs the issues.

## Zooming in
**Zoom crops on request, without tool calls** (decided, for a later version: the first version has none), for `extract`, `review` and probably `apply_review`:
- **The first answer has one of two shapes,** in one schema: the stage's answer itself, when the model needs nothing more (a clean system), or a list of requests: zoom boxes on the crops it was sent (and, for `review`, other systems' crops), at most N, each with a short reason ("dot near the A♭: staccato or smudge?").
- **The second request** repeats the first, adds the model's requests as its answer and the zoom crops, each labelled (§7.2), and asks for the stage's answer; this one can't ask for more. Its prefix is the first request, so prompt caching makes the repeated part cheap.
- **So at most two rounds per call,** plus the follow-ups for failed checks, if those come too (`extract`). This is a tool loop with one round, built ourselves: the same on every provider (no tool-use APIs, no loop in the adapters), every call record a plain request and answer, and the cap enforced by the schema rather than by the model's judgement (the manual run's over-exploration, §13).
- **Code cuts the zoom crops** from the deskewed page at the page image's resolution. A zoom gives the model real detail where its view of a large crop was shrunk (Claude sees at most 2576 px on the long edge); on a low-resolution scan it is only a closer look at the same pixels, which may still help it focus.
- **The zoom boxes and their reasons are recorded** with the call (§5.2), and the issues that come from them can point at the same boxes: evidence for the reviewer and the user.
- **Perhaps, later: zoom crops accumulated across stages** (§15, "Zoom crops accumulated across stages").
